# Command Design Pattern

The **Command Design Pattern** is a behavioral design pattern that turns a request into a standalone object containing all information needed to perform the action. This enables you to parameterize objects with different requests, queue or log operations, and support undoable actions while decoupling invokers from receivers.

![Command Design Pattern Overview](https://raw.githubusercontent.com/shouvik126/LLD_images/main/7.34-command-overview.png)

It is particularly valuable in situations where:
- You want to encapsulate operations as standalone objects.
- You need to queue, schedule, delay, or log requests for asynchronous processing.
- You need to support undo and redo operations natively.
- You want to decouple invokers (UI buttons, remote controls, schedulers) from the receivers executing actual business logic.

Below is a step-by-step walk-through demonstrating how to apply the Command Pattern to decouple invocation from execution and build a testable, extensible command execution framework.

---

## 1. The Problem: The Tightly Coupled Smart Home Hub

Imagine building a smart home controller hub. The hub controls various home devices: lights, thermostats, garage doors, and audio systems.

A naive implementation directly binds the controller to every concrete device:

```java
public class Light {
    public void turnOn() { System.out.println("Light turned ON."); }
    public void turnOff() { System.out.println("Light turned OFF."); }
}

public class Thermostat {
    private int temperature = 20;
    public void setTemperature(int temp) { 
        this.temperature = temp;
        System.out.println("Thermostat set to " + temp + "°C"); 
    }
    public int getTemperature() { return temperature; }
}

public class SmartHomeControllerNaive {
    private Light livingRoomLight;
    private Thermostat mainThermostat;

    public SmartHomeControllerNaive(Light light, Thermostat thermostat) {
        this.livingRoomLight = light;
        this.mainThermostat = thermostat;
    }

    public void pressLightOnButton() { livingRoomLight.turnOn(); }
    public void pressLightOffButton() { livingRoomLight.turnOff(); }
    public void setThermostatTemperature(int temp) { mainThermostat.setTemperature(temp); }
}
```

```java
public class ClientNaiveApp {
    public static void main(String[] args) {
        Light light = new Light();
        Thermostat thermostat = new Thermostat();
        SmartHomeControllerNaive controller = new SmartHomeControllerNaive(light, thermostat);

        controller.pressLightOnButton();
        controller.setThermostatTemperature(22);
    }
}
```

### Why This Design Fails as the System Grows

1. **Tight Coupling**  
   `SmartHomeControllerNaive` references concrete device classes directly. Adding a new device (e.g., `Sprinkler` or `Speaker`) forces edits inside the controller class.

2. **Poor Scalability**  
   Every new device action expands the controller class with new fields and methods, turning it into a bloated monolith.

3. **Lack of Undo/Redo Support**  
   There is no mechanism to reverse an executed action. Implementing "undo last action" requires writing complex conditional state tracking for every device method.

4. **No Scheduling or Queuing Support**  
   Requests cannot be queued or scheduled for delayed execution (e.g., "turn off lights at 11 PM") because operations are hardcoded method calls rather than storable objects.

5. **No Action Reusability**  
   If the "turn on light" action needs to be triggered from a physical wall switch, mobile app, timer, or voice assistant, every trigger point duplicates coupling code to `Light`.

### Desired Architecture
We require a design that:
- Encapsulates requests ("turn on light", "set temperature to 22°C") into standalone objects.
- Decouples invokers (remote buttons, schedulers) from receiver devices.
- Enables commands to execute and undo themselves natively.
- Allows commands to be stored, queued, and executed dynamically.

This is precisely what the **Command Design Pattern** delivers.

---

## 2. The Command Design Pattern

The Command Pattern encapsulates a request as an object, allowing you to parameterize clients with different requests, delay execution, queue operations, and support undo functionality.

Core characteristics:
- **Request Encapsulation**: Each action becomes an object implementing a shared `Command` interface.
- **Invoker-Receiver Decoupling**: The invoker triggers `command.execute()` without knowing the target receiver or underlying business logic.

### Real-World Analogy

Consider ordering food at a restaurant:
- **Customer (Client)**: Chooses meals and creates an order request.
- **Waiter (Invoker)**: Takes the written order slip and delivers it to the kitchen.
- **Order Slip (Command)**: Contains all parameters needed to fulfill the meal request.
- **Chef (Receiver)**: Reads the slip and cooks the dish.

The waiter does not cook the meal, and the chef doesn't interact directly with the dining table. The order slip decouples waiter from chef, and allows orders to be queued, reordered, or canceled.

![Command Class Diagram](https://raw.githubusercontent.com/shouvik126/LLD_images/main/7.34-command-class-diagram.png)

### Pattern Participants

1. **Command (`Command`)**  
   Declares the common execution contract (`execute()`, `undo()`).

2. **ConcreteCommand (`LightOnCommand`, `SetTemperatureCommand`)**  
   Bridges invoker and receiver by binding action parameters and delegating execution to the target `Receiver`.

3. **Receiver (`Light`, `Thermostat`)**  
   Performs actual domain operations without any awareness of commands or invokers.

4. **Invoker (`RemoteControl`)**  
   Triggers command execution and maintains command history for undo operations.

---

## 3. How It Works

The workflow execution of the Command pattern follows these steps:

![Command Execution Workflow](https://raw.githubusercontent.com/shouvik126/LLD_images/main/7.34-command-workflow.png)

1. **Instantiate Receivers & Commands**: The client creates target device objects and wraps them in concrete command instances.
2. **Configure Invoker**: Commands are assigned to invoker slots (e.g., remote buttons).
3. **Execute**: The user triggers an invoker action; the invoker calls `command.execute()`.
4. **Delegate to Receiver**: `execute()` saves state if necessary and delegates to receiver operations.
5. **History Tracking**: The invoker pushes executed commands onto an undo history stack.
6. **Undo**: Invoking `pressUndo()` pops the latest command and calls `command.undo()`.

## 4. Implementing the Command Pattern

Let's refactor the Smart Home Controller using the Command Pattern with undo support.

![Command Implementation Diagram](https://raw.githubusercontent.com/shouvik126/LLD_images/main/7.34-command-implementation.png)

### Step 1: Define the Command Interface

```java
public interface Command {
    void execute();
    void undo();
}
```

### Step 2: Define Receivers

```java
public class Light {
    private final String location;

    public Light(String location) {
        this.location = location;
    }

    public void on() {
        System.out.println("[" + location + "] Light turned ON.");
    }

    public void off() {
        System.out.println("[" + location + "] Light turned OFF.");
    }
}

public class Thermostat {
    private int currentTemp = 20;

    public void setTemperature(int temp) {
        this.currentTemp = temp;
        System.out.println("[Thermostat] Temperature set to " + temp + "°C");
    }

    public int getCurrentTemperature() {
        return currentTemp;
    }
}
```

### Step 3: Implement Concrete Commands

```java
public class LightOnCommand implements Command {
    private final Light light;

    public LightOnCommand(Light light) {
        this.light = light;
    }

    @Override
    public void execute() {
        light.on();
    }

    @Override
    public void undo() {
        light.off();
    }
}

public class LightOffCommand implements Command {
    private final Light light;

    public LightOffCommand(Light light) {
        this.light = light;
    }

    @Override
    public void execute() {
        light.off();
    }

    @Override
    public void undo() {
        light.on();
    }
}

public class SetTemperatureCommand implements Command {
    private final Thermostat thermostat;
    private final int newTemp;
    private int previousTemp;

    public SetTemperatureCommand(Thermostat thermostat, int newTemp) {
        this.thermostat = thermostat;
        this.newTemp = newTemp;
    }

    @Override
    public void execute() {
        previousTemp = thermostat.getCurrentTemperature(); // Save state before mutation
        thermostat.setTemperature(newTemp);
    }

    @Override
    public void undo() {
        thermostat.setTemperature(previousTemp); // Restore saved state
    }
}
```

### Step 4: Implement Invoker with Undo History

```java
import java.util.Stack;

public class RemoteControl {
    private final Stack<Command> history = new Stack<>();

    public void executeCommand(Command command) {
        command.execute();
        history.push(command);
    }

    public void undoLast() {
        if (!history.isEmpty()) {
            Command lastCommand = history.pop();
            lastCommand.undo();
        } else {
            System.out.println("Nothing to undo.");
        }
    }
}
```

### Step 5: Client Execution & Verification

```java
public class CommandPatternDemo {
    public static void main(String[] args) {
        Light livingRoomLight = new Light("Living Room");
        Thermostat thermostat = new Thermostat();
        RemoteControl remote = new RemoteControl();

        Command lightOn = new LightOnCommand(livingRoomLight);
        Command lightOff = new LightOffCommand(livingRoomLight);
        Command setTemp24 = new SetTemperatureCommand(thermostat, 24);

        System.out.println("--- Executing Commands ---");
        remote.executeCommand(lightOn);
        remote.executeCommand(setTemp24);
        remote.executeCommand(lightOff);

        System.out.println("\n--- Triggering Undo Operations ---");
        remote.undoLast(); // Undoes LightOff -> Turns Light ON
        remote.undoLast(); // Undoes SetTemperature -> Restores 20°C
        remote.undoLast(); // Undoes LightOn -> Turns Light OFF
        remote.undoLast(); // Stack empty
    }
}
```

### Console Output
```text
--- Executing Commands ---
[Living Room] Light turned ON.
[Thermostat] Temperature set to 24°C
[Living Room] Light turned OFF.

--- Triggering Undo Operations ---
[Living Room] Light turned ON.
[Thermostat] Temperature set to 20°C
[Living Room] Light turned OFF.
Nothing to undo.
```

### Comparison: Naive vs Command Pattern

| Architectural Aspect | Naive Controller | Command Design Pattern |
| :--- | :--- | :--- |
| **Coupling** | Direct references to concrete devices | Interacts exclusively via `Command` interface |
| **Extensibility** | Editing controller class per new device | Adding new concrete command classes without editing invoker |
| **Undo Support** | Complex manual state tracking per method | Built-in state capture and `undo()` execution per command |
| **Queueing / Logging** | Not supported (hardcoded method calls) | Fully supported (commands are storable objects) |

## 5. Practical Example: Text Editor with Undo/Redo

Consider a text editor supporting text append and delete operations with multi-level Undo/Redo stacks.

![Text Editor Command Diagram](https://raw.githubusercontent.com/shouvik126/LLD_images/main/7.34-text-editor-command-diagram.png)

### Implementation

```java
import java.util.Stack;

// Receiver
public class TextEditor {
    private final StringBuilder content = new StringBuilder();

    public void append(String text) {
        content.append(text);
    }

    public String deleteLast(int count) {
        int length = content.length();
        int deleteCount = Math.min(count, length);
        int start = length - deleteCount;
        String deleted = content.substring(start);
        content.delete(start, length);
        return deleted;
    }

    public String getContent() {
        return content.toString();
    }
}

// Command Interface
public interface EditorCommand {
    void execute();
    void undo();
}

// Concrete Command 1: Type
public class TypeCommand implements EditorCommand {
    private final TextEditor editor;
    private final String text;

    public TypeCommand(TextEditor editor, String text) {
        this.editor = editor;
        this.text = text;
    }

    @Override
    public void execute() {
        editor.append(text);
    }

    @Override
    public void undo() {
        editor.deleteLast(text.length());
    }
}

// Concrete Command 2: Delete
public class DeleteCommand implements EditorCommand {
    private final TextEditor editor;
    private final int count;
    private String deletedText = "";

    public DeleteCommand(TextEditor editor, int count) {
        this.editor = editor;
        this.count = count;
    }

    @Override
    public void execute() {
        deletedText = editor.deleteLast(count); // Save deleted text for undo
    }

    @Override
    public void undo() {
        editor.append(deletedText); // Restore deleted text
    }
}

// Invoker with Undo & Redo Stacks
public class EditorInvoker {
    private final Stack<EditorCommand> undoStack = new Stack<>();
    private final Stack<EditorCommand> redoStack = new Stack<>();

    public void execute(EditorCommand cmd) {
        cmd.execute();
        undoStack.push(cmd);
        redoStack.clear(); // Clear redo stack on new action
    }

    public void undo() {
        if (!undoStack.isEmpty()) {
            EditorCommand cmd = undoStack.pop();
            cmd.undo();
            redoStack.push(cmd);
        } else {
            System.out.println("Nothing to undo.");
        }
    }

    public void redo() {
        if (!redoStack.isEmpty()) {
            EditorCommand cmd = redoStack.pop();
            cmd.execute();
            undoStack.push(cmd);
        } else {
            System.out.println("Nothing to redo.");
        }
    }
}
```

```java
// Client Demo
public class TextEditorCommandDemo {
    public static void main(String[] args) {
        TextEditor editor = new TextEditor();
        EditorInvoker invoker = new EditorInvoker();

        invoker.execute(new TypeCommand(editor, "Hello"));
        invoker.execute(new TypeCommand(editor, " World"));
        System.out.println("Content: \"" + editor.getContent() + "\"");

        invoker.execute(new TypeCommand(editor, "!"));
        System.out.println("Content: \"" + editor.getContent() + "\"");

        System.out.println("\n--- Undoing ---");
        invoker.undo();
        System.out.println("After 1st Undo: \"" + editor.getContent() + "\"");
        invoker.undo();
        System.out.println("After 2nd Undo: \"" + editor.getContent() + "\"");

        System.out.println("\n--- Redoing ---");
        invoker.redo();
        System.out.println("After Redo: \"" + editor.getContent() + "\"");

        System.out.println("\n--- New Delete Action ---");
        invoker.execute(new DeleteCommand(editor, 5));
        System.out.println("After Delete: \"" + editor.getContent() + "\"");

        System.out.println("\n--- Undoing Delete ---");
        invoker.undo();
        System.out.println("After Undo Delete: \"" + editor.getContent() + "\"");
    }
}
```

### Console Output
```text
Content: "Hello World"
Content: "Hello World!"

--- Undoing ---
After 1st Undo: "Hello World"
After 2nd Undo: "Hello"

--- Redoing ---
After Redo: "Hello World"

--- New Delete Action ---
After Delete: "Hello"

--- Undoing Delete ---
After Undo Delete: "Hello World"
```

### Summary
`EditorInvoker` manages dual stacks (`undoStack` and `redoStack`) without exposing `TextEditor` string buffers directly. Each concrete command (`TypeCommand`, `DeleteCommand`) encapsulates its own mutation and state restoration logic.
