# Prototype Design Pattern

The **Prototype Design Pattern** is a creational design pattern that enables you to generate new objects by copying (cloning) existing prototype instances, rather than constructing them from scratch via direct instantiation.

![Prototype Design Pattern Overview](https://raw.githubusercontent.com/shouvik126/LLD_images/main/7.10-prototype-overview.png)

It is particularly valuable in scenarios where:
- Creating a new instance is computationally expensive, time-consuming, or resource-heavy.
- You want to avoid duplicating complex, multi-step initialization logic.
- Your application requires many similar objects that differ only in minor properties.

By cloning a pre-configured prototype object, the Prototype pattern guarantees object consistency while significantly reducing boilerplate and instantiation overhead.

---

## 1. The Challenge of Cloning Objects

Suppose you have an object in your system and need to produce an exact duplicate of it. How would you accomplish this?

A common initial attempt is:
1. Instantiate a new object of the target class.
2. Manually copy each field value from the original instance to the new instance.

While this seems straightforward, it introduces major architectural flaws:

### Problem 1: Encapsulation Violations
This naive approach assumes that all fields within the object are publicly accessible. However, well-architected systems encapsulate data using private or protected access modifiers. External code cannot access or copy these private fields directly without breaking encapsulation rules.

### Problem 2: Tightly Coupled Class Dependencies
Even if fields were accessible, the caller must know the exact concrete class of the object to instantiate a duplicate. This creates tight coupling to concrete implementations, which:
- Violates the **Open/Closed Principle (OCP)**.
- Reduces system flexibility if concrete class structures evolve.
- Complicates object creation when working with polymorphic interfaces.

### Problem 3: Interface-Only Contexts
In polymorphic systems, client code frequently operates against interfaces rather than concrete classes:

```java
public void processShape(Shape shape) {
    // Client knows 'shape' implements Shape interface, but does not know 
    // whether it is a Circle, Rectangle, or Polygon.
}
```

Here, the client cannot instantiate a new object because it does not know the underlying concrete type or its constructor requirements. The only clean solution is to allow the object itself to create its own clone.

### The Solution: Self-Cloning Objects
The Prototype pattern addresses this by shifting the responsibility of copying onto the object itself. The object exposes a `clone()` or `copy()` method that returns a duplicate containing identical state.

This approach:
- **Preserves Encapsulation**: Private fields are copied internally within the class scope.
- **Decouples Client Code**: Clients clone objects via an interface without depending on concrete classes.
- **Enhances Extensibility**: New prototype classes can be introduced without modifying existing client code.

---

## Shallow Copy vs. Deep Copy

Understanding the distinction between a **shallow copy** and a **deep copy** is vital when implementing the Prototype pattern.

### What is a Shallow Copy?
A **shallow copy** duplicates the primary object structure, but shares references for any contained objects.
- Primitive fields (`int`, `double`, `boolean`, etc.) and immutable reference types (`String`) are copied by value.
- Mutable reference fields (`List`, `Map`, custom objects) are copied by reference. Consequently, both the original object and its clone reference the exact same memory locations.

### What is a Deep Copy?
A **deep copy** duplicates the primary object along with all referenced objects recursively. The resulting clone is entirely independent—modifying nested objects in the clone has zero side effects on the original object.

> **Key Rule**: Prototype implementations must perform a **deep copy** whenever objects encapsulate mutable reference types.

## 2. Real-World Scenario: Spawning Game Enemies

Consider a 2D action game where enemies spawn frequently throughout gameplay.

The game features several distinct enemy types:
- **BasicEnemy**: Low health, slow speed (used in early stages).
- **ArmoredEnemy**: High health, medium speed, damage reduction armor (used in mid stages).
- **FlyingEnemy**: Medium health, high speed, specialized aerial weapon (used for surprise attacks).

Each enemy instance is initialized with multiple properties:
- `health` (maximum damage capacity)
- `speed` (movement velocity)
- `armor` (damage mitigation factor)
- `weapon` (laser, cannon, or missile type)
- `sprite` (graphical asset reference)

### Naive Implementation (Without Prototype)

```java
// Manually constructing enemy instances across game loop logic
Enemy enemy1 = new Enemy("Flying", 100, 25.0, "Laser", 5);
enemy1.loadSprites();
enemy1.configureAI();

Enemy enemy2 = new Enemy("Flying", 100, 25.0, "Laser", 5);
enemy2.loadSprites();
enemy2.configureAI();
```

### Why This Approach Fails at Scale
- **Repetitive Instantiation Logic**: Identical setup and configuration code is duplicated across spawning functions.
- **Scattered Default Configurations**: Changing a default property (e.g., boosting default speed) requires updating every instantiation site across the codebase.
- **Fragile & Error-Prone**: Omitting a setup method call or misconfiguring an attribute leads to silent runtime bugs.
- **Cluttered Game Loop**: Construction details bloat core game loop logic.

Applying the Prototype Design Pattern provides a centralized, reusable mechanism to clone fully configured enemy templates instantly.

## 3. The Prototype Design Pattern Architecture

The Prototype pattern configures pre-initialized template instances and produces new objects by copying (cloning) these prototypes.

Key principles:
1. **Self-Cloning**: The object manages its own cloning logic internally.
2. **Decoupled Creation**: Clients request clones via a common prototype interface containing a `clone()` method.

![Prototype Class Diagram](https://raw.githubusercontent.com/shouvik126/LLD_images/main/7.10-prototype-class-diagram.png)

### Participants in the Pattern

1. **Prototype (Interface)**
   - Declares the `clone()` method contract implemented by all cloneable objects.
2. **ConcretePrototype**
   - Implements `clone()` to create a copy of itself.
   - Copies internal state (performing shallow or deep copy depending on field types).
3. **Client**
   - Requests new object instances by invoking `clone()` on prototype objects.
   - Optionally customizes the cloned instance after creation.
4. **Prototype Registry (Optional)**
   - Maintains a dictionary of pre-configured prototype instances indexed by key identifiers.
   - Returns fresh clones on demand when requested by clients.

---

## 4. How the Prototype Pattern Works

The execution flow consists of five core steps:

![Prototype Workflow Diagram](https://raw.githubusercontent.com/shouvik126/LLD_images/main/7.10-prototype-workflow.png)

1. **Initialize Prototype Templates**: Create and configure default instances for each object type (e.g., pre-loading assets for a `FlyingEnemy`).
2. **Register Prototypes**: Store prototype templates in a centralized `PrototypeRegistry` keyed by name (e.g., `"flying"`, `"armored"`).
3. **Client Requests Clone**: When a new instance is needed, the client queries the registry by key.
4. **Prototype Clones Itself**: The prototype executes its `clone()` method, creating a distinct duplicate in memory.
5. **Client Customizes Clone**: The client modifies specific properties on the clone without mutating the original template.

## 5. Java Implementation Step-by-Step

Let's build a complete, production-grade enemy spawning system using the Prototype pattern.

### Step 1: Define the Prototype Interface

```java
public interface EnemyPrototype {
    EnemyPrototype clone();
}
```

### Step 2: Implement Concrete Prototype with Shallow Copy

When enemy fields consist solely of primitives or immutable types (`String`), a shallow copy constructor is sufficient.

```java
public class BasicEnemy implements EnemyPrototype {
    private String type;
    private int health;
    private double speed;
    private String weapon;

    public BasicEnemy(String type, int health, double speed, String weapon) {
        this.type = type;
        this.health = health;
        this.speed = speed;
        this.weapon = weapon;
    }

    // Copy constructor used by clone()
    public BasicEnemy(BasicEnemy target) {
        if (target != null) {
            this.type = target.type;
            this.health = target.health;
            this.speed = target.speed;
            this.weapon = target.weapon;
        }
    }

    @Override
    public EnemyPrototype clone() {
        return new BasicEnemy(this);
    }

    public void setHealth(int health) {
        this.health = health;
    }

    public int getHealth() {
        return health;
    }

    @Override
    public String toString() {
        return "BasicEnemy [type=" + type + ", health=" + health + 
               ", speed=" + speed + ", weapon=" + weapon + "]";
    }
}
```

### Step 3: Deep Copy Implementation (Handling Mutable References)

If an enemy carries a mutable inventory list (`List<String>`), shallow cloning causes original and cloned instances to share the same inventory list. A deep copy ensures complete data isolation.

```java
import java.util.ArrayList;
import java.util.List;

public class ArmoredEnemy implements EnemyPrototype {
    private String type;
    private int health;
    private double speed;
    private List<String> inventory;

    public ArmoredEnemy(String type, int health, double speed, List<String> inventory) {
        this.type = type;
        this.health = health;
        this.speed = speed;
        this.inventory = inventory;
    }

    // Copy constructor handling deep copy of mutable references
    public ArmoredEnemy(ArmoredEnemy target) {
        if (target != null) {
            this.type = target.type;
            this.health = target.health;
            this.speed = target.speed;
            // Deep copy of mutable list field
            this.inventory = new ArrayList<>(target.inventory);
        }
    }

    @Override
    public EnemyPrototype clone() {
        return new ArmoredEnemy(this);
    }

    public List<String> getInventory() {
        return inventory;
    }

    public void addInventoryItem(String item) {
        this.inventory.add(item);
    }

    @Override
    public String toString() {
        return "ArmoredEnemy [type=" + type + ", health=" + health + 
               ", speed=" + speed + ", inventory=" + inventory + "]";
    }
}
```

### Step 4: Implement Prototype Registry

The `PrototypeRegistry` centralizes template management and ensures callers receive fresh clones rather than internal prototype references.

```java
import java.util.HashMap;
import java.util.Map;

public class EnemyRegistry {
    private Map<String, EnemyPrototype> prototypes = new HashMap<>();

    public void registerPrototype(String key, EnemyPrototype prototype) {
        prototypes.put(key, prototype);
    }

    public EnemyPrototype get(String key) {
        EnemyPrototype prototype = prototypes.get(key);
        if (prototype != null) {
            return prototype.clone(); // Always return a fresh clone!
        }
        throw new IllegalArgumentException("No prototype registered for key: " + key);
    }
}
```

### Step 5: Client Demonstration Code

```java
import java.util.ArrayList;
import java.util.List;

public class PrototypeGameDemo {
    public static void main(String[] args) {
        EnemyRegistry registry = new EnemyRegistry();

        // 1. Configure default prototypes
        BasicEnemy flyingPrototype = new BasicEnemy("FlyingEnemy", 100, 50.0, "Laser");
        
        List<String> armoredGear = new ArrayList<>();
        armoredGear.add("Shield");
        armoredGear.add("Potion");
        ArmoredEnemy armoredPrototype = new ArmoredEnemy("ArmoredEnemy", 250, 15.0, armoredGear);

        // 2. Register prototypes
        registry.registerPrototype("flying", flyingPrototype);
        registry.registerPrototype("armored", armoredPrototype);

        // 3. Spawn enemies by requesting clones
        BasicEnemy spawnedFlying1 = (BasicEnemy) registry.get("flying");
        BasicEnemy spawnedFlying2 = (BasicEnemy) registry.get("flying");
        spawnedFlying2.setHealth(80); // Customizing clone state

        ArmoredEnemy spawnedArmored1 = (ArmoredEnemy) registry.get("armored");
        spawnedArmored1.addInventoryItem("Heavy Helmet");

        // 4. Verify independence between prototypes and clones
        System.out.println("Spawned Flying 1: " + spawnedFlying1);
        System.out.println("Spawned Flying 2 (Weakened): " + spawnedFlying2);
        System.out.println("Spawned Armored 1: " + spawnedArmored1);
        System.out.println("Original Prototype Inventory: " + armoredPrototype.toString());
    }
}
```

### Output:
```text
Spawned Flying 1: BasicEnemy [type=FlyingEnemy, health=100, speed=50.0, weapon=Laser]
Spawned Flying 2 (Weakened): BasicEnemy [type=FlyingEnemy, health=80, speed=50.0, weapon=Laser]
Spawned Armored 1: ArmoredEnemy [type=ArmoredEnemy, health=250, speed=15.0, inventory=[Shield, Potion, Heavy Helmet]]
Original Prototype Inventory: ArmoredEnemy [type=ArmoredEnemy, health=250, speed=15.0, inventory=[Shield, Potion]]
```

## 6. Practical Real-World Example: Bulk Email Templates

Consider an enterprise bulk email system. The marketing department sends monthly newsletters where each department receives a baseline email template customized with specific recipient lists (`to`, `cc`) and subject lines.

Without Prototype, constructing each department's email requires recreating complex nested objects repeatedly. Using Prototype, a base template is created once and cloned for each department variant.

### Deep Copying Nested Objects

Here, `RecipientList` contains nested mutable lists (`to` and `cc`). Deep copying ensures that adding a recipient to the HR department email does not leak into the Marketing email.

```java
import java.util.ArrayList;
import java.util.List;

class RecipientList {
    private List<String> toList;
    private List<String> ccList;

    public RecipientList(List<String> toList, List<String> ccList) {
        this.toList = toList;
        this.ccList = ccList;
    }

    // Deep copy constructor
    public RecipientList(RecipientList other) {
        this.toList = new ArrayList<>(other.toList);
        this.ccList = new ArrayList<>(other.ccList);
    }

    public RecipientList deepCopy() {
        return new RecipientList(this);
    }

    public void addTo(String email) {
        toList.add(email);
    }

    public void addCc(String email) {
        ccList.add(email);
    }

    @Override
    public String toString() {
        return "To: " + toList + ", CC: " + ccList;
    }
}

class EmailTemplate implements EnemyPrototype {
    private String subject;
    private String bodyContent;
    private RecipientList recipients;

    public EmailTemplate(String subject, String bodyContent, RecipientList recipients) {
        this.subject = subject;
        this.bodyContent = bodyContent;
        this.recipients = recipients;
    }

    // Deep copy constructor
    public EmailTemplate(EmailTemplate target) {
        if (target != null) {
            this.subject = target.subject;
            this.bodyContent = target.bodyContent;
            // Explicit deep copy of nested mutable object
            this.recipients = target.recipients.deepCopy();
        }
    }

    @Override
    public EmailTemplate clone() {
        return new EmailTemplate(this);
    }

    public void setSubject(String subject) {
        this.subject = subject;
    }

    public RecipientList getRecipients() {
        return recipients;
    }

    @Override
    public String toString() {
        return "EmailTemplate [Subject='" + subject + "', Body='" + bodyContent + 
               "', Recipients=" + recipients + "]";
    }
}

public class EmailTemplateDemo {
    public static void main(String[] args) {
        // 1. Create base corporate email template
        List<String> defaultTo = new ArrayList<>();
        defaultTo.add("all-employees@company.com");
        
        List<String> defaultCc = new ArrayList<>();
        defaultCc.add("compliance@company.com");

        RecipientList baseRecipients = new RecipientList(defaultTo, defaultCc);
        EmailTemplate monthlyNewsletterBase = new EmailTemplate(
            "Company Monthly Update", 
            "Welcome to this month's company-wide updates...", 
            baseRecipients
        );

        // 2. Clone base template for Engineering Department
        EmailTemplate engineeringEmail = monthlyNewsletterBase.clone();
        engineeringEmail.setSubject("Company Update - Engineering Edition");
        engineeringEmail.getRecipients().addTo("eng-lead@company.com");

        // 3. Clone base template for HR Department
        EmailTemplate hrEmail = monthlyNewsletterBase.clone();
        hrEmail.setSubject("Company Update - HR & Operations Edition");
        hrEmail.getRecipients().addCc("hr-audit@company.com");

        // 4. Print results verifying deep copy independence
        System.out.println("Base Template: " + monthlyNewsletterBase);
        System.out.println("Engineering Email: " + engineeringEmail);
        System.out.println("HR Email: " + hrEmail);
    }
}
```

### Output:
```text
Base Template: EmailTemplate [Subject='Company Monthly Update', Body='Welcome to this month's company-wide updates...', Recipients=To: [all-employees@company.com], CC: [compliance@company.com]]
Engineering Email: EmailTemplate [Subject='Company Update - Engineering Edition', Body='Welcome to this month's company-wide updates...', Recipients=To: [all-employees@company.com, eng-lead@company.com], CC: [compliance@company.com]]
HR Email: EmailTemplate [Subject='Company Update - HR & Operations Edition', Body='Welcome to this month's company-wide updates...', Recipients=To: [all-employees@company.com], CC: [compliance@company.com, hr-audit@company.com]]
```

## 7. Summary & Key Takeaways

- **Creational Intent**: Enables cloning of existing objects without coupling code to concrete classes.
- **Encapsulation Preservation**: Private member variables are copied within the scope of the class itself.
- **Deep Copy Requirement**: Objects holding mutable reference types (lists, maps, objects) must implement deep copying to prevent shared state side effects.
- **Prototype Registry**: Centralizes pre-configured prototypes and enforces returning fresh clones on every access.
