# Bridge Design Pattern

The **Bridge Design Pattern** is a structural design pattern that decouples an abstraction from its implementation so that the two can vary independently.

![Bridge Design Pattern Overview](https://raw.githubusercontent.com/shouvik126/LLD_images/main/7.23-bridge-overview.png)

It is particularly valuable in situations where:
- You have classes that can be expanded along multiple orthogonal dimensions (e.g., shape type vs. rendering engine, UI widget vs. operating system platform).
- You want to prevent a deep class hierarchy that multiplies combinations of features.
- You need to dynamically configure multiple implementation variants at runtime.

The Bridge Pattern divides a system into two distinct class hierarchies:
- **Abstraction Hierarchy**: High-level domain concepts (e.g., Shape, Remote Control).
- **Implementation Hierarchy**: Low-level operational engines (e.g., Renderer, Device Platform).

These hierarchies are linked via object composition (a bridge reference) rather than class inheritance, enabling flexible composition without rigid subclass coupling.

Below is a step-by-step walk-through demonstrating how to apply the Bridge Pattern to build a flexible and scalable system without inheritance explosion.

---

## 1. The Problem: Drawing Shapes

Imagine building a cross-platform graphics library. It supports rendering geometric shapes like circles and rectangles across different rendering modes:
- 🟢 **Vector rendering**: For resolution-independent, scalable output.
- 🔵 **Raster rendering**: For pixel-based display output.

You must support:
- Multiple shape abstractions (`Circle`, `Rectangle`).
- Multiple rendering strategies (`VectorRenderer`, `RasterRenderer`).

### Naive Approach: Subclassing Every Combination

A initial attempt creates concrete subclasses for every permutation of shape and rendering mode:

```java
// Base abstract class
public abstract class Shape {
    public abstract void draw();
}

// Concrete subclass combinations
public class VectorCircle extends Shape {
    @Override
    public void draw() {
        System.out.println("Drawing circle using vector graphics.");
    }
}

public class RasterCircle extends Shape {
    @Override
    public void draw() {
        System.out.println("Drawing circle using raster pixels.");
    }
}

public class VectorRectangle extends Shape {
    @Override
    public void draw() {
        System.out.println("Drawing rectangle using vector graphics.");
    }
}

public class RasterRectangle extends Shape {
    @Override
    public void draw() {
        System.out.println("Drawing rectangle using raster pixels.");
    }
}
```

![Naive Inheritance Hierarchy Problem](https://raw.githubusercontent.com/shouvik126/LLD_images/main/7.23-shape-rendering-problem.png)

Each subclass merges two separate concerns: shape geometry and rendering technique.

### Why This Approach Fails at Scale

1. **Class Explosion**  
   Every new combination of shape and renderer demands a new class:
   - 2 shapes × 2 renderers = 4 classes
   - Adding a 3rd renderer (e.g., `OpenGLRenderer`) requires 6 classes.
   - Adding more shapes (`Triangle`, `Ellipse`) causes combinatorial growth (*N* × *M* classes).

2. **Tight Coupling**  
   Shape logic is bound to specific rendering implementations. Rendering code cannot be reused across shapes independently.

3. **Violation of Open/Closed Principle**  
   Introducing a new rendering engine forces you to write new subclasses for every existing shape.

### Desired Architecture
We require a solution that:
- Separates domain abstractions (`Shape`) from technical implementations (`Renderer`).
- Allows new renderers to be added without modifying shape classes.
- Enables new shapes to be added without duplicating rendering logic.
- Keeps class hierarchies shallow and composable.

This is precisely what the **Bridge Design Pattern** provides.

---

## 2. The Bridge Design Pattern

The Bridge Design Pattern separates a class into two independent hierarchies: an **Abstraction** hierarchy and an **Implementation** hierarchy.

Core design characteristics:
- **Orthogonal Variation**: Abstractions (shapes) and implementations (renderers) evolve independently. Adding a shape requires zero changes to renderers, and vice-versa.
- **Composition Over Inheritance**: The abstraction holds a reference to an implementor interface and delegates execution at runtime, avoiding subclass proliferation.

### Real-World Analogy

Consider a television remote control and a TV. 
- The **Remote** is the abstraction: providing user buttons (power, volume, channel).
- The **TV** is the implementation: executing actual hardware commands (tuning frequencies, driving speakers).

A single remote model can control a Samsung TV or a Sony TV. Similarly, a smart TV can be operated via a basic remote or a universal touch remote. The remote and device hierarchies vary independently, linked by an infrared or Bluetooth protocol—the **bridge**.

### Class Diagram

![Bridge Pattern Class Diagram](https://raw.githubusercontent.com/shouvik126/LLD_images/main/7.23-bridge-class-diagram.png)

### Pattern Participants

1. **Abstraction (`Shape`)**  
   Defines the high-level interface consumed by clients. Maintains a reference to the `Implementor`.

2. **RefinedAbstraction (`Circle`, `Rectangle`)**  
   Extends `Abstraction` with specific domain logic, delegating low-level operations to the implementor.

3. **Implementor (`Renderer`)**  
   Defines the low-level interface required by primitive operations.

4. **ConcreteImplementor (`VectorRenderer`, `RasterRenderer`)**  
   Provides platform-specific logic implementing `Implementor`.

## 3. How It Works

The workflow execution of the Bridge pattern follows these steps:

![Bridge Execution Workflow](https://raw.githubusercontent.com/shouvik126/LLD_images/main/7.23-bridge-workflow.png)

1. **Instantiate Implementor**: The client creates a concrete implementation instance (e.g., `VectorRenderer`).
2. **Inject Implementor**: The client instantiates a `Circle`, passing `VectorRenderer` into its constructor.
3. **Invoke Abstraction**: The client calls `circle.draw()`.
4. **Delegate Execution**: Inside `draw()`, `Circle` delegates primitive rendering to `renderer.renderCircle(radius)`.
5. **Execute Low-Level Operations**: `VectorRenderer` executes vector rendering logic using the provided parameters.

## 4. Implementing the Bridge Pattern

Refactoring the graphics library with the Bridge pattern decouples shapes from rendering techniques.

### Step 1: Define the Implementor Interface (`Renderer`)

```java
public interface Renderer {
    void renderCircle(double radius);
    void renderRectangle(double width, double height);
}
```

### Step 2: Create Concrete Implementors

#### Vector Renderer
```java
public class VectorRenderer implements Renderer {
    @Override
    public void renderCircle(double radius) {
        System.out.println("Drawing a circle of radius " + radius + " using Vector graphics.");
    }

    @Override
    public void renderRectangle(double width, double height) {
        System.out.println("Drawing a rectangle " + width + "x" + height + " using Vector graphics.");
    }
}
```

#### Raster Renderer
```java
public class RasterRenderer implements Renderer {
    @Override
    public void renderCircle(double radius) {
        System.out.println("Drawing a circle of radius " + radius + " as a grid of pixels.");
    }

    @Override
    public void renderRectangle(double width, double height) {
        System.out.println("Drawing a rectangle " + width + "x" + height + " as a grid of pixels.");
    }
}
```

### Step 3: Define the Abstraction (`Shape`)

```java
public abstract class Shape {
    protected Renderer renderer; // The Bridge Reference

    protected Shape(Renderer renderer) {
        this.renderer = renderer;
    }

    public abstract void draw();
}
```

### Step 4: Create Refined Abstractions (`Circle`, `Rectangle`)

#### Circle
```java
public class Circle extends Shape {
    private double radius;

    public Circle(Renderer renderer, double radius) {
        super(renderer);
        this.radius = radius;
    }

    @Override
    public void draw() {
        renderer.renderCircle(radius);
    }
}
```

#### Rectangle
```java
public class Rectangle extends Shape {
    private double width;
    private double height;

    public Rectangle(Renderer renderer, double width, double height) {
        super(renderer);
        this.width = width;
        this.height = height;
    }

    @Override
    public void draw() {
        renderer.renderRectangle(width, height);
    }
}
```

### Step 5: Client Code Demonstration

```java
public class BridgePatternDemo {
    public static void main(String[] args) {
        Renderer vectorRenderer = new VectorRenderer();
        Renderer rasterRenderer = new RasterRenderer();

        Shape circle1 = new Circle(vectorRenderer, 5.0);
        Shape circle2 = new Circle(rasterRenderer, 10.0);
        Shape rectangle1 = new Rectangle(vectorRenderer, 4.0, 7.0);

        circle1.draw();
        circle2.draw();
        rectangle1.draw();
    }
}
```

### Console Output
```text
Drawing a circle of radius 5.0 using Vector graphics.
Drawing a circle of radius 10.0 as a grid of pixels.
Drawing a rectangle 4.0x7.0 using Vector graphics.
```

### Key Architectural Gains
- **Independent Evolution**: Shapes and renderers can be extended without touching one another.
- **Open/Closed Compliant**: New renderers or shapes are added seamlessly without modifying existing code.
- **Class Explosion Prevented**: *N* + *M* classes instead of *N* × *M* combinations.
- **Runtime Adaptability**: Renderers can be swapped dynamically based on system context.

## 5. Practical Example: Remote Controls and Devices

To demonstrate the Bridge pattern in a hardware control context, let's model remote controls and electronic devices.

![Remote Control Device Bridge Diagram](https://raw.githubusercontent.com/shouvik126/LLD_images/main/7.23-remote-device-bridge.png)

### Implementation

#### Implementor Interface & Concrete Devices
```java
// Implementor
public interface Device {
    boolean isEnabled();
    void enable();
    void disable();
    int getVolume();
    void setVolume(int volume);
}

// ConcreteImplementor 1: TV
public class TV implements Device {
    private boolean on = false;
    private int volume = 30;

    @Override
    public boolean isEnabled() { return on; }

    @Override
    public void enable() { on = true; System.out.println("TV powered ON."); }

    @Override
    public void disable() { on = false; System.out.println("TV powered OFF."); }

    @Override
    public int getVolume() { return volume; }

    @Override
    public void setVolume(int volume) {
        this.volume = Math.max(0, Math.min(100, volume));
        System.out.println("TV volume set to " + this.volume + "%");
    }
}

// ConcreteImplementor 2: Radio
public class Radio implements Device {
    private boolean on = false;
    private int volume = 15;

    @Override
    public boolean isEnabled() { return on; }

    @Override
    public void enable() { on = true; System.out.println("Radio powered ON."); }

    @Override
    public void disable() { on = false; System.out.println("Radio powered OFF."); }

    @Override
    public int getVolume() { return volume; }

    @Override
    public void setVolume(int volume) {
        this.volume = Math.max(0, Math.min(100, volume));
        System.out.println("Radio volume set to " + this.volume + "%");
    }
}
```

#### Abstraction & Refined Remotes
```java
// Abstraction
public class Remote {
    protected Device device; // Bridge reference

    public Remote(Device device) {
        this.device = device;
    }

    public void togglePower() {
        if (device.isEnabled()) {
            device.disable();
        } else {
            device.enable();
        }
    }

    public void volumeDown() {
        device.setVolume(device.getVolume() - 10);
    }

    public void volumeUp() {
        device.setVolume(device.getVolume() + 10);
    }
}

// RefinedAbstraction: AdvancedRemote
public class AdvancedRemote extends Remote {
    public AdvancedRemote(Device device) {
        super(device);
    }

    public void mute() {
        System.out.println("Advanced Remote: Muting device.");
        device.setVolume(0);
    }
}
```

#### Client Execution
```java
public class DeviceRemoteClient {
    public static void main(String[] args) {
        Device tv = new TV();
        Remote basicRemote = new Remote(tv);
        basicRemote.togglePower();
        basicRemote.volumeUp();

        System.out.println();

        Device radio = new Radio();
        AdvancedRemote advancedRemote = new AdvancedRemote(radio);
        advancedRemote.togglePower();
        advancedRemote.volumeUp();
        advancedRemote.mute();
    }
}
```

### Summary
The `Device` interface defines platform primitive operations. `TV` and `Radio` implement device behavior. `Remote` defines control operations and delegates to `Device`. `AdvancedRemote` adds extra functionality (`mute()`) without modifying device implementations. Adding a new device (e.g., `Projector`) or remote type (e.g., `VoiceRemote`) requires adding only a single class.
