# Mediator Design Pattern

The **Mediator Design Pattern** is a behavioral design pattern that defines an object (the Mediator) to encapsulate and coordinate how a set of objects interact with one another.

![Mediator Design Pattern Overview](https://raw.githubusercontent.com/shouvik126/LLD_images/main/7.44-mediator-overview.png)

It promotes loose coupling by preventing objects from referring to each other directly, allowing their interaction logic to be modified independently.

It is particularly valuable in situations where:
- A set of tightly coupled UI elements or domain objects must exchange state and commands.
- Modifying one object triggers cascades of updates across multiple peer components.
- You want to centralize complex communication logic into a single controller to simplify maintenance and testing.

Below is a detailed walk-through of how to apply the Mediator Pattern to build modular systems where components communicate cleanly and consistently.

---

## 1. The Problem: Tightly Coupled UI Components

Imagine building a login form containing four UI components:
- `usernameField`: Text input for user identity.
- `passwordField`: Text input for credentials.
- `loginButton`: Action button to submit credentials.
- `statusLabel`: Text feedback display showing operation results.

The form business rules dictate:
1. `loginButton` must remain disabled until both `usernameField` and `passwordField` contain non-empty values.
2. Clicking `loginButton` executes credential verification and updates `statusLabel` with success or error messaging.

### Naive Implementation: Direct Peer References

In a naive implementation, components maintain direct references to one another:

```java
public class TextField {
    private String text = "";
    private Button loginButton;

    public void setLoginButton(Button loginButton) {
        this.loginButton = loginButton;
    }

    public void setText(String text) {
        this.text = text;
        // Direct call to peer component
        if (loginButton != null) {
            loginButton.onFieldChanged();
        }
    }

    public String getText() {
        return text;
    }
}
```

```java
public class Button {
    private boolean enabled = false;
    private TextField usernameField;
    private TextField passwordField;
    private Label statusLabel;

    public Button(TextField user, TextField pass, Label status) {
        this.usernameField = user;
        this.passwordField = pass;
        this.statusLabel = status;
    }

    public void onFieldChanged() {
        boolean valid = !usernameField.getText().trim().isEmpty() 
                     && !passwordField.getText().trim().isEmpty();
        this.enabled = valid;
        System.out.println("Button state updated. Enabled: " + enabled);
    }

    public void click() {
        if (enabled) {
            statusLabel.setText("Logging in user: " + usernameField.getText() + "...");
        } else {
            statusLabel.setText("Error: Fields cannot be empty.");
        }
    }
}
```

```java
public class Label {
    private String text = "";

    public void setText(String text) {
        this.text = text;
        System.out.println("[Status Label]: " + text);
    }
}
```

### Why This Design Fails as the System Grows

1. **Tight Coupling**  
   Components maintain explicit references to peers (`TextField` knows `Button`; `Button` knows `TextField` and `Label`). A change in one component's logic forces cascading updates across peers.

2. **Lack of Reusability**  
   Components cannot be reused in another form because their logic is hardcoded to specific peer component types.

3. **Maintenance Complexity**  
   Adding new UI elements (e.g., a "Remember Me" checkbox or "Captcha" verification) requires expanding cross-component references across multiple classes, violating the Open/Closed Principle.

4. **Sprawling Control Logic**  
   Form validation logic is scattered across individual widget classes rather than isolated in a central controller.

### Desired Architecture
We require a design that:
- Decouples UI components from one another entirely.
- Centralizes interaction and validation rules inside a dedicated mediator.
- Enables components to be added, removed, or modified without breaking peer classes.

This is precisely what the **Mediator Design Pattern** provides.

---

## 2. The Mediator Design Pattern

The Mediator Pattern promotes loose coupling by centralizing all communication between related components. Instead of objects calling methods on each other directly, they notify a mediator object when their state changes.

Core characteristics:
- **Centralized Communication**: All interaction logic resides inside the mediator. Components notify the mediator of state updates rather than communicating directly with peer components.
- **Loose Coupling**: Components depend exclusively on the `Mediator` interface. They do not maintain references to peer components.

### Real-World Analogy

Consider an airport air traffic control tower. Approaching aircraft do not negotiate landing sequences or runway access by communicating directly with one another. Doing so would lead to chaotic N × N communication paths.

Instead, every pilot communicates exclusively with the control tower (the Mediator). The tower evaluates speed, altitude, and runway availability, broadcasting clear instructions: *"Flight 202, hold at 4,000 feet. Flight 405, cleared for runway 09R."*

The control tower acts as the Mediator; aircraft act as Components.

### Class Diagram

![Mediator Class Diagram](https://raw.githubusercontent.com/shouvik126/LLD_images/main/7.44-mediator-class-diagram.png)

### Pattern Participants

1. **Mediator Interface (`UIMediator`)**  
   Declares the notification contract (e.g., `componentChanged(UIComponent component)`) used by components to report state events.

2. **ConcreteMediator (`FormMediator`)**  
   Implements interaction and validation logic across managed components. Maintains references to concrete components.

3. **Component Base Class (`UIComponent`)**  
   Holds a reference to the mediator and exposes notification helper methods.

4. **ConcreteComponents (`TextField`, `Button`, `Label`)**  
   Executes widget-specific duties and notifies the mediator whenever state changes occur.

---

## 3. How It Works

The workflow execution follows a centralized hub sequence:

1. **Component State Update**: User types text into `usernameField`.
2. **Notify Mediator**: `usernameField` calls `mediator.componentChanged(this)`.
3. **Mediator Evaluation**: `FormMediator` inspects state values across `usernameField` and `passwordField`.
4. **Coordinated Response**: `FormMediator` enables `loginButton` and updates `statusLabel`.
5. **No Direct Component Calls**: `TextField` remains unaware of `Button` or `Label`.

## 4. Implementing the Mediator Pattern

Let's refactor the login form system using the Mediator Pattern in five steps.

### Step 1: Define the Mediator Interface

```java
public interface UIMediator {
    void componentChanged(UIComponent component);
}
```

### Step 2: Define the Component Abstract Base Class

```java
public abstract class UIComponent {
    protected UIMediator mediator;

    public UIComponent(UIMediator mediator) {
        this.mediator = mediator;
    }

    public void notifyMediator() {
        if (mediator != null) {
            mediator.componentChanged(this);
        }
    }
}
```

### Step 3: Implement Concrete Components

#### TextField
```java
public class TextField extends UIComponent {
    private String text = "";

    public TextField(UIMediator mediator) {
        super(mediator);
    }

    public void setText(String text) {
        this.text = text;
        notifyMediator(); // Report change to mediator
    }

    public String getText() {
        return text;
    }
}
```

#### Button
```java
public class Button extends UIComponent {
    private boolean enabled = false;

    public Button(UIMediator mediator) {
        super(mediator);
    }

    public void setEnabled(boolean enabled) {
        this.enabled = enabled;
        System.out.println("[UI Button] State updated. Enabled: " + enabled);
    }

    public boolean isEnabled() {
        return enabled;
    }

    public void click() {
        if (enabled) {
            notifyMediator(); // Trigger action event via mediator
        } else {
            System.out.println("[UI Button] Click ignored. Button is disabled.");
        }
    }
}
```

#### Label
```java
public class Label extends UIComponent {
    private String text = "";

    public Label(UIMediator mediator) {
        super(mediator);
    }

    public void setText(String text) {
        this.text = text;
        System.out.println("[UI Label] Text: " + text);
    }

    public String getText() {
        return text;
    }
}
```

### Step 4: Implement Concrete Mediator (`FormMediator`)

```java
public class FormMediator implements UIMediator {
    private TextField usernameField;
    private TextField passwordField;
    private Button loginButton;
    private Label statusLabel;

    public void registerComponents(TextField user, TextField pass, Button btn, Label label) {
        this.usernameField = user;
        this.passwordField = pass;
        this.loginButton = btn;
        this.statusLabel = label;
    }

    @Override
    public void componentChanged(UIComponent component) {
        if (component == usernameField || component == passwordField) {
            handleFieldChange();
        } else if (component == loginButton) {
            handleButtonClick();
        }
    }

    private void handleFieldChange() {
        boolean valid = !usernameField.getText().trim().isEmpty() 
                     && !passwordField.getText().trim().isEmpty();
        loginButton.setEnabled(valid);
    }

    private void handleButtonClick() {
        statusLabel.setText("Authenticating user: " + usernameField.getText() + "...");
    }
}
```

### Step 5: Client Execution & Verification

```java
public class MediatorPatternDemo {
    public static void main(String[] args) {
        FormMediator mediator = new FormMediator();

        TextField userField = new TextField(mediator);
        TextField passField = new TextField(mediator);
        Button loginBtn = new Button(mediator);
        Label statusLbl = new Label(mediator);

        mediator.registerComponents(userField, passField, loginBtn, statusLbl);

        System.out.println("--- Step 1: User Types Username ---");
        userField.setText("alice");

        System.out.println("\n--- Step 2: User Types Password ---");
        passField.setText("secret123");

        System.out.println("\n--- Step 3: User Clicks Login Button ---");
        loginBtn.click();
    }
}
```

### Console Output
```text
--- Step 1: User Types Username ---
[UI Button] State updated. Enabled: false

--- Step 2: User Types Password ---
[UI Button] State updated. Enabled: true

--- Step 3: User Clicks Login Button ---
[UI Label] Text: Authenticating user: alice...
```

## 5. Practical Example: Multi-User Chat Room System

Consider a multi-user chat room system. Users send text messages to a chat room mediator, which broadcasts incoming messages to all connected participants without requiring users to hold direct references to one another.

![Chat Mediator Diagram](https://raw.githubusercontent.com/shouvik126/LLD_images/main/7.44-chat-mediator-diagram.png)

### Implementation

```java
import java.util.ArrayList;
import java.util.List;

// Mediator Interface
public interface ChatMediator {
    void sendMessage(String message, User sender);
    void addUser(User user);
}

// Concrete Mediator
public class ChatRoom implements ChatMediator {
    private final List<User> users = new ArrayList<>();

    @Override
    public void addUser(User user) {
        this.users.add(user);
        System.out.println("[ChatRoom] " + user.getName() + " joined the room.");
    }

    @Override
    public void sendMessage(String message, User sender) {
        for (User u : users) {
            // Broadcast to all participants except sender
            if (u != sender) {
                u.receive(message, sender.getName());
            }
        }
    }
}

// Component Base Class
public abstract class User {
    protected ChatMediator mediator;
    protected String name;

    public User(ChatMediator mediator, String name) {
        this.mediator = mediator;
        this.name = name;
    }

    public String getName() {
        return name;
    }

    public abstract void send(String message);
    public abstract void receive(String message, String from);
}

// Concrete Component
public class ChatUser extends User {
    public ChatUser(ChatMediator mediator, String name) {
        super(mediator, name);
    }

    @Override
    public void send(String message) {
        System.out.println("\n[" + name + " sends]: " + message);
        mediator.sendMessage(message, this);
    }

    @Override
    public void receive(String message, String from) {
        System.out.println("[" + name + " received from " + from + "]: " + message);
    }
}
```

```java
// Client Demo
public class ChatRoomDemo {
    public static void main(String[] args) {
        ChatMediator chatRoom = new ChatRoom();

        User alice = new ChatUser(chatRoom, "Alice");
        User bob = new ChatUser(chatRoom, "Bob");
        User charlie = new ChatUser(chatRoom, "Charlie");

        chatRoom.addUser(alice);
        chatRoom.addUser(bob);
        chatRoom.addUser(charlie);

        alice.send("Hello everyone!");
        bob.send("Hey Alice!");
    }
}
```

### Console Output
```text
[ChatRoom] Alice joined the room.
[ChatRoom] Bob joined the room.
[ChatRoom] Charlie joined the room.

[Alice sends]: Hello everyone!
[Bob received from Alice]: Hello everyone!
[Charlie received from Alice]: Hello everyone!

[Bob sends]: Hey Alice!
[Alice received from Bob]: Hey Alice!
[Charlie received from Bob]: Hey Alice!
```

### Comparison: Mediator vs. Observer Pattern

| Architectural Aspect | Mediator Design Pattern | Observer Design Pattern |
| :--- | :--- | :--- |
| **Communication Flow** | Bi-directional multi-object coordination | One-way publisher-to-subscriber notifications |
| **Data Routing** | Mediator actively filters, transforms, and routes data selectively | Subject blindly broadcasts uniform state changes to all subscribers |
| **Coupling Model** | Centralized hub object absorbs system structural coupling | Publisher maintains weak interface coupling to dynamic listener lists |
