# Decorator Design Pattern

The **Decorator Design Pattern** is a structural design pattern that lets you dynamically attach new behaviors or responsibilities to individual objects at runtime without modifying their underlying source code or class definitions.

![Decorator Design Pattern Overview](https://raw.githubusercontent.com/shouvik126/LLD_images/main/7.17-decorator-overview.png)

It is particularly valuable in situations where:
- You want to extend object functionality without relying on subclassing or class inheritance.
- You need to compose multiple optional features dynamically at runtime in flexible combinations.
- You want to avoid monolithic classes cluttered with conditional `if-else` flags for optional features.

By wrapping concrete components inside decorator instances, the Decorator pattern achieves modularity, runtime composability, and strict adherence to the **Open/Closed Principle (OCP)**.

---

## 1. The Problem: Feature Combinations in a Text Renderer

Imagine developing a rich text rendering system for a text editor or markdown previewer. The core component is a `TextView` that outputs unformatted text.

As application requirements expand, new formatting options are introduced:
- Bold text formatting
- Italic text formatting
- Underlined text formatting
- Arbitrary combinations (e.g., Bold + Italic, Bold + Underline, Italic + Underline, or all three combined)

### The Naive Approach: Subclassing Every Combination

A common initial instinct is to create a distinct subclass for every feature combination:

![Subclass Explosion Diagram](https://raw.githubusercontent.com/shouvik126/LLD_images/main/7.17-subclass-explosion.png)

With only 3 optional features (Bold, Italic, Underline), supporting every combination requires 2³ - 1 = 7 distinct subclasses. Adding a 4th feature (e.g., Highlight) increases the requirement to 15 subclasses. A 5th feature (e.g., Strikethrough) expands it to 31 subclasses. In general, *n* independent features require 2ⁿ - 1 subclasses.

### Naive Implementation (Without Decorator)

```java
// Base Component
public class TextView {
    public String render(String text) {
        return text;
    }
}

// Subclasses for individual features
public class BoldTextView extends TextView {
    @Override
    public String render(String text) {
        return "<b>" + super.render(text) + "</b>";
    }
}

public class ItalicTextView extends TextView {
    @Override
    public String render(String text) {
        return "<i>" + super.render(text) + "</i>";
    }
}

// Subclasses for feature combinations
public class BoldItalicTextView extends TextView {
    @Override
    public String render(String text) {
        return "<i><b>" + super.render(text) + "</b></i>";
    }
}

public class BoldUnderlineTextView extends TextView {
    @Override
    public String render(String text) {
        return "<u><b>" + super.render(text) + "</b></u>";
    }
}

public class BoldItalicUnderlineTextView extends TextView {
    @Override
    public String render(String text) {
        return "<u><i><b>" + super.render(text) + "</b></i></u>";
    }
}
```

### Why This Approach Fails at Scale
1. **Class Explosion**: The number of required subclasses grows exponentially with each added feature (2ⁿ - 1).
2. **Rigid Compile-Time Composition**: Behaviors cannot be toggled dynamically at runtime. Adding or removing a style requires instantiating an entirely different subclass.
3. **Violates Open/Closed Principle**: Introducing a new style requires creating new combination subclasses for every existing variation.
4. **Code Duplication**: Formatting logic (e.g., `<b>` wrapping) is duplicated across every subclass combination that includes bold text.

---

## 2. The Decorator Design Pattern

The Decorator pattern attaches additional responsibilities to an object dynamically. Rather than extending class functionality via inheritance, it wraps the base object inside a decorator object that adds the desired behavior.

### Key Characteristics
1. **Interface Preservation**: Every decorator implements the same interface as the wrapped component. Client code interacts with decorators transparently.
2. **Dynamic Composition**: Decorators can be nested and stacked at runtime in any order or combination.

### Real-World Analogy: Coffee Customization
Consider ordering a basic coffee. You can add milk, add sugar, or add whipped cream. Each ingredient enhances the original beverage without altering the base coffee recipe itself. Ingredients can be stacked dynamically (e.g., Coffee + Milk + Double Sugar).

![Decorator Class Diagram](https://raw.githubusercontent.com/shouvik126/LLD_images/main/7.17-decorator-class-diagram.png)

### Participants in the Pattern
1. **Component Interface** (`TextView`): Defines the common contract for both base components and decorators.
2. **ConcreteComponent** (`PlainTextView`): The base component being decorated.
3. **Decorator** (`TextDecorator`): Abstract base class implementing `Component` while holding a reference to a wrapped `Component`.
4. **ConcreteDecorator** (`BoldDecorator`, `ItalicDecorator`, `UnderlineDecorator`): Extends the decorator base to add specific behaviors before or after delegating to the wrapped component.

---

## 3. How the Decorator Pattern Works

The execution flow of stacked decorators follows a nested delegation pipeline:

![Decorator Execution Workflow](https://raw.githubusercontent.com/shouvik126/LLD_images/main/7.17-decorator-workflow.png)

1. **Client Instantiates Base Component**: Create a `PlainTextView` containing `"Hello"`.
2. **Wrap in First Decorator**: Wrap `PlainTextView` inside `BoldDecorator`.
3. **Stack Subsequent Decorators**: Wrap `BoldDecorator` inside `ItalicDecorator`, then wrap that inside `UnderlineDecorator`.
4. **Client Calls Operation**: The client invokes `render()` on the outermost decorator (`UnderlineDecorator`).
5. **Delegation Inward**:
   - `UnderlineDecorator` prepends `<u>`, then calls `render()` on `ItalicDecorator`.
   - `ItalicDecorator` prepends `<i>`, then calls `render()` on `BoldDecorator`.
   - `BoldDecorator` prepends `<b>`, then calls `render()` on `PlainTextView`.
6. **Execution Outward**: `PlainTextView` returns `"Hello"`, `BoldDecorator` appends `</b>`, `ItalicDecorator` appends `</i>`, and `UnderlineDecorator` appends `</u>`.
7. **Final Output**: `<u><i><b>Hello</b></i></u>`.

## 4. Java Implementation Step-by-Step

Let's build a modular text rendering system using the Decorator pattern.

![Text Renderer Decorator Class Diagram](https://raw.githubusercontent.com/shouvik126/LLD_images/main/7.17-text-decorator-class-diagram.png)

### Step 1: Define Component Interface

```java
public interface TextView {
    String render();
}
```

### Step 2: Implement Concrete Component

```java
public class PlainTextView implements TextView {
    private final String text;

    public PlainTextView(String text) {
        this.text = text;
    }

    @Override
    public String render() {
        return text;
    }
}
```

### Step 3: Create Abstract Decorator Base Class

```java
public abstract class TextDecorator implements TextView {
    protected final TextView innerTextView;

    public TextDecorator(TextView innerTextView) {
        this.innerTextView = innerTextView;
    }

    @Override
    public String render() {
        return innerTextView.render();
    }
}
```

### Step 4: Implement Concrete Decorators

#### Bold Decorator
```java
public class BoldDecorator extends TextDecorator {
    public BoldDecorator(TextView innerTextView) {
        super(innerTextView);
    }

    @Override
    public String render() {
        return "<b>" + super.render() + "</b>";
    }
}
```

#### Italic Decorator
```java
public class ItalicDecorator extends TextDecorator {
    public ItalicDecorator(TextView innerTextView) {
        super(innerTextView);
    }

    @Override
    public String render() {
        return "<i>" + super.render() + "</i>";
    }
}
```

#### Underline Decorator
```java
public class UnderlineDecorator extends TextDecorator {
    public UnderlineDecorator(TextView innerTextView) {
        super(innerTextView);
    }

    @Override
    public String render() {
        return "<u>" + super.render() + "</u>";
    }
}
```

### Step 5: Client Demonstration Code

```java
public class DecoratorDemoApp {
    public static void main(String[] args) {
        // Base plain text
        TextView plainText = new PlainTextView("Hello World");
        System.out.println("Plain: " + plainText.render());

        // Single decoration (Bold)
        TextView boldText = new BoldDecorator(plainText);
        System.out.println("Bold: " + boldText.render());

        // Layered decorations (Bold + Italic)
        TextView boldItalicText = new ItalicDecorator(new BoldDecorator(new PlainTextView("Hello World")));
        System.out.println("Bold + Italic: " + boldItalicText.render());

        // Full stacked decorations (Underline + Italic + Bold)
        TextView fullyFormattedText = new UnderlineDecorator(
            new ItalicDecorator(
                new BoldDecorator(
                    new PlainTextView("Hello World")
                )
            )
        );
        System.out.println("Fully Formatted: " + fullyFormattedText.render());
    }
}
```

### Expected Output:
```text
Plain: Hello World
Bold: <b>Hello World</b>
Bold + Italic: <i><b>Hello World</b></i>
Fully Formatted: <u><i><b>Hello World</b></i></u>
```

## 5. Practical Real-World Example: Coffee Shop Ordering System

Consider an enterprise coffee ordering system where base beverages can be augmented with dynamic condiments (Milk, Sugar, Whipped Cream), each contributing to total cost and item description.

![Coffee Ordering Decorator Class Diagram](https://raw.githubusercontent.com/shouvik126/LLD_images/main/7.17-coffee-decorator-class-diagram.png)

### Coffee Shop Decorator Implementation

```java
// Component Interface
interface Coffee {
    double getCost();
    String getDescription();
}

// Concrete Component
class SimpleCoffee implements Coffee {
    @Override
    public double getCost() {
        return 2.00;
    }

    @Override
    public String getDescription() {
        return "Plain Coffee";
    }
}

// Abstract Decorator
abstract class CoffeeDecorator implements Coffee {
    protected final Coffee innerCoffee;

    public CoffeeDecorator(Coffee innerCoffee) {
        this.innerCoffee = innerCoffee;
    }

    @Override
    public double getCost() {
        return innerCoffee.getCost();
    }

    @Override
    public String getDescription() {
        return innerCoffee.getDescription();
    }
}

// Concrete Decorator 1: Milk
class MilkDecorator extends CoffeeDecorator {
    public MilkDecorator(Coffee innerCoffee) {
        super(innerCoffee);
    }

    @Override
    public double getCost() {
        return super.getCost() + 0.50;
    }

    @Override
    public String getDescription() {
        return super.getDescription() + ", Milk";
    }
}

// Concrete Decorator 2: Sugar
class SugarDecorator extends CoffeeDecorator {
    public SugarDecorator(Coffee innerCoffee) {
        super(innerCoffee);
    }

    @Override
    public double getCost() {
        return super.getCost() + 0.25;
    }

    @Override
    public String getDescription() {
        return super.getDescription() + ", Sugar";
    }
}

// Concrete Decorator 3: Whipped Cream
class WhippedCreamDecorator extends CoffeeDecorator {
    public WhippedCreamDecorator(Coffee innerCoffee) {
        super(innerCoffee);
    }

    @Override
    public double getCost() {
        return super.getCost() + 0.75;
    }

    @Override
    public String getDescription() {
        return super.getDescription() + ", Whipped Cream";
    }
}

// Demonstration Client
public class CoffeeShopDemo {
    public static void main(String[] args) {
        // Order 1: Simple Coffee
        Coffee order1 = new SimpleCoffee();
        System.out.println(order1.getDescription() + " -> $" + order1.getCost());

        // Order 2: Coffee with Milk and Sugar
        Coffee order2 = new SugarDecorator(new MilkDecorator(new SimpleCoffee()));
        System.out.println(order2.getDescription() + " -> $" + order2.getCost());

        // Order 3: Coffee with Double Milk, Sugar, and Whipped Cream
        Coffee order3 = new WhippedCreamDecorator(
            new SugarDecorator(
                new MilkDecorator(
                    new MilkDecorator(
                        new SimpleCoffee()
                    )
                )
            )
        );
        System.out.println(order3.getDescription() + " -> $" + order3.getCost());
    }
}
```

### Output:
```text
Plain Coffee -> $2.0
Plain Coffee, Milk, Sugar -> $2.75
Plain Coffee, Milk, Milk, Sugar, Whipped Cream -> $4.0
```

## 6. Summary & Key Takeaways

- **Dynamic Runtime Enhancement**: Attach new behaviors to individual objects dynamically without compile-time subclassing.
- **Prevents Class Explosion**: Replaces exponential subclass combinations (2ⁿ - 1) with linear class counts (1 + n).
- **Open/Closed Principle**: Introduce new capabilities by writing new decorator classes without modifying existing components.
- **Single Responsibility Principle**: Each decorator encapsulates a single, dedicated responsibility (e.g., Bold, Milk, Underline).
