# Observer Design Pattern

The **Observer Design Pattern** is a behavioral design pattern that defines a one-to-many dependency between objects so that when one object (the subject) changes its state, all its registered dependents (observers) are automatically notified and updated.

![Observer Design Pattern Overview](https://raw.githubusercontent.com/shouvik126/LLD_images/main/7.32-observer-overview.png)

This pattern excels in scenarios where:
- Multiple modules or sub-components in a system must react synchronously or asynchronously to state changes in a central data source.
- You want to decouple the publisher of data from subscribers reacting to events.
- You need a dynamic, event-driven communication model without hardcoding listener dependencies.

Below is a detailed walk-through of how to apply the Observer Pattern to build a flexible, extensible, and loosely coupled notification system.

---

## 1. The Problem: Broadcasting Fitness Data

Imagine building a Fitness Tracker application connected to a wearable device. The wearable device streams real-time fitness metrics: steps taken, active minutes, and calories burned. This data updates a central `FitnessData` state object.

Multiple app modules react to these metrics:
- **LiveActivityDisplay**: Shows real-time statistics on the user dashboard.
- **ProgressLogger**: Persists fitness metrics to a local database for trend analysis.
- **GoalNotifier**: Sends alerts when users hit daily milestones (e.g., 10,000 steps).

![Fitness Data Problem Scenario](https://raw.githubusercontent.com/shouvik126/LLD_images/main/7.32-fitness-data-problem.png)

### Naive Implementation

In a naive design, `FitnessData` holds direct references to dependent display, logging, and notification classes:

```java
public class LiveActivityDisplay {
    public void updateDisplay(int steps, int activeMinutes, int calories) {
        System.out.println("[Display] Steps: " + steps + " | Active Mins: " + activeMinutes + " | Calories: " + calories);
    }
}

public class ProgressLogger {
    public void logProgress(int steps, int activeMinutes, int calories) {
        System.out.println("[Logger] Saved to DB -> Steps: " + steps + ", Mins: " + activeMinutes);
    }
}

public class NotificationService {
    public void checkMilestones(int steps) {
        if (steps >= 10000) {
            System.out.println("[Alert] Congratulations! You reached your 10,000 steps goal!");
        }
    }
}

public class FitnessDataNaive {
    private int steps;
    private int activeMinutes;
    private int calories;

    private LiveActivityDisplay display = new LiveActivityDisplay();
    private ProgressLogger logger = new ProgressLogger();
    private NotificationService notifier = new NotificationService();

    public void newFitnessDataPushed(int steps, int activeMinutes, int calories) {
        this.steps = steps;
        this.activeMinutes = activeMinutes;
        this.calories = calories;

        // Directly invoking concrete module methods
        display.updateDisplay(steps, activeMinutes, calories);
        logger.logProgress(steps, activeMinutes, calories);
        notifier.checkMilestones(steps);
    }
}
```

```java
public class FitnessAppNaiveClient {
    public static void main(String[] args) {
        FitnessDataNaive tracker = new FitnessDataNaive();
        tracker.newFitnessDataPushed(5000, 30, 250);
        tracker.newFitnessDataPushed(10200, 65, 520);
    }
}
```

### Why This Approach Fails at Scale

1. **Tight Coupling**  
   `FitnessDataNaive` depends directly on concrete implementations (`LiveActivityDisplay`, `ProgressLogger`, `NotificationService`). Changing method signatures or replacing a concrete class forces edits inside `FitnessDataNaive`.

2. **Violation of Open/Closed Principle**  
   Adding new features (such as a `WeeklySummaryGenerator` or `SocialSharingService`) requires creating new fields and adding hardcoded invocation lines inside `FitnessDataNaive`.

3. **Static and Inflexible Design**  
   Listeners cannot be subscribed or unsubscribed at runtime. If a user turns off notifications in app settings, disabling alerts requires branching conditionals inside core data methods.

4. **Violation of Single Responsibility Principle**  
   `FitnessData` should focus solely on tracking fitness state. Managing UI rendering, database persistence, and alert rules overburdens the class.

### Desired Architecture
We require a design that allows:
- `FitnessData` to broadcast updates to multiple listeners without knowing their concrete types.
- Modules to subscribe or unsubscribe dynamically at runtime.
- Loose coupling between publisher and subscribers.
- Observers to independently determine how they react to state changes.

This is the core objective of the **Observer Design Pattern**.

---

## 2. The Observer Design Pattern

The Observer pattern establishes a decoupled event-handling architecture between a **Subject** (Publisher) and multiple **Observers** (Subscribers).

Two primary traits define the pattern:
- **One-to-Many Notification**: A single subject broadcasts updates to any number of registered observers.
- **Loose Coupling**: The subject interacts exclusively via an `Observer` interface, unaware of concrete listener details.

### Real-World Analogy

Think of a newspaper subscription. A publisher prints daily newspapers and delivers them to all active subscribers. The publisher doesn't care whether a subscriber reads the front page, checks sports scores, or uses the paper for crafts. If a customer cancels a subscription, deliveries stop; when a new customer signs up, they receive daily editions. The publisher's printing process remains unchanged.

### Class Diagram

![Observer Pattern Class Diagram](https://raw.githubusercontent.com/shouvik126/LLD_images/main/7.32-observer-class-diagram.png)

### Pattern Participants

1. **Subject Interface (`Subject`)**  
   Declares observer management methods (`registerObserver`, `removeObserver`, `notifyObservers`).

2. **Observer Interface (`FitnessDataObserver`)**  
   Declares the callback contract (`update`) invoked when subject state changes.

3. **ConcreteSubject (`FitnessData`)**  
   Implements `Subject`, storing state and broadcasting updates to registered observers.

4. **ConcreteObservers (`LiveActivityDisplay`, `ProgressLogger`, `GoalNotifier`)**  
   Implements `FitnessDataObserver` to execute specialized reactions upon receiving update events.

---

## 3. How It Works

The workflow execution of the Observer pattern follows these steps:

![Observer Execution Workflow](https://raw.githubusercontent.com/shouvik126/LLD_images/main/7.32-observer-workflow.png)

1. **Registration**: Observers register themselves with the subject via `subject.registerObserver(observer)`.
2. **State Change**: State changes occur inside the subject (e.g., `setMeasurements(...)`).
3. **Broadcast Notification**: The subject iterates through its observer collection, calling `observer.update(this)`.
4. **Data Pull / Process**: Each observer queries state getters on the subject reference to retrieve updated values and process custom logic.
5. **Unregistration**: Observers can call `subject.removeObserver(observer)` to stop receiving future updates.

## 4. Implementing the Observer Pattern

Let's refactor the fitness tracker using the Observer pattern.

### Step 1: Define the Observer Interface

```java
public interface FitnessDataObserver {
    void update(FitnessData fitnessData);
}
```

### Step 2: Define the Subject Interface

```java
public interface Subject {
    void registerObserver(FitnessDataObserver observer);
    void removeObserver(FitnessDataObserver observer);
    void notifyObservers();
}
```

### Step 3: Implement Concrete Subject (`FitnessData`)

```java
import java.util.ArrayList;
import java.util.List;

public class FitnessData implements Subject {
    private final List<FitnessDataObserver> observers = new ArrayList<>();
    private int steps;
    private int activeMinutes;
    private int calories;

    @Override
    public void registerObserver(FitnessDataObserver observer) {
        if (!observers.contains(observer)) {
            observers.add(observer);
        }
    }

    @Override
    public void removeObserver(FitnessDataObserver observer) {
        observers.remove(observer);
    }

    @Override
    public void notifyObservers() {
        for (FitnessDataObserver observer : observers) {
            observer.update(this);
        }
    }

    public void setMeasurements(int steps, int activeMinutes, int calories) {
        this.steps = steps;
        this.activeMinutes = activeMinutes;
        this.calories = calories;
        notifyObservers(); // Trigger automated notification broadcast
    }

    // Getters for observers to pull data
    public int getSteps() { return steps; }
    public int getActiveMinutes() { return activeMinutes; }
    public int getCalories() { return calories; }
}
```

### Step 4: Implement Concrete Observers

#### Live Activity Display
```java
public class LiveActivityDisplay implements FitnessDataObserver {
    @Override
    public void update(FitnessData fitnessData) {
        System.out.println("[Display] Dashboard Updated -> Steps: " + fitnessData.getSteps() + 
                           ", Active Mins: " + fitnessData.getActiveMinutes() + 
                           ", Calories: " + fitnessData.getCalories());
    }
}
```

#### Progress Logger
```java
public class ProgressLogger implements FitnessDataObserver {
    @Override
    public void update(FitnessData fitnessData) {
        System.out.println("[Logger] Persisting to DB -> Steps: " + fitnessData.getSteps() + 
                           ", Mins: " + fitnessData.getActiveMinutes());
    }
}
```

#### Goal Notifier
```java
public class GoalNotifier implements FitnessDataObserver {
    private static final int STEP_GOAL = 10000;
    private boolean goalReachedNotified = false;

    @Override
    public void update(FitnessData fitnessData) {
        if (fitnessData.getSteps() >= STEP_GOAL && !goalReachedNotified) {
            System.out.println("[Goal Notifier] Alert: Daily milestone achieved! (" + fitnessData.getSteps() + " steps)");
            goalReachedNotified = true;
        }
    }
}
```

### Step 5: Client Execution & Verification

```java
public class ObserverPatternDemo {
    public static void main(String[] args) {
        FitnessData fitnessData = new FitnessData();

        LiveActivityDisplay display = new LiveActivityDisplay();
        ProgressLogger logger = new ProgressLogger();
        GoalNotifier notifier = new GoalNotifier();

        // Register observers
        fitnessData.registerObserver(display);
        fitnessData.registerObserver(logger);
        fitnessData.registerObserver(notifier);

        System.out.println("--- First Workout Update ---");
        fitnessData.setMeasurements(4500, 25, 200);

        System.out.println("\n--- Second Workout Update ---");
        fitnessData.setMeasurements(10500, 60, 510);

        // Dynamically unsubscribe logger at runtime
        System.out.println("\n--- Unregistering Logger ---");
        fitnessData.removeObserver(logger);

        System.out.println("\n--- Third Workout Update ---");
        fitnessData.setMeasurements(12000, 75, 600);
    }
}
```

### Console Output
```text
--- First Workout Update ---
[Display] Dashboard Updated -> Steps: 4500, Active Mins: 25, Calories: 200
[Logger] Persisting to DB -> Steps: 4500, Mins: 25

--- Second Workout Update ---
[Display] Dashboard Updated -> Steps: 10500, Active Mins: 60, Calories: 510
[Logger] Persisting to DB -> Steps: 10500, Mins: 60
[Goal Notifier] Alert: Daily milestone achieved! (10500 steps)

--- Unregistering Logger ---

--- Third Workout Update ---
[Display] Dashboard Updated -> Steps: 12000, Active Mins: 75, Calories: 600
```

### Architectural Benefits
- **Decoupled Architecture**: `FitnessData` contains zero concrete observer references.
- **Open/Closed Compliant**: Adding new observers requires no modifications to `FitnessData`.
- **Runtime Flexibility**: Listeners subscribe or unsubscribe dynamically via `registerObserver` and `removeObserver`.

## 5. Evolving the System: Adding a Weekly Summary Generator

To demonstrate Open/Closed principle compliance, let's add a `WeeklySummaryGenerator` feature. We create a new observer without modifying existing subject or observer code:

```java
public class WeeklySummaryGenerator implements FitnessDataObserver {
    private int weeklySteps = 0;
    private int weeklyActiveMinutes = 0;

    @Override
    public void update(FitnessData fitnessData) {
        weeklySteps += fitnessData.getSteps();
        weeklyActiveMinutes += fitnessData.getActiveMinutes();
        System.out.println("[Weekly Summary] Accumulated Steps: " + weeklySteps + 
                           " | Total Active Mins: " + weeklyActiveMinutes);
    }
}
```

### Registration
```java
WeeklySummaryGenerator summaryGen = new WeeklySummaryGenerator();
fitnessData.registerObserver(summaryGen);
```

## 6. Practical Example: Stock Price Ticker System

Consider a stock exchange system where `StockExchange` publishes price fluctuations to multiple consumer services: `PriceDisplay`, `AlertService`, and `TradingBot`.

![Stock Observer System Diagram](https://raw.githubusercontent.com/shouvik126/LLD_images/main/7.32-stock-observer-diagram.png)

### Implementation

```java
import java.util.ArrayList;
import java.util.HashMap;
import java.util.List;
import java.util.Map;

// Observer Interface
public interface StockObserver {
    void onPriceUpdate(StockExchange exchange);
}

// Subject
public class StockExchange {
    private final List<StockObserver> observers = new ArrayList<>();
    private final Map<String, Double> prices = new HashMap<>();
    private String lastUpdatedSymbol;

    public void registerObserver(StockObserver observer) {
        observers.add(observer);
    }

    public void removeObserver(StockObserver observer) {
        observers.remove(observer);
    }

    public void notifyObservers() {
        for (StockObserver observer : observers) {
            observer.onPriceUpdate(this);
        }
    }

    public void updatePrice(String symbol, double price) {
        prices.put(symbol, price);
        this.lastUpdatedSymbol = symbol;
        notifyObservers();
    }

    public double getPrice(String symbol) {
        return prices.getOrDefault(symbol, 0.0);
    }

    public String getLastUpdatedSymbol() {
        return lastUpdatedSymbol;
    }
}

// Concrete Observer 1: Price Display
public class PriceDisplay implements StockObserver {
    @Override
    public void onPriceUpdate(StockExchange exchange) {
        String symbol = exchange.getLastUpdatedSymbol();
        System.out.println("[Ticker Display] " + symbol + " -> $" + exchange.getPrice(symbol));
    }
}

// Concrete Observer 2: Alert Service
public class AlertService implements StockObserver {
    private final Map<String, Double> thresholds = new HashMap<>();

    public void setThreshold(String symbol, double thresholdPrice) {
        thresholds.put(symbol, thresholdPrice);
    }

    @Override
    public void onPriceUpdate(StockExchange exchange) {
        String symbol = exchange.getLastUpdatedSymbol();
        double currentPrice = exchange.getPrice(symbol);
        if (thresholds.containsKey(symbol) && currentPrice >= thresholds.get(symbol)) {
            System.out.println("[Alert Service] THRESHOLD ALERT: " + symbol + " crossed $" + thresholds.get(symbol) + " (Current: $" + currentPrice + ")");
        }
    }
}

// Concrete Observer 3: Automated Trading Bot
public class TradingBot implements StockObserver {
    @Override
    public void onPriceUpdate(StockExchange exchange) {
        String symbol = exchange.getLastUpdatedSymbol();
        double price = exchange.getPrice(symbol);
        if ("AAPL".equals(symbol) && price < 150.0) {
            System.out.println("[Trading Bot] BUY ORDER EXECUTED for AAPL at $" + price);
        }
    }
}
```

```java
// Client Demo
public class StockExchangeDemo {
    public static void main(String[] args) {
        StockExchange exchange = new StockExchange();

        PriceDisplay display = new PriceDisplay();
        AlertService alertService = new AlertService();
        TradingBot bot = new TradingBot();

        alertService.setThreshold("GOOGL", 2800.0);

        exchange.registerObserver(display);
        exchange.registerObserver(alertService);
        exchange.registerObserver(bot);

        System.out.println("--- Update 1 ---");
        exchange.updatePrice("AAPL", 145.50);

        System.out.println("\n--- Update 2 ---");
        exchange.updatePrice("GOOGL", 2850.00);
    }
}
```

### Console Output
```text
--- Update 1 ---
[Ticker Display] AAPL -> $145.5
[Trading Bot] BUY ORDER EXECUTED for AAPL at $145.5

--- Update 2 ---
[Ticker Display] GOOGL -> $2850.0
[Alert Service] THRESHOLD ALERT: GOOGL crossed $2800.0 (Current: $2850.0)
```

### Summary
The `StockExchange` subject broadcasts price updates through a shared `StockObserver` contract. Observers consume data independently without coupling to publisher internals or other subscriber implementations.
