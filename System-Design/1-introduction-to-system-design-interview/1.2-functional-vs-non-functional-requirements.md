# Functional vs. Non-Functional Requirements

> *"Design a URL shortener."*

Two candidates listen to the exact same prompt. The first immediately begins sketching architecture components. The second pauses and says: *"Before drawing any components, let me clarify what the system needs to do, and how effectively it must perform."*

These reflect the two fundamental categories of requirements, each fulfilling a distinct role:

- **Functional requirements** define **what** the system does—its features (e.g., *"A user can shorten a long URL"*).
- **Non-functional requirements** define **how well** it performs—its operational qualities (e.g., *"Redirect requests resolve in under 50 ms at the 99th percentile"*).

Here is the key insight many candidates overlook: **Functional requirements determine which components exist in your diagram. Non-functional requirements dictate how many components are needed, where they are placed, and how they interact.** Shortening a URL is conceptually identical whether serving a thousand users or a hundred million. However, handling a hundred million users requires a completely transformed architecture.

## Functional Requirements

Functional requirements represent the capabilities available to a user. Evaluating them is binary: you can answer with a simple yes or no—the feature is either supported or it is not.

For a URL shortener system:
- A user can submit a long URL and receive a shortened link.
- Accessing a short URL redirects the client to the original URL.
- A user can optionally specify a custom alias for the link.
- A shortened link can optionally be assigned an expiration timestamp.

Aim to define **3 to 5 core functional requirements** and then stop. The essential skill during this step is not brainstorming exhaustive feature lists, but deliberately scoping them down.

When an interviewer asks you to *"design Twitter"*, they do not expect full feature parity with Twitter. Instead, they expect a scoping statement like:
> *"I will focus on posting tweets, following users, and rendering the home timeline. I will exclude search, direct messaging, ads, and trending topics for now. Does that align with what you'd like to evaluate?"*

This single statement accomplishes three critical goals:
1. It demonstrates your ability to define clear boundaries.
2. It prevents you from wasting 40 minutes designing an unasked subsystem.
3. It allows the interviewer an immediate opportunity to adjust your focus.

Candidates who fail to scope upfront frequently construct impressive designs for components that were never being evaluated.

## Non-Functional Requirements

Non-functional requirements describe the operational qualities of the system. The benchmark here is different: **a well-defined non-functional requirement always contains a concrete number.**

Stating *"the system should be fast"* is merely a goal, not a technical requirement. Specifying *"p99 read latency under 50 ms"* provides an actionable metric you can design toward and measure against.

The key non-functional attributes to clarify, ordered roughly by their impact on architectural decisions:

1. **Scale**: How many users and what volume of traffic must the system support? Clarify Daily Active Users (DAU), peak Requests Per Second (RPS/QPS), and annual data storage growth. This baseline dictates nearly all architectural choices.
2. **Latency**: How fast must operations complete, expressed as a percentile? Always request p99 values instead of averages, as mean values mask the long-tail latency that users actually experience.
3. **Read-to-Write Ratio**: A 100:1 read-to-write ratio leads toward heavy caching and read replicas. Conversely, a write-heavy workload demands message queues and write-optimized storage engines.
4. **Availability**: What level of system downtime is tolerable? Understanding the real-world impact per year is essential:

| Availability Target | Tolerable Downtime Per Year |
| :--- | :--- |
| **99%** ("two nines") | ~3.65 days |
| **99.9%** ("three nines") | ~8.8 hours |
| **99.99%** ("four nines") | ~53 minutes |
| **99.999%** ("five nines") | ~5 minutes |

Each additional "nine" introduces exponential cost and operational complexity. Candidates who propose "five nines" without prompting often overlook the underlying trade-offs and financial cost.

5. **Consistency**: Must every reader observe a write instantly, or is minor propagation delay permissible? Most systems require nuanced choices: user account balances demand strong consistency, whereas view counts tolerate eventual consistency.
6. **Durability**: Is data loss permissible, and if so, to what extent? Financial transactions and user photos require absolute persistence, whereas ephemeral telemetry events can tolerate minor loss.
7. **Security & Privacy**: Authentication, authorization, encryption standards (at rest and in transit), and regulatory compliance requirements governing user data.
8. **Cost Efficiency**: Though rarely stated explicitly by interviewers, infrastructure budget is a real-world constraint. Highlighting when a design choice is cost-prohibitive and proposing a cost-effective alternative signals engineering maturity.

## Connecting Requirements Directly to Architectural Decisions

Gathering non-functional requirements is critical because every quality attribute directly maps to specific architectural components:

| Non-Functional Requirement | Architectural Pattern / Component |
| :--- | :--- |
| **Extremely high read traffic** | Multi-tier caching, read replicas, Content Delivery Networks (CDNs) |
| **Low latency for global users** | Edge CDNs, multi-region deployments, geo-distributed data hosting |
| **High availability** | Full component redundancy, eliminating Single Points of Failure (SPOFs), multi-AZ clusters |
| **Strong data consistency** | Single-primary database, synchronous replication, accepting higher write latency |
| **High write throughput** | Message queues, write batching, database sharding, LSM-tree storage engines |
| **Massive data storage volume** | Data partitioning, cloud object stores, cold storage tiering |
| **Unpredictable, spiky traffic** | Asynchronous queues for burst absorption, automatic horizontal scaling |

If you collect non-functional requirements but fail to incorporate them into your architecture, interviewers will take note. Your non-functional requirements should explicitly motivate every component choice. The most compelling move in a system design interview is linking a design decision directly back to an earlier requirement:
> *"I am introducing an in-memory cache layer here specifically to handle the 100:1 read-to-write ratio we established during requirements gathering."*

## Executing the Requirements Phase in an Interview

1. **Limit this phase to roughly 5 minutes**: Allocate sufficient time to establish key metrics while leaving ample time for architectural design. Allowing requirements gathering to drag on for 15 minutes is a common pitfall that starves the core design phase.
2. **Document requirements visibly**: Write them clearly on the shared board or editor. You will reference these constraints continuously throughout the session.
3. **Request explicit metrics, or state your assumptions out loud**: Interviewers intentionally leave scale metrics ambiguous to test your initiative. Proactively state:
   > *"Since specific traffic metrics were not provided, I will assume 100 million Daily Active Users (DAU) and approximately 500,000 peak redirect requests per second. Please let me know if you prefer different scale assumptions."*
   Stating explicit assumptions out loud is significantly stronger than guessing silently or waiting passively.
4. **Convert high-level scale into actionable throughput**: For instance, 100 million users performing 5 operations daily translates to an average throughput of ~5.8k QPS, with peak load reaching a multiple of that value. Calculating this early supplies the exact throughput figures needed for capacity planning.
5. **Avoid generic boilerplate lists**: Stating that a system *"must be scalable, highly available, secure, and maintainable"* provides zero meaningful insight. Identify the 2 or 3 critical quality attributes that genuinely govern the architecture and assign quantitative metrics to them.

---

### 💡 System Design Interview Strategy

> Structure the first 5 minutes consistently across every interview prompt:
> 1. Outline **3 to 5 functional requirements** and explicitly state out-of-scope features.
> 2. Obtain or state explicit numerical targets for **scale, latency, and availability**.
> 3. Conclude the requirements phase with a single synthesis sentence that bridges requirements to architecture, such as:
> 
> *"Since this system is read-heavy (100:1 ratio), demands p99 read latency under 50 ms globally, and permits eventual consistency for redirects, our design points toward aggressive edge caching and a CDN without requiring complex distributed transactions."*
> 
> A candidate who opens with this synthesis demonstrates immediate architectural intent to the interviewer.

## Key Takeaway

- **Functional requirements** define **what** the system does (evaluated binarily as yes/no).
- **Non-functional requirements** define **how well** it performs (quantified with explicit numerical targets).
- **Functional requirements** determine *which* components appear in your diagram, whereas **non-functional requirements** dictate *how many* instances are needed, *where* they reside, and *how* they interoperate—which is why the same core feature designed at two different scales yields two entirely different architectures.
- Spend ~5 minutes scoping features down, establishing explicit numbers, and ensuring those metrics visibly drive your subsequent architectural decisions.
