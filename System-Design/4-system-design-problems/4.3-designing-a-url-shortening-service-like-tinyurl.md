# Designing a URL Shortening Service like TinyURL

Every case study in this section follows the same seven-step methodology detailed in [System Design Interviews: A Step-by-Step Guide](./4.1-system-design-interviews-a-step-by-step-guide.md) and constructs its architecture using the components from the [System Design Master Template](./4.2-system-design-master-template.md). Keep both open as references, and try designing each system independently before reviewing the solution.

---

## Why Do We Need URL Shortening?

URL shortening creates compact aliases for long web addresses. We refer to these shortened aliases as "short links." When users open a short link, they are automatically redirected to the original destination URL.

Short links conserve valuable space when shared in messages, printed materials, emails, or social media posts. Furthermore, shorter URLs minimize user typing errors.

For instance, shortening a long destination link:
`https://www.example.com/courses/grokking-the-system-design-interview`

Might produce a compact short link:
`https://tinyurl.com/vzet59pa`

The shortened link is less than half the length of the original URL; longer original links yield even greater relative space savings.

A URL shortening service serves two core functions:
1. Converting a long URL into a compact short link.
2. Redirecting any client opening that short link back to the original destination URL.

Beyond space savings, URL shortening is used to optimize links across devices, track click metrics, perform audience analytics, measure advertising campaign performance, or obscure affiliate links.

## Step 1: Clarify the Requirements

> [!TIP]
> Always clarify system requirements at the beginning of an interview. Ask targeted questions to establish the exact functional and scale boundaries expected by the interviewer.

![System Overview](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.3-tinyurl-overview.png)

### Functional Requirements
1. **Short Link Generation:** Given a long original URL, the system returns a unique shortened link.
2. **URL Redirection:** Accessing a short link redirects the user to the corresponding original URL.
3. **Custom Aliases:** Users can optionally specify a custom short alias (e.g., `tinyurl.com/my-custom-link`).
4. **Link Expiration:** Links expire after a default lifespan, and users can optionally define a custom expiration timestamp.

**Extended (Secondary) Requirements:**
* **Click Analytics:** Link owners can view click statistics and telemetry for their short links.
* **Link Visibility/Privacy:** Links can be marked private so only authorized users may access them.

*(While extended requirements do not alter the fundamental request-response path, key architectural decisions later depend on them.)*

### Non-Functional Requirements
1. **High Availability:** If the shortening service fails, every short link distributed across the internet breaks. Outages impact external sites, emails, and posts.
2. **Ultra-Low Redirect Latency:** Redirection adds an extra hop before landing on the target site. The HTTP redirect must respond almost instantaneously.
3. **Non-Guessable Short Keys:** Short links must be unpredictable. Unauthenticated users must not be able to discover private links by iterating through sequential keys.

### Out of Scope
Expressing explicit out-of-scope boundaries allows the interviewer to adjust scope early:
* User billing, subscription plans, and payments.
* Link destination preview cards and thumbnail generation.
* Real-time malware/phishing detection on target URLs.

> [!WARNING]
> Keep the non-guessability requirement in mind. It is easy to agree to during scoping, but easy to violate during key generation design.

## Step 2: Estimate the Scale

Assume two baseline inputs provided by the interviewer:
* **500 million new links generated per month.**
* **100 read requests (redirects) for every 1 write request (shortening).**

![Scale Estimation Summary](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.3-tinyurl-scale-estimates.png)
*Every estimate for this system derives from two baseline numbers: 500 million new links per month and a 100:1 read-to-write ratio.*

### Traffic (QPS)
Traffic is read-heavy. Assuming a day has roughly 100,000 seconds:

```text
500M per month / 30 days       = ~17M new links per day
17M / 100,000 seconds          = ~170, call it 200 writes per second
200 x 100                      = 20,000 reads per second
20,000 x 3 (peak factor)       = ~60,000 reads per second at peak
```

### Storage
Keep every link for five years. Assuming an average row size of 500 bytes:

```text
500M x 12 months x 5 years     = 30 billion links
30 billion x 500 bytes         = ~15 TB
```

### Bandwidth
Both directions are small, because we are moving text.

```text
200 writes x 500 bytes         = ~100 KB per second in
20,000 reads x 500 bytes       = ~10 MB per second out
```

### Cache Memory
If 20 percent of links produce 80 percent of the traffic (80/20 Pareto principle), we want that 20 percent in memory:

```text
20,000 x 100,000 seconds       = ~2 billion reads per day
0.2 x 2 billion x 500 bytes    = ~200 GB
```

*(Note: Since many daily reads hit duplicate popular URLs, 200 GB represents an upper bound. The actual unique working set memory requirement is lower.)*

### Key Architectural Takeaways from Scale:
1. **30 Billion Rows (15 TB Storage):** Exceeds single-node database capacity; data must be partitioned across nodes.
2. **100:1 Read-to-Write Ratio:** Extremely read-heavy; an in-memory caching tier in front of storage provides maximum architectural leverage.
3. **10 MB/s Network Egress:** Modest network bandwidth; does not require complex CDN edge caching for text payload responses.

## Step 3: Define the API

Defining explicit API contracts clarifies system boundaries and uncovers missing requirements early.

### 1. Shorten URL Endpoint
`POST /urls`
* **Request Body:**
  ```json
  {
    "original_url": "https://www.example.com/long-page-path",
    "custom_alias": "my-custom-alias",
    "expires_at": "2030-12-31T23:59:59Z"
  }
  ```
* **Response (201 Created):**
  ```json
  {
    "short_url": "https://tinyurl.com/vzet59p",
    "short_key": "vzet59p",
    "expires_at": "2030-12-31T23:59:59Z"
  }
  ```

### 2. Redirect Endpoint
`GET /{short_key}`
* **Response (302 Found):**
  * `Location: https://www.example.com/long-page-path`

### 3. Delete URL Endpoint
`DELETE /urls/{short_key}`
* **Response (204 No Content)**

*(Note: Endpoints for listing user-owned links or retrieving link analytics are standard paginated database queries and do not alter the core system design.)*

> [!IMPORTANT]
> Rate limiting must be enforced on write operations per user account and per IP address to prevent automated scripts from exhausting available short keys.

## Step 4: Define the Data Model

The dataset exhibits simple structural properties:
* Billions of records.
* Small individual record size (< 1 KB).
* Simple relationship: a link belongs to a user.
* Single primary read query: lookup by `short_key`.

![Data Model Architecture](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.3-tinyurl-data-model.png)
*Data model containing one primary row per short link, with click analytics offloaded to a separate event store.*

### Database Selection
A **Key-Value Store** or **Wide-Column NoSQL Database** (such as Amazon DynamoDB, Apache Cassandra, or ScyllaDB) is ideal. They excel at distributing billions of rows horizontally across nodes while offering \(O(1)\) key lookups under high QPS.

Relational databases (RDBMS) are unnecessary here because redirect queries do not require complex table joins or multi-entity ACID transactions.

> [!CAUTION]
> Do not store click counters directly inside the URL table row. Incrementing a counter on every redirect converts read traffic into synchronous database writes, turning viral links into severe database write hotspots. Click analytics must be handled asynchronously.

## Step 5: High-Level Design

The architecture features two distinct request paths with contrasting traffic characteristics.

![High-Level Read and Write Paths](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.3-tinyurl-high-level-design.png)
*The system decouples into a low-volume write path (200 QPS) and a high-volume read path (20,000 QPS).*

1. **Write Path (Shortening Service):** Handles ~200 QPS. Receives a long URL, obtains a unique key, and inserts a row into the database.
2. **Read Path (Redirect Service):** Handles ~20,000 QPS (\(100\times\) volume). Receives a short key, checks the cache/database, and returns an HTTP 302 redirect.

Because reads outnumber writes by 100 to 1, caching layers and read-replicas are deployed exclusively on the read path. The write path requires no caching, but must guarantee that every generated key is strictly unique across concurrent nodes.

## Step 6: Deep Dive

### 1. Key Generation Strategy

Generating a short, unique key for every URL is the core technical challenge of this system.

#### Key Length & Guessability
Common consensus often suggests 6 characters, but 6 characters is insufficient for 30 billion records.

* **Alphabet:** Base62 (`[A-Z, a-z, 0-9]`) containing 62 characters.
* **6 Characters:** $62^6 \approx 56.8$ billion possible combinations. Storing 30 billion links occupies $>52\%$ of the total keyspace. A user randomly guessing keys would hit a valid link on every second attempt, violating the non-guessability requirement.
* **7 Characters:** $62^7 \approx 3.5$ trillion possible combinations. Storing 30 billion links consumes only $\sim 0.9\%$ of the keyspace. Random key guessing succeeds only once every ~117 attempts, which rate-limiting can easily control.

![Key Length vs Guessability](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.3-tinyurl-key-length-guessability.png)
*At 30 billion stored records, 6 characters leaves over half the keyspace occupied, whereas 7 characters keeps occupancy at 0.9%.*

*(Note: Base64 is avoided because standard Base64 includes `+` and `/`. In URLs, `/` acts as a path delimiter and `+` is often decoded as a space by HTTP proxies, forcing percent-encoding which lengthens the URL.)*

#### Where Do Keys Come From?

![Hashing vs Key Generation Service](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.3-tinyurl-hashing-vs-kgs.png)
*Hashing places collision detection and retries on the synchronous request path; a Key Generation Service pre-computes unique keys offline.*

* **Approach A: Hash the Original URL**
  * Generate an MD5 or SHA-256 hash of the original URL and take the first 7 Base62 characters.
  * *Drawback 1:* Identical long URLs yield identical short keys. If two users shorten the same link, they share a key, preventing individual custom expirations, separate analytics, or independent deletions. Appending a user ID or sequence counter resolves this.
  * *Drawback 2 (Critical):* Truncating a hash down to 7 characters (42 bits) creates hash collisions across 30 billion items. Resolving collisions requires querying the database on every write to check key existence, causing expensive retry loops on the live request path as the database fills.

* **Approach B: Dedicated Key Generation Service (KGS)**
  * A standalone background service (KGS) pre-computes random 7-character Base62 keys offline and stores them in an unused key pool.
  * When a write request arrives, the Shortening Service simply fetches an available pre-generated key from KGS and writes the database record—eliminating hashing, collision checks, and retry loops from the request path.

![KGS Key Block Allocation](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.3-tinyurl-kgs-key-allocation.png)
*KGS allocates contiguous blocks of pre-generated keys to shortening servers in memory to prevent key collision across nodes.*

#### How KGS Prevents Duplicate Allocations
KGS pre-allocates keys to application server instances in bulk blocks (e.g., 1,000 keys at a time). When a server requests keys, KGS marks the entire block as "used" in its database in a single atomic transaction and loads the block into the application server's RAM.

* **Server Failure:** If an application server crashes while holding 800 unspent keys in memory, those keys are permanently lost. Given a 3.5 trillion keyspace, losing a small fraction of keys is completely acceptable compared to the overhead of distributed locking per write.
* **KGS Availability:** High availability for KGS is maintained using an active-standby pair. Even during a master KGS failover, application servers continue fulfilling writes using their buffered in-memory key blocks.

#### Handling Custom Aliases
When a user provides a custom short alias (e.g., `custom-link`), pre-generated KGS keys cannot be used. The system performs an explicit database read/write collision check. If the custom key exists, HTTP 409 Conflict is returned. Since custom aliases represent a minor fraction of total writes, this synchronous check is acceptable.

To keep database column sizing consistent, the `short_key` column is defined as `VARCHAR(16)` to accommodate custom aliases up to 16 characters.

### 2. Redirect Flow & HTTP Status Codes

![Redirect Decision Flow](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.3-tinyurl-redirect-flow.png)
*The redirect execution path performs a cache/DB lookup followed by status checks.*

When a client accesses `GET /{short_key}`:
1. Check the in-memory cache for `short_key`.
2. On a cache miss, query the database and populate the cache.
3. Evaluate the retrieved record state:
   * **Key Not Found:** Return `HTTP 404 Not Found`.
   * **Link Expired:** Return `HTTP 410 Gone` (signals permanent deletion to clients).
   * **Private Link (Unauthorized):** Return `HTTP 401 Unauthorized` (if unauthenticated) or `HTTP 403 Forbidden` (if authenticated user lacks access).
   * **Valid Link:** Return `HTTP 302 Found` with `Location: <original_url>` header, and asynchronously publish a click event to the analytics queue.

#### Why HTTP 302 Found Instead of HTTP 301 Moved Permanently?
* **HTTP 301 (Permanent Redirect):** Browsers aggressively cache the redirect target locally. Subsequent user clicks never reach the URL shortening servers, disabling click analytics tracking.
* **HTTP 302 (Temporary Redirect):** Browsers do not cache the redirect permanently. Every click reaches the URL shortener servers, allowing accurate real-time click tracking.

---

### 3. Caching Strategy

The read path handles 20,000 QPS, making in-memory caching essential.

* **Cache Implementation:** Distributed in-memory cache (e.g., Redis cluster) positioned in front of the database.
* **Cached Payload:** Stores the `original_url`, `expires_at`, and `visibility` flags.
* **Immutability Advantage:** Because a short link's target destination URL never changes once created, cache entries do not suffer from write-invalidation race conditions.
* **Eviction Policy:** **Least Recently Used (LRU)** eviction ensures popular hot links remain in memory while dormant links age out.
* **Cache Sizing:** Sized at ~200 GB RAM, answering ~90% of daily read queries directly from memory.
* **Negative Caching:** Non-existent or expired keys are cached with a short TTL (e.g., 2 minutes) to protect the database from cache-penetration attacks caused by dead key queries.

---

### 4. Database Partitioning & Replication

Storing 30 billion records (15 TB) requires horizontal database partitioning.

* **Partitioning Key:** Partition data by hashing the `short_key` using **Consistent Hashing**.
* **Uniform Distribution:** Because KGS generates pseudo-random key strings, hashing `short_key` distributes storage and read/write load uniformly across physical nodes, preventing hot partition spots.
* **Range Partitioning Avoidance:** Range-based partitioning (e.g., by first letter `A-Z`) is avoided because it creates uneven data distribution and provides no benefit for point lookups.
* **Replication:** Each database partition uses primary-replica replication (1 primary for writes, 2+ read replicas for high read throughput and failover redundancy).

---

### 5. Link Expiration & Garbage Collection

Rather than running heavy continuous database scans to purge expired rows:
1. **Lazy Deletion:** When a request hits an expired link during a live query, return `HTTP 410 Gone` and asynchronously delete the record.
2. **Off-Peak Batch Cleanup:** A low-priority background daemon periodically scans partitions during low-traffic windows to remove dormant expired links.

> [!CAUTION]
> Expired short keys should **never** be recycled back into the KGS key pool. Reusing a key causes old printed links, bookmarks, or emails to suddenly point to new external destinations, creating severe security and phishing vulnerabilities. With 3.5 trillion available 7-character keys, key recycling is unnecessary.

---

### 6. Analytics Pipeline

Analytics collection must be strictly decoupled from the synchronous redirect path.

![Analytics Processing Pipeline](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.3-tinyurl-analytics-queue.png)
*Click events are published asynchronously to a message queue (Kafka), ensuring analytics writes never block user redirects.*

1. **Event Emission:** Upon issuing an HTTP 302 response, the Redirect Service asynchronously emits an event payload (including `short_key`, `timestamp`, `IP_address`, `user_agent`, `referrer`) to an Apache Kafka topic.
2. **Asynchronous Ingestion:** Stream processors (e.g., Apache Flink or Spark Streaming) consume Kafka events in batches.
3. **Analytics Storage:** Aggregated metrics (click counts by country, device, time) land in an OLAP database optimized for aggregation (e.g., ClickHouse or Snowflake).
4. **Consistency Model:** Click analytics are **eventually consistent**, lagging live clicks by a few seconds.

## Step 7: Bottlenecks & Failure Points

![Bottlenecks and Failure Points Summary](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.3-tinyurl-bottlenecks-failure-points.png)
*System saturation points and failure isolation mechanisms across architecture components.*

1. **KGS Exhaustion / Failure:** If KGS goes down, application servers continue serving writes from local in-memory key blocks while a standby KGS instance assumes control.
2. **Database Partition Outage:** Read replicas satisfy read QPS during primary node failover. Consistent hashing minimizes re-sharding impact when adding database nodes.
3. **Architectural Isolation:** The redirect path relies *only* on the cache and database. If KGS, the analytics queue, or background cleanup jobs fail completely, URL redirection continues operating without degradation.

## Summary & Key Takeaways

| Component | Choice / Metric | Rationale |
| :--- | :--- | :--- |
| **Traffic Profile** | 200 Write QPS / 20,000 Read QPS | 100:1 Read-heavy architecture; optimize caching on read path |
| **Storage Capacity** | 30 Billion Rows / 15 TB (5 Years) | Requires horizontal database partitioning via Consistent Hashing |
| **Short Key Length** | 7 Base62 Characters ($62^7 = 3.5$ Trillion) | Prevents key-guessing security vulnerabilities ($<0.9\%$ occupied) |
| **Key Generation** | Key Generation Service (KGS) | Eliminates hash collisions and retry loops from synchronous write path |
| **Database** | Key-Value / NoSQL (DynamoDB/Cassandra) | Optimized for $O(1)$ primary key lookups without complex joins |
| **Redirect Status** | HTTP 302 Found | Prevents client-side browser caching, enabling per-click analytics |
| **Analytics Processing** | Asynchronous Kafka Queue | Isolates analytics writes completely from user redirect latency |

> [!TIP]
> **In the Interview:** Emphasize why 6 Base62 characters violates the non-guessability requirement at 30 billion items, and articulate how KGS shifts key uniqueness verification off the live request path into offline background processing.
