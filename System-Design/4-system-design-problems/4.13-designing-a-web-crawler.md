## What is a Web Crawler?

A **web crawler** (also known as a spider, web robot, or web scraper) is an automated software program designed to systematically and methodically navigate the World Wide Web. It begins its execution with a starting list of URLs, known as the **seed set**. The crawler fetches each web document from the seed set, parses its raw HTML content to extract outgoing hyperlinks, enqueues newly discovered links, and repeats this cycle autonomously until it achieves its target crawl depth or document quota.

```
                              THE CORE CRAWLER LOOP
┌──────────────────────┐    Fetch Page    ┌──────────────────────┐
│     Seed URLs /      │ ───────────────> │    HTML Downloader   │
│     URL Frontier     │                  └──────────┬───────────┘
└──────────▲───────────┘                             │ Raw Content
           │ Enqueue New                             ▼
           │ Outlinks                     ┌──────────────────────┐
           └───────────────────────────── │    Link Extractor    │
                                          └──────────────────────┘
```

Search engines like Google, Bing, and DuckDuckGo represent the largest operators of distributed web crawlers. They continuously archive and update web pages to build a massive **Inverted Search Index**—the specialized data structure that enables search engines to answer complex queries over hundreds of billions of web pages in milliseconds.

Beyond general search engine indexing, web crawlers perform several vital infrastructure functions across the internet ecosystem:

1. **Web Archiving & Site Mirroring**: Creating exact historical replicas of vital websites and documentation repositories for offline access and digital preservation.
2. **Syntactic & Structural Site Auditing**: Scanning corporate websites to discover broken links (`404 Not Found`), invalid HTML markups, and structural syntax errors.
3. **Content & Change Monitoring**: Tracking specific websites to alert downstream systems whenever text content, pricing models, or site structures are modified.
4. **Copyright & Automated Threat Intelligence**: Scanning public pages to detect illegal copy distribution, copyright infringements, or credential leakage.
5. **Vertical & Specialized Domain Indexing**: Aggregating targeted data types across specialized domains, such as academic publications, financial reports, or multimedia assets.

> [!NOTE]
> While a simple web scraper can be written in a few lines of code to fetch a single website, designing a **distributed web crawler** capable of ingesting billions of web pages across the global internet requires solving massive engineering challenges around scalability, network bandwidth, distributed memory management, DNS resolution latency, politeness enforcement, and fault tolerance.

## Step 1: Clarify the Requirements

> [!TIP]
> Never assume the scope of a system design problem. "Crawl the web" can range from a script running on a laptop to a global infrastructure spanning thousands of server nodes. Always spend the first few minutes clarifying functional boundaries, supported protocols, scale, and expected behavior.

### Functional Requirements

1. **Seed-Based Crawling**: The crawler accepts a list of initial seed URLs, downloads their contents, extracts all outgoing hyperlinks, and recursively enqueues newly discovered URLs.
2. **Metadata & Payload Storage**: The system stores all downloaded web page contents alongside essential metadata (canonical URL, HTTP response status, fetch timestamp, content length) for consumption by downstream indexing pipelines.
3. **Protocol & Content Support**: The crawler handles standard web pages fetched via standard web protocols (`HTTP` and `HTTPS`).
4. **Robots Exclusion Compliance**: The crawler must fetch, parse, and strictly comply with rules declared in every target host's `robots.txt` file before downloading content.

### Non-Functional Requirements

1. **Massive Scalability**: The service must scale horizontally to crawl **15 billion distinct web pages** within a 4-week window (~6,200 pages per second).
2. **Politeness (Server Protection)**: The system must never overload target web servers. It must enforce rate limits and ensure that no target web host receives concurrent aggressive connections from multiple crawler threads.
3. **Extensibility & Modularity**: The component architecture must be loosely coupled so that support for new MIME types (PDFs, images, videos) or network protocols (FTP) can be added without altering core queueing or deduplication logic.
4. **High Robustness & Fault Tolerance**: The system must handle malformed HTML responses, invalid URLs, unresponsive DNS servers, crawler traps, and server hardware crashes gracefully without data corruption.

### Critical Scope Clarification Questions

To narrow the architectural scope, ask your interviewer the following four questions early in the conversation:

```
                               SCOPE DECISION TREE
                                        │
           ┌────────────────────────────┴────────────────────────────┐
           ▼                                                         ▼
   [ Content Types? ]                                       [ Volume & Scale? ]
  HTML Only (Scope Limit)                                15 Billion Pages / 4 Weeks
(Modular parsing for future)                              (Requires 6,200 QPS)
           │                                                         │
           ▼                                                         ▼
   [ Protocols? ]                                           [ Politeness? ]
   HTTP / HTTPS Only                                     Strict robots.txt &
 (Extensible interfaces)                                 Per-Host Rate Limiting
```

1. **Is this crawler restricted to HTML pages, or must it process media assets (images, PDFs, videos)?**
   - *Assumption*: We will focus on HTML documents. However, we will design the document processing pipeline using a modular handler pattern so future media extractors can be plugged in seamlessly.
2. **Which network transport protocols must be supported?**
   - *Assumption*: `HTTP` and `HTTPS`. Protocol handling will be encapsulated behind protocol-specific driver interfaces.
3. **What is the target scale of the crawl job?**
   - *Assumption*: We must crawl **15 billion web pages** across an estimated 1 billion distinct websites within 4 weeks.
4. **Should the crawler obey the Robots Exclusion Protocol?**
   - *Assumption*: Yes. A polite crawler must inspect and enforce `robots.txt` directives before making GET requests to any domain.

## Step 2: Estimate the Scale

Every structural choice in our distributed architecture stems directly from two numbers: crawling **15 billion pages** within **4 weeks**.

```
                                  SCALE AT A GLANCE
┌──────────────────────────────┬──────────────────────────────┬──────────────────────────────┐
│      15 Billion Pages        │       6,200 Pages/sec        │     2.16 Petabytes Storage   │
│      (Crawled in 4 Weeks)    │     (Network Throughput)     │    (Includes 30% Headroom)   │
└──────────────────────────────┴──────────────────────────────┴──────────────────────────────┘
```

### 1. Ingestion Throughput (QPS & Bandwidth)

First, calculate the total duration of a 4-week crawling window in seconds:
$$\text{Duration} = 4\text{ weeks} \times 7\text{ days/week} \times 24\text{ hours/day} \times 3,600\text{ seconds/hour} = 2,419,200\text{ seconds}$$

To crawl 15 billion pages within this time frame, calculate required page fetch throughput:
$$\text{Crawl Velocity (QPS)} = \frac{15,000,000,000\text{ pages}}{2,419,200\text{ seconds}} \approx 6,199.8\text{ pages/second} \approx 6,200\text{ QPS}$$

Assuming an average HTML page payload size of **$100\text{ KB}$** plus **$500\text{ bytes}$** of associated metadata per record:
$$\text{Payload per Page} = 100\text{ KB} + 0.5\text{ KB} = 100.5\text{ KB}$$

$$\text{Network Ingress Bandwidth} = 6,200\text{ QPS} \times 100.5\text{ KB/page} = 623,100\text{ KB/sec} \approx 623\text{ MB/sec} = 4.98\text{ Gbps}$$

### 2. Disk Storage Requirements

Calculate the raw data volume accumulated over the 4-week crawl:
$$\text{Raw Document Storage} = 15 \times 10^9\text{ pages} \times 100.5\text{ KB/page} = 1,507,500\text{ GB} \approx 1.51\text{ Petabytes (PB)}$$

To protect disk read/write throughput from degradation on physical storage nodes, we enforce a **70% maximum storage capacity ceiling** (maintaining 30% overhead):
$$\text{Total Storage Provisioned} = \frac{1.51\text{ PB}}{0.70} \approx 2.16\text{ Petabytes}$$

### 3. Memory Sizing for Hash Registers

To track seen URLs and seen document contents, we store 8-byte (64-bit) hashes instead of full text strings:
$$\text{URL Hash Table Memory} = 15 \times 10^9\text{ URLs} \times 8\text{ bytes} = 120\text{ GB}$$
$$\text{Document Hash Table Memory} = 15 \times 10^9\text{ Documents} \times 8\text{ bytes} = 120\text{ GB}$$

> [!IMPORTANT]
> **Engineering Conclusion**: Fetching 6,200 pages per second over a 5 Gbps network link and storing 2.16 Petabytes of data is far beyond the bandwidth, memory, and disk IOPS capabilities of any single server. The web crawler must be designed as a **highly distributed, fault-tolerant system** from day one.

## Step 4: Define the Data Model

A distributed web crawler maintains four distinct data repositories, categorized by operational access patterns, performance requirements, and scale:

```
                            DATA REPOSITORY ARCHITECTURE
┌─────────────────────────┬─────────────────────────┬─────────────────────────┐
│     URL Frontier        │    Seen URL Register    │  Seen Document Register │
│ (Disk Queues + RAM)     │  (120 GB 8-Byte Hashes) │  (120 GB 8-Byte Hashes) │
└────────────┬────────────┴────────────┬────────────┴────────────┬────────────┘
             │                         │                         │
             └─────────────────────────┼─────────────────────────┘
                                       ▼
                         ┌───────────────────────────┐
                         │     Document Datastore    │
                         │    (2.16 PB Blob Store)   │
                         └───────────────────────────┘
```

### Data Schema Overview

| Dataset | Data Format & Record Structure | Total Capacity | Target Storage Medium | Primary Indexing / Key Pattern |
| :--- | :--- | :--- | :--- | :--- |
| **URL Frontier** | Pending URLs categorized by host queue: `<Canonical_URL, Priority_Score, Retries>` | ~180M active items (~50 GB) | Disk-backed queues with RAM buffers | FIFO Queue per Canonical Hostname |
| **URL Store** | 8-byte (64-bit) MurmurHash3 checksum of canonical URL strings | 120 GB | In-memory distributed KV Store (Redis/RocksDB) | Primary Key: `URL_Hash` (8 Bytes) |
| **Document Checksum Store** | 8-byte (64-bit) SHA-256/MD5 fingerprint of page HTML body | 120 GB | Distributed In-memory Hash Table | Primary Key: `Document_Hash` (8 Bytes) |
| **Document Datastore** | Compressed HTML content + Metadata payload (JSON/Protobuf) | 2.16 Petabytes | Distributed Blob Store (S3, HDFS, Google Cloud Storage) | Primary Key: `Doc_ID` (`Host_Hash` + `Timestamp`) |

### Database Schema Conceptual Layout

![Database Schema for Web Crawler](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.13-database-schema-web-crawler.svg)

### Storage Optimization Rationale

Storing full URL strings (which average 80–200 characters) across 15 billion entries would require up to **3 TB of memory** just to maintain the URL filter list. 

By passing canonical URL strings through a non-cryptographic hash function (like **MurmurHash3** or **xxHash**) to generate a uniform **8-byte (64-bit) integer fingerprint**, we shrink the total register memory requirement down to **120 GB**. This entire footprint fits comfortably within the RAM of a handful of commodity server nodes.

## Step 5: Draw the High-Level Design

Every web crawler, regardless of scale, executes the same basic iterative cycle:

```
 1. Pop URL ──────> 2. DNS Lookup ──────> 3. HTTP Fetch ──────> 4. Parse & Extract ──────> 5. Deduplicate ──────> 6. Store
```

### Traversal Algorithms: BFS vs. DFS

When discovering pages across the web, the crawler must decide the order in which links are explored:

```
      BREADTH-FIRST SEARCH (BFS)                       DEPTH-FIRST SEARCH (DFS)
       Level 0: [ Seed Page ]                           Level 0: [ Seed Page ]
                   │                                                │
       ┌───────────┴───────────┐                                    ▼
       ▼                       ▼                        Level 1: [ Page A ]
  Level 1: [ Page A ]     [ Page B ]                                │
       │                       │                                    ▼
       ▼                       ▼                        Level 2: [ Page A1 ]
  Level 2: [ Page A1 ]    [ Page B1 ]                               │
                                                                    ▼
                                                        Level 3: [ Page A1a ]
```

1. **Breadth-First Search (BFS)**: Visits all pages at the current link distance before moving deeper. BFS is the **standard approach** for web crawlers because it prioritizes high-authority root pages before descending into deep, lower-priority subpages.
2. **Depth-First Search (DFS)**: Follows a single chain of links deep into a site before backtracking. DFS is generally avoided because it risks getting stuck in deep directory structures or crawler traps on a single host.
3. **Path-Ascending Crawling**: Given a deep URL like `https://example.com/a/b/c/page.html`, the crawler explicitly probes parent paths (`/a/b/c/`, `/a/b/`, `/a/`, `/`) to discover unlinked orphan directories that lack direct inbound links.

### High-Level Architecture Component Diagram

![High-Level Design of Web Crawler](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.13-web-crawler-high-level-design.svg)

### Core Components Summary

1. **URL Frontier**: The centralized scheduler that stores pending URLs, enforces politeness per host, and prioritizes crawl order.
2. **DNS Resolver**: Resolves domain hostnames to IP addresses using aggressive local datacenter caching.
3. **HTML Fetcher**: Worker component that connects to target web servers over HTTP/HTTPS to download documents while enforcing `robots.txt` rules.
4. **Document Input Stream (DIS)**: Memory/disk abstraction layer that buffers fetched web pages so downstream parsers can read the stream repeatedly without network re-fetches.
5. **Link Extractor & URL Filter**: Parses raw HTML to extract `<a href="...">` hyperlinks and discards invalid, non-HTML, or blacklisted domains.
6. **URL & Document Deduplicators**: Checksum engines that ensure the system neither enqueues the same URL twice nor stores duplicate mirrored content.
7. **Document Storage**: Persistent distributed object storage layer holding 2.16 PB of web data.

## Step 6: Go Deep

### How one worker processes one URL

To understand how the distributed crawler functions, trace the step-by-step lifecycle of a single URL handled by one worker thread inside a crawling node:

![Detailed Worker and Component Processing Flow](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.13-web-crawler-detailed-design.svg)

```
                            SINGLE WORKER EXECUTION PIPELINE
                            
  [ URL Frontier ]
         │
         ▼ 1. Dequeue Absolute URL
  [ Worker Thread ] ──> 2. Query Protocol Router ──> [ Protocol Module (HTTP/HTTPS) ]
                                                                 │
                                                                 ▼ 3. Download Payload
                                                    [ Document Input Stream (DIS) ]
                                                                 │
                                                                 ▼ 4. Compute 64-bit Hash
                                                    [ Document Dedupe Test ]
                                                                 │
                                              ┌──────────────────┴──────────────────┐
                                              ▼ Match Found                         ▼ Unique Body
                                       (Drop & Skip)                      [ MIME Processing Router ]
                                                                                    │
                                                                                    ▼ Extract Outlinks
                                                                          [ HTML Link Extractor ]
                                                                                    │
                                                                                    ▼ Apply Regex Rules
                                                                            [ URL Filter ]
                                                                                    │
                                                                                    ▼ Check 64-bit Hash
                                                                            [ URL Dedupe Test ]
                                                                                    │
                                                                                    ▼ Enqueue New URLs
                                                                           [ URL Frontier ]
```

1. **Dequeuing**: The worker thread pops an absolute URL (e.g., `https://news.ycombinator.com/item?id=123`) from its assigned per-host queue inside the URL Frontier.
2. **Protocol Routing**: The worker passes the URL to the Protocol Router, which selects the appropriate network module (`http://` vs `https://`).
3. **Stream Buffering**: The Protocol Module opens an HTTP connection, downloads the content body, and wraps it inside a **Document Input Stream (DIS)**.
4. **Document Deduplication**: The worker reads the DIS payload, calculates an **8-byte document hash**, and queries the Document Dedupe Store. If a matching hash is found (indicating mirrored content), processing terminates immediately.
5. **MIME Router Dispatch**: If unique, the DIS stream is passed to the MIME Type Router. For `text/html` documents, the **HTML Processing Module** is invoked.
6. **Link Extraction & Normalization**: The module parses the HTML tree, extracts all outlinks, converts relative paths (`/about`) into canonical absolute URLs (`https://news.ycombinator.com/about`), and strips redundant tracking parameters.
7. **URL Filtering & Deduplication**: Extracted URLs pass through customizable **URL Filters** (blocking blacklisted domains or unwanted file types) and the **URL Dedupe Test** (verifying whether the link has already been seen).
8. **Enqueuing & Storage**: New, validated URLs are enqueued back into the URL Frontier, while the DIS document payload is written to the persistent Document Store.

### The URL frontier

The **URL Frontier** is the core scheduling data structure of the web crawler. It manages hundreds of millions of pending URLs while balancing two competing requirements: **Politeness** and **Priority**.

```
                               URL FRONTIER ARCHITECTURE
                               
   Incoming Discovered URLs
              │
              ▼
   ┌──────────────────────┐
   │   Priority Router    │ ──> Categorizes URLs by Domain Authority / PageRank
   └──────────┬───────────┘
              │
              ▼
   ┌──────────────────────┐
   │   Priority Queues    │ (F1, F2, F3...)
   └──────────┬───────────┘
              │
              ▼
   ┌──────────────────────┐
   │  Politeness Router   │ ──> Hashes Canonical Hostname to Per-Host Queue
   └──────────┬───────────┘
              │
              ▼
   ┌──────────────────────┐
   │  Per-Host B-Queues   │ (Queue_HostA, Queue_HostB...)
   └──────────┬───────────┘
              │
              ▼ (Enforces 500ms Delay Between Pulls)
    Worker Thread Execution
```

#### Enforcing Politeness

A naive crawler using a single global queue will pick URLs at random. If 50 worker threads pull URLs belonging to `example.com` simultaneously, they will flood `example.com` with 50 concurrent requests, triggering rate-limiting errors or bringing down the host.

To guarantee politeness:
1. **Canonical Hostname Hash Routing**: We extract the canonical hostname from every URL (`https://www.example.com/page1` -> `example.com`) and pass it through a hash function:
   $$\text{Queue_ID} = \text{Hash}(\text{canonical_hostname}) \pmod N$$
2. **Dedicated Per-Host Queues**: Each sub-queue $Q_k$ holds URLs belonging to a **single distinct host**.
3. **Single Thread Mapping**: A worker thread is assigned to service specific queues exclusively. Since only **one worker thread** fetches from `Queue_HostA` at any given time, and enforces a mandatory delay (e.g., 500ms) between consecutive requests, the crawler can never overload target web servers.

#### Disk Sizing & RAM Buffering

With hundreds of millions of URLs queued, the Frontier cannot fit in RAM alone. We use a **two-tier queue buffering model**:

```
 ┌──────────────────────┐          Async Bulk Flush          ┌──────────────────────┐
 │   Enqueue Buffer     │ ─────────────────────────────────> │     Disk-Backed      │
 │       (In RAM)       │                                    │     Queue Store      │
 └──────────────────────┘                                    └──────────┬───────────┘
                                                                        │
 ┌──────────────────────┐           Batch Prefetch                      │
 │   Dequeue Buffer     │ <─────────────────────────────────────────────┘
 │       (In RAM)       │
 └──────────────────────┘
```

- **Enqueue RAM Buffer**: Collects incoming URLs in memory. When full, it flushes URLs in sequential blocks to disk.
- **Dequeue RAM Buffer**: Prefetches blocks of URLs from disk into memory so worker threads pull next-to-fetch URLs instantly without incurring disk seek latency.

### The fetcher

The **Fetcher** module executes network requests to download web pages over HTTP/HTTPS.

```
                              FETCHER CACHING PIPELINE
                              
                             Worker Dequeues Target Host
                                          │
                                          ▼
                             ┌─────────────────────────┐
                             │  Robots Rules RAM Cache │
                             └────────────┬────────────┘
                                          │
                   ┌──────────────────────┴──────────────────────┐
                   │ Cache Hit                                   │ Cache Miss
                   ▼                                             ▼
       [ Enforce Allowed Rules ]                     [ Fetch host/robots.txt ]
                   │                                             │
                   ▼                                             ▼
       [ Issue HTTP GET Request ]                    [ Parse & Store in Cache ]
```

#### Robots Exclusion Protocol Handling

Before fetching a web page from `https://example.com/article`, the fetcher must check `https://example.com/robots.txt` to verify if crawling `/article` is permitted.

Fetching `robots.txt` over the network before every page fetch would double network traffic (6,200 page QPS + 6,200 robots QPS = 12,400 QPS).

##### Solution: In-Memory Host Rules Cache
1. The Fetcher maintains a local in-memory LRU cache mapping `hostname -> parsed_robots_rules`.
2. When visiting a host for the first time, the Fetcher downloads its `robots.txt`, parses the rules, and stores them in RAM with a 24-hour Time-To-Live (TTL).
3. Subsequent page fetches for that hostname query the local RAM cache instantly.

### The document input stream

When a web page is downloaded, multiple components require access to its content body:
- **Document Deduplicator**: Computes an 8-byte hash of the raw payload.
- **HTML Link Extractor**: Parses DOM nodes to extract outbound links.
- **Document Store Writer**: Compresses and saves the page payload to disk storage.

If each module re-downloaded the page or forced full memory copies, bandwidth and memory usage would skyrocket.

```
                         DOCUMENT INPUT STREAM (DIS) BUFFERING
                         
                         Network Socket Stream
                                   │
                                   ▼
                   ┌──────────────────────────────┐
                   │ Document Input Stream (DIS)  │
                   └──────────────┬───────────────┘
                                  │
         ┌────────────────────────┴────────────────────────┐
         ▼ Small Payload (<= 64 KB)                        ▼ Large Payload (> 64 KB)
  [ Keep Payload in RAM ]                       [ Spool to Temp Local Disk File ]
         │                                                 │
         └────────────────────────┬────────────────────────┘
                                  │
                                  ▼
                    Offers re-seekable .read() / .reset()
                 to Link Extractor, Deduper, & Disk Writer
```

#### The DIS Solution

The **Document Input Stream (DIS)** wraps the incoming TCP socket connection and acts as a reusable, re-seekable content buffer:

- For small documents ($\le 64\text{ KB}$), the DIS holds the raw bytes entirely in direct memory.
- For large documents ($> 64\text{ KB}$), the DIS spools the incoming bytes to a temporary local disk file.
- The DIS provides `.read()` and `.reset()` methods, allowing independent processing modules to re-read the exact document content sequentially without re-fetching data over the network.

### The document dedupe test

The web contains massive volumes of duplicate and mirrored content. For example, popular news articles or open-source documentation are frequently copied across hundreds of different websites under distinct URLs.

```
                          DOCUMENT DEDUPLICATION FLOW
                          
                       Downloaded Document Content Stream
                                       │
                                       ▼
                         ┌───────────────────────────┐
                         │   MD5 / SHA-256 Hasher    │
                         └─────────────┬─────────────┘
                                       │
                                       ▼ Computes 64-bit Fingerprint
                         ┌───────────────────────────┐
                         │ Document Checksum Store   │
                         │    (120 GB Hash Register) │
                         └─────────────┬─────────────┘
                                       │
                ┌──────────────────────┴──────────────────────┐
                │ Match Exists                                │ Unique Fingerprint
                ▼                                             ▼
        [ Abort Processing ]                      [ Process & Save Document ]
         Discard Duplicate                         Insert Hash into Store
```

#### Hash Sizing & Lookup Strategy

To prevent storing the same text thousands of times, the crawler computes an **8-byte (64-bit) fingerprint** (using MD5, SHA-256, or MurmurHash3) over the stripped document text payload.

$$\text{Document Hash Memory Footprint} = 15 \times 10^9\text{ documents} \times 8\text{ bytes} = 120\text{ GB}$$

Because 120 GB fits inside modern distributed in-memory key-value stores (e.g., Redis or RocksDB clusters), the crawler checks document hashes with sub-millisecond latency:
1. If the hash exists in the Seen Document Store, the content is a duplicate. The worker drops the document immediately.
2. If the hash is absent, the hash is inserted into the store, and processing proceeds.

### URL filters

The **URL Filter** component provides configurable business rules to decide whether a discovered link should be enqueued into the URL Frontier:

```
                            URL FILTER EVALUATION STAGE
                            
                              Extracted Candidate Link
                                         │
                                         ▼
                            ┌──────────────────────────┐
                            │    URL Filter Module     │
                            └────────────┬─────────────┘
                                         │
     ┌───────────────────────────────────┼───────────────────────────────────┐
     ▼                                   ▼                                   ▼
[ Extension Check ]              [ Domain Blacklist ]                [ Scheme Whitelist ]
Drop .pdf, .jpg, .mp4            Drop banned/spam hosts              Drop mailto:, ftp://
     │                                   │                                   │
     └───────────────────────────────────┼───────────────────────────────────┘
                                         │
                                         ▼ Passed All Filters
                             [ Forward to URL Dedupe ]
```

- **File Extension Exclusion**: Drops URLs ending in static binary extensions (`.png`, `.jpg`, `.pdf`, `.mp4`, `.zip`) when configured for HTML-only crawls.
- **Domain Blacklisting**: Prevents the crawler from visiting known malware networks, adult sites, or web traps.
- **Protocol Whitelisting**: Ensures only `http://` and `https://` URLs are accepted, dropping schemes like `mailto:`, `ftp://`, or `javascript:`.

### Domain name resolution

Before making an HTTP connection to `https://example.com/page`, the crawler must resolve `example.com` to an IP address (e.g., `93.184.216.34`) via DNS lookup.

Standard external DNS queries introduce significant network latency (100ms–300ms per lookup). Performing 6,200 external DNS queries per second would create a severe bottleneck.

```
                           LOCAL DNS CACHING INFRASTRUCTURE
                           
                              Worker Requests Host IP
                                         │
                                         ▼
                             ┌────────────────────────┐
                             │ Datacenter Local DNS   │
                             │ Cache (Unbound / RAM)  │
                             └───────────┬────────────┘
                                         │
                     ┌───────────────────┴───────────────────┐
                     │ Cache Hit (99% Hits)                  │ Cache Miss
                     ▼                                       ▼
             [ Return Cached IP ]                 [ Async External DNS Query ]
             (Sub-millisecond)                    (Fetch & Update Local Cache)
```

#### Datacenter DNS Optimization

1. **Local DNS Cache Infrastructure**: We deploy dedicated DNS caching servers (using tools like Unbound or dnsmasq) directly inside our crawler datacenter.
2. **Preemptive TTL Refreshing**: Background resolver threads monitor cached IP records and refresh them asynchronously before their Time-To-Live (TTL) expires, maintaining a 99%+ local cache hit rate.

### The URL dedupe test

Web pages contain hundreds of outbound links, many of which point to common navigation pages (`/index.html`, `/about`, `/contact`, `/privacy`). 

Across 15 billion web pages, the crawler encounters hundreds of billions of raw links. The **URL Dedupe Test** ensures the crawler never enqueues or visits the same URL twice.

```
                             URL DEDUPLICATION PIPELINE
                             
                                Raw Candidate Link
                                         │
                                         ▼
                             ┌────────────────────────┐
                             │  Canonicalizer Module  │
                             └───────────┬────────────┘
                                         │ Converts to Canonical Form
                                         ▼
                             ┌────────────────────────┐
                             │   MurmurHash3 (64-Bit) │
                             └───────────┬────────────┘
                                         │ Generates 8-Byte Fingerprint
                                         ▼
                             ┌────────────────────────┐
                             │  Seen URL Hash Register│
                             │ (120 GB RAM / Redis)   │
                             └───────────┬────────────┘
                                         │
                   ┌─────────────────────┴─────────────────────┐
                   │ Hash Exists                               │ Hash Absent
                   ▼                                           ▼
          [ Discard Duplicate ]                        [ Enqueue into Frontier ]
```

#### Canonicalization

Before checking duplicates, URLs must be normalized into a standard canonical form:
- Convert scheme and host to lowercase: `HTTP://WWW.Example.com` -> `http://www.example.com`
- Remove default ports: `http://example.com:80/page` -> `http://example.com/page`
- Remove fragment anchors: `http://example.com/page#section2` -> `http://example.com/page`
- Sort URL query parameters alphabetically: `?b=2&a=1` -> `?a=1&b=2`

#### Hash Check Lookup

The canonical URL is hashed into an **8-byte integer**. The crawler queries the **Seen URL Store** (120 GB distributed in-memory register). If the hash is present, the link is discarded; if absent, the hash is stored and the URL is enqueued into the Frontier.

### Can we use a Bloom filter?

Candidates often ask whether a **Bloom Filter** can replace the 120 GB Seen URL Store to save RAM.

```
                              BLOOM FILTER BEHAVIOR
                              
                              Input URL String
                                     │
                                     ▼
                          ┌─────────────────────┐
                          │  k Hash Functions   │
                          └──────────┬──────────┘
                                     │
                                     ▼ Sets/Checks k bits in Bit Array
                          ┌─────────────────────┐
                          │   m-bit Bit Vector  │
                          └──────────┬──────────┘
                                     │
            ┌────────────────────────┴────────────────────────┐
            │ Bit Pattern Match Results                       │
            ▼                                                 ▼
      Returns FALSE                                     Returns TRUE
  "Definitely NOT in set"                           "POSSIBLY in set"
(Guaranteed Safe to Crawl)                          (Potential False Positive!)
```

#### What is a Bloom Filter?

A Bloom filter is a space-efficient, probabilistic data structure used to test set membership. It consists of a bit array of size $m$ and $k$ independent hash functions:
- **No False Negatives**: If the Bloom filter returns `FALSE`, the URL is **definitely unvisited**.
- **False Positives Possible**: If the Bloom filter returns `TRUE`, the URL is **probably visited**, but there is a small probability $p$ that other entries set those same bits by coincidence.

#### The Risk of False Positives in Web Crawling

> [!WARNING]
> In a web crawler, a false positive is catastrophic if unhandled. If the Bloom filter falsely claims an unvisited URL has "already been seen," the crawler silently drops the link. As a result, the crawler will permanently miss that page and **fail to discover all sub-pages branching from it**.

#### The Two-Tiered Architectural Solution

We can safely use a Bloom Filter by implementing a **Two-Tier Verification Pattern**:

```
                       TWO-TIER BLOOM FILTER LOOKUP PATTERN
                       
                               Candidate Outbound URL
                                         │
                                         ▼
                             ┌───────────────────────┐
                             │  In-Memory Bloom      │
                             │  Filter (Ultra-Fast)  │
                             └───────────┬───────────┘
                                         │
                     ┌───────────────────┴───────────────────┐
                     │ Returns FALSE                         │ Returns TRUE
                     ▼                                       ▼ (Possible False Positive)
          [ Guaranteed Unique ]                   ┌───────────────────────┐
          Enqueue into Frontier                   │ Check Exact DB Hash   │
                                                  │ Store (Disk / KV)     │
                                                  └───────────┬───────────┘
                                                              │
                                              ┌───────────────┴───────────────┐
                                              │ Match Found                   │ No Match (False Positive!)
                                              ▼                               ▼
                                     [ Drop Duplicate ]            [ Enqueue into Frontier ]
```

1. **Tier 1 (Bloom Filter in RAM)**: Check the candidate URL against the Bloom filter.
   - If `FALSE` (95%+ of unique links), enqueue the URL immediately without querying disk storage.
2. **Tier 2 (Exact Database Check)**: If `TRUE`, execute an exact lookup against the persistent disk-backed database store.
   - If the URL exists in the DB, it is a true duplicate $\rightarrow$ drop it.
   - If absent in the DB, it was a Bloom filter false positive $\rightarrow$ enqueue the URL and update the filter.

This pattern eliminates 95%+ of expensive disk queries while ensuring **zero page loss**.

### Checkpointing

Crawling 15 billion web pages takes up to 4 weeks. Over a operational window that long, hardware crashes, node failures, network blips, and power outages are guaranteed.

To prevent restarting a 4-week crawl job from scratch after a crash, the system implements **Periodic Checkpointing**:

```
                            DISTRIBUTED CHECKPOINTING
                            
                 Crawling Workers Operating
                            │
                            ▼ Every 6 Hours / Snapshots
                 ┌────────────────────────────────┐
                 │  Checkpoint Snapshot Manager   │
                 └──────────────┬─────────────────┘
                                │
   ┌────────────────────────────┼────────────────────────────┐
   ▼                            ▼                            ▼
[ URL Frontier Offsets ]    [ Seen URL Hash Table ]   [ Seen Document Table ]
   │                            │                            │
   └────────────────────────────┼────────────────────────────┘
                                │ Write Compact State Log
                                ▼
                 ┌────────────────────────────────┐
                 │ Persistent Distributed Storage │
                 │        (S3 / HDFS Storage)     │
                 └────────────────────────────────┘
```

1. **State Snapshots**: Every 6 hours, the system pauses queue updates briefly to write compact snapshots of the URL Frontier queue offsets, Seen URL Hash registers, and Seen Document Hash registers to persistent object storage (S3/HDFS).
2. **Crash Recovery**: When a crawler node crashes, its replacement node fetches the latest snapshot log from object storage, restores its in-memory hash registers and queue offsets, and resumes execution seamlessly.

## Step 7: Bottlenecks and Failure Points

```
                             BOTTLENECK REMEDIATION MAP
┌──────────────────────────────┬──────────────────────────────┬──────────────────────────────┐
│     Node Crashes & Failure   │     Crawler Traps & Cycles   │     Storage I/O Exhaustion   │
│   Remediation: Consistent    │    Remediation: Path Depth   │  Remediation: Sequential DIS │
│   Hashing & Checkpoints      │    Limits & Regex Filters    │  Appends & Batch Storage     │
└──────────────────────────────┴──────────────────────────────┴──────────────────────────────┘
```

### 1. Worker Node Crashes

- **Problem**: A crawling node hosting 10,000 active worker threads dies mid-crawl.
- **Solution**: We partition canonical hostnames across crawling nodes using **Consistent Hashing**. When a node fails, the hash ring remaps only its assigned hostnames to surviving nodes. The replacement node loads the dead node's latest checkpoint snapshot from S3 and resumes crawling without disrupting the rest of the cluster.

### 2. Crawler Traps & Infinite Loops

- **Problem**: A crawler trap is a web site or dynamic script configured to generate an infinite sequence of unique URLs (e.g., `/calendar?date=2026-10-01`, `/calendar?date=2026-10-02`...) or recursive symbolic link directories (`/a/b/a/b/a/b/...`). Traps can consume unlimited queue space and bandwidth.
- **Solutions**:
  - **Path Depth Caps**: Enforce a maximum directory depth limit (e.g., max 10 subfolders deep).
  - **URL Length Limits**: Automatically drop URLs exceeding 2,048 characters.
  - **Host Yield Counters**: Monitor page generation rates per domain. If a single domain yields $>100,000$ unique pages without increasing overall domain authority, flag it as a potential trap and halt crawling on that domain.

### 3. Disk Storage & I/O Bottlenecks

- **Problem**: Writing 6,200 raw HTML pages per second (623 MB/sec) directly to a database causes severe disk IOPS bottlenecking.
- **Solution**: Workers append compressed document payloads sequentially to bulk log files (e.g., HDFS sequence files or AWS S3 multipart uploads) in memory chunks before flushing to disk, avoiding random write seek operations.

## Where AI Fits in This Design

In modern web crawling infrastructure, Artificial Intelligence (AI) and Machine Learning (ML) extend and enhance core system components rather than replacing them.

```
                           AI ENHANCEMENTS TO CRAWLER ARCHITECTURE
                           
                 ┌─────────────────────────────────────────────────┐
                 │           Existing Crawler Infrastructure       │
                 └────────────────────────┬────────────────────────┘
                                          │
            ┌─────────────────────────────┴─────────────────────────────┐
            ▼                                                           ▼
┌───────────────────────────────────────┐   ┌───────────────────────────────────────┐
│     Predictive Frontier Prioritizer   │   │  Semantic Near-Duplicate Detection    │
│  • Replaces naive FIFO ordering       │   │  • Replaces exact byte checksums      │
│  • ML model scores URL PageRank/Value │   │  • Vector Embeddings + LSH Indexing   │
│  • Dequeues high-value pages first    │   │  • Detects reworded/mirrored content  │
└───────────────────────────────────────┘   └───────────────────────────────────────┘
```

### 1. Smart URL Frontier Prioritization (Predictive Crawling)

- **Limitation of Traditional Design**: A standard FIFO queue treats all URLs from a host equally, fetching low-value footer links before important news articles.
- **AI-Powered Solution**: An ML scoring model evaluates candidate URLs *before* they are fetched based on features like domain historical authority, update frequency, incoming link count, and topic relevance. High-scoring URLs are promoted to priority queues, ensuring high-value content is indexed first.

### 2. Semantic Near-Duplicate Detection

- **Limitation of Traditional Design**: 64-bit document checksums detect exact 100% byte matches, but fail when a page is slightly modified (e.g., the same news article with different advertisements, timestamps, or recommended links).
- **AI-Powered Solution**: We pass document body text through a lightweight embedding model to generate a dense **Vector Embedding**. We then use **Locality Sensitive Hashing (LSH)** or a **Vector Index** to identify semantically identical pages even when their raw HTML text differs.

> [!IMPORTANT]
> **Key Interview Takeaway**: Always position AI as an enhancement layer built on top of robust deterministic architecture. Use exact 64-bit checksums for cheap, instant duplicate detection first, and apply AI vector embeddings as a secondary filter for edge cases.

## Architectural Summary & Interview Blueprint

To succeed in a system design interview for a Web Crawler, structure your discussion around these primary takeaways:

1. **Scale Driving Architecture**: 15 billion pages in 4 weeks requires **6,200 QPS**, **623 MB/sec network ingress**, and **2.16 Petabytes of storage**, mandating a distributed queue and storage design.
2. **Politeness by Design**: Never use global queues. Hash canonical hostnames to dedicated per-host sub-queues serviced by a single worker thread with enforced fetch delays.
3. **Memory Sizing via Hashes**: Replace variable-length URL and document strings with **8-byte (64-bit) hashes**, shrinking register memory footprints to **120 GB**.
4. **Two-Tier Bloom Filters**: Use Bloom filters in RAM for 95%+ fast negative filtering, backed by exact database lookups to prevent false positive page loss.
5. **Fault Tolerance**: Protect against crash failures using **Consistent Hashing** for host assignment and **periodic checkpoint snapshots** saved to durable object storage.
