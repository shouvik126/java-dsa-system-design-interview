# Designing an API Rate Limiter

Every case study in this section follows the same seven-step framework detailed in [System Design Interviews: A Step-by-Step Guide](./4.1-system-design-interviews-a-step-by-step-guide.md) and constructs its architecture using components from the [System Design Master Template](./4.2-system-design-master-template.md). Keep both open beside you, and attempt each problem independently before reviewing the solution.

---

## What is a Rate Limiter?

Imagine a service receiving a high volume of requests that can only process a set capacity per second. To remain operational and healthy, it requires a mechanism to drop or decline excessive requests. This control mechanism is known as rate limiting or throttling.

A rate limiter restricts the maximum number of requests or actions an entity can perform within a specific time window. The entity may be a registered user, a client device, or an IP address. When the cap is reached, the rate limiter blocks subsequent requests from that sender until the current time window resets. For instance:
* A user can send at most one message per second.
* A user is permitted only three failed credit card attempts per day.
* A single IP address can create no more than twenty accounts per day.

---

## Why do we need rate limiting?

Rate limiting guards backend services against application-layer abuse, such as [Denial-of-Service (DoS)](https://en.wikipedia.org/wiki/Denial-of-service_attack) attacks, brute-force login attempts, and credit card validation spam. These attacks flood APIs with HTTP requests formatted like legitimate user traffic, often driven by botnets that make detection challenging.

In day-to-day operations, rate limiting provides key operational benefits:
* **Preventing client misbehavior and runaway scripts:** Certain clients or buggy scripts issue excessive requests, whether intentionally or accidentally. Imposing limits prevents low-priority workloads (such as bulk analytics exports) from degrading performance for critical operations like checkout transactions.
* **Enhancing security:** Restricting attempt frequencies mitigates brute-force risks on sensitive endpoints like password logins or multi-factor authentication (MFA) checks.
* **Cost and infrastructure control:** Backend systems are provisioned around human usage patterns (e.g., posting once per minute). Automated scripts can blast thousands of requests per second through the same API. Rate limits constrain compute overhead and cloud infra expenses.
* **Monetization tiers:** Standard API access can be capped with default rate limits, allowing higher throughput limits to be offered as premium paid tiers.
* **Mitigating traffic spikes:** Enforcing per-client caps stabilizes overall service reliability during unexpected surge traffic.

## Step 1: Clarify the Requirements

> [!TIP]
> Always clarify requirements at the beginning of the interview. Ask targeted questions until you establish the precise scope expected by the interviewer.

#### Functional Requirements
* **Enforce rate limits:** Restrict the number of requests an entity can execute against an API within a defined window (e.g., 15 requests per second).
* **Distributed enforcement:** The API operates across a cluster of server nodes, so rate limits must be globally enforced across all nodes. Exceeding the limit results in an error regardless of which node receives the request.

#### Non-Functional Requirements
* **High Availability:** Because the rate limiter defends downstream services against traffic floods, it must be highly available and resilient.
* **Low Latency:** The rate limit check evaluates on every inbound request prior to handling the API logic; it must introduce minimal, unnoticeable latency (sub-millisecond overhead).

#### Throttling Strategies
Throttling defines how rate limit rules are enforced. Three common strategies exist:
1. **Hard Throttling:** Request counts can strictly never cross the specified limit.
2. **Soft Throttling:** Traffic is permitted to exceed the threshold by a designated margin (e.g., a 10% tolerance on a 100 request/minute limit allows up to 110 requests/minute).
3. **Elastic / Dynamic Throttling:** Clients can burst past limits if backend server capacity is idle, but are throttled during high system load.

We will focus on **hard throttling**. When a client crosses the limit, the server immediately returns HTTP status `429 Too Many Requests`.

#### Fixed Window vs. Rolling Window
Measuring a constraint like "15 requests per second" depends on the window framing strategy:

* **Fixed Window:** Time is split into fixed interval slots (e.g., 0–1s, 1–2s). Request arrival timing inside a window is ignored. For example, if two messages arrive between 0 and 1s, and three messages arrive between 1 and 2s with a limit of 2 requests/sec, fixed windowing throttles only the 5th message ($m_5$).

![Fixed Window vs Rolling Window Comparison](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.11-fixed-vs-rolling-window.png)

* **Rolling (Sliding) Window:** The window dynamically begins at the arrival timestamp of a request and extends for the window duration. If requests arrive at 300 ms and 400 ms into a 1-second interval, they remain within the window until 300 ms into the following second. Under a limit of 2 requests/sec, a rolling window evaluates $m_1$ through $m_4$ together and throttles both $m_3$ and $m_4$.

Rolling windows provide fairer and stricter control but require recording historical timestamps, which increases memory overhead.

## Step 2: Estimate the Scale

Clarify key scale parameters with the interviewer: the number of concurrent active entities and their configured rate limits. For our baseline, assume **1 million active users** with a limit of **10 requests per second per user**.

#### Traffic Load & Throughput
In the worst-case scenario where every active user bursts to their maximum allowed throughput:

$$\text{Peak QPS} = 1\text{ Million Users} \times 10\text{ Requests/sec} = 10\text{ Million checks/second}$$

While 10M QPS represents an upper bound and average client usage will be lower, the rate limiter must inspect *every* incoming API request. Hence, the system requires a distributed cluster of evaluation nodes regardless of dataset footprint.

#### Memory Footprint
Memory requirements depend on the per-user data structure required by the chosen algorithm. Memory consumption spans from **32 MB to ~12 GB** for 1 million active entities. This wide variation forms the primary basis for comparing rate-limiting algorithms.

## Step 3: Define the API

The rate limiter exposes a single core internal evaluation interface called by the Web Server or API Gateway for every incoming request:

```text
is_allowed(entity_id, api_name)
```

#### Return Signatures
* **Allowed:** `{ "allowed": true, "remaining": <count> }`
* **Throttled:** `{ "allowed": false, "retry_after_seconds": <seconds> }`

#### Parameters & Response Headers
* `entity_id`: User ID (for authenticated users) or IP address (for unauthenticated client traffic).
* `api_name`: Endpoint identifier, enabling granular per-route rate limits.

When `allowed` returns `false`, the API Gateway returns HTTP status `429 Too Many Requests` along with a standard `Retry-After` header indicating the required backoff period. Rate-limit rules per API endpoint and account tier are stored separately as configuration metadata.

---

## Step 4: Define the Data Model

The rate limiter relies on a key-value data model: a single key per entity mapped to a compact tracking record.

* **Key:** `UserID` (authenticated requests) or `IP address` (anonymous traffic).
* **Value:** Algorithmic tracking state (e.g., counter + start time, timestamp collection, or bucket state).

Alongside per-user tracking state, the system stores **Rate Limit Rules** defining configured throughput caps (e.g., 500 requests/hour for basic tier users).

![The Rate Limiter Data Model](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.11-rate-limiter-data-model.png)

#### Data Schema Breakdown
1. **Rate Limit Rule:** Identified by `(APIName, AccountTier)`. Stores static configuration parameters like `Limit` and `Window`. Stored as application configuration rather than volatile user state.
2. **Fixed Window Counter:** Stores `Count` (integer) and `StartTime` (normalized epoch timestamp). May include an optional lock field for distributed sync.
3. **Sliding Window:** Stores a sorted set of individual request timestamps. Precise, but memory-intensive.
4. **Sliding Window with Counters:** Stores a hash mapping minute-level offsets to request counts (up to 60 sub-counters for an hourly limit window).
5. **Token Bucket:** Stores `TokenCount` and `LastRefillTime` (similar in size to a fixed window counter).

#### Storage Engine Selection
Because operations consist of ultra-fast key lookups without complex relational joins, in-memory key-value stores like [Redis](https://en.wikipedia.org/wiki/Redis) or [Memcached](https://en.wikipedia.org/wiki/Memcached) are ideal. Redis natively supports sorted sets and hashes, making it the primary backend store for rate limiter state.

## Step 5: Draw the High-Level Design

The rate limiter functions as a gateway middleware sitting directly in front of core API application servers.

![High-Level Architecture of Rate Limiter](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.11-rate-limiter-hld.png)

#### Request Flow
1. **Client** issues an HTTP request to the API infrastructure.
2. **Web Server / API Gateway** intercepts the request and queries the **Rate Limiter Service**.
3. **Rate Limiter** checks the entity's current record in the **Redis Counter Store**.
4. If the check passes (`allowed: true`), the Web Server forwards the request to the downstream **API Application Servers**.
5. If the limit is crossed (`allowed: false`), the Web Server drops the request immediately and returns HTTP `429 Too Many Requests` with a `Retry-After` header.

Because rate limit evaluations complete at the gateway layer, rejected requests bypass backend application servers entirely, protecting downstream databases and services from processing redundant load.

## Step 6: Go Deep

### Fixed window with a counter

In a fixed window counter algorithm, the system maintains two fields per user in an in-memory hash table: the total request count (`Count`) and the start time of the current window (`StartTime`).

![The Fixed Window Record Format](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.11-fixed-window-record.png)

#### Evaluation Algorithm
Assume a rate limit of 3 requests per minute per user. When a request arrives:
1. If `UserID` is missing from the table, create an entry with `Count = 1` and `StartTime` set to the current minute boundary. Allow the request.
2. If `UserID` exists:
   * If $\text{CurrentTime} - \text{StartTime} \ge 1\text{ minute}$, the previous window expired. Reset `StartTime` to the current minute boundary, set `Count = 1`, and allow the request.
   * If $\text{CurrentTime} - \text{StartTime} < 1\text{ minute}$:
     * If `Count < 3`, increment `Count` by 1 and allow the request.
     * If `Count >= 3`, reject the request with HTTP `429`.

`StartTime` is always normalized to clock-minute boundaries (seconds set to 00).

![Fixed Window Counter Lifecycle](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.11-fixed-window-lifecycle.png)

#### Key Weaknesses

1. **Window Edge Bursting:** Because counters reset at fixed interval boundaries, a user can send double the rate limit across the boundary. If a user sends 3 requests at 00:59 and 3 requests at 01:01, 6 requests pass within 2 seconds, violating the intended per-minute restriction.

![Window Edge Traffic Spike Issue](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.11-fixed-window-edge-issue.png)

2. **Race Conditions & Atomicity:** Distributed API servers executing non-atomic "read-then-write" operations on shared counters introduce race conditions. Two servers concurrently reading `Count = 2` will both increment to 3 and allow both requests, letting 4 requests pass instead of 3.

![Distributed Race Condition on Counter Update](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.11-fixed-window-race-condition.png)

To resolve concurrency issues without heavy explicit distributed locks ([Redis Lock](https://redis.io/topics/distlock)), evaluation logic is executed atomically using Redis `INCR` commands with key expiry or atomic Lua scripts executed inside Redis. Refer to [Token Bucket vs Leaky Bucket](../3-system-design-trade-offs/3.24-token-bucket-vs-leaky-bucket.md) for further discussion on shared counter synchronization.

#### Fixed Window Memory Estimation
* `UserID`: 8 bytes
* `Count` (uint16 up to 65,535): 2 bytes
* `StartTime` (normalized offset): 2 bytes
* **Base Record Size:** $8 + 2 + 2 = 12\text{ bytes}$
* Hash table overhead: ~20 bytes/record

$$\text{Total Memory (1M Users)} = (12 + 20)\text{ bytes} \times 1\text{ Million} = 32\text{ MB}$$

Including an optional 4-byte synchronization lock increases total footprint to **36 MB**.

---

### Sliding window

To eliminate boundary bursts, the sliding window algorithm maintains exact request timestamps in a Redis [Sorted Set](https://redis.io/topics/data-types) (ZSET) for each entity.

![The Sliding Window Record Format](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.11-sliding-window-record.png)

#### Evaluation Algorithm
Assuming a limit of 3 requests per minute per user:
1. Evict all timestamps older than $\text{CurrentTime} - 1\text{ minute}$ from the ZSET using `ZREMRANGEBYSCORE`.
2. Count remaining elements in the ZSET using `ZCARD`. If element count $\ge 3$, reject the request without writing new timestamps.
3. If element count $< 3$, append `CurrentTime` to the ZSET and allow the request.

![Sliding Window Execution Timeline](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.11-sliding-window-timeline.png)

#### Sliding Window Memory Estimation
Assume a rate limit rule of 500 requests/hour:
* `UserID`: 8 bytes
* Timestamp (epoch integer): 4 bytes
* ZSET node overhead (prev/next 64-bit pointers + metadata): ~20 bytes/element
* Hash table record overhead: 20 bytes

$$\text{Per-User Footprint} = 8 + (4 + 20) \times 500 + 20 \approx 12\text{ KB}$$
$$\text{Total Memory (1M Users)} = 12\text{ KB} \times 1\text{ Million} \approx 12\text{ GB}$$

While sliding windowing provides exact rate control, storing individual request timestamps increases memory consumption to **~12 GB** (compared to 32 MB for fixed windows).

---

### Sliding window with counters

Sliding window with counters combines fixed window efficiency with sliding window precision by dividing the time window into granular sub-buckets (e.g., 60 one-minute sub-counters for an hourly limit).

Counters are tracked using a [Redis Hash](https://redis.io/topics/data-types) key with automatic [key expiry](https://redis.io/commands/ttl) set to the window length.

![Sliding Window with Sub-Counters Structure](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.11-sliding-window-counters.png)

When an incoming request arrives, the system sums sub-counters across the trailing window interval. If the aggregate sum exceeds the configured limit, the request is throttled.

#### Memory Estimation
For a 500 request/hour limit using 60 one-minute sub-buckets:
* `UserID`: 8 bytes
* Key offset (minute epoch timestamp): 4 bytes
* Sub-counter (uint16): 2 bytes
* Hash entry overhead: ~20 bytes/entry
* Hash table key overhead: 20 bytes

$$\text{Per-User Footprint} = 8 + (4 + 2 + 20) \times 60 + 20 \approx 1.6\text{ KB}$$
$$\text{Total Memory (1M Users)} = 1.6\text{ KB} \times 1\text{ Million} \approx 1.6\text{ GB}$$

Sliding window with counters reduces memory consumption by **~86%** relative to raw sliding windows (1.6 GB vs. 12 GB) while preserving sub-window accuracy.

---

### Token bucket

The token bucket algorithm maintains a bucket per entity with a maximum token `Capacity` and a continuous token `RefillRate` (tokens added per second).

* Each processed API request consumes 1 token.
* If tokens remain in the bucket, the request is allowed.
* If the bucket is empty (`tokens == 0`), the request is rejected with HTTP `429`.

#### State Footprint & Advantages
Per-user state consists of only two fields: `Tokens` (integer) and `LastRefillTimestamp`. This requires only **~12 bytes per user** (identical footprint to a fixed window counter), while completely preventing window edge exploitation. Idle users can burst up to maximum capacity, while sustained traffic is capped strictly to the refill rate.

For full architectural trade-offs between bucket algorithms, refer to [Token Bucket vs Leaky Bucket](../3-system-design-trade-offs/3.24-token-bucket-vs-leaky-bucket.md).

#### Algorithm Selection Summary
* **Public APIs:** **Token Bucket** (minimal 12-byte footprint per user, handles natural client burstiness cleanly).
* **Strict Hourly Boundaries:** **Sliding Window with Counters** (prevents sliding window boundary breaches with low 1.6 GB memory overhead).
* **Low-Volume Security Endpoints (e.g., Login Attempts):** **Sliding Window** (exact accuracy where tracking history sizes are minimal).

### Sharding and caching

#### Data Sharding
To scale memory and throughput past a single Redis instance, rate limiter keys are partitioned across Redis cluster nodes using **Consistent Hashing** on `UserID` or `IP`. When different API routes enforce separate rate limits, keys are composite: `(UserID, APIName)`. For instance, in a service like [Designing a URL Shortening Service like TinyURL](./4.3-designing-a-url-shortening-service-like-tinyurl.md), `createURL()` and `deleteURL()` can carry independent limit counters per user.

#### Write-Back Caching & LRU Eviction
Local in-memory caches on API gateway nodes reduce network round-trips to remote Redis instances:
* **Write-Back Cache Strategy:** Gateway nodes perform token evaluations and counter increments within local cache memory, flushing aggregated updates asynchronously to Redis at periodic intervals.
* **Throttled Read Short-Circuiting:** Once an entity exceeds its rate limit, subsequent evaluations fail fast locally in cache without hitting Redis remote storage.
* **LRU Eviction Policy:** Evict Least Recently Used entries to retain high-volume active clients in fast local memory.

---

### Rate limit by IP or by user?

#### Rate Limiting by IP Address
* **Pros:** Works for unauthenticated traffic and anonymous endpoints.
* **Cons:** Public NAT gateways, corporate networks, and mobile carrier proxies multiplex thousands of users behind a single IP, risking false-positive throttling for legitimate users. Conversely, IPv6 subnets allow malicious bots to rotate across millions of distinct IP addresses, exhausting limiter storage.

#### Rate Limiting by User ID
* **Pros:** Accurately targets specific authenticated account tokens regardless of location or IP changes.
* **Cons:** Inapplicable prior to authentication (e.g., `/login`). Rate limiting unauthenticated login attempts solely by targeted username allows malicious actors to trigger targeted account lockouts (Denial of Service against specific users).

#### Hybrid Approach
Production architectures employ a **hybrid strategy**: rate-limiting unauthenticated traffic by IP address (with subnet-level aggregation for IPv6) and authenticated requests by User ID / API token.

## Step 7: Bottlenecks and Failure Points

* **Redis Latency & Failopen Strategy:** Because rate limit checks reside on the critical path of every request, database latency directly impacts API latency. If the Redis cluster fails or experiences network partitioning, the system must choose between:
  * **Fail-Open (Recommended for Public APIs):** Allow traffic through to prevent cascading API outages.
  * **Fail-Closed:** Block traffic to protect downstream infrastructure under active attacks.
* **Network Hop Overhead:** Evaluating remote Redis state on every request adds network round-trips. Local gateway caching or localized bucket delegation mitigates remote calls.
* **Memory Exhaustion Under Distributed Attacks:** Unauthenticated IPv6 floods can bloat key-value storage. Enforce hard bounds on active key capacity combined with aggressive LRU eviction.

## Where AI Fits in This Design

In high-throughput rate-limiting systems, placing machine learning models directly on the synchronous request evaluation path introduces prohibitive latency and eliminates deterministic explainability (clients receiving HTTP `429` require clear `Retry-After` headers and rule identifiers).

#### Offline Anomaly Detection & Rule Generation
Instead of evaluating live requests, AI models operate **offline** by analyzing access logs:
* **Pattern Recognition:** Anomaly detection models parse historical access logs to identify distributed botnets, credential stuffing patterns, and stealthy scraping scripts operating just under static rate thresholds.
* **Dynamic Rule Tuning:** The offline AI engine generates recommended configuration updates (e.g., adjusting per-route limits or flagging suspicious IP ranges), which are pushed asynchronously into rate limiter configuration stores.

> **Key Architectural Principle:** *AI advises rule configuration offline; deterministic logic enforces checks online.*

> **Interview Strategy:**  
> Focus your interview time on algorithm selection and distributed counter storage. State the throttling rule and window type upfront. Select **Token Bucket** for general public APIs due to its low 12-byte per-user state and clean handling of bursty traffic. Highlight atomic counter operations in Redis (Lua scripts / `INCR`), consistent hashing by `UserID`, and memory numbers (32 MB vs. 1.6 GB vs. 12 GB). When asked about bottlenecks, identify remote database network round-trips as the primary constraint.

> [!IMPORTANT]
> **Key Takeaway:**  
> A rate limiter maintains a small tracking record per entity, evaluated on every request across a distributed cluster. Position the rate limiter at the API gateway layer so dropped requests consume zero downstream application resources, returning HTTP `429 Too Many Requests` with a `Retry-After` header. Fixed window counters use 12 bytes per user but suffer from window-edge traffic spikes. Sliding window timestamps eliminate edge spikes but consume ~12 GB per million users. Sliding window with sub-counters reduces memory to ~1.6 GB. Token bucket matches fixed-window memory efficiency (12 bytes/user) while smoothing burst traffic. Shared counter state is sharded in Redis using consistent hashing, updated via atomic operations, and optimized with local write-back caching and LRU eviction.
