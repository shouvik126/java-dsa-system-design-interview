## What is a Rate Limiter?

A **rate limiter** (or API throttling engine) is a core traffic-control mechanism designed to track and cap the number of requests an entity can transmit to a service within a defined time frame. 

The entity being limited can be a specific **User ID**, an **API Key**, an **IP Address**, a **Client Device ID**, or an entire **Tenant Account**. Once an entity reaches its allocated threshold, the rate limiter intercepts subsequent requests and denies them before they consume downstream application or database resources.

```
+------------------+         +----------------------+         +----------------------+
|  Client Requests |  ---->  |  API Rate Limiter    |  ---->  |  Backend Services    |
| (100 req/sec)    |         | (Quota: 10 req/sec)  |         | (Processes 10 req/s) |
+------------------+         +----------------------+         +----------------------+
                                        |
                                        v [90 Requests Rejected]
                             HTTP 429 Too Many Requests
```

### Real-World Quota Examples
* **Messaging APIs**: A user may transmit at most **1 message per second** to prevent chat spam.
* **Payment Processing**: A credit card token is allowed a maximum of **3 failed authorization attempts per day** to mitigate fraudulent card testing.
* **User Authentication**: An IP address is limited to **5 login attempts per minute** to block password guessing attacks.
* **Public Search Endpoints**: An unauthenticated web crawler is capped at **20 requests per minute** per IP address.

> [!NOTE]
> **Key Concept**: A rate limiter acts as a gateway guard. When a client stays within its quota, requests pass through seamlessly. When a client exceeds its quota, the rate limiter responds immediately with HTTP Status `429 Too Many Requests` along with a `Retry-After` header indicating when the client may retry.

## Why do we need rate limiting?

Rate limiting is not merely a convenience feature; it is an essential safeguard for production microservices. Without rate limiting, any single user or malicious bot script can degrade service availability for everyone else.

```
                                    +-----------------------+
                                 +--| Denial-of-Service     |
                                 |  +-----------------------+
                                 |  +-----------------------+
                                 +--| Brute-Force Defense   |
                                 |  +-----------------------+
                                 |  +-----------------------+
Why We Need Rate Limiting? ------+--| Noisy Neighbor Control|
                                 |  +-----------------------+
                                 |  +-----------------------+
                                 +--| Cloud Infrastructure  |
                                 |  | Cost Management       |
                                 |  +-----------------------+
                                 |  +-----------------------+
                                 +--| Tiered Monetization   |
                                    +-----------------------+
```

### 1. Cyber Attack & Abuse Protection
Automated botnets generate floods of legitimate-looking HTTP requests to execute **Denial-of-Service (DoS)** attacks, credential stuffing, or brute-force credit card verification attempts. Rate limiting caps request velocity at the network edge, making brute-force scans computationally impractical for attackers.

### 2. Preventing Resource Exhaustion ("Noisy Neighbors")
In multi-tenant cloud systems, a single misbehaving client or poorly configured background script can issue thousands of requests per second. Rate limiting isolates tenant traffic so that heavy analytical exports by one user never starve critical transactional API calls of other users.

### 3. Controlling Infrastructure Costs
Modern cloud architectures scale elastically to handle load spikes. However, auto-scaling without boundaries during an attack or traffic surge can trigger massive, unexpected cloud bills. Rate limiting establishes a hard ceiling on backend resource consumption and operational costs.

### 4. API Monetization & Service Tiers
Commercial API providers structure their business models around usage tiers. Free accounts receive a conservative allowance (e.g., 100 calls/hour), while enterprise subscriptions unlock higher capacity (e.g., 10,000 calls/hour). Rate limiters technical enforce these contractual SLAs.

### 5. Flattening Traffic Spikes
Uncontrolled bursts of traffic can overload memory buffers, thread pools, and database connection pools. By shedding excess traffic during peak surges, rate limiters keep overall service operations stable and available.

## Step 1: Clarify the Requirements

> [!TIP]
> **Interview Strategy**: In a system design interview, never start coding or selecting algorithms until you have explicitly clarified constraints with your interviewer. Establish traffic parameters, distribution models, and failure behaviors up front.

### Functional Requirements
1. **Accurate Quota Enforcement**: The system must accurately cap the number of requests an entity can make within a specified time window (e.g., 15 requests per second).
2. **Distributed Consistency**: The rate limiter operates across a clustered fleet of gateway/application servers. The user's quota must be enforced globally regardless of which server receives a request.
3. **Immediate Rejection Feedback**: When an entity crosses its quota threshold, the system must drop the request and return HTTP status `429 Too Many Requests`.

### Non-Functional Requirements
1. **Ultra-Low Check Latency**: The rate check sits directly on the execution path of *every* incoming API request. To avoid degrading user experience, server-side rate checking latency must remain under **1 to 2 milliseconds**.
2. **High Availability & Fault Tolerance**: The rate limiter itself must not become a single point of failure. If the rate limiter engine experiences partial outages, the system should degrade gracefully rather than blocking all system traffic.
3. **High Throughput Scalability**: The counter engine must comfortably scale to handle millions of check requests per second.
4. **Minimal Memory Overhead**: Dynamic per-user state tracking must consume minimal RAM to allow hundreds of millions of active entity records to reside in memory.

---

### Throttling Strategies: Hard, Soft, and Elastic

When clarifying functional requirements, agree on how strictly throttling rules should be enforced:

| Throttling Model | Mechanics | Ideal Use Case |
| :--- | :--- | :--- |
| **Hard Throttling** | Requests are strictly capped at the threshold. Any excess request is immediately blocked with HTTP `429`. | Security endpoints, payment gateways, strict public APIs. |
| **Soft Throttling** | Allows requests to exceed the limit by a defined buffer percentage (e.g., +10% over quota). | Consumer applications where minor temporary bursts are acceptable. |
| **Elastic / Dynamic Throttling** | Permits clients to burst past their quotas when overall system CPU/memory utilization is low, but enforces strict caps during heavy load. | Internal microservice communication, batch processing workloads. |

*In this design, we will architect for **Hard Throttling**.*

---

### Measuring Time Windows: Fixed Window vs Rolling Window

A rule specifying "15 requests per second" can be measured in two distinct ways, leading to significantly different runtime behaviors:

```
Fixed Window (Aligned to Clock Boundaries):
Minute 1: [00:00 - 00:01] -> Counter resets at 00:01:00
Minute 2: [00:01 - 00:02] -> Counter resets at 00:02:00

Rolling / Sliding Window (Relative to Current Request Timestamp):
Request at 00:01:45 -> Window covers [00:00:45 to 00:01:45]
```

![Fixed Window vs Rolling Window Comparison](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.11-fixed-vs-rolling-window.svg)

1. **Fixed Window**: Time is segmented into static intervals (e.g., `12:00-12:01`, `12:01-12:02`). The request counter resets to zero at the start of each interval. While memory-efficient and simple to implement, fixed windows suffer from **traffic burst vulnerabilities** near window boundaries.
2. **Rolling (Sliding) Window**: The time window starts dynamically at the exact timestamp of an incoming request and looks backward over the window duration. This approach provides strict accuracy and eliminates boundary bursts, but requires storing granular timestamp data.

## Step 2: Estimate the Scale

To size the distributed rate limiter infrastructure, let us assume a large-scale system profile:

* **Active User Base**: 1 Million Daily Active Entities ($10^6$ active callers).
* **Default Rate Limit**: 10 requests per second per caller.

### Throughput Estimations
In the worst-case scenario where all active users transmit requests simultaneously at their maximum allowed rate:

$$\text{Peak Check Load} = 1,000,000 \text{ entities} \times 10 \text{ req/sec} = 10,000,000 \text{ checks/sec (10M QPS)}$$

Because every single incoming HTTP request requires a rate limit check before reaching application logic, our rate check engine must process **10 Million Query Checks Per Second (QPS)** at peak. 

This immense throughput dictates that rate limit state **must reside in ultra-fast in-memory data structures** (such as Redis or Memcached). Storing counters in relational databases on disk would introduce unviable I/O latency and locking contention.

---

### Memory Scale Calculations Across Algorithms

Memory consumption is the primary trade-off when evaluating rate limiting algorithms. Below is a comparative memory forecast for tracking **1 Million active users** across different algorithmic models (detailed further in Step 6):

$$\begin{aligned}
\text{Fixed Window Counter} &\approx 32 \text{ MB} \\
\text{Sliding Window (Sorted Set)} &\approx 12 \text{ GB (at 500 req/hr limit)} \\
\text{Sliding Window with Counters} &\approx 1.6 \text{ GB} \\
\text{Token Bucket} &\approx 32 \text{ MB}
\end{aligned}$$

Notice that memory footprint ranges from **32 MB to 12 GB** depending on whether we store a single compact integer counter or a sorted list of individual request timestamps per user.

## Step 3: Define the API

The Rate Limiter engine is executed internally by the Web Server or API Gateway layer on every incoming request.

### Internal RPC / Service API Contract

```typescript
interface RateLimitResult {
  allowed: boolean;                 // True if request is under quota
  remaining: number;                // Remaining requests allowed in current window
  reset_time_epoch_seconds: number; // Unix timestamp when quota fully resets
  retry_after_seconds: number;      // Wait time in seconds before retrying (if throttled)
}

function is_allowed(
  entity_id: string,                // UserID, API Key, or IP Address
  api_name: string                  // Target API endpoint (e.g., "POST /v1/payments")
): RateLimitResult;
```

---

### Client-Facing HTTP Response Headers

When an API Gateway executes the rate check, it translates the internal `RateLimitResult` into standard client-facing HTTP headers:

#### 1. Successful Request (`HTTP 200 OK`)
```http
HTTP/1.1 200 OK
Content-Type: application/json
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 42
X-RateLimit-Reset: 1700000060

{
  "status": "success",
  "data": { ... }
}
```

#### 2. Throttled Request (`HTTP 429 Too Many Requests`)
```http
HTTP/1.1 429 Too Many Requests
Content-Type: application/json
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1700000060
Retry-After: 15

{
  "error": "Too Many Requests",
  "message": "API rate limit exceeded. Please retry after 15 seconds."
}
```

> [!IMPORTANT]
> Rate limit rules (such as mapping `Free Tier -> 100 req/hr` vs `Enterprise Tier -> 10,000 req/hr`) are configured centrally as static metadata rules. The rate limiter engine evaluates incoming caller identity (`entity_id`) against these rules to determine the applicable threshold.

The data model for rate limiting consists of two main structures: **Configuration Rules** and **Dynamic Entity State**.

```
                       +-----------------------------------+

|  | Fixed Window Schema    |  | Sliding Window Schema  |  | Token Bucket      |  |
|  | Key: UserID            |  | Key: UserID            |  | Key: UserID       |  |
|  | Val: { Count, Start }  |  | Val: SortedSet[TS]     |  | Val: {Tokens, TS} |  |
|  +------------------------+  +------------------------+  +-------------------+  |

```

![Rate Limiter Data Model Schemas in Redis](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.11-rate-limiter-data-model.svg)

### 1. Static Configuration Rules
Rules define the quota policies per API endpoint and account tier. Because rules change infrequently, they are loaded into local Gateway memory and cached.

| APIName | AccountTier | MaxLimit | WindowSeconds |
| :--- | :--- | :--- | :--- |
| `POST /v1/messages` | `Free` | 10 | 60 |
| `POST /v1/messages` | `Pro` | 1000 | 60 |
| `GET /v1/search` | `Anonymous_IP` | 20 | 60 |

### 2. Dynamic Entity State (Redis Data Structures)

Dynamic records are stored in a distributed in-memory key-value store (**Redis**). The choice of algorithm determines the Redis value type used:

* **Fixed Window**: Key = `rate:user_123:search`, Value = `Hash { count: 4, start_time: 1700000000 }`
* **Sliding Window (Sorted Set)**: Key = `rate:user_123:search`, Value = `Sorted Set (ZSET)` containing Unix timestamp scores `[1700000010, 1700000025, 1700000040]`
* **Sliding Window with Counters**: Key = `rate:user_123:search`, Value = `Hash` mapping minute buckets to integers `{ "12:00": 3, "12:01": 5, "12:02": 1 }`
* **Token Bucket**: Key = `rate:user_123:search`, Value = `Hash { tokens: 7.5, last_refill_time: 1700000045 }`

## Step 5: Draw the High-Level Design

The rate limiter must be positioned **in front of** application servers so rejected requests can be dropped immediately without executing downstream business code or database queries.

```
+--------+      1. HTTP Request      +-------------------+
| Client | ------------------------> |    API Gateway    |
+--------+                           +-------------------+
    ^                                  |               |
    |                                  | 2. Check      | 4. Forward
    | 5. HTTP 429                      v    Quota      v    Allowed
    |    (If Throttled)              +-------------------+  +-------------------+
    +------------------------------- | Distributed Rate  |  |  Backend API      |
                                     | Limiter (Redis)   |  |  Application      |
                                     +-------------------+  |  Servers          |
                                                            +-------------------+
                                                                      |
                                                                      v
                                                            +-------------------+
                                                            | Primary Database  |
                                                            +-------------------+
```

![High-Level Design of API Rate Limiter Architecture](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.11-rate-limiter-high-level-design.svg)

### End-to-End Request Workflow
1. **Client Request**: A client sends an HTTP request to the system endpoint.
2. **Gateway Interception**: The API Gateway intercepts the request, extracts authorization credentials (`UserID`, `API Key`, or client `IP`), and identifies the route (`api_name`).
3. **In-Memory Rate Check**: The Gateway queries the distributed Rate Limiter service (Redis cluster).
4. **Quota Evaluation**:
   * **Allowed**: If the caller's request count is within policy limits, Redis updates the counter state. The Gateway passes the request to the Backend API Servers, which access the primary database.
   * **Throttled**: If the caller has exceeded quota, the request is terminated at the Gateway. An HTTP `429` response is returned to the client immediately.
5. **Database Protection**: Notice that rejected requests never reach the backend API servers or primary databases, preserving backend computational capacity.

## Step 6: Go Deep

Now let us analyze the four primary rate limiting algorithms in detail, evaluating their execution logic, failure edge cases, and exact memory footprints.

---

### Fixed window with a counter

The **Fixed Window Counter** algorithm segments time into fixed clock intervals (e.g., 60-second windows starting on the minute). Each caller is assigned a simple integer counter per window.

![Fixed Window Hash Record Structure](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.11-fixed-window-record.svg)

#### Execution Algorithm (Limit = 3 requests per minute)
1. Normalize the current Unix timestamp to the minute boundary (e.g., `12:01:45` -> `12:01:00`).
2. Fetch the entity record from the hash table using key `user_id:window_start`.
3. If the key does not exist:
   * Insert key with `Count = 1` and `StartTime = 12:01:00`. Set TTL expiry to 60 seconds. Allow request.
4. If the key exists:
   * If `CurrentTime - StartTime < 1 minute`:
     * If `Count < 3`: Increment `Count` by 1. Allow request.
     * If `Count >= 3`: Reject request with HTTP `429`.
   * If `CurrentTime - StartTime >= 1 minute`: Reset `StartTime = 12:02:00`, reset `Count = 1`. Allow request.

![Fixed Window Counter Timeline and Resets](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.11-fixed-window-counter-timeline.svg)

---

#### Critical Edge Cases & Vulnerabilities

##### 1. The Boundary Traffic Burst Problem
Because counters reset at static clock boundaries, a client can concentrate traffic at window edges and transmit **double their allowed quota** across a short time span.

![Fixed Window Edge Traffic Burst Problem](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.11-fixed-window-edge-burst.svg)

*Suppose limit is 3 requests per minute:*
* User sends 3 requests at `12:00:59` (last second of Window 1). All allowed.
* User sends 3 requests at `12:01:01` (first second of Window 2). All allowed.
* **Result**: The user successfully executed **6 requests within a 2-second span**, completely bypassing the intended limit of 3 requests per minute!

##### 2. Distributed Race Conditions
In a multi-server deployment, parallel requests hitting different gateway instances trigger a classic **Read-Then-Write race condition**.

![Race Condition in Concurrent Shared Counter Updates](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.11-fixed-window-race-condition.svg)

* If `Count` is currently 2 (limit = 3), and two parallel requests arrive simultaneously:
  * Gateway Server A reads `Count = 2` -> Decides allowed.
  * Gateway Server B reads `Count = 2` -> Decides allowed.
  * Server A writes `Count = 3`. Server B writes `Count = 3`.
  * **Result**: The user was allowed 4 requests in the window instead of 3.

> [!TIP]
> **Resolving Race Conditions**: Avoid distributed locking (such as Redis Redlock), as locks introduce unacceptable latency. Instead, execute the check-and-increment operations **atomically inside Redis** using single-threaded **Atomic Redis Lua Scripts** or `INCR` commands with key expiry.

##### Example Atomic Redis Lua Script for Fixed Window
```lua
-- KEYS[1]: rate key (e.g. "rate:user123:12:01")
-- ARGV[1]: window limit (e.g. 3)
-- ARGV[2]: window TTL in seconds (e.g. 60)

local current = redis.call("INCR", KEYS[1])
if current == 1 then
    redis.call("EXPIRE", KEYS[1], ARGV[2])
end

if current > tonumber(ARGV[1]) then
    return 0 -- Throttled
else
    return 1 -- Allowed
end
```

---

#### Memory Calculation
* **UserID String Key**: 8 Bytes
* **Count (Integer)**: 2 Bytes (supports count up to 65,535)
* **StartTime (Epoch Minute)**: 2 Bytes
* **Redis Hash Table Overhead**: ~20 Bytes per key
* **Total Per Entity**: $8 + 2 + 2 + 20 = 32 \text{ Bytes}$

$$\text{Memory for 1M Users} = 32 \text{ Bytes} \times 1,000,000 = 32 \text{ MB}$$

*Fixed window is extremely memory-cheap (~32 MB), but vulnerable to edge bursts.*

---

### Sliding window

To eliminate boundary burst spikes, the **Sliding Window** algorithm maintains an exact log of request timestamps for each entity inside a **Redis Sorted Set (ZSET)**.

![Sliding Window Sorted Set Record Structure](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.11-sliding-window-sorted-set-record.svg)

#### Execution Algorithm (Limit = 3 requests per minute)
When a request arrives at timestamp `now`:
1. Remove all historical timestamps older than `now - 1 minute` from the sorted set (`ZREMRANGEBYSCORE`).
2. Count the remaining element timestamps in the set (`ZCARD`).
3. If `Count >= 3`: Reject the request. Do not insert the new timestamp.
4. If `Count < 3`: Insert `now` into the sorted set (`ZADD`) and allow the request.

![Sliding Window Timestamp Evaluation Timeline](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.11-sliding-window-evaluation-timeline.svg)

---

#### Memory Calculation (The Hidden Cost)
While 100% accurate, tracking individual timestamps incurs severe memory overhead:

* Assume quota limit = **500 requests per hour**.
* **UserID Key**: 8 Bytes
* **Timestamp Score**: 4 Bytes
* **Redis ZSET Pointer Overhead**: 20 Bytes per element (double pointers for sorted ordering)
* **Hash Structure Overhead**: 20 Bytes per key
* **Per User Memory**: $8 + (4 + 20) \times 500 + 20 \approx 12 \text{ KB}$

$$\text{Memory for 1M Users} = 12 \text{ KB} \times 1,000,000 \approx 12 \text{ GB}$$

*Pure sliding window requires 12 GB of RAM for 1M users—375x more memory than fixed window!*

---

### Sliding window with counters

The **Sliding Window with Counters** algorithm offers a hybrid approach: it achieves near-perfect accuracy while cutting memory usage by **86%** compared to pure timestamp logs.

Instead of logging individual timestamps, time is split into small fixed sub-buckets (e.g., 60 1-minute buckets for a 1-hour quota). Counters are stored in a compact **Redis Hash**.

![Sliding Window with Counters Redis Hash Record](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.11-sliding-window-counters-hash-record.svg)

#### Weighted Counter Formula
When a request arrives, we calculate an estimated request count across the sliding window by combining the current bucket count with a weighted percentage of the previous bucket count:

$$\text{Estimated Count} = \text{Count}_{\text{current}} + \text{Count}_{\text{previous}} \times \left(1 - \frac{\text{Time Elapsed in Current Bucket}}{\text{Bucket Duration}}\right)$$

#### Practical Calculation Example
* **Rule**: Limit 100 requests per hour.
* **State**: 
  * Previous minute bucket had **80 requests**.
  * Current minute bucket is **18 seconds in** (30% through the current minute) and has logged **10 requests**.
* **Calculation**:
  $$\text{Estimated Count} = 10 + 80 \times \left(1 - \frac{18}{60}\right) = 10 + 80 \times 0.70 = 10 + 56 = 66 \text{ requests}$$
* Since $66 < 100$, the request is allowed.

---

#### Memory Calculation
* **60 Minute Sub-Buckets**: Each hash entry contains 4B key timestamp + 2B integer counter + 20B hash element overhead.
* **Per User Memory**: $8 + 60 \times (4 + 2 + 20) + 20 \approx 1.6 \text{ KB}$

$$\text{Memory for 1M Users} = 1.6 \text{ KB} \times 1,000,000 \approx 1.6 \text{ GB}$$

*Sliding window with counters reduces memory from 12 GB down to 1.6 GB while maintaining high accuracy.*

### Token bucket

The **Token Bucket** algorithm is the industry standard choice for public API rate limiting (used by platforms like Stripe, AWS, and GitHub).

#### Conceptual Mechanics
1. A centralized bucket holds tokens up to a maximum capacity $C$.
2. Refill tokens are added to the bucket continuously at a fixed rate $r$ tokens per second.
3. When an API request arrives:
   * If `tokens >= 1`: Deduct 1 token and allow request.
   * If `tokens < 1`: Reject request with HTTP `429`.

---

#### Lazy Refill Optimization (Solving background thread overhead)
A naive implementation might use a background timer thread to constantly add tokens to millions of user buckets every second. This would exhaust CPU resources.

Instead, production token buckets use **Lazy Refill**: tokens are recalculated *on-demand* only when a request actually arrives!

```
Lazy Refill Equation:
elapsed_time = current_timestamp - last_refill_timestamp
tokens_to_add = elapsed_time * refill_rate
new_tokens = min(capacity, current_tokens + tokens_to_add)
```

#### Redis Token Bucket State Schema
Each user requires only two numerical values stored in a Redis Hash:
```json
{
  "tokens": 4.5,
  "last_refill_time": 1700000030
}
```

```lua
-- Atomic Token Bucket Lua Script in Redis
local key = KEYS[1]
local capacity = tonumber(ARGV[1])
local refill_rate = tonumber(ARGV[2])
local now = tonumber(ARGV[3])
local requested = 1

local data = redis.call("HMGET", key, "tokens", "last_refill_time")
local tokens = tonumber(data[1])
local last_refill_time = tonumber(data[2])

if not tokens then
    tokens = capacity
    last_refill_time = now
else
    local elapsed = now - last_refill_time
    tokens = math.min(capacity, tokens + elapsed * refill_rate)
    last_refill_time = now
end

if tokens >= requested then
    tokens = tokens - requested
    redis.call("HMSET", key, "tokens", tokens, "last_refill_time", last_refill_time)
    return 1 -- Allowed
else
    return 0 -- Throttled
end
```

---

#### Token Bucket vs Leaky Bucket

| Algorithm | Mechanics | Behavior under Traffic Bursts | Primary Use Case |
| :--- | :--- | :--- | :--- |
| **Token Bucket** | Tokens accumulate up to capacity $C$; requests consume tokens. | Allows burst traffic up to capacity $C$, then throttles down to refill rate $r$. | User-facing Web APIs (Stripe, GitHub). |
| **Leaky Bucket** | Requests enter a fixed FIFO queue and leak out at a constant output rate. | Smooths out bursts into a steady, constant traffic flow. Excess requests spill (dropped). | Data ingestion pipelines, video streaming buffering. |

---

### Comparison Summary of Rate Limiting Algorithms

| Algorithm | Memory (1M Users) | Edge Burst Vulnerability | Accuracy | Implementation Complexity | Best Used For |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Fixed Window Counter** | ~32 MB | High | Low | Very Low | Simple internal limits |
| **Sliding Window (ZSET)** | ~12 GB | None | 100% Exact | High | Security-critical low-volume checks |
| **Sliding Window Counters** | ~1.6 GB | None | High (~99%) | Medium | High-accuracy billing quotas |
| **Token Bucket** | **~32 MB** | **None (Bounded by $C$)** | **High** | **Low (with Lua)** | **General Public Web APIs** |

### Sharding and caching

At 10 Million QPS, a single Redis server will become a bottleneck. We scale the rate limiting infrastructure using **Data Sharding** and **Multi-Layer Caching**.

```
+-----------------------------------------------------------------------------------+
|                            Gateway In-Memory L1 Cache                             |
|  (Local Memory LRU: Caches Throttled Keys -> Blocks requests locally for 15s)     |
+-----------------------------------------------------------------------------------+
                                         |
                       +-----------------+-----------------+
                       |                                   |
                       v (Consistent Hash Ring)            v
         +--------------------------+        +--------------------------+
         | Redis Shard 1 (Keys A-M) |        | Redis Shard 2 (Keys N-Z) |
         +--------------------------+        +--------------------------+
```

#### 1. Redis Cluster Sharding with Consistent Hashing
Rate limit state keys (`rate:user_id:api_name`) are distributed across a cluster of Redis nodes using **Consistent Hashing**.
* Partitioning by `UserID` ensures all request checks for a specific caller route to the exact same Redis shard instance.
* Consistent hashing minimizes key reassignment when Redis shards are added or removed during scaling events.

#### 2. Local Gateway L1 Caching (Write-Back Defense)
When an entity exceeds its rate limit, the API Gateway caches the `throttled` status locally in local node RAM (using an LRU eviction policy) for the remaining duration of the window.
* Subsequent blocked requests from that abusive entity are rejected instantly in Gateway RAM **without emitting a network call to Redis**.
* This shields the Redis cluster from network exhaustion during active DoS attacks.

### Rate limit by IP or by user?

Choosing how to identify entities involves trade-offs:

```
                  +----------------------------------------------+
                  |           Rate Limiting Identity             |
                  +----------------------------------------------+
                                   |            |
             +---------------------+            +---------------------+
             |                                                        |
             v                                                        v
+--------------------------+                               +--------------------------+
|      IP-Based Limits     |                               |    User-ID Based Limits  |
| - Pre-auth endpoints     |                               | - Post-auth APIs         |
| - Weakness: Shared NATs, |                               | - Weakness: Vulnerable   |
|   IPv6 Subnet Floods     |                               |   to Account Lockout DoS |
+--------------------------+                               +--------------------------+
```

#### 1. Limiting by IP Address
* **Pros**: Identifies callers on unauthenticated public endpoints (e.g., `/login`, `/register`).
* **Cons**:
  * **Shared IP (NAT) Problem**: Thousands of employees behind a corporate office proxy or cellular network share a single public IP. One misbehaving user can cause the rate limiter to block all legitimate colleagues.
  * **IPv6 Address Rotation**: An attacker can dynamically cycle through an IPv6 `/64` subnet ($1.8 \times 10^{19}$ addresses) to exhaust rate limiter memory.
  * *Mitigation*: Aggregate IPv6 limits at the `/64` subnet level rather than per individual IP address.

#### 2. Limiting by User ID / API Key
* **Pros**: Highly accurate. Targets specific account quotas regardless of client IP changes.
* **Cons**: Cannot protect public endpoints before authentication occurs.
* **Account Lockout Vulnerability**: If password verification endpoints rate-limit strictly by User ID, an attacker can intentionally send failed password attempts for a victim's email address to lock out the legitimate account owner.

> [!RECOMMENDATION]
> **The Hybrid Strategy**: Apply **IP-based (and subnet-aggregated) rate limiting** to pre-authentication endpoints (`/login`, `/register`), and **User-ID / API-Key based rate limiting** to authenticated API routes (`/v1/dashboard`).

## Step 7: Bottlenecks and Failure Points

System design interviewers will expect you to identify failure modes under strain:

```
                                  +-----------------------+
                               +--| Redis Network Latency |
                               |  +-----------------------+
                               |  +-----------------------+
Rate Limiter Failure Points ---+--| System Fail-Open      |
                               |  vs Fail-Closed Policy   |
                               |  +-----------------------+
                               |  +-----------------------+
                               +--| Memory Exhaustion     |
                                  | under IP Floods       |
                                  +-----------------------+
```

### 1. The Redis Network Latency Overhead
Because the rate check sits on the critical request path, every API call pays a network latency penalty to Redis (~1-2 ms). 
* **Mitigation**: Deploy Redis instances co-located in the same local availability zones (AZ) as API Gateway nodes, and keep connection pools persistent to eliminate TCP handshake overhead.

### 2. Cache Failure Mode: Fail-Open vs Fail-Closed
What happens if the Redis rate limiter cluster crashes or becomes partitioned?

* **Fail-Open (Recommended for Public Web Apps)**: The API Gateway bypasses rate checking and allows API requests to pass directly to backend services. This prioritizes service availability over strict traffic control.
* **Fail-Closed (Recommended for Sensitive Financial Endpoints)**: The API Gateway blocks incoming requests if the rate limiter cannot be reached. Used for high-risk endpoints (e.g., payment processing, password resets, SMS OTP generation).

### 3. Redis Memory Exhaustion Under Malicious Attack
An attacker generating millions of requests from randomized IP addresses can create millions of tracking keys in Redis, threatening out-of-memory crashes.
* **Mitigation**: Configure Redis max memory caps with an **LRU Eviction Policy** (`allkeys-lru`). When RAM capacity is reached, Redis evicts the oldest inactive IP tracking keys automatically.

## Where AI Fits in This Design

A rate limiter must make deterministic decisions in sub-milliseconds. Introducing machine learning model inference into the inline execution path adds unacceptable latency (20-100+ ms) and unpredictable error behavior.

Instead, modern architectures separate the system into two distinct layers:

```
INLINE ENFORCEMENT PATH (Sub-millisecond & Deterministic):
Client Request --> API Gateway --> Redis Lua Token Bucket --> Allow / Block 429

OFFLINE AI ANALYTICAL PATH (Asynchronous Log Processing):
API Gateway Logs --> Kafka Stream --> AI Anomaly Detector --> Updates Rate Rules Config
```

### Inline Enforcement Path vs Offline AI Analysis

1. **Inline Enforcement Path (Deterministic)**: Executed inline using deterministic rules stored in Redis (e.g., Token Bucket Lua scripts). Returns immediate `429` responses with exact retry headers.
2. **Offline AI Path (Asynchronous)**: An AI anomaly detection engine reads request access logs asynchronously from a stream (e.g., Apache Kafka).

#### AI Engine Responsibilities
* **Detecting Distributed Botnets**: Identifies low-and-slow botnets that rotate across thousands of residential proxy IPs, keeping each IP just below static threshold limits.
* **Credential Stuffing Pattern Recognition**: Flags abnormal request payload signatures across endpoints.
* **Dynamic Rule Optimization**: Automatically generates proposed rule updates (e.g., "Temporarily drop rate limit for IP range `198.51.100.0/24` to 2 req/min").

> [!NOTE]
> **Key Architectural Rule**: **"AI Advises, Rules Enforce."** Machine learning models run offline to analyze trends and adjust configuration parameters, while lightweight deterministic algorithms execute inline to enforce quotas at low latency.

### Interview Summary Checklist

* **Location**: Place the rate limiter at the **API Gateway** layer, in front of backend servers.
* **Storage**: Store counters in **Redis**, sharded by key using **Consistent Hashing**.
* **Algorithm Choice**: Recommend **Token Bucket** for general public APIs (compact state, handles bursts smoothly). Use **Sliding Window with Counters** for strict hourly billing quotas.
* **Race Condition Defense**: Execute check-and-increment operations atomically inside Redis using **Lua Scripts**.
* **Failure Strategy**: Default to **Fail-Open** for general availability; use **Fail-Closed** for payment/security endpoints.
