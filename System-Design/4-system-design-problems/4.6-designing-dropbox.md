# Designing Dropbox

Every case study in this chapter follows the same seven steps from [System Design Interviews: A step by step guide](https://www.designgurus.io/course-play/grokking-the-system-design-interview/doc/system-design-interviews-a-step-by-step-guide), and builds its design from the components in the [System Design Master Template](https://www.designgurus.io/course-play/grokking-the-system-design-interview/doc/system-design-master-template). Keep both open beside you, and try each problem yourself before reading the solution.

## Why Cloud Storage?

Dropbox is a cloud file storage service. It keeps users' files on remote servers and synchronizes them across all of the user's devices.

Cloud storage services have become very popular. The main reason is the shift from one personal computer to many portable devices. The same person now uses a laptop, a smartphone, and a tablet. Each runs a different platform and is used from a different place at any time. Cloud storage gives all of these devices one view of the same files.

Three benefits explain the popularity:

- **Availability:** Users can access their files from any device, wherever they are, whenever they like.
- **Reliability and Durability:** Cloud storage keeps multiple copies of every file on servers in different geographic locations. If one server fails, no data is lost.
- **Scalability:** Users never run out of space. Storage is unlimited, as long as they are ready to pay for it.

If you haven't used dropbox.com before, please create an account there. Upload and edit a file, and go through the different options their service offers. This will help you a lot in understanding this chapter.

## Step 1: Clarify the Requirements

> [!TIP]
> Always clarify requirements at the beginning of the interview. Ask questions until you know the exact scope of the system the interviewer has in mind.

### Functional requirements
- Users can upload and download their files and photos from any device.
- Users can share files or folders with other users.
- Devices synchronize automatically. Update a file on one device, and every other device receives the change.
- The system supports large files, up to a gigabyte.
- Users can edit files offline. Once the device comes back online, all changes sync to the servers and to the other devices.

### Non-functional requirements
- **ACID guarantees on all file operations.** ACID stands for Atomicity, Consistency, Isolation, and Durability. Atomicity means an operation either completes fully or does not happen at all. A failed update must never leave half a file.
- **Heavy load in both directions.** Expect huge read and write volumes, in roughly equal amounts. Every device uploads its own changes, so writes are as common as reads.

### Extended requirements
- The system should support snapshotting of the data. A snapshot is a saved version of a file, so users can go back to any earlier version.

---

## Step 2: Estimate the Scale

Ask the interviewer for four numbers: total users, daily active users, files per user, and average file size.

- Assume **500 million total users** and **100 million daily active users (DAU)**.
- On average, each user connects from **three different devices**.
- Each user stores about **200 files or photos**, giving **100 billion files in total**.
- Assume an average file size of **100KB**.

$$500\text{M users} \times 200\text{ files} = 100\text{B total files}$$

$$100\text{B files} \times 100\text{KB} = 10\text{PB of total storage}$$

Also assume **one million active connections per minute**. This number sizes the servers, not the storage. Clients wait for updates on open connections, as step 6 explains. So the servers and load balancers must hold that many requests open at the same time.

---

## Step 3: Define the API

Clients do two jobs: they move file data, and they exchange metadata updates. The API splits the same way. File data moves as chunks, small fixed-size pieces of a file. Step 6 explains why we split files.

```http
POST /chunks
Body: { chunk_hash, chunk_data }
Response 201: { chunk_hash }

GET /chunks/{chunk_hash}
Response 200: the chunk data

POST /files/{file_id}/commit
Body: { version, chunk_hashes, name, size }
Response 200: { new_version }

GET /updates?since={version}
Response 200: all metadata changes after that version
```

`GET /updates` is the request a client waits on for changes; step 6 shows how the server holds it open. Every call carries the user's authentication token, and uploads are rate limited per account.

## Step 4: Define the Data Model

The metadata database stores information about five objects:
1. **Chunks**
2. **Files**
3. **Users**
4. **Devices**
5. **Workspaces** (the sync folders)

Here is how they connect:

![Database schema for Dropbox](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.6-dropbox-db-schema.png)

- **File** carries the most information. For each file, the metadata records the name, the directory, the size, and the current version. It also records the ordered list of chunks that make up the file. A client that holds those chunks, in that order, can rebuild the file. The file's permission record lives here too. Step 6's security section reads it to decide who may view or modify the file.
- **Chunk** has one row per stored chunk. Its key is a hash of the chunk's contents (SHA-256, for example), so identical chunks always get the same key. The row does not hold the chunk data. The data lives in cloud storage, and the row keeps only a pointer to it. Large binary data never goes into a metadata database. The reference count records how many files use the chunk. This is the deduplication idea from step 6: a chunk that two files share is stored once and referenced twice.
- **Versioning** comes with the model. A commit raises the file's version, and an old version is simply an older chunk list. Unchanged chunks are shared between versions. So the snapshot requirement from step 1 costs very little extra storage.
- **User, Device, and Workspace** stay small. A user owns a workspace, the folder that syncs. Each user connects from about three devices. Each device row tracks the last version the device has synced, which is the `since` value it sends in `GET /updates`.
- The **File and Chunk tables** grow very large. There are 100 billion files, and at least one chunk row for each. A few hundred bytes of metadata per file, multiplied by 100 billion files, is tens of terabytes of metadata alone. That is why step 6 partitions this database.

### SQL or NoSQL?
The metadata can live in a relational database like MySQL, or in a NoSQL store like DynamoDB. The deciding question is ACID. Whichever we pick, the sync logic must give every client a consistent view of the files. This matters most when several users edit the same file at once. NoSQL stores often give up native ACID support in exchange for scalability and performance. Choose one, and we must build the ACID guarantees programmatically into the Synchronization Service, described in step 6. A relational database supports ACID natively, which keeps that logic much simpler.

## Step 5: Draw the High-Level Design

The user marks one folder on their device as the workspace. Any file placed in it is uploaded to the cloud. Modify or delete a file, and the cloud copy changes the same way. The user sets up the same workspace on every device, so a change on one device propagates to all the others.

We store two kinds of data: the file contents, and the metadata about them. So we need servers for file transfer, servers for metadata, and a way to notify every client when a change happens.

As the diagram below shows, **Block servers** work with clients to upload and download files from cloud storage. **Metadata servers** keep the file metadata in a SQL or NoSQL database. **Synchronization servers** handle the workflow of notifying all clients about changes.

## Step 6: Go Deep

Let's go through the major parts of the system one by one.

### The client

The client application monitors the workspace folder and syncs it with the remote cloud storage. It works with the block servers to move actual file data. It works with the Synchronization Service for metadata updates, like a change in a file's name or size.

The client has three essential jobs:
1. Upload and download files.
2. Detect file changes in the workspace folder.
3. Resolve conflicts caused by offline or concurrent updates.

**How do we transfer files efficiently?** Split each file into fixed-size chunks, say 4MB each. Then we transfer only the chunks that changed, never the whole file. Failure also gets cheaper: if an upload fails, only the failing chunk is retried, not the entire file. Three inputs set a good chunk size: the storage hardware and its input/output operations per second (IOPS), the network bandwidth, and the average file size in our storage.

For a very small change inside a chunk, the client can save even more. It can upload only the diff, the exact difference between the two versions, instead of the whole chunk.

That saving has a price, and naming it is worth interview credit. Chunks in storage are immutable, so a diff cannot be applied in place. A block server must fetch the old chunk, apply the diff to build the new chunk, hash it, and store it. The bandwidth saved by the client becomes read, compute, and write work on the server. This is why delta sync is reserved for small edits to large chunks. When most of a chunk changed anyway, uploading the whole 4MB chunk is simpler and often cheaper.

**Should the client keep a copy of the metadata?** Yes. A local copy lets the user edit files while offline. The client records each change locally and syncs it once the device is back online. The local copy also saves a lot of round trips to the server.

**How do clients learn about changes made on other devices?** The simple answer is polling: each client periodically asks the server whether anything changed. This has two problems: changes arrive late because they wait for the next check, and most checks return an empty response, which wastes bandwidth and keeps the server busy for nothing. Pulling information this way does not scale.

The better answer is **HTTP long polling**. The client sends a request, and the server may not answer immediately. If it has nothing new, it holds the request open until new information arrives or the request times out. Then it responds at once, and the client immediately issues the next request. So the client is always waiting on one open request.

Based on all this, we can divide the client into four parts:
- **The Internal Metadata Database** keeps track of all files, chunks, their versions, and their locations in the file system.
- **The Chunker** splits files into chunks and reconstructs a file from its chunks. It also detects the parts of a file the user modified, so only those parts are transferred. This saves bandwidth and synchronization time.
- **The Watcher** monitors the local workspace folders. It notifies the Indexer when the user creates, deletes, or updates a file or folder. The Watcher also listens for changes on other clients, which the Synchronization Service broadcasts.
- **The Indexer** processes events from the Watcher and updates the internal metadata database. Once chunks upload or download successfully, the Indexer notifies the remote Synchronization Service. The service then broadcasts the change to other clients and updates the remote metadata database.

Two more client questions are worth answering before we move to the server side:
- **How should clients handle slow servers?** With exponential backoff. If a server is busy or not responding, the client delays its retry. Each failure makes the next delay longer. So an overloaded server receives fewer retries exactly when it can handle the fewest.
- **Should mobile clients sync immediately?** No. Desktop and web clients sync remote changes as they happen. Mobile clients usually sync on demand, to save the user's bandwidth and storage space.

### The Synchronization Service

The Synchronization Service processes file updates made by one client and applies them to all other subscribed clients. It also keeps each client's local metadata database consistent with the remote Metadata Database. When the service receives an update, it checks the Metadata Database for consistency, applies the update, and notifies every subscribed device. A client that was offline polls the service for new updates as soon as it comes back online.

The service should transmit as little data as possible, because less data means faster sync. So instead of whole files, we transmit only the difference between two versions: the modified 4MB chunks. To recognize a chunk, the client and the server compute a hash of it, for example with SHA-256. A hash is a short, fixed-size signature of the chunk's contents. Identical chunks always produce the same hash. So if the server already holds a chunk with the same hash, even from another user, it stores a reference instead of a copy.

One instance of the service cannot serve millions of clients directly. So we put a messaging middleware between the clients and the Synchronization Service. It provides scalable [message queuing](https://en.wikipedia.org/wiki/Message_queue) and change notifications. Many Synchronization Service instances can then read requests from one shared global queue, and the middleware balances the load between them.

---

### The Message Queuing Service

The Message Queuing Service carries these messages. The communication is asynchronous: the sender puts a message in a queue and continues without waiting for the receiver. That keeps the two sides loosely coupled. Sync instances can be added, removed, or run slowly for a while, without blocking any client. The queues must store any number of messages reliably and stay highly available.

The service uses two kinds of queues:
- **Request Queue:** Global, and all clients share it. A client's request to update the metadata goes into the Request Queue first. The Synchronization Service takes it from there and updates the Metadata Database.
- **Response Queues:** Deliver update notifications to the clients. A message is deleted from a queue once it is received. But one update must reach every subscribed device. So each subscribed client gets its own Response Queue, and a copy of the update goes into every one of them.

### Cloud/Block Storage

Cloud storage holds the actual chunks of the users' files. It can be an [object storage](https://en.wikipedia.org/wiki/Object_storage) service like Amazon S3. Clients interact with the storage directly to send and receive chunks. Keeping the metadata separate from the storage has one large benefit: we can use any storage backend, in the cloud or in-house, without changing the metadata layer.

### The file processing workflow

Here is the sequence when Client A updates a file shared with Clients B and C. If B or C is offline, the Message Queuing Service keeps their notifications in their Response Queues until they come back online.

1. Client A uploads its changed chunks to cloud storage.
2. Client A updates the metadata and commits the change.
3. Client A gets confirmation, and notifications are sent to Clients B and C.
4. Clients B and C receive the metadata change and download the updated chunks.

---

### Data deduplication

Deduplication means eliminating duplicate copies of data, to save storage and network transfer. For each new chunk, we compute its hash and compare it with the hashes of the stored chunks. The check can run at two different times:

- **Post-process deduplication:** Store every new chunk first, and let a background process scan for duplicates later. The client never waits for a hash lookup, so storage performance does not degrade. The costs: duplicate data is transferred, consuming bandwidth, and it occupies storage until the cleanup process removes it.
- **In-line deduplication:** Compute the hash in real time, while the data is arriving. If the chunk already exists, add only a reference to it in the metadata, never a second copy. This gives optimal network and storage usage. The price is that the hash lookup now runs on the upload path, while the user waits.

---

### Metadata partitioning

The Metadata Database must hold information about millions of users and billions of files and chunks. That does not fit on one server, so we partition it. Three schemes are worth comparing:

- **Vertical partitioning:** Split by feature: all user-related tables in one database, all file and chunk tables in another. This is straightforward, but has two problems: chunk tables outgrow one database requiring re-partitioning, and joining tables across separate databases causes performance/consistency issues.
- **Range-based partitioning:** Choose the partition from the first letter of the file path (e.g., files starting with 'A' go to one partition, 'B' to the next). The scheme is static and predictable, but leads to unbalanced servers if certain initial letters dominate.
- **Hash-based partitioning:** Hash the `FileID` of each file and map the hash to a partition number (e.g., between 1 and 256). The hash spreads files evenly. Consistent hashing solves server addition/removal with minimal data movement, as explained in the [TinyURL lesson](https://www.designgurus.io/course-play/grokking-the-system-design-interview/doc/designing-a-url-shortening-service-like-tinyurl).

---

### Caching

We can use two caches. The first is a block cache for hot chunks (chunks requested most often). A memory store like [Memcached](https://en.wikipedia.org/wiki/Memcached) holds whole chunks, keyed by their IDs or hashes. Block servers check this cache before reading from cloud storage.

$$\text{144GB} / \text{4MB per chunk} \approx 36\text{K chunks per cache server}$$

**Which replacement policy fits?** When the cache is full, we must evict a chunk to admit a hotter one. Least Recently Used (LRU) is a reasonable policy: discard the chunk that has gone unused the longest. A chunk is requested most soon after it changes, and its popularity fades with age.

Caching chunks is safe because a chunk's contents never change; a modified chunk gets a new hash. So a cached entry can never become stale. We can also put a similar cache in front of the Metadata Database.

---

### Load balancing

Load balancers belong in two places: between clients and block servers, and between clients and metadata servers. A simple round-robin balancer works initially by distributing requests equally and removing dead servers from rotation. However, it ignores actual server load. A smarter balancer queries servers periodically about their load and adjusts traffic accordingly.

---

### Security, permissions, and file sharing

Users can share files or make them public, so privacy is a primary concern. We store each file's permissions in the Metadata Database. Before serving a file, the service checks that record to decide who may view or modify it.

---

## Step 7: Bottlenecks and Failure Points

The interviewer does not expect this design to be limitless. They expect you to know where it ends.

- **Metadata Database dependency:** Every sync passes through the Metadata Database. If it is unavailable, no device can commit a change or learn about one. Its partitions and replicas deserve as much attention as the file storage.
- **Open connection capacity limit:** Long polling keeps around a million connections open at once. Servers and load balancers must be sized for simultaneous open requests, not just completed ones.
- **Offline Response Queue accumulation:** Response Queues grow while a device stays offline. Weeks of pending notifications accumulate, and the queue service must store all of them until the device returns.
- **In-line deduplication bottleneck:** In-line deduplication runs on the upload path. Every uploaded chunk waits for a hash lookup. If that lookup becomes slow, every upload in the system becomes slow with it.

## Where AI Fits in This Design

After the main design, interviewers often ask one more question: where would AI fit in this system?

For a file store, the fit is **search that understands meaning**. Users forget file names. They remember that a document was about a lease, or taxes, or a job offer. To serve that, compute an **embedding** for each file: a list of numbers that captures what the content means. Files about similar things get similar numbers. A search for "rental contract" then finds the lease, whatever its file name is. For scanned documents, optical character recognition (OCR) reads the printed text inside the image and feeds it into the same index.

The design already provides the trigger. The Synchronization Service knows the moment a file changes, and the message queues already carry those notifications. A background worker subscribes to them, computes the embedding for the changed file, and writes it to a search index beside the Metadata Database. The work happens once per file change, never per search, and the sync path is never blocked.

Say the key property out loud: **the index is derived data**. It is built from the files, so losing it loses nothing. Rebuild it by re-reading the files. The metadata and the chunks remain the only source of truth.

> [!TIP]
> **In the interview:** Spend your time on the client's four parts and on the synchronization path. The requirements, the estimates, and the API together should take about ten minutes. Two moments give the interviewer the most information:
> 1. Explaining that chunking plus hashing turns file sync into chunk sync (only changed chunks move, and duplicate chunks are stored once).
> 2. Using the one million open connections to justify long polling and to size the servers.
> If you have time left, post-process versus in-line deduplication is the follow-up you are most likely to be asked.

## Key Takeaway

Dropbox is a metadata and synchronization problem more than a storage problem. Split every file into 4MB chunks and hash each chunk. Sync then moves only changed chunks, retries only failed chunks, and stores duplicate chunks once. Keep a copy of the metadata on the client, so offline edits work and round trips are rare. Keep the metadata separate from the chunk storage, so each can scale on its own. Decouple millions of clients from the Synchronization Service with a global Request Queue and one Response Queue per subscribed device. Deliver changes through long polling rather than periodic polling. Cache hot chunks with LRU eviction, partition the metadata by hashing the FileID, and remember that round-robin balancing ignores server load.
