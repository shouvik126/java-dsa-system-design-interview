# Designing Pastebin

Every case study in this section follows the same seven-step methodology detailed in [System Design Interviews: A Step-by-Step Guide](./4.1-system-design-interviews-a-step-by-step-guide.md) and constructs its architecture using components from the [System Design Master Template](./4.2-system-design-master-template.md).

---

## 1. What is Pastebin?

Pastebin-like services allow users to store plain text blocks or source code snippets over the web and generate unique access URLs for the uploaded data. These services enable rapid text sharing across networks by sending a compact link instead of transmitting large text payloads directly.

A Pastebin service performs two primary operations:
1. Storing textual content uploaded by a user and returning a unique access URL.
2. Serving the stored text snippet to any client accessing that unique URL.

Pastebin is commonly used to share code snippets, log files, configuration blocks, or debugging traces across development teams and online forums.

---

## 2. Requirements and Goals of the System

> [!TIP]
> Clarify scope at the start of the interview. Establish exact limits on text payload size, URL customization, retention policies, and API availability.

### Functional Requirements
1. **Paste Upload:** Users can upload plain text data and receive a unique, generated access URL.
2. **Text-Only Support:** Uploads are restricted strictly to textual data (code, logs, config).
3. **Link & Data Expiration:** Pastes automatically expire after a default retention period; users can optionally set a custom expiration timestamp during creation.
4. **Custom Aliases:** Users can optionally specify a custom URL alias for their paste.

### Non-Functional Requirements
1. **High Durability:** Once a paste is successfully uploaded, its contents must never be lost or corrupted.
2. **High Availability:** The service must maintain high uptime so shared links remain continuously accessible.
3. **Ultra-Low Read Latency:** Users must be able to view paste contents in real-time with minimal retrieval delay.
4. **Non-Guessable Keys:** Generated short URLs must be unpredictable to prevent unauthorized enumeration of pastes.

### Extended (Secondary) Requirements
* **Access Analytics:** Track click count telemetry and view statistics for uploaded pastes.
* **REST API Support:** Provide programmatic REST endpoints for external tools and CLI integrations.

---

## 3. Design Considerations

While Pastebin shares architectural similarities with a URL shortener, key differences require distinct design considerations:

1. **Payload Size Limit:** Unlike URL shorteners (which handle tiny text URLs), Pastebin stores full text bodies. To prevent denial-of-service (DoS) abuse and storage exhaustion, single paste uploads are capped at **10 MB**.
2. **Custom URL Constraints:** Custom aliases are supported, but maximum length boundaries (e.g., 16 characters) are enforced to maintain consistent database column sizing and index efficiency.

---

## 4. Capacity Estimation and Constraints

Pastebin is a **read-heavy** system. Assume a **5:1 read-to-write ratio** (5 reads for every 1 new paste created).

### Traffic Estimates
Assuming 1 million new pastes per day and 5 million reads per day (5:1 ratio):

```text
1M / (24 hours * 3600 seconds)   = ~12 pastes per second
5M / (24 hours * 3600 seconds)   = ~58 reads per second
```

### Storage Estimates
While the maximum upload size limit is 10 MB, typical paste payloads (source code, logs, configs) average 10 KB.

```text
1M x 10 KB                     = 10 GB per day
10 GB x 365 days x 10 years    = 36.5 TB storage
1M x 365 days x 10 years       = 3.65 billion pastes in 10 years
```

#### Key Space & Memory Sizing:
Using Base64 encoding (`[A-Z, a-z, 0-9, ., -]`) with a 6-character key string:

```text
64^6                           = ~68.7 billion unique keys
3.65 billion x 6 bytes         = ~22 GB key index storage
36.5 TB / 0.70 (70% margin)    = ~51.4 TB allocated storage capacity
```

### Bandwidth Estimates

```text
12 writes x 10 KB               = ~120 KB per second in
58 reads x 10 KB                = ~0.6 MB per second out
```

### Memory Cache Estimates
Applying the 80/20 Pareto principle (caching the top 20% of hot pastes generating 80% of read traffic):

```text
5 million read requests per day
0.20 x 5 million x 10 KB        = ~10 GB RAM
```

## 5. System APIs

The service exposes REST endpoints for creating, retrieving, and deleting pastes.

### 1. Create Paste Endpoint
`POST /api/v1/pastes`

**Parameters:**
* `api_dev_key` *(string)*: Developer API key for authentication and rate-limiting quota enforcement.
* `paste_data` *(string)*: Raw text content of the paste.
* `custom_url` *(string, optional)*: Custom short URL alias requested by the user.
* `user_name` *(string, optional)*: Optional account username.
* `paste_name` *(string, optional)*: Optional title/name for the paste.
* `expire_date` *(string, optional)*: Expiration timestamp (ISO 8601).

**Response (201 Created):**
Returns the generated paste access URL string (e.g., `https://pastebin.com/aB3x9Z`), or an error code on failure.

### 2. Retrieve Paste Endpoint
`GET /api/v1/pastes/{api_paste_key}`

**Parameters:**
* `api_paste_key` *(string)*: The unique short key identifying the paste.

**Response (200 OK):**
Returns the raw text payload of the paste.

### 3. Delete Paste Endpoint
`DELETE /api/v1/pastes/{api_paste_key}`

**Parameters:**
* `api_dev_key` *(string)*: API key of the paste owner.
* `api_paste_key` *(string)*: Key of the paste to delete.

**Response (200 OK):**
Returns `true` on successful deletion; `false` otherwise.

## 6. Database Design

Key characteristics of Pastebin storage:
* Billions of records over time.
* Metadata objects are small (< 1 KB per record).
* Paste content objects can be medium-sized (up to 10 MB).
* Minimal relational complexity (a paste belongs to an optional user).
* Heavily read-oriented workload.

![Pastebin Database Schema](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.4-pastebin-db-schema.png)
*Database schema separating paste metadata (with external content object references) from user account data.*

### Database Schema Structure

#### `Pastes` Table
| Column Name | Type | Description |
| :--- | :--- | :--- |
| `URLHash` | `VARCHAR(16)` | Primary Key. The short key alias (e.g., `aB3x9Z`) |
| `ContentKey` | `VARCHAR(512)` | Pointer reference URI to the raw text file in Object Storage |
| `ExpirationDate` | `DATETIME` | Expiration timestamp |
| `CreationDate` | `DATETIME` | Timestamp when the paste was created |
| `UserID` | `INT` | Foreign key referencing the creator's `UserID` |

#### `Users` Table
| Column Name | Type | Description |
| :--- | :--- | :--- |
| `UserID` | `INT` | Primary Key. Auto-incremented user identifier |
| `Name` | `VARCHAR(64)` | User's full name |
| `Email` | `VARCHAR(512)` | User's email address |
| `CreationDate` | `DATETIME` | Account creation timestamp |
| `LastLogin` | `DATETIME` | Last login timestamp |

> [!IMPORTANT]
> The `ContentKey` column holds an S3 object pointer rather than raw text. Storing multi-megabyte text payloads directly inside relational/NoSQL table rows degrades database buffer pool efficiency and index performance.

## 7. High-Level Design

The system separates metadata management from raw text storage.

![High Level Design Architecture](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.4-pastebin-high-level-design.png)
*High-level architecture decoupling metadata storage from S3 object storage.*

1. **Application Layer:** Handles client HTTP requests, enforces rate-limiting, interacts with key generation logic, and routes reads/writes to storage tiers.
2. **Metadata Storage:** A NoSQL Key-Value Store or Relational DB storing small `Pastes` metadata records.
3. **Object Storage:** An Object Store (e.g., Amazon S3, Google Cloud Storage) storing the actual raw text payloads.

Decoupling metadata from file contents allows each storage tier to scale independently based on throughput and disk volume needs.

## 8. Component Design

![Detailed Component Architecture](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.4-pastebin-component-design.png)
*Detailed component design for Pastebin including KGS, Redis cache, object storage, and load balancers.*

### A. Application Layer Processing

#### Handling Write Requests:
1. When a paste creation request arrives, the Application Server requests a unique 6-character key.
2. If the user did not provide a custom alias, the server fetches a key from the **Key Generation Service (KGS)**.
3. The server writes the raw text body to **Object Storage (S3)**, receiving a unique `ContentKey` URI.
4. The server writes the metadata record (`URLHash`, `ContentKey`, `UserID`, `ExpirationDate`) to the **Metadata Database**.
5. Upon successful insertion, the server returns the short URL access link to the client.

#### Key Generation Handling (KGS):
* Generating random keys on demand during a write request can cause database collision checks and retry loops.
* **KGS Solution:** A background Key Generation Service pre-computes unique 6-character Base64 keys offline and stores them in an unused key pool. When a write request arrives, the application server immediately retrieves a pre-generated key with zero collision latency.
* **Server Failover & Buffering:** KGS pre-allocates bulk key blocks to application servers in RAM. If an app server crashes holding unspent keys, those keys are discarded. With 68.7 billion available 6-character keys, minor key loss is acceptable compared to the overhead of distributed locks.

#### Handling Read Requests:
1. Upon receiving `GET /api/v1/pastes/{api_paste_key}`, the Application Server checks the **In-Memory Cache (Redis)**.
2. On a cache hit, the server returns the cached text payload immediately.
3. On a cache miss, the server queries the **Metadata Database** for `api_paste_key`.
4. If found, it fetches the raw text from **Object Storage** using `ContentKey`, populates the cache, and returns the payload.
5. If the key is missing or expired, it returns an error code (`HTTP 404` or `HTTP 410`).

---

### B. Datastore Layer

1. **Metadata Database:** A Key-Value/Wide-Column Store (e.g., Cassandra, DynamoDB) or RDBMS (PostgreSQL) storing metadata records. NoSQL is ideal due to simple primary key lookups without multi-table joins.
2. **Object Storage:** Amazon S3 or Google Cloud Storage storing raw text files. S3 provides near-infinite storage scalability, high durability ($99.999999999\%$), and cost-effective cold storage options.

Expired pastes must be removed to free up storage space.

## 10. Data Partitioning and Replication

Storing 51.4 TB of data and handling read throughput requires horizontal partitioning.

* **Consistent Hashing by `URLHash`:** Partitions metadata and object storage references evenly across database nodes.
* **Replication:** Uses Primary-Replica replication to maintain high availability and read scalability.

For in-depth partitioning strategies, refer to [Designing a URL Shortening Service like TinyURL](./4.3-designing-a-url-shortening-service-like-tinyurl.md#4-database-partitioning--replication).

---

## 11. Cache and Load Balancer

* **Redis Cache:** Positions an in-memory cache in front of the datastore, caching 10 GB of hot pastes (20% working set under LRU eviction policy).
* **Load Balancers:** Positioned at the edge and between application servers and storage layers to distribute QPS evenly and handle server health checks.

For complete caching and load balancing mechanics, refer to [Designing a URL Shortening Service like TinyURL](./4.3-designing-a-url-shortening-service-like-tinyurl.md#3-caching-strategy).

---

## 12. Security and Permissions

* **Rate Limiting:** API Developer Keys (`api_dev_key`) enforce rate limits per account and per IP address at the API Gateway to prevent service abuse.
* **Access Control:** Private pastes store visibility flags and authorized user IDs within the metadata record, checked synchronously before fetching text from Object Storage.

For additional security patterns, refer to [Designing a URL Shortening Service like TinyURL](./4.3-designing-a-url-shortening-service-like-tinyurl.md#6-abuse-and-access-control).

## Summary & Key Takeaways

| Metric / Layer | Choice | Rationale |
| :--- | :--- | :--- |
| **Traffic Profile** | 12 Write QPS / 58 Read QPS | 5:1 Read-heavy system |
| **Max Payload Size** | 10 MB per paste | Prevents DoS storage abuse; 10 KB average paste size |
| **10-Year Storage** | 36.5 TB Raw (51.4 TB Allocated) | 3.65 billion pastes stored across S3 and NoSQL metadata store |
| **Key Encoding** | 6 Base64 Characters ($64^6 =$ 68.7 Billion) | Provides sufficient keyspace headroom for 3.65B records |
| **Metadata DB** | Key-Value NoSQL (Cassandra/DynamoDB) | $O(1)$ lookup performance by `URLHash` without joins |
| **Payload Storage** | Object Storage (Amazon S3) | Keeps database rows small while offering high durability and scale |
| **Key Generation** | Offline KGS (Key Generation Service) | Eliminates hash collisions and DB retries from write path |
