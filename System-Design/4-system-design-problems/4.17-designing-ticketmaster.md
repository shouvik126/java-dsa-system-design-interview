## What is an online movie ticket booking system?

An online movie ticket booking platform allows consumers to explore currently running films, inspect cinema locations and showtimes, examine interactive seating maps, and purchase reserved theater seats digitally from mobile or desktop devices. Prominent commercial services operating in this domain include **Ticketmaster**, **BookMyShow**, and **Fandango**.

```
                        ONLINE TICKET BOOKING WORKFLOW
 ┌──────────────┐     1. Search Movies & Shows    ┌─────────────────────────┐
 │              │ ──────────────────────────────> │                         │
 │   Customer   │     2. Select Seats & Hold      │   Ticketmaster System   │
 │ (Web/Mobile) │ ──────────────────────────────> │   (API & DB Tier)       │
 │              │ <────────────────────────────── │                         │
 └──────────────┘     3. 5-Min Hold Confirmed     └─────────────────────────┘
        │                                                      │
        │             4. Submit Payment                        │ 5. Lock DB Seat
        └──────────────────────────────────────────────────────► & Confirm Ticket
```

From an architectural standpoint, the core engineering difficulty of a ticket reservation platform does **not** stem from raw data volume. Storing information for thousands of cinemas and millions of seats requires only modest disk storage. Instead, the central challenge lies in **extreme write concurrency over non-fungible inventory**:

> **The Core Problem:** Thousands of users frequently attempt to purchase the exact same physical seat (e.g., Seat 12 in Row F for a blockbuster release) at the exact same millisecond. Because a physical seat can be sold to only one customer, the architecture must guarantee **strict isolation** and **zero overbooking**, while providing temporary seat holds and fair queueing for waiting users.

If you have never booked tickets through a platform like Ticketmaster or BookMyShow, take a moment to visit one. Select a showtime, choose a seat, and observe the **countdown timer** holding your seat during checkout. Understanding this temporary hold behavior provides crucial practical context for the architecture we will construct in this chapter.

## Step 1: Clarify the Requirements

Always begin a system design interview by clarifying requirements with your interviewer. Setting concrete boundaries early ensures that your architecture directly addresses the intended scope without wasting time on irrelevant features.

### Functional Requirements

1. **City & Cinema Directory**: The platform lists cities containing affiliate cinema halls.
2. **Movie & Show Schedule Discovery**: Selecting a city displays all released movies currently playing in that city. Selecting a movie reveals affiliate cinema halls, show dates, and showtimes.
3. **Interactive Seating Arrangement**: Selecting a specific showtime renders an interactive hall layout displaying available vs. reserved/booked seats.
4. **Seat Selection & Maximum Limit**: Customers can select specific seats for booking. To prevent inventory hoarding and scalping abuse, a single transaction can reserve a maximum of **10 seats**.
5. **Temporary Reservation Hold**: When a user selects available seats, the system holds them under a temporary lock for **5 minutes** while the user completes payment.
6. **Waitlisting & Queue Management**: If requested seats are currently held by another buyer, waiting users can join a waitlist. If the hold expires without payment, waiting customers are notified.
7. **Fair First-Come, First-Served (FCFS) Processing**: Customers waiting for freed seat inventory must be served strictly in order of arrival time.

### Non-Functional Requirements

1. **High Concurrency & Zero Overbooking**: Thousands of concurrent users may attempt to reserve the same seat simultaneously. The platform must guarantee absolute atomicity—**no seat can ever be double-booked**.
2. **Financial ACID Compliance**: Ticket purchasing involves financial transactions. Database operations must adhere strictly to ACID properties (Atomicity, Consistency, Isolation, Durability).
3. **Low Latency Browsing vs. Strong Consistency Booking**: Show browsing and search queries must return within milliseconds (< 100 ms), whereas booking operations prioritize strong consistency over raw speed.
4. **High Availability during Spikes**: The system must withstand intense traffic spikes during major movie releases or high-demand concert ticket launches without crashing or corrupting state.

### Assumptions and Out-of-Scope Constraints

* **Authentication**: User authentication is assumed to be handled upstream by an identity service; sessions are tracked via unique Session IDs.
* **All-or-Nothing Booking**: Partial bookings are disallowed. If a user requests 4 seats, the system grants either all 4 seats or 0 seats.
* **Payment Gateways**: Third-party payment gateway integration (e.g., Stripe, PayPal) is treated as an external black box API call.

## Step 2: Estimate the Scale

Back-of-the-envelope calculations establish whether our architecture is constrained by network bandwidth, raw storage volume, or database write IOPS.

### System Traffic Assumptions

* **Monthly Page Views**: 3 billion page views per month.
* **Monthly Ticket Purchases**: 10 million tickets sold per month.
* **Time Simplification**: Assume 1 day $\approx$ 100,000 seconds to streamline division.

### Traffic Throughput (QPS)

$$\text{Daily Page Views} = \frac{3,000,000,000 \text{ views}}{30 \text{ days}} = 100,000,000 \text{ views/day}$$

$$\text{Read Throughput (QPS)} = \frac{100,000,000 \text{ views}}{100,000 \text{ seconds}} = 1,000 \text{ read QPS}$$

$$\text{Daily Ticket Purchases} = \frac{10,000,000 \text{ tickets}}{30 \text{ days}} \approx 333,333 \text{ tickets/day}$$

$$\text{Booking Write Throughput (QPS)} = \frac{333,333 \text{ tickets}}{100,000 \text{ seconds}} \approx 3.33 \text{ write QPS}$$

> **Read-to-Write Ratio Analysis:**
> For every 1 ticket sold, customers execute roughly 300 page view requests. The platform is **heavily read-dominated** for movie search and showtime browsing. While baseline write traffic appears low ($\approx 3.33$ QPS average), write traffic exhibits **extreme burstiness**: when tickets for a popular show go live, thousands of write requests target the exact same database rows simultaneously.

### Storage Capacity Requirements

Assume the platform operates across **500 cities**, each city hosting **10 cinemas**, each cinema containing **2,000 seats**, with each hall running **2 shows per day**:

$$\text{Daily Seat Records} = 500 \times 10 \times 2,000 \times 2 = 20,000,000 \text{ seat records/day}$$

Each seat booking record requires approximately **50 bytes** (IDs, status flag, timestamp, show reference). Movie and theater metadata require an additional **50 bytes** per seat record:

$$\text{Daily Data Volume} = 20,000,000 \text{ records} \times 100 \text{ bytes} = 2,000,000,000 \text{ bytes} = 2 \text{ GB/day}$$

$$\text{5-Year Storage Capacity} = 2 \text{ GB/day} \times 365 \text{ days} \times 5 \text{ years} = 3.65 \text{ TB}$$

### Scale Insights & Architectural Takeaways

1. **Read Traffic (1,000 QPS baseline)**: Movie catalogs, cinema schedules, and pricing structures rarely change during a day. Browsing traffic can be aggressively cached using distributed memory grids (Redis/Memcached), shielding the database.
2. **Storage Volume (3.65 TB over 5 years)**: Storage requirements are modest and fit comfortably on modern enterprise relational databases. Disk capacity is **not** the engineering bottleneck.
3. **The Concurrency Bottleneck**: The fundamental engineering challenge is managing concurrent write lock contention on small clusters of relational database rows representing specific theater seats.

## Step 3: Define the API

We expose platform capabilities using structured RESTful HTTP endpoints. Two core operations dominate the workflow: searching for movie showtimes and reserving seats.

### 1. Search Movies and Showtimes (`SearchMovies`)

Retrieves available movies and corresponding showtimes based on geographic or text search filters.

```http
GET /api/v1/movies/search?city=NewYork&keyword=Batman&results_per_page=20
```

#### Request Parameters

| Parameter | Type | Required | Description |
| :--- | :--- | :--- | :--- |
| `api_dev_key` | `string` | Yes | Developer API key for rate limiting and telemetry tracking. |
| `keyword` | `string` | No | Search phrase matching movie title or description. |
| `city` | `string` | No | Target city filter (e.g., `"New York"`). |
| `lat_long` | `string` | No | Latitude/Longitude coordinates for spatial proximity search. |
| `radius` | `number` | No | Search radius in kilometers around `lat_long`. |
| `start_datetime` | `string` | No | Lower bound ISO-8601 timestamp for showtimes. |
| `end_datetime` | `string` | No | Upper bound ISO-8601 timestamp for showtimes. |
| `results_per_page`| `number` | No | Pagination limit (Default: 20, Maximum: 30). |
| `sorting_order` | `string` | No | Sorting criteria (e.g., `'date,asc'`, `'distance,asc'`). |

#### Response JSON Payload

```json
[
  {
    "MovieID": 401,
    "ShowID": 8902,
    "Title": "Inception: Special Edition",
    "Description": "A thief who steals corporate secrets through dream-sharing technology...",
    "Duration": 148,

    "Language": "English",

      {

```

> **Design Note:** The `SearchMovies` response intentionally returns general seat category availability (`"Available"`, `"Almost Full"`, `"Full"`) rather than full graphical seat maps. Fetching granular seat states across hundreds of search results would inflate network payloads and compromise latency. Granular seat layouts are fetched only when a user selects a specific showtime.

### 2. Reserve Seats (`ReserveSeats`)

Attempts to lock a list of specific physical seats for a 5-minute hold window.

```http
POST /api/v1/reservations/reserve
Content-Type: application/json
```

#### Request JSON Body

```json
{
  "api_dev_key": "dev_key_sec_9981",
  "session_id": "sess_8830192_user_44",
  "movie_id": "401",
  "show_id": "8902",
  "seats_to_reserve": [54, 55, 56]
}
```

#### Response JSON Payload

```json
{
  "status": "Reservation Successful",
  "booking_id": "bk_99012384",
  "reservation_expiry": "2026-10-15T19:05:00Z",
  "message": "Seats locked for 5 minutes. Please complete payment before expiry."
}
```

#### Status Return Codes

* `"Reservation Successful"`: The requested seats were successfully locked in the database under a 5-minute hold.
* `"Reservation Failed - Show Full"`: All seats in the hall are permanently booked.
* `"Reservation Failed - Seats Held, Retry or Wait"`: The requested seats are currently held by another user undergoing checkout. The client can enter a waiting queue or choose alternate seats.

## Step 4: Define the Data Model

### Selecting the Database Engine: SQL vs. NoSQL

Selecting the appropriate database paradigm is critical for system correctness. In previous case studies like TinyURL, a NoSQL key-value store was chosen because queries were simple single-key lookups without complex transactional constraints.

For a movie ticket reservation platform, **a Relational Database Management System (RDBMS) adhering to ACID properties is mandatory**:

1. **Multi-Table Transactional Integrity**: Reserving a ticket atomically updates the seat inventory status (`Show_Seat`), creates a reservation record (`Booking`), and generates a pending financial ledger entry (`Payment`). If any single step fails, all mutations must roll back seamlessly.
2. **Isolation Guarantees**: Relational databases support strict transaction isolation levels (such as **Serializable** isolation with row-level locks), ensuring that two concurrent writes competing for the exact same seat row execute serially.

### Relational Database Schema

The database design comprises 10 primary entities, separated into static metadata tables and dynamic operational tables:

### Table Definitions & Key Relationships

| Table Name | Primary Key | Foreign Keys | Key Attributes & Description |
| :--- | :--- | :--- | :--- |
| **`City`** | `CityID` | None | `Name`, `State`, `ZipCode`. Physical region tracking. |
| **`Cinema`** | `CinemaID` | `CityID` | `Name`, `Address`, `TotalHalls`. Theater physical venues. |
| **`Cinema_Hall`** | `CinemaHallID` | `CinemaID` | `HallName`, `TotalSeats`. Specific projection rooms inside a cinema. |
| **`Cinema_Seat`** | `CinemaSeatID` | `CinemaHallID` | `SeatNumber`, `Type` (Regular/VIP). Static physical seat catalog. |
| **`Movie`** | `MovieID` | None | `Title`, `Description`, `Duration`, `Genre`, `Language`. Catalog of films. |
| **`Show`** | `ShowID` | `MovieID`, `CinemaHallID` | `Date`, `StartTime`, `EndTime`. Individual movie screening events. |
| **`Show_Seat`** | `ShowSeatID` | `CinemaSeatID`, `ShowID`, `BookingID` | `Status` (0=Free, 1=Reserved, 2=Booked), `Price`. Maps physical seats to a show. |
| **`Booking`** | `BookingID` | `ShowID`, `UserID` | `NumberOfSeats`, `Timestamp`, `Status` (1=Reserved, 2=Booked, 3=Expired). Holds reservation metadata. |
| **`User`** | `UserID` | None | `Name`, `Email`, `Phone`. Customer account profiles. |
| **`Payment`** | `PaymentID` | `BookingID` | `Amount`, `Timestamp`, `Method`, `TxnRemoteID`. Ledger of financial transactions. |

### Operational Deep Dive into Key Tables

1. **`Show_Seat` Table**: Contains one record per physical seat for every show. The `Status` column indicates seat availability: `0 (Free)`, `1 (Reserved under hold)`, or `2 (Permanently Booked)`. Pricing is attached here so that seat prices can vary dynamically per showtime (e.g., matinee discounts vs. prime weekend screenings).
2. **`Booking` Table**: Represents an active or completed reservation transaction. When a hold is initiated, a `Booking` row is inserted with `Status = 1 (Reserved)` and marked with a creation `Timestamp`. If payment succeeds within 5 minutes, `Status` moves to `2 (Booked)`. If the timer expires, `Status` transitions to `3 (Expired)` and seats are released back to `Status = 0 (Free)`.

> **Schema Design Note:** The total count of free seats is **not** stored as an explicit integer column in the `Show` table. Incrementing and decrementing a shared counter column under high concurrency creates severe database row-lock contention. Instead, available seat counts are calculated dynamically (`SELECT COUNT(*) FROM Show_Seat WHERE ShowID = ? AND Status = 0`) and cached in memory.

## Step 5: Draw the High-Level Design

The system architecture separates read-heavy browsing traffic from write-heavy transactional reservation traffic:

1. **Browsing Path (Read Heavy)**: Served through aggressive distributed cache layers (Redis/Memcached) backed by read replicas.
2. **Reservation Path (Write Heavy & Transactional)**: Routed directly to application servers executing ACID database transactions, supported by two specialized in-memory daemon services managing temporary holds and waiting queues.

## Step 6: Go Deep

### The booking workflow

The ticket purchasing workflow follows a structured progression from browsing to confirmation:

![The reservation workflow](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.17-ticketmaster-reservation-workflow.svg)

```
                          DETAILED SEAT RESERVATION WORKFLOW
                          
   [ User Searches Movie ] ──> [ Selects City & Cinema ] ──> [ Selects Showtime ]
                                                                     │
                                                                     ▼
                                                          [ Inspects Seat Map ]
                                                                     │
                                                                     ▼
                                                          [ Selects Seat IDs ]
                                                                     │
                                                                     ▼
                                                          [ Submit Reservation ]
                                                                     │
                                          ┌──────────────────────────┴──────────────────────────┐
                                          │                                                     │
                                          ▼                                                     ▼
                               (Seats Available?)                                     (Seats Occupied?)
                                          │                                                     │
                                          ├── YES ──> [ 5-Min Database Lock & Hold Created ]    ├── YES ──> [ Show Full Error ]
                                          │           [ Start Client 5-Min Countdown ]          │           Return to Seat Map
                                          │                          │                          │
                                          │                          ▼                          └── HELD ─> [ Enter Waitlist Queue ]
                                          │                 (Payment Successful?)                           (Long Polling Notification)
                                          │                          │
                                          │                          ├── YES ──> [ Status = BOOKED (2) ]
                                          │                          │           [ Ticket Issued ]
                                          │                          │
                                          │                          └── NO ───> [ Timer Expires ]
                                          │                                      [ Status = EXPIRED (3) ]
                                          │                                      [ Notify Waiting Queue ]
```

1. **Discovery & Selection**: The customer searches for a movie, selects a cinema showtime, and inspects the theater seating map.
2. **Reservation Request**: The user selects specific seat IDs (e.g., Seats 54, 55, 56) and submits a reserve request.
3. **Reservation Execution Branching**:
   * **Case A: Seats Available**: The system atomically locks the requested seat rows in the database, sets their status to `Reserved (1)`, registers a `Booking` entry, and starts a **5-minute hold timer**.
   * **Case B: Show Fully Booked**: The system returns a rejection message (`"Show Full"`), prompting the user to explore alternative showtimes.
   * **Case C: Seats Held by Others**: If the requested seats are held under a temporary hold by another buyer undergoing checkout, the system invites the user to enter a **waiting queue**.
4. **Checkout Completion**:
   * If payment succeeds within 5 minutes, `Booking` status transitions to `Booked (2)`, `Show_Seat` status becomes `2`, and digital tickets are issued.
   * If the 5-minute timer expires without payment, the hold is voided, seat statuses revert to `Free (0)`, and waiting customers are notified immediately.

> **Why a 5-Minute Hold Window?**
> A hold duration must balance user convenience against operational throughput. A long hold window (e.g., 20 minutes) gives buyers extra time to locate credit cards, but leaves inventory locked away from other buyers if abandoned. A short hold window (e.g., 1 minute) rushes users, leading to payment failures. Five minutes represents an optimal trade-off in commercial ticketing.

### Tracking reservations and waiting users

Managing unconfirmed seat holds and waiting queues in a database alone introduces heavy polling overhead. To maintain responsiveness without saturating the database, we deploy two background daemon services:

1. **`ActiveReservationsService`**: Tracks active unconfirmed seat holds in memory and monitors hold expiration timestamps.
2. **`WaitingUsersService`**: Tracks waiting customers queued for held seats and notifies them when inventory frees up.

```
                           IN-MEMORY DAEMON ARCHITECTURE
                           
                 HASHTABLE (Key = ShowID, Value = LinkedHashMap)
                 
   ShowID: 8902 ──> LinkedHashMap [ Insertion & Expiry Ordered ]
                    ┌──────────────────────────────────────────────────────────┐
                    │ Head (Oldest Hold)  ──>  BookingID: 101  (Expires T+5s)  │
                    │                          BookingID: 102  (Expires T+40s) │
                    │ Tail (Newest Hold)  ──>  BookingID: 103  (Expires T+4m)  │
                    └──────────────────────────────────────────────────────────┘
```

---

#### ActiveReservationsService

The `ActiveReservationsService` retains active seat holds in memory using a combined data structure: a primary **`HashTable`** mapped to nested **`LinkedHashMap`** collections:

![ActiveReservationsService keeping track of all active reservations](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.17-ticketmaster-active-reservations-service.svg)

```java
// ShowID -> LinkedHashMap<BookingID, ExpiryTimestamp>
Map<Long, LinkedHashMap<Long, Long>> activeHoldsMap = new ConcurrentHashMap<>();
```

#### Data Structure Rationale

* **`HashTable` (Outer Map)**: Keys are indexed by `ShowID`. This provides $O(1)$ time complexity when fetching or mutating holds for a specific showtime.
* **`LinkedHashMap` (Inner Collection)**: Retains key-value pairs (`BookingID` $\rightarrow$ `ExpiryTimestamp`) while maintaining explicit **insertion order**.
  * **$O(1)$ Direct Cancellation/Completion**: When a customer completes payment or cancels, the system looks up the `BookingID` key directly and removes it in $O(1)$ time.
  * **$O(1)$ Immediate Expiration Monitoring**: Because elements are inserted in chronological sequence, **the head of the `LinkedHashMap` always points to the oldest hold (the next hold set to expire)**.

```
                  ActiveReservationsService METRIC ADVANTAGE
                  
  Database Polling Strategy (Inefficient)      In-Memory LinkedHashMap (Optimal)
  ---------------------------------------      ----------------------------------
  - Executes periodic SQL UPDATE queries.      - Head node ALWAYS contains next
  - Scans DB indexes continuously.               expiring hold.
  - High disk IOPS under heavy load.           - Thread sleeps until exact expiry
  - Expiry tied to polling frequency.            timestamp, eliminating overhead.
```

When a hold expires, `ActiveReservationsService`:
1. Mutates database records: marks `Booking` status as `Expired (3)` and reverts `Show_Seat` status to `Free (0)`.
2. Evicts the `BookingID` from the in-memory `LinkedHashMap`.
3. Dispatches an event trigger to `WaitingUsersService` to process queued customers.

---

#### WaitingUsersService

When a requested show is fully held, interested customers can join a waiting queue managed by `WaitingUsersService`.

```java
// ShowID -> LinkedHashMap<UserID, UserWaitRequest>
Map<Long, LinkedHashMap<Long, UserWaitRequest>> waitingQueueMap = new ConcurrentHashMap<>();
```

Like the hold tracking service, `WaitingUsersService` uses a `HashTable` indexed by `ShowID` containing a `LinkedHashMap` of waiting users. This structure guarantees strict **First-Come, First-Served (FCFS) fairness**: the head of the `LinkedHashMap` represents the customer who has waited longest.

#### Seat Allocation and Capacity Evaluation Logic

When `ActiveReservationsService` releases seats, `WaitingUsersService` evaluates the longest-waiting user at the head of the queue:

```
                    WAITING QUEUE SEAT ALLOCATION LOGIC
                    
   Freed Seats: 2 Seats Available
   
   Queue Head: User A (Needs 4 Seats)  ──>  Insufficient Capacity!
                                            Retain User A at Head of Queue.
                                            
   Next Queue: User B (Needs 2 Seats)  ──>  Match Found!
                                            Grant User B Seat Reservation Access.
```

> **Fairness & Partial Order Guarantee:**
> If User A (queue head) requires 4 seats, but only 2 seats were freed, **User A is not skipped or evicted**. User A retains their place at the head of the queue. `WaitingUsersService` inspects subsequent users (User B, needing 2 seats) to fill available capacity efficiently without assigning partial orders or compromising queue priority.

#### Push Notifications via Long Polling

Waiting clients maintain connection state with `WaitingUsersService` using **HTTP Long Polling**:

```
                       LONG POLLING COMMUNICATION PATTERN
                       
  Client Device                                            WaitingUsersService
        │                                                           │
        │ ─── 1. HTTP GET /api/v1/wait-status (Hold Open) ────────> │
        │                                                           │
        │                                              (Seats Become Available)
        │                                                           │
        │ <── 2. HTTP 200 OK Response (Notify: Choose Seats) ───────│
```

The client issues a long-polling request. The server holds the connection open until seats become available or the request times out. When inventory opens, the server instantly responds over the held connection, prompting the client UI to render the interactive seating chart.

### Reservation expiration

To keep the server-side hold timer and the client-side UI countdown clock aligned, the system incorporates a **5-second clock skew buffer**:

```
                       5-SECOND CLOCK SKEW BUFFER STRATEGY
                       
  Server Hold Timer : [==========================================] 5 Min + 5 Sec
  Client UI Display : [====================================] 5 Min 00 Sec
                                                           ▲
                                                           │
                                              Client Countdown Expires
```

* **Client UI Countdown**: Renders a 5-minute countdown clock (300 seconds).
* **Server-Side Hold Window**: Configured for 5 minutes plus 5 seconds (305 seconds).

> **Why the 5-Second Buffer Matters:**
> Network latency or client CPU drift can cause client and server clocks to fall out of sync. Without a buffer, a user submitting payment at second 299 might reach the server at second 301. If the server had already voided the hold, the user's credit card would be charged for seats that were just assigned to someone else. The 5-second buffer ensures the client timer *always* expires before the server voids the database hold.

### Concurrency: no two users get the same seat

The core challenge of this system is managing high-concurrency write contention when two users attempt to reserve the exact same seat at the exact same millisecond.

```
                           THE CONCURRENCY RACE CONDITION
                           
  User A Request (Seat 54) ────┐
                               ├──> [ Concurrent Database Writes ] ──> Overbooking Risk!
  User B Request (Seat 54) ────┘
```

To resolve race conditions reliably, we combine **SQL Database Isolation Levels** with **Row-Level Explicit Locking (`SELECT ... FOR UPDATE`)**.

#### SQL Isolation Levels Refresher

| Isolation Level | Dirty Reads | Non-Repeatable Reads | Phantom Reads | Performance Impact |
| :--- | :--- | :--- | :--- | :--- |
| **Read Uncommitted** | Allowed | Allowed | Allowed | Maximum Speed / Zero Safety |
| **Read Committed** | Prevented | Allowed | Allowed | High Speed / Baseline SQL |
| **Repeatable Read** | Prevented | Prevented | Allowed | Balanced |
| **Serializable** | Prevented | Prevented | Prevented | Strict Safety / Highest Contention |

* **Dirty Read**: A transaction reads uncommitted data written by a concurrent transaction that later rolls back.
* **Non-Repeatable Read**: Re-reading a row within a transaction returns modified column values because another transaction committed an update.
* **Phantom Read**: Re-running a range query returns newly inserted or deleted rows committed by another transaction.

#### Implementation: Transaction Isolation with Explicit Row Locking

To eliminate double-booking, seat reservation queries execute under **Serializable Isolation** using explicit row locking (`FOR UPDATE`):

```sql
-- Step 1: Set transaction isolation level
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;

-- Step 2: Begin explicit ACID transaction
BEGIN TRANSACTION;

-- Step 3: Query and acquire exclusive row locks on requested seats
-- Selects seats for ShowID = 8902 and SeatIDs (54, 55, 56) that are Free (Status = 0)
SELECT ShowSeatID, Status 
FROM Show_Seat WITH (UPDLOCK, ROWLOCK)
WHERE ShowID = 8902 
  AND CinemaSeatID IN (54, 55, 56) 
  AND Status = 0;

-- Step 4: Application logic verifies returned row count matches requested count (3 seats)
-- If count < 3, at least one seat was taken; ROLLBACK TRANSACTION and return failure.

-- Step 5: Update seat status to Reserved (1)
UPDATE Show_Seat 
SET Status = 1, BookingID = @generated_booking_id 
WHERE ShowID = 8902 
  AND CinemaSeatID IN (54, 55, 56);

-- Step 6: Insert pending booking entry
INSERT INTO Booking (BookingID, ShowID, UserID, NumberOfSeats, Status, Timestamp)
VALUES (@generated_booking_id, 8902, @current_user_id, 3, 1, CURRENT_TIMESTAMP);

-- Step 7: Commit transaction (releases database row locks)
COMMIT TRANSACTION;
```

#### How Row Locks Stop Double-Booking

When User A and User B concurrently attempt to reserve Seat 54:
1. User A's transaction executes `SELECT ... FOR UPDATE` first, placing an **exclusive write lock** on the `Show_Seat` row for Seat 54.
2. User B's transaction attempts to read Seat 54, but is forced to **block** until User A's transaction completes.
3. User A's transaction updates the status to `1 (Reserved)` and commits. The lock is released.
4. User B's transaction unblocks and executes its query. Because Seat 54 now has `Status = 1`, the query returns zero free rows.
5. User B's application layer detects the shortfall and returns a `"Reservation Failed"` message.

> **Critical Distinction: Database Lock vs. Application Hold:**
> The database row lock (`FOR UPDATE`) is held **only during the SQL transaction** (a few milliseconds). Once the transaction commits, database locks are released. The subsequent 5-minute hold is **not** an open database lock; it is represented by application state (`Status = 1` in the database and a tracked timer in `ActiveReservationsService`).

### Fault tolerance

```
                      SYSTEM FAULT TOLERANCE MATRIX
                      
  Component               Failure Mode             Recovery Strategy
  ----------------------  -----------------------  ---------------------------------------
  ActiveReservationsDaemon In-Memory Crash          Rebuild state from SQL `Booking` table
                                                   where `Status = 1`.
  WaitingUsersDaemon      In-Memory Queue Loss     Primary-Secondary replication (Active-
                                                   Passive sync).
  Database Primary        Hardware Crash           Automated Multi-AZ failover to Primary
                                                   Replica.
```

1. **Rebuilding `ActiveReservationsService` State**: If the server hosting `ActiveReservationsService` crashes, in-memory holds are lost. However, because hold records are committed to the persistent `Booking` database table (`Status = 1`), the daemon can rebuild its in-memory map on startup by running:
   ```sql
   SELECT BookingID, ShowID, Timestamp 
   FROM Booking 
   WHERE Status = 1;
   ```
2. **Protecting `WaitingUsersService` State**: Waiting queues exist only in memory to minimize database traffic. To prevent losing queues during node failures, `WaitingUsersService` instances operate in **Primary-Secondary pairs**. All queue insertions and evictions are logged to a secondary standby node via stream replication.
3. **Database High Availability**: Relational databases deploy Multi-AZ Primary-Secondary replication with continuous write-ahead logging (WAL). If the primary node fails, an automated failover promotes a secondary replica to primary status within seconds.

### Data partitioning

To scale write operations beyond a single database node, we apply **Database Sharding** and **Service Partitioning using Consistent Hashing**.

#### Database Partitioning: Partition by `ShowID` vs. `MovieID`

```
                        DATABASE SHARDING COMPARISON
                        
  Option 1: Partition by MovieID (POOR)       Option 2: Partition by ShowID (OPTIMAL)
  ------------------------------------       ---------------------------------------
  - All shows for a blockbuster sit on       - Shows for a movie are distributed
    a single database shard.                   across dozens of database shards.
  - Creates extreme HOTSPOT SHARDS.          - EVENLY DISTRIBUTES write throughput.
```

* **Partitioning by `MovieID` (Suboptimal)**: All screenings for a blockbuster film map to a single database shard. During a major release, 90% of global reservation traffic hits that single shard, creating a severe bottleneck.
* **Partitioning by `ShowID` (Optimal)**: A movie screening in Hall 3 on Friday at 7 PM has a distinct `ShowID` from a screening in Hall 1 on Saturday at 2 PM. Partitioning by `ShowID` spreads reservations across the database cluster, distributing write traffic evenly.

#### Service Partitioning via Consistent Hashing

Instances of `ActiveReservationsService` and `WaitingUsersService` are sharded across application servers using **Consistent Hashing** on `ShowID`:

```
                       CONSISTENT HASHING SERVICE ROUTING
                       
   ShowID: 8902 ──> [ Hash Function ] ──> Ring Position ──> App Server Cluster Node 3
```

All hold tracking and queue management for a given `ShowID` are routed deterministically to the same application server pair.

## Step 7: Bottlenecks and Failure Points

An experienced system designer must identify architectural limits and failure modes:

1. **Hotspot Contention on Popular Show Seats**: When thousands of users race for seats in a single hall, row-level locks force transactions to execute serially. If a transaction takes 10 ms, a single row can process at most 100 reservation attempts per second.
   * *Mitigation*: Keep SQL transactions minimal (only lock, update, and insert essential rows). Expose seat availability via cached memory grids to shed failed attempts before they reach the database.
2. **Third-Party Payment Gateway Delays**: If an external payment provider experiences elevated latency, users may spend several minutes waiting for confirmation while seats remain locked under hold.
   * *Mitigation*: Set strict timeout limits on external payment calls (e.g., 30 seconds). If a payment call times out, release the seat hold and prompt the user to retry.
3. **Volatile Waiting Queues**: Because waiting queues reside in memory, a double-node crash of both primary and secondary `WaitingUsersService` instances would drop waiting queue state.
   * *Mitigation*: Treat waiting queues as best-effort notifications. If state is lost, clients automatically re-query show seat maps when long polling connections reset.

## Where AI Fits in This Design

In high-demand ticketing platforms, the primary threat to availability is often not organic user traffic, but **scalping bots**:

```
                       AI BOT DETECTION ARCHITECTURE
                       
  Reservation Request ──> [ AI Fraud Classifier ] ──► Low Risk  ──> [ SQL Transaction ]
                                 │
                                 └──► High Risk ──> [ CAPTCHA Challenge / Block ]
```

### The Scalper Bot Attack Vector

Automated scripts run by ticket scalpers can launch thousands of concurrent reservation requests the instant sales open. These bots lock up high-demand seats using the 5-minute free hold without paying immediately. Scalpers then list those held tickets on secondary markets at inflated prices. If a secondary buyer purchases the ticket, the bot completes payment; if not, the hold is allowed to expire and another bot re-reserves the seat.

### Inline ML Fraud Classification

To block automated reservation attacks, an **Inline Machine Learning Bot Detection Model** is embedded directly into the API Gateway validation path:

1. **Feature Extraction**: As a `ReserveSeats` request arrives, the proxy extracts behavioral telemetry:
   * Mouse cursor movement patterns and touch dynamics on mobile clients.
   * Form completion speeds (bots fill form fields in milliseconds).
   * IP subnet reputation, device fingerprinting, and account age.
   * Historical hold-to-purchase ratios (scalper accounts hold many seats but convert very few).
2. **Real-Time Scoring (< 15 ms Budget)**: A lightweight tree model (e.g., XGBoost) evaluates the feature vector and outputs a fraud score ($0.0 - 1.0$).
3. **Adaptive Mitigation**:
   * **Low Risk (< 0.3)**: Request proceeds directly to the transactional reservation path.
   * **Medium Risk (0.3 - 0.7)**: Request is redirected to an interactive CAPTCHA challenge before attempting database holds.
   * **High Risk (> 0.7)**: Request is rejected immediately, preserving database lock throughput for genuine fans.

> **Architectural Guardrail:**
> The AI model handles identity verification and fraud prevention, but **never** makes concurrency or inventory decisions. Physical seat locking remains strictly managed by SQL ACID transactions and row-level locks.
