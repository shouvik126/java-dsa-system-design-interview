## Why Yelp or a Proximity Server?

A **Proximity Server** (also referred to as a Location-Based Service or Spatial Search Engine) is a specialized backend architecture built to discover points of interest—such as restaurants, cafes, theaters, gas stations, or retail stores—located within a specific geographic distance of a target user coordinate.

When a user opens an application like Yelp, Google Maps, or TripAdvisor, the client device transmits its current geographic coordinates `(latitude, longitude)`. The proximity service evaluates these coordinates against millions of registered venues and instantly returns all matching locations within a defined radius (e.g., 5 kilometers or 10 miles).

```
                   THE PROXIMITY SEARCH QUERY PATTERN
┌──────────────────────┐    Latitude, Longitude, Radius    ┌─────────────────────────┐
│     Client App       │ ────────────────────────────────> │    Proximity Server     │
│ (User at 37.77, -122)│ <───────────────────────────────  │  (Spatial Index Lookups)│
└──────────────────────┘    Ranked Nearby Places JSON      └─────────────────────────┘
```

If you have not interacted with Yelp or a similar mapping platform recently, take a moment to perform a few location-based queries online. Filter restaurants by rating, search for nearby coffee shops, and adjust search boundaries. Experiencing how users interact with real-time location filtering will provide practical context for the engineering choices made throughout this case study.

### The Core Engineering Challenge: 2D Spatial Indexing

At the heart of any proximity service lies a specialized **Spatial Index**. Standard database indexes (such as B-Trees used in relational databases) excel at single-dimensional range queries, such as searching for numeric IDs or timestamps. However, geographic search requires querying two spatial dimensions simultaneously: **Latitude** (North/South position) and **Longitude** (East/West position).

As we will explore in detail, querying two independent 1D indexes forces the system to intersect two massive candidate sets in memory, degrading query throughput. Most of this lesson focuses on selecting, building, and sharding an in-memory spatial index structure—specifically a **QuadTree**—capable of answering 2D spatial queries in milliseconds.

### Critical Assumption: Static vs. Dynamic Locations

Before designing a proximity architecture, we must establish one foundational constraint:

> [!IMPORTANT]
> **Places are stationary; people and vehicles move.**
> A business entity (such as a restaurant or shopping center) maintains fixed geographic coordinates permanently. Because place locations rarely change, write operations to our spatial index occur infrequently. This allows us to optimize the index aggressively for high-throughput, low-latency **read operations**. 
> 
> By contrast, tracking dynamic entities whose locations change constantly (such as drivers in Uber or friends in Nearby Friends) requires an index optimized for continuous high-frequency updates, which is addressed in separate case studies like [Designing Uber](./4.16-designing-uber-backend.md).

## Step 1: Clarify the Requirements

Always clarify functional boundaries and system constraints at the start of a system design discussion. Asking targeted questions ensures your design addresses the interviewer's specific requirements.

### Functional Requirements

1. **Place Management**: Business owners or system administrators can add, update, and delete place records (name, address, category, coordinates, description).
2. **Proximity Search**: Given a user's location `(latitude, longitude)` and an optional search radius, the system returns all places within that radius.
3. **Feedback & Media**: Users can submit reviews, text feedback, star ratings (1 to 10 scale), and photo attachments for any business place.

### Non-Functional Requirements

1. **Ultra-Low Latency**: Search queries must return results in real time (< 200 milliseconds) to deliver an instant search experience.
2. **Read-Heavy Asymmetry**: The system experiences an overwhelming read-to-write ratio (e.g., 100:1 or higher). Search volume far exceeds place registration or updates.
3. **High Availability**: Search functionality must remain resilient against individual node failures.
4. **Scalability**: The system must scale gracefully as place registrations and search query volumes expand over time.

---

## Step 2: Estimate the Scale

To establish data storage and infrastructure sizing, we begin with foundational assumptions provided during the interview:

* **Initial Stored Places**: 500 million places globally.
* **Initial Search Traffic**: 100,000 queries per second (QPS).
* **Annual Growth Rate**: 20% annual growth for both stored places and search traffic.

### Compound Growth Sizing

While a 20% annual growth rate appears modest, compound growth doubles system requirements over a four-year horizon:

$$1.20 \times 1.20 \times 1.20 \times 1.20 = (1.20)^4 \approx 2.0736$$

Planning for a 4-year lifecycle requires scaling our architecture to support:
* **Target Places Capacity**: **1 billion places** (\(500\text{ million} \times 2.07\)).
* **Target Query Capacity**: **200,000 QPS** (\(100,000\text{ QPS} \times 2.07\)).

### Persistent Storage Sizing (Disk)

As derived in [Step 4](#step-4-define-the-data-model), each primary business place record consumes approximately **793 bytes** of raw storage:

$$\text{Initial Storage} = 500\text{ million places} \times 793\text{ bytes} \approx 396.5\text{ GB} \approx 400\text{ GB}$$

$$\text{4-Year Storage} = 1\text{ billion places} \times 793\text{ bytes} \approx 793\text{ GB} \approx 800\text{ GB}$$

> [!NOTE]
> User reviews and high-resolution photo attachments consume terabytes of disk space. However, reviews and media are stored in dedicated blob/document stores and do not enter the real-time spatial index path.

### Index Memory Sizing (RAM)

As derived in [Step 6](#step-6-go-deep), each spatial index entry requires only **24 bytes** of memory per place (8 bytes for `LocationID`, 8 bytes for `Latitude`, and 8 bytes for `Longitude`):

$$\text{Current Index Memory} = 24\text{ bytes} \times 500\text{ million places} = 12\text{ GB}$$

$$\text{4-Year Index Memory} = 24\text{ bytes} \times 1\text{ billion places} = 24\text{ GB}$$

```
                           SCALE & MEMORY BREAKDOWN
┌───────────────────────────────────┬───────────────────┬───────────────────┐
│ Metric                            │ Current (Year 0)  │ Target (Year 4)   │
├───────────────────────────────────┼───────────────────┼───────────────────┤
│ Total Places Stored               │ 500 Million       │ 1 Billion         │
│ Search Query Load (QPS)           │ 100,000 QPS       │ 200,000 QPS       │
│ Place Records Disk Storage        │ ~400 GB           │ ~800 GB           │
│ Spatial Index In-Memory Size      │ ~12 GB            │ ~24 GB            │
└───────────────────────────────────┴───────────────────┴───────────────────┘
```

### Architectural Takeaways

1. **In-Memory Spatial Indexing is mandatory**: Serving 100,000 to 200,000 read queries per second with sub-200ms latency is impossible if spatial lookups require disk I/O. The search index must reside entirely in server RAM.
2. **Partitioning is required for Throughput**: Although a 12 GB–24 GB index can technically fit within the RAM of a single modern enterprise server, a single node cannot handle 200,000 QPS due to CPU socket and network interface card (NIC) bandwidth limits. The spatial index must be partitioned across a cluster of servers to distribute query throughput.

## Step 4: Define the Data Model

To achieve high search throughput, we divide our data storage into two separate storage tiers:

1. **Disk-Based Relational Database**: Stores full business profiles, descriptions, operating hours, reviews, and photo URLs.
2. **In-Memory Spatial Index**: Stores minimal coordinate-to-ID mappings required to evaluate proximity searches rapidly.

![Database Schema for Yelp](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.15-yelp-database-schema.svg)

### Relational Database Schema (Disk)

#### `Places` Table

Stores core entity attributes for every registered location.

```sql
CREATE TABLE Places (
    LocationID   BIGINT PRIMARY KEY,  -- 8 bytes: Unique 64-bit identifier
    Name         VARCHAR(256),        -- 256 bytes: Business title
    Latitude     DOUBLE PRECISION,    -- 8 bytes: IEEE 754 floating-point coordinate
    Longitude    DOUBLE PRECISION,    -- 8 bytes: IEEE 754 floating-point coordinate
    Description  VARCHAR(512),        -- 512 bytes: Profile overview text
    Category     TINYINT              -- 1 byte: Numeric category code (0-255)
);
```

$$\text{Record Size} = 8 + 256 + 8 + 8 + 512 + 1 = 793\text{ bytes per place}$$

> [!TIP]
> **Why allocate 8 bytes for `LocationID`?**
> A 4-byte unsigned integer supports up to 4.29 billion IDs, which appears sufficient for 500 million places. However, allocating an 8-byte `BIGINT` prevents ID exhaustion as global place data expands over decades and avoids costly database migration cycles.

#### `Reviews` Table

Stores user feedback associated with business entities. Because a single place accumulates many reviews over time, reviews are stored in a separate table keyed by `LocationID`:

```sql
CREATE TABLE Reviews (
    ReviewID     BIGINT PRIMARY KEY,  -- 8 bytes: Unique review identifier
    LocationID   BIGINT NOT NULL,     -- 8 bytes: Foreign key referencing Places
    UserID       BIGINT NOT NULL,     -- 8 bytes: Author identifier
    Rating       TINYINT NOT NULL,    -- 1 byte: Rating score (1 to 10 scale)
    ReviewText   VARCHAR(512),        -- 512 bytes: Review body
    CreatedAt    TIMESTAMP            -- 8 bytes: Submission timestamp
);
```

#### `Photos` Table

Stores media attachments linked to places and reviews:

```sql
CREATE TABLE Photos (
    PhotoID      BIGINT PRIMARY KEY,  -- 8 bytes: Unique image identifier
    LocationID   BIGINT NOT NULL,     -- 8 bytes: Foreign key referencing Places
    PhotoURL     VARCHAR(256),        -- 256 bytes: Object store S3 bucket path
    CreatedAt    TIMESTAMP            -- 8 bytes: Upload timestamp
);
```

### In-Memory Index Schema (RAM)

The spatial index **never** copies full place records into memory. Instead, it maintains a lightweight index tuple containing only three fields per place:

```
┌────────────────────────────────────────────────────────┐
│             IN-MEMORY SPATIAL INDEX ENTRY              │
├────────────────────────┬───────────────────────────────┤
│ LocationID             │ 8 Bytes (BIGINT)              │
│ Latitude               │ 8 Bytes (DOUBLE PRECISION)    │
│ Longitude              │ 8 Bytes (DOUBLE PRECISION)    │
├────────────────────────┼───────────────────────────────┤
│ Total Entry Size       │ 24 Bytes                      │
└────────────────────────┴───────────────────────────────┘
```

By keeping the index entry size down to **24 bytes**, 500 million places require only **12 GB** of memory, enabling ultra-fast spatial operations.

## Step 5: Draw the High-Level Design

At a high level, the system separates spatial filtering from business metadata retrieval:

1. **Client requests** enter through a Load Balancer to stateless **Application Servers**.
2. **Spatial Index Query**: The Application Server queries the in-memory **Spatial Search Index (QuadTree)** with the user's coordinates `(latitude, longitude)` and search radius. The index returns a candidate list of matching `LocationID`s.
3. **Profile Lookup**: The Application Server queries an in-memory **Distributed Cache (Redis/Memcached)** using the matching `LocationID` keys to retrieve business profiles, average star ratings, and thumbnail image paths.
4. **Database Fallback**: On cache misses, the server reads missing place profiles from the **Relational Database** and populates the cache.
5. **Response Assembly**: The Application Server formats, ranks, and returns the JSON payload to the client.

```
                                HIGH-LEVEL SYSTEM ARCHITECTURE
  ┌───────────┐         ┌─────────────────┐         ┌─────────────────────────┐
  │  Client   │ ──────> │  Load Balancer  │ ──────> │   Application Servers   │
  │ (App/Web) │         └─────────────────┘         │  (Search & Aggregators) │
  └───────────┘                                     └────────────┬────────────┘
                                                                 │
                                ┌────────────────────────────────┴────────────────────────────────┐
                                ▼                                                                 ▼
                    ┌────────────────────────┐                                        ┌───────────────────────┐
                    │ In-Memory Spatial      │                                        │  Redis / Memcached    │
                    │ Search Index (QuadTree)│                                        │     Cache Layer       │
                    └────────────────────────┘                                        └───────────┬───────────┘
                                                                                                  │ Cache Miss
                                                                                                  ▼
                                                                                      ┌───────────────────────┐
                                                                                      │  Relational Database  │
                                                                                      │ (Places, Reviews, DB) │
                                                                                      └───────────────────────┘
```

## Step 6: Go Deep

### Storing places in SQL

Can a conventional relational database (like MySQL or PostgreSQL) handle proximity searches directly using standard SQL queries?

Suppose we store all places in a standard relational table where `Latitude` and `Longitude` are stored in separate columns, each indexed with a traditional B-Tree index:

```sql
SELECT LocationID FROM Places 
WHERE Latitude BETWEEN (X - D) AND (X + D)
  AND Longitude BETWEEN (Y - D) AND (Y + D);
```

#### Why 1D SQL Indexes Fail for 2D Spatial Queries

While this SQL query is syntactically simple, it performs poorly at scale:

1. **Independent Index Traversal**: The database engine can only use one B-Tree index efficiently at a time. It scans the `Latitude` index (returning millions of locations in a horizontal band around the globe) and the `Longitude` index (returning millions of locations in a vertical band around the globe).
2. **Costly Intersections**: The engine must perform an expensive in-memory intersection of these two massive candidate lists to identify records satisfying both conditions.
3. **Bounding Box Inaccuracy**: The query selects places within a square bounding box. Calculating actual spherical distances requires executing the Haversine formula (Pythagorean theorem on a sphere) across all returned candidates, placing significant computational load on database CPU cores.

```
                   1D SQL INDEX INTERSECTION INEFFICIENT QUERY
  Longitude Slice (Y-D to Y+D) 
           │       │
  ─────────┼───────┼───────── Latitude Slice (X-D to X+D)
           │ MATCH │  <--- Intersection forces scanning millions of
  ─────────┼───────┼─────────      unrelated global locations!
           │       │
```

To achieve real-time search performance, we must index geographic space using a true **2D Spatial Index**.

---

### Grids

The simplest method to create a 2D spatial index is **Fixed Grid Partitioning**.

We divide the surface of the map into a grid of uniform, fixed-size geographic squares. Each grid square is assigned a unique 4-byte `GridID`.

```
                        MAP DIVIDED INTO FIXED-SIZE GRIDS
  ┌──────────┬──────────┬──────────┐
  │ GridID_1 │ GridID_2 │ GridID_3 │
  ├──────────┼──────────┼──────────┤
  │ GridID_4 │ GridID_5 │ GridID_6 │  <--- User resides in GridID_5
  ├──────────┼──────────┼──────────┤       Search checks Grid 5 + 8 neighbors
  │ GridID_7 │ GridID_8 │ GridID_9 │
  └──────────┴──────────┴──────────┘
```

![Map Divided into Fixed-Size Grids](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.15-fixed-size-grids.svg)

#### Grid Query Workflow

1. We set the grid cell width equal to the maximum search radius (e.g., 10 miles).
2. Given a user's location `(latitude, longitude)`, simple mathematical division maps their coordinates directly to their home `GridID` and its 8 neighboring grid cells (9 grids total).
3. The SQL query filters records explicitly by `GridID`:

```sql
SELECT LocationID FROM Places 
WHERE GridID IN (GridID_1, GridID_2, ..., GridID_9)
  AND Latitude BETWEEN (X - D) AND (X + D)
  AND Longitude BETWEEN (Y - D) AND (Y + D);
```

#### Memory Requirements for Fixed Grids

* Earth surface land area: ~200 million square miles.
* Grid size: 10 miles \(\times\) 10 miles = 100 square miles per grid cell.
* Total grid cells: \(\frac{200\text{ million}}{100} = 2\text{ million grid cells}\).

$$\text{Grid Memory} = (4\text{ bytes} \times 2\text{M grids}) + (8\text{ bytes} \times 500\text{M places}) \approx 8\text{ MB} + 4\text{ GB} \approx 4\text{ GB}$$

#### Why Fixed Grids Fail (The Density Problem)

Fixed grid partitioning encounters a severe bottleneck in real-world deployment: **Geographic Population Density is Non-Uniform**.

* **Sparse Grids**: Ocean grid cells contain zero places, while rural grids contain only a handful of places, wasting memory allocations.
* **Dense Grids**: Urban centers (such as Downtown Manhattan or Central London) contain tens of thousands of businesses within a single grid cell.

When a user searches within a high-density urban grid, the fixed grid index still returns thousands of candidates that must be scanned sequentially. Consequently, fixed grids suffer performance degradation in high-density urban areas—the exact regions where search query volume is highest.

To solve this, we require a dynamic data structure that adapts grid cell sizes automatically based on local place density.

---

### Dynamic-size grids: the QuadTree

A **QuadTree** is a spatial tree data structure where every internal node has exactly four children. Each node represents a rectangular geographic bounding box.

```
                         QUADTREE RECURSIVE DECOMPOSITION
  
         World / Root Grid                         QuadTree Node Hierarchy
  ┌─────────────────┬─────────────────┐                       [Root]
  │                 │                 │                     /  /   \  \
  │       NW        │       NE        │                   NW  NE   SW  SE
  │                 │                 │                             / | \ \
  ├─────────────────┼─────────────────┤                            NW NE SW SE
  │                 │  Dense City     │
  │       SW        │  ┌──┬──┐        │
  │                 │  ├──┼──┤ SE     │
  └─────────────────┴──┴──┴──┴────────┘
```

![QuadTree Spatial Index Decomposition](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.15-quadtree-spatial-index.svg)

#### The QuadTree Splitting Rule

1. We establish a maximum place threshold per leaf node (e.g., **maximum 500 places per grid node**).
2. We initialize the QuadTree with a single root node representing the entire world map.
3. Places are inserted into the tree iteratively based on their `(latitude, longitude)` coordinates.
4. Whenever a leaf node accumulates more than 500 places, it splits into **four equal quadrant child nodes**:
   * North-West (**NW**)
   * North-East (**NE**)
   * South-West (**SW**)
   * South-East (**SE**)
5. Places contained in the parent node are redistributed among its four child nodes.
6. Only **leaf nodes** (nodes at the bottom of the tree without children) store place pointers.

As a result, dense urban regions decompose recursively into thousands of tiny sub-grid cells, while sparse ocean regions remain large, unsplit leaf nodes.

#### QuadTree Navigation & Neighbor Discovery

##### 1. Point Lookup
To find the grid containing a user's location `(latitude, longitude)`, we traverse down from the root node. At each internal node, we determine which of its four child quadrants encapsulates the coordinate, repeating until we land on a leaf node.

##### 2. Neighboring Grid Traversal
Once the target leaf node is reached, if it does not contain enough matching places to fulfill the request, we expand our search into adjacent neighboring grid cells using one of two techniques:

* **Parent Pointers**: Each node maintains a pointer to its parent node. We step up to the parent node and inspect sibling child branches.
* **Doubly-Linked Leaf Chains**: Every leaf node maintains direct pointers to its forward and backward spatial leaf neighbors, allowing horizontal index traversal without re-traversing upper tree branches.

#### QuadTree Sizing and Memory Analysis

Let us calculate the precise memory required to host a QuadTree containing 500 million places with a leaf threshold of 500 places per node:

1. **Place Data Storage**:
   Each index entry stores `LocationID` (8B), `Latitude` (8B), and `Longitude` (8B) = 24 bytes per place.

$$\text{Data Storage} = 24\text{ bytes} \times 500\text{ million places} = 12\text{ GB}$$

2. **Leaf Node Count**:
   With 500 million places and a maximum cap of 500 places per leaf:

$$\text{Leaf Nodes} = \frac{500\text{ million places}}{500\text{ places/leaf}} = 1\text{ million leaf nodes}$$

3. **Internal Node Count**:
   In a balanced 4-ary tree, the number of internal nodes is approximately one-third the number of leaf nodes:

$$\text{Internal Nodes} \approx \frac{1\text{ million}}{3} \approx 333,333\text{ internal nodes}$$

4. **Pointer Overhead**:
   Each internal node stores 4 child node pointers (8 bytes each):

$$\text{Pointer Memory} = 333,333\text{ internal nodes} \times (4 \times 8\text{ bytes}) \approx 10.66\text{ MB}$$

5. **Total QuadTree Index RAM**:

$$\text{Total Memory} = 12\text{ GB (Data)} + 0.01\text{ GB (Pointers)} \approx 12.01\text{ GB}$$

The entire global QuadTree index requires approximately **12.01 GB of RAM**, fitting comfortably within the memory capacity of a standard modern server.

---

### Partitioning the QuadTree

While a 12.01 GB QuadTree index fits within a single server's RAM, two factors require partitioning the tree across multiple machines:

1. **Traffic Throughput Limits**: A single server cannot process 100,000 to 200,000 QPS due to CPU socket contention and network bandwidth saturation.
2. **Future Data Expansion**: As place data doubles to 1 billion records (24 GB index), memory consumption will outgrow cost-effective single-node hardware.

We evaluate two partitioning strategies:

#### Strategy A: Partitioning by Geographic Region

We divide places into fixed geographic territories (e.g., zip codes, states, or countries) and assign each territory to a dedicated QuadTree partition server.

```
                           SHARDING BY GEOGRAPHIC REGION
┌─────────────────────────┐   ┌─────────────────────────┐   ┌─────────────────────────┐
│  Server 1: US West      │   │  Server 2: US East      │   │  Server 3: Europe       │
│  (San Francisco, LA)    │   │  (New York, Miami)      │   │  (London, Paris)        │
└─────────────────────────┘   └─────────────────────────┘   └─────────────────────────┘
```

##### Drawbacks of Regional Sharding
1. **Hotspotting**: Highly populated cities experience massive search volume, causing servers hosting urban regions (e.g., New York or Tokyo) to overload while rural region servers sit idle.
2. **Uneven Memory Distribution**: Urban servers exhaust memory rapidly due to high place concentration, while rural servers remain underutilized.

#### Strategy B: Partitioning by LocationID (Consistent Hashing)

We apply a uniform cryptographic hash function (such as `MurmurHash3`) to each place's `LocationID` to determine its assigned QuadTree server:

$$\text{Server ID} = \text{Hash}(\text{LocationID}) \pmod{N}$$

Where \(N\) is the total number of QuadTree partition shards.

```
                         SHARDING BY LOCATION ID (SCATTER-GATHER)
                                  ┌───────────────────────┐
                                  │  Aggregator Server    │
                                  └───────────┬───────────┘
                                              │
                      ┌───────────────────────┼───────────────────────┐
                      │ Scatter               │ Scatter               │ Scatter
                      ▼                       ▼                       ▼
          ┌───────────────────────┐ ┌───────────────────────┐ ┌───────────────────────┐
          │  QuadTree Shard 1     │ │  QuadTree Shard 2     │ │  QuadTree Shard N     │
          │  (Holds 1/N Places)   │ │  (Holds 1/N Places)   │ │  (Holds 1/N Places)   │
          └───────────────────────┘ └───────────────────────┘ └───────────────────────┘
```

##### Search Execution via Scatter-Gather
1. **Scatter Phase**: The Aggregator server receives a search request containing user coordinates `(latitude, longitude)` and radius. It broadcasts the request to **all \(N\) QuadTree partition shards simultaneously**.
2. **Local Evaluation Phase**: Each partition server searches its local in-memory QuadTree (which holds \(\frac{1}{N}\) of global places) and extracts matching candidate places within the radius.
3. **Gather Phase**: Each shard returns its top candidate `LocationID`s to the Aggregator server.
4. **Merge Phase**: The Aggregator merges partial result sets, performs final sorting by distance or rating, truncates the list to the requested page size, and returns the response to the user.

> [!TIP]
> **Do QuadTrees look different on each shard server?**
> Yes. Because places are hashed uniformly by `LocationID`, each shard server receives a different random subset of global coordinates. Consequently, QuadTree nodes on different shards split at different thresholds. This structural variation does not affect search correctness because every search query checks matching spatial bounds across all shards.

### Replication and fault tolerance

To guarantee high availability and scale read throughput, every QuadTree shard server is deployed in a **Primary-Secondary (Leader-Follower)** replication topology.

```
                       PRIMARY-SECONDARY REPLICATION TOPOLOGY
                                  ┌──────────────────────┐
                                  │  Primary Node        │
                                  │  (Processes Writes)  │
                                  └──────────┬───────────┘
                                             │ Async Replication
                                ┌────────────┴────────────┐
                                ▼                         ▼
                     ┌────────────────────┐    ┌────────────────────┐
                     │ Secondary Node 1   │    │ Secondary Node 2   │
                     │ (Processes Reads)  │    │ (Processes Reads)  │
                     └────────────────────┘    └────────────────────┘
```

1. **Read Distribution**: Search queries (which account for >99% of total system traffic) are distributed across Secondary nodes.
2. **Write Replication**: New place insertions are routed to the Primary node first and replicated asynchronously to Secondaries. Minor replication lag (a few milliseconds) is acceptable for newly registered businesses.
3. **Automatic Failover**: If a Primary node fails, an automated cluster orchestrator promotes a healthy Secondary node to Primary.

#### Fast Recovery via the QuadTree Index Server

If both the Primary and all Secondary replicas of a shard fail simultaneously, a clean server must be provisioned.

* **Brute-Force Recovery (Slow)**: The new node scans the entire 500 million record database on disk, hashes every `LocationID`, and identifies records belonging to its shard. Scanning hundreds of gigabytes of disk data takes hours, during which the shard cannot serve traffic.
* **Optimized Recovery via QuadTree Index Server (Fast)**:
  We deploy a dedicated **QuadTree Index Server** cluster that maintains an in-memory reverse mapping table:

$$\text{Key: QuadTree Server ID} \longrightarrow \text{Value: Hash Set of } (\text{LocationID}, \text{Latitude}, \text{Longitude})$$

```
                   QUADTREE INDEX SERVER FAST RECOVERY PIPELINE
  ┌───────────────────────────┐    1. Request My Places List    ┌───────────────────────────┐
  │  Recovering Shard Server  │ ──────────────────────────────> │   QuadTree Index Server   │
  │     (Clean Node)          │ <────────────────────────────── │  (In-Memory Reverse Map)  │
  └───────────────────────────┘    2. Return Shard HashSet      └───────────────────────────┘
```

When a shard node restarts, it queries the QuadTree Index Server, fetches its assigned place tuples directly from RAM, and rebuilds its local QuadTree in memory within seconds.

### Caching

To prevent high-volume metadata queries from overwhelming the primary relational database, we deploy an in-memory caching tier (such as Redis or Memcached) in front of the database.

```
                           CACHED READ WORKFLOW
 ┌─────────────┐  1. Find LocationIDs   ┌────────────────┐  2. Batch GET Profiles  ┌──────────────┐
 │ App Server  │ ─────────────────────> │ QuadTree Index │ ──────────────────────> │ Redis Cache  │
 └──────┬──────┘                        └────────────────┘                         └──────┬───────┘
        │                                                                                 │
        │ 3. Read Missing Profiles on Cache Miss                                          │ Cache Hit
        ▼                                                                                 ▼
 ┌─────────────┐                                                                   ┌──────────────┐
 │ Relational  │ <─────────────────────────────────────────────────────────────────┤ Return Places│
 │ Database    │                                                                   └──────────────┘
 └─────────────┘
```

1. The QuadTree spatial index processes coordinates and returns matching candidate `LocationID`s.
2. The Application Server executes a multi-key batch lookup (`MGET`) against the Redis cache using the `LocationID` keys.
3. **Cache Hit**: Profiles found in Redis are returned immediately.
4. **Cache Miss**: Profiles missing from Redis are queried from the relational database, stored in Redis, and returned.

#### Cache Eviction & Invalidations

* **Eviction Policy**: **Least Recently Used (LRU)** eviction discards inactive places while keeping popular venues cached.
* **Cache Invalidation**: Because business metadata (names, addresses, categories) changes infrequently, cache entries are assigned long Time-To-Live (TTL) durations (e.g., 24 hours), avoiding complex cache invalidation logic.

### Load balancing

Load balancers are positioned at two strategic layers within the architecture:

1. **Layer 1 (Client to Application Servers)**: Distributes incoming HTTP REST search requests across stateless Application Server instances.
2. **Layer 2 (Application Servers to QuadTree Shards & Caches)**: Distributes internal scatter-gather queries across spatial index shards and Redis nodes.

```
                          TWO-LAYER LOAD BALANCING
┌─────────────┐
│ Client App  │
└──────┬──────┘
       │
       ▼
┌────────────────────────────────────────────────────────────────────────┐
│ Layer 1 Load Balancer (Round-Robin / Least Connections)                │
└──────┬─────────────────────────────────────────────────────────────────┘
       │
       ▼
┌────────────────────────────────────────────────────────────────────────┐
│ Stateless Application Servers                                          │
└──────┬─────────────────────────────────────────────────────────────────┘
       │
       ▼
┌────────────────────────────────────────────────────────────────────────┐
│ Layer 2 Load Balancer (Shard-Aware Routing & Health Checking)          │
└──────┬─────────────────────────────────────────────────────────────────┘
       │
       ├───────────────────────────────┬───────────────────────────────┐
       ▼                               ▼                               ▼

└──────────────┘                └──────────────┘                └──────────────┘
```

#### Routing Algorithms

* **Weighted Round-Robin**: Directs traffic across backend servers proportional to their hardware capacity.
* **Dynamic Load-Aware Routing**: Periodically polls backend nodes for active connections, CPU utilization, and latency, throttling requests sent to degraded shards.

### Ranking

While proximity search prioritizes spatial distance, users expect search results ranked by a combination of **Distance**, **Popularity** (average star rating and review count), and **Category Relevance**.

#### Multi-Factor Ranking Pipeline

1. **Popularity Score Calculation**:
   Each place maintains an aggregated popularity rating computed from its review history:

$$\text{Popularity Score} = \text{Average Rating} \times \log_{10}(\text{Review Count} + 1)$$

2. **Index Pre-loading**:
   The 4-byte popularity score is cached alongside the 24-byte entry in QuadTree leaf nodes.
3. **Shard-Level Top-K Selection**:
   Each QuadTree partition shard ranks candidate places within the search radius using a composite ranking formula:

$$\text{Composite Score} = (w_1 \times \text{Proximity Score}) + (w_2 \times \text{Popularity Score})$$

Each shard returns only its top \(K\) highest-scoring candidates to the Aggregator server.
4. **Global Merge**:
   The Aggregator merges the top \(K\) candidates from all shards using a min-heap, returning the final top results to the client.

#### Asynchronous Popularity Updates

> [!WARNING]
> Updating QuadTree memory structures synchronously on every user review submission introduces severe write locking and CPU overhead.
> Popularity scores do not require real-time precision. We recompute popularity scores asynchronously via **nightly batch processing jobs** (or off-peak hourly stream jobs) and update QuadTree nodes during periods of lowest traffic.

## Step 7: Bottlenecks and Failure Points

No system design is unlimited. Identifying operational boundaries and failure points demonstrates senior engineering maturity:

### 1. Scatter-Gather Latency Amplification (Tail Latency)

* **Bottleneck**: Sharding by `LocationID` requires every search query to fan out to every QuadTree shard. The slowest shard server (due to garbage collection pauses or transient network congestion) dictates the overall response time of the search request.
* **Mitigation**: Implement aggressive request timeouts (e.g., 50ms) on shard queries, utilize hedge requests (sending redundant queries to secondary replicas if the primary replica delays), and cap the maximum number of shards per cluster.

### 2. QuadTree Index Server Dependencies

* **Failure Point**: If a QuadTree shard crashes and the QuadTree Index Server is offline simultaneously, the recovering shard must fall back to scanning the disk database, resulting in prolonged downtime.
* **Mitigation**: Deploy QuadTree Index Servers in multi-region primary-secondary configurations with persistent state snapshots backed up to distributed storage (S3).

### 3. Structural QuadTree Hotspots

* **Bottleneck**: Exceptionally dense metropolitan centers (e.g., Manhattan or Tokyo) create deeply nested QuadTree sub-branches compared to rural areas.
* **Mitigation**: Enforce a hard cap on maximum QuadTree depth and truncate leaf nodes exceeding density bounds, delegating fine-grained filtering to downstream application memory.

## Where AI Fits in This Design

Modern location-based platforms integrate Artificial Intelligence to enhance search relevance and user engagement. Following system design principles, AI components are architected around one core rule:

> [!IMPORTANT]
> **Precompute and Cache; Never Execute LLM Inference on the Synchronous Search Path.**
> AI model inference introduces hundreds of milliseconds of latency. Because search queries require sub-200ms performance at 200,000 QPS, generative AI tasks must be executed asynchronously offline.

```
                        OFFLINE AI ENRICHMENT PIPELINE
  ┌────────────────┐    Trigger Batch    ┌────────────────┐    Store Summary    ┌────────────────┐
  │ User Reviews   │ ──────────────────> │ Offline LLM    │ ──────────────────> │ Places DB /    │
  │ Stream (Kafka) │                     │ Summarizer     │                     │ Redis Cache    │
  └────────────────┘                     └────────────────┘                     └────────────────┘
```

### 1. Automated AI Review Summarization

* **Capability**: A venue with thousands of user reviews requires concise, digestible summaries (e.g., *"Visitors highlight the cold brew and cozy outdoor seating, but note limited parking during weekends."*).
* **Architecture**: An offline asynchronous pipeline monitors new reviews submitted via Kafka event streams. A Large Language Model (LLM) periodically generates a single-paragraph summary for the place.
* **Storage & Serving**: The summary is written to the `Places` database table and cached in Redis alongside place metadata. It is served directly during profile retrieval without executing AI models during user requests.

### 2. Semantic & Natural Language Search via Vector Embeddings

* **Capability**: Enables users to search using natural language phrases such as *"quiet cafe with fast wifi for remote work"* without requiring exact keyword matches in place titles.
* **Architecture**: 
  1. **Offline**: Generate dense vector embeddings for places based on their aggregated review text using an embedding model. Store vector embeddings in a specialized Vector Database (or Redis Vector Search).
  2. **Online Query Execution**:
     * **Step 1 (Spatial Filter)**: The QuadTree spatial index identifies all `LocationID`s within the user's geographic radius (filtering millions of global places down to ~50 local candidates).
     * **Step 2 (Semantic Re-Ranking)**: The Aggregator computes vector similarity scores between the user's query embedding and the pre-computed embeddings of those 50 local candidates, re-ranking final search results.

By leveraging spatial indexing to narrow candidate sets *before* performing vector calculations, the system maintains ultra-low latency while delivering intelligent, natural language search capabilities.
