# Designing Typeahead Suggestion

Every case study in this section follows the same seven-step methodology detailed in [System Design Interviews: A Step-by-Step Guide](./4.1-system-design-interviews-a-step-by-step-guide.md) and constructs its architecture using components from the [System Design Master Template](./4.2-system-design-master-template.md). Keep both open beside you, and attempt each problem independently before reviewing the solution.

---

## What is Typeahead Suggestion?

Typeahead suggestion is the list of search terms that appears while you type in a search box. As you type, the service predicts your query from the characters entered so far. It shows known, frequently searched terms that complete what you have typed.

The goal is not to make the search itself faster. The goal is to help users build their query and choose better terms. The user picks a suggestion instead of typing the rest, and often finds a better phrasing than their own.

Try it on google.com before reading on. Type a few characters and watch the suggestions change with every keystroke. This lesson designs the service behind that list.



## Step 1: Clarify the Requirements

> [!TIP]
> Always clarify requirements at the beginning of the interview. Ask questions until you know the exact scope of the system the interviewer has in mind.

#### Functional Requirements
As the user types their query, the service suggests the top 10 terms that start with the typed prefix. The prefix is the characters entered so far.

#### Non-Functional Requirements
* Suggestions must appear in real time. The user should see them within **200 ms**.
* The 200 ms budget is the number to remember. A suggestion that arrives after the next keystroke is useless. Almost every decision in this design exists to protect that budget.
* High availability: The suggestion system must remain online and responsive even during backend updates or node failures.

#### Extended Requirements
One extended requirement is worth naming: suggestions can be personalized from the user's own history. It does not drive the core design, so we return to it at the end.

---

## Step 2: Estimate the Scale

Assume we are building at the scale of Google. That means about **5 billion searches per day**.

#### Query Volume & QPS
$$\text{QPS} = \frac{5\text{ Billion}}{86,400\text{ seconds}} \approx 60,000\text{ queries per second (60K QPS)}$$

#### Unique Index Terms
How many terms do we index? There are many duplicates in 5 billion queries. Assume only 20 percent of them are unique. We also do not need rare terms. A term searched only a few times should never be suggested anyway. If we index only the more popular half of the terms, we drop a lot more. Assume we end with **100 million unique terms** to index.

This assumption matters, so be precise about what it changes. Read traffic stays at 60K queries per second, because every query is still served. But the index stores each distinct term once. So the index size depends only on the number of unique terms.

#### Storage Estimations
Assume an average query has 3 words, and an average word has 5 characters. Assume 2 bytes per character, because queries arrive in many languages and need Unicode:

$$\text{Query length} = 3\text{ words} \times 5\text{ characters} = 15\text{ characters per query}$$
$$\text{Storage per query} = 15\text{ characters} \times 2\text{ bytes} = 30\text{ bytes per query}$$
$$\text{Base Index Size} = 100\text{ million} \times 30\text{ bytes} \approx 3\text{ GB}$$

New terms appear every day, and old terms stop being searched. Assume 2 percent of queries are new each day, and that we keep an index covering one year:

$$\text{1-Year Storage} = 3\text{ GB} + (0.02 \times 3\text{ GB} \times 365\text{ days}) \approx 25\text{ GB}$$

Note the shape of these two numbers. The load is heavy: 60K queries per second, each with a 200 ms budget. The data is small: about 25 GB. That combination decides the whole design, as Step 4 will show.

## Step 3: Define the API

One endpoint covers the whole product.

```http
GET /suggestions?prefix=<typed text>&limit=10
```

#### Response Format (200 OK)
```json
{
  "suggestions": [
    "term 1",
    "term 2",
    "term 3",
    "term 4",
    "term 5",
    "term 6",
    "term 7",
    "term 8",
    "term 9",
    "term 10"
  ]
}
```

The client calls this endpoint while the user types, so it is called far more often than search itself. Every call must finish well inside the 200 ms budget. The client section in Step 6 shows how to call it less often.

## Step 4: Define the Data Model

Where should 100 million terms live? Not in a database on disk. A disk-based lookup is too slow to answer a prefix query on every keystroke. The index must live in memory, in a structure built for prefix search. At 25 GB, it fits there.

That structure is the **trie** (pronounced "try"). A trie is a tree that stores strings one character per node. The path from the root down to any node spells out a prefix. Every stored term that starts with that prefix sits in that node's sub-tree, the part of the tree below it. So one walk from the root finds every completion of a prefix.

The trie is the data model. There is no table with one row per query here. But the questions a schema answers still apply: what each record holds, what its key is, and where it lives. Five records cover the whole design:
1. **The trie node**, the record every read is served from.
2. **The top 10 entry**, ten of which sit inside each trie node.
3. **The query log entry**, one per sampled query.
4. **The term frequency row**, built from the logs by an offline job.
5. **The snapshot file**, a periodic copy of the trie on disk.

The schema summary below shows all five and where each one lives:

![Database schema for Typeahead Suggestion](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.10-typeahead-db-schema.png)

#### Trie Node Schema
Trie node is the most important record. Every other record either feeds it or rebuilds it. Its key is the prefix it represents, and the node does not even store it: the path from the root spells the prefix. `Characters` holds the letters this node adds to that path, usually one. A storage optimization later in this step lets one node carry several. `Children` holds references to the child nodes, one for each way the prefix continues. A reference is a pointer to another node.

`Top10List` is the field the 200 ms budget depends on. It caches the ten best completions of this node's prefix, so a read can stop at the prefix node. Each entry is a top 10 entry: a reference to a terminal node, plus that term's frequency. A terminal node is the node where a stored term ends. `Count` sits on terminal nodes and records how many searches ended exactly there. Step 6 shows why we cache the list instead of walking the sub-tree on every request.

The top 10 list is derived data: every entry in it can be recomputed from the counts. A classic schema would keep derived data out of its tables. Here we store it deliberately, and Step 6 names the trade: memory for latency. Every trie node lives in the memory of a trie server. Reads never touch a disk.

Two records feed the trie, and both live on disk, on the update path. A query log entry holds one sampled query as raw text. That is about 30 bytes by the Step 2 estimate. A term frequency row holds one distinct term and a count of its recent searches. An offline job builds these rows from the log entries. The update path then applies them to the trie without ever blocking a read. Step 6 covers that pipeline in detail.

The snapshot file is a periodic copy of the trie on disk. It stores each node's characters and child count, level by level, and nothing else. A restarted trie server rebuilds its trie from this file instead of replaying old logs. Step 6 shows the file format and why the top 10 lists stay out of it.

Note what stays small here. The index holds 100 million terms in about 25 GB, so one server's memory can hold the whole structure. Step 6 still partitions it across servers, for latency rather than size, and shows three ways to draw the partition lines.

#### Unmerged vs. Merged Trie
The rest of this step makes the trie concrete. Suppose we store the terms `'cap'`, `'cat'`, `'caption'`, `'captain'`, and `'capital'`. The trie looks like this:

![A trie storing 'cap', 'cat', 'caption', 'captain', and 'capital', one character per node](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.10-typeahead-standard-trie.png)

Now suppose the user has typed `'cap'`. The service walks from the root to the node `'P'`. Every term that completes the prefix sits below that node, like `cap-tion` and `cap-ital`.

Can we make the trie smaller? Yes, through node merging: combining nodes that have only one child. A chain of single-child nodes becomes one node holding several characters. Node merging reduces the number of nodes and the depth of the tree, which saves storage. The trie above can be stored like this:

![The same trie after node merging: single-child chains become one node](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.10-typeahead-merged-trie.png)

The merged trie holds the same five terms with far fewer nodes.

Should the trie be case insensitive? Yes. For a search use case, `'Cap'` and `'cap'` mean the same thing. So assume the data is case insensitive.

## Step 5: Draw the High-Level Design

The system has two halves, and they must never compete with each other.

#### Read Path vs. Update Path
* **The read path** serves suggestions. The client sends the prefix to a load balancer. The load balancer forwards it to application servers. The application servers query the trie servers, which hold the in-memory trie.
* **The update path** keeps the trie fresh. It collects query logs, computes term frequencies offline, and builds new versions of the trie. It never touches a trie that is currently serving reads.

Keep that separation in mind as you draw. Every read-path part exists to answer in under 200 ms. Every update-path part exists to stay out of the read path's way. Step 6 fills in both halves.

## Step 6: Go Deep

### Finding the top 10 suggestions

Walking to the prefix node finds all completions. It does not find the best ones.

How do we rank the completions? Store a count at each terminal node, the node where a stored term ends. The count is how many searches ended exactly there. Say users searched `'CAPTAIN'` 100 times and `'CAPTION'` 500 times. Each count sits at the last node of its phrase. For the prefix `'CAP'`, the top suggestion is `'CAPTION'`.

Is traversing the sub-tree fast enough? No. At our scale the tree is huge, and its sub-trees are deep. The phrase `'system design interview questions'` alone is 30 levels deep. Visiting a whole sub-tree on every keystroke would break the 200 ms budget.

So store the top 10 suggestions directly within each node. Each node keeps the 10 best completions of its own prefix. When a request reaches the prefix node, the answer is already sitting there. No sub-tree traversal at all. The price is storage, because the same term now appears in the list of many nodes. We accept the storage increase to get the required speed. That trade, memory for latency, repeats through this whole design.

Can we cut that storage cost? Yes. Do not store full phrases in each list. Store references to the terminal nodes of the top terms instead, along with each term's frequency. A reference is a pointer to another node. To show a suggestion, follow parent references upward from its terminal node and rebuild the phrase.

How is the trie built? Bottom up. Each node asks its children for their top suggestions and their counts. Each parent merges its children's lists to compute its own top 10. The root finishes last.

### Updating the trie

At 60K queries per second, we cannot update the trie on every search. Constant writes would be extremely resource intensive, and they would slow the reads too. So update the trie offline, on a regular interval.

What do we log? As queries come in, log them with their frequencies. We do not need every query. Sampling works: log every 1000th query. That is safe if we never suggest a term searched fewer than 1000 times.

Who processes the logs? A [MapReduce](https://en.wikipedia.org/wiki/MapReduce) job. MapReduce is a framework that processes very large data sets in parallel batches. Run it on an interval, say every hour. Each run computes the frequency of every term searched in the past hour. That output is what updates the trie.

How do we apply the update without blocking reads? Take the current snapshot of the trie and apply the new terms and frequencies to it. There are two ways to serve traffic while that happens:
* Each server keeps a copy of its trie. Update the copy offline, switch to it, and discard the old one.
* Run each trie server as a primary-secondary pair. Update the secondary while the primary serves traffic. Then promote the secondary to primary. Update the old primary later, and it can serve traffic again.

Both options mean the same thing: a read never waits for an update.

### Updating the frequencies

The top 10 lists store frequencies, so those need updating too. Do not recount every term from scratch. Apply only the differences. If our counts cover the last 10 days, subtract the oldest day and add the newest. A useful tool here is the [Exponential Moving Average (EMA)](https://en.wikipedia.org/wiki/Moving_average#Exponential_moving_average). EMA is an average that gives more weight to the latest data. That fits search well, because what people search for right now matters most.

After a term's frequency changes at its terminal node, the change must travel upward. The term may now belong in the top 10 of nodes above it. So traverse from the terminal node back up to the root. At each parent, check whether the term is already in its top 10. If it is, update its frequency. If not, compare it with the lowest entry in the list. If the term's frequency is higher, insert it and remove the lowest one.

### Removing a term

Sometimes a term must disappear immediately, for legal reasons or because it is hateful. The trie itself only changes at the next regular update, and that is too slow here. So add a filtering layer on each server. The filter drops the banned term from every result before it reaches users. The term is then fully removed from the trie at the next regular update.

### Ranking beyond counts

A raw count is not the only ranking signal. Real systems also weigh freshness, user location, language, demographics, and personal search history.

### Storing the trie permanently

A trie server will restart at some point, and everything in memory is lost then. Rebuilding from a year of raw logs would take far too long. Instead, take a snapshot of the trie periodically and store it in a file. A snapshot is a point-in-time copy. A restarted server rebuilds its trie from the last snapshot.

Store the snapshot level by level, starting at the root. For each node, write its character and its number of children. Right after each node, write its children. Suppose we have the following trie:

![The example trie for the snapshot file](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.10-typeahead-snapshot-trie.png)

With this scheme, the file for this trie is `"C2,A2,R1,T,P,O1,D"`. From this line we can rebuild the exact same trie.

Notice what the file does not contain: the top 10 lists and their counts. Those lists hold references to terminal nodes, and this simple text format has no way to express them: it is written top-down, so a parent is written before its children exist. Formats built for this do exist. Assign each node a sequential index and store references as indices, or store relative byte offsets the way FlatBuffers does, and references serialize fine. The price is a more complex format and a second resolution pass on load. We keep the simple format and recalculate the counts and lists while the trie is rebuilt. Each node computes its top suggestions and passes them to its parent. Each parent merges the results from all of its children, the same bottom-up merge as before.

### Partitioning the trie

Our index is about 25 GB, so it can easily fit on one server. We still partition it, for higher efficiency and lower latency. How do we split a trie across servers?

#### Option A: Range-based partitioning
Store phrases in partitions based on their first letter. All terms starting with `'A'` go to one partition, `'B'` to another, and so on. Less frequent letters can share a partition. The scheme is static, so storing and searching stay predictable.

The problem is balance. Some letters start far more terms than others. A partition for a heavy letter may not fit on its server. Every statically defined scheme has this flaw. We cannot know in advance whether each partition will fit on one server, and this leads to unbalanced servers.

#### Option B: Partition by server capacity
Keep storing terms on a server as long as it has memory available. When a sub-tree no longer fits, break the partition exactly there and move to the next server. The range boundaries now come from how much data fits, not from fixed letters. Say server 1 can hold all terms from `'A'` to `'AABC'`. The next server then starts at `'AABD'` and fills up at `'BXA'`. A small hash table records the map:

```text
Server 1: A to AABC
Server 2: AABD to BXA
Server 3: BXB to CDA
```

Routing follows the map. If the user typed `'A'`, servers 1 and 2 may both hold matches, so we query both. At `'AA'` the same two servers apply. At `'AAA'`, only server 1 can match. A load balancer in front of the trie servers stores this map and redirects each request. The client never needs to know which server holds a term.

When one query goes to several servers, someone must merge the partial results. We can do it on the client, or on the server side. Doing it server-side needs one more layer between the load balancer and the trie servers. Call these servers aggregators. An aggregator combines the top 10 lists from several trie servers into one final top 10 for the client.

Capacity-based partitioning can still produce hotspots. A hotspot is a server that receives far more traffic than the others. If terms starting with `'cap'` are very popular, the server holding them carries much more load than the rest.

#### Option C: Partition by a hash of the term
Pass each term through a hash function that picks its server. Terms now spread randomly across servers, which minimizes hotspots. But a hash scatters terms that share a prefix. Any server may hold a completion of `'cap'`, so every query must go to all the servers. Then the results must be aggregated. That fan-out, one request becoming a request to every server, is the cost of this scheme.

Note the contrast with [Designing a URL Shortening Service like TinyURL](./4.3-designing-a-url-shortening-service-like-tinyurl.md). Hash partitioning is ideal there, because every lookup is an exact key. A prefix query has no single hash value, so the same scheme forces a fan-out here.

### Caching

A small share of terms produces most of the traffic. So place cache servers in front of the trie servers. They hold the most frequently searched terms and their typeahead suggestions. Application servers check the cache first, and only go to the trie servers on a miss. A cache hit skips the trie traversal entirely.

This cache is easy to keep correct. The trie only changes at the offline update, so cached entries stay valid between updates. Refresh them when a new trie version goes live.

We can also fill the cache in advance with a simple Machine Learning model, a program that learns patterns from data. The model predicts the engagement on each suggestion from counts, trends, or personalization, and caches the likely winners before they are asked for.

### Replication and fault tolerance

Run replicas of every trie server. Replicas share the read load, and they cover failures. The load balancer keeps track of the partition map and routes each prefix to the right servers.

What happens when a trie server dies? Its secondary takes over after failover, as in the primary-secondary setup above. A server that comes back up rebuilds its trie from the last snapshot. It may miss the newest counts until the next update, which is acceptable for suggestions.

### Client-side optimizations

The client can remove a lot of load and latency on its own.
* Only send a request after the user has paused typing for **50 ms** (debouncing). Without the pause, the client would request suggestions for every prefix the user types past.
* If the user keeps typing, cancel the in-progress requests. Their responses answer prefixes the user has already extended, so they are no longer relevant.
* Wait until the user has entered the first couple of characters before requesting at all.
* Pre-fetch some data from the server to save future requests.
* Store the recent history of suggestions locally. Recent history has a very high chance of being reused.
* Open a connection to the server as soon as the search page opens. When the first character arrives, the connection setup time is already paid, and the request goes out immediately.
* The server can push part of its cache to CDNs and Internet Service Providers. A CDN (content delivery network) is a set of servers placed close to users. Both shorten the path a request must travel.

### Personalization

Users expect suggestions shaped by their own history, location, and language. Store each user's personal search history separately on the server, and cache it on the client too. The server adds matching personal terms to the final suggestion set. Personalized suggestions should always come before the global ones.

## Step 7: Bottlenecks and Failure Points

The interviewer does not expect this design to be limitless. They expect you to know where it ends.
* The read path depends on the cache and the trie servers, and nothing else. Logging, MapReduce, and the trie builder can all be down at once, and suggestions keep serving. They only grow stale.
* Partitioning is a trade with no clean winner. Range-based schemes drift toward unbalanced servers and hotspots. Hashing removes hotspots but sends every query to every server. Know the cost of both before you pick one.
* A crashed trie server recovers from its last snapshot, so recovery speed depends on snapshot frequency. Counts gathered after that snapshot are lost until the next update. For suggestions, slightly stale counts are an acceptable loss.

## Where AI Fits in This Design

After the main design, interviewers often ask one more question: where would AI fit in this system?

For typeahead, the honest answer starts with the budget. A suggestion must appear while the user is still typing, so the read path is a walk through a trie held in memory. A model call takes longer than that whole budget. So AI never runs on the request path in this design.

It runs where the lesson already does its heavy work: the offline update. The top suggestions stored at every node are ranked by frequency counts today. A model can rank them better. It predicts which completions users will actually pick, using trends, time of day, and the personalization signals the lesson already stores. The design already warms its cache with a simple learned model; this is the same idea applied to every stored top list.

The output is ordinary data. The rebuilt trie ships with model-ranked lists inside it, and the serving path cannot tell the difference. When the next snapshot goes live, the better rankings go live with it.

The rule this case study teaches is simple: when the latency budget is tiny, AI builds what the servers serve. Offline it has minutes. On the request path it has no time at all.

> [!TIP]
> **Interview Strategy:**  
> Spend your time on the trie and the update path. Two moments give the interviewer the most information. The first is when you store the top 10 suggestions at each node and name the trade. You spend extra memory so reads never traverse a sub-tree. The second is when you move every update offline, so a read never waits for a write. If time remains, partitioning is the likely follow-up. Be ready to explain why hashing removes hotspots but forces every prefix query to fan out to all servers.

> [!IMPORTANT]
> **Key Takeaway:**  
> Typeahead is a heavy read load over a small data set, about 60K queries per second against roughly 25 GB. So the whole index lives in memory as a trie, and the design spends storage to save time. Precompute the top 10 suggestions at every node, stored as references to terminal nodes with their frequencies. Update the trie offline from sampled logs, and switch versions through a primary-secondary pair, so reads never wait. Snapshot the trie level by level to a file, so a restarted server can rebuild it. Partition for latency rather than size, and cache the popular terms in front of the trie servers. Let the client help: wait 50 ms before sending, cancel outdated requests, and open the connection early.
