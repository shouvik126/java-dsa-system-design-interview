## What is Twitter Search?

Twitter allows hundreds of millions of users worldwide to publish short real-time text updates known as tweets. While core social network architectures focus on delivering posts to a user's home timeline based on follower graphs (mapping `User -> Followed Accounts -> Tweets`), a search engine serves a fundamentally different purpose.

**Twitter Search** enables users to discover public tweets instantaneously by querying specific keywords, multi-word phrases, hashtags, and boolean expressions (`AND`, `OR`), sorted by freshness, relevance, or user engagement.

### The Engineering Challenge: Timeline Delivery vs. Search Retrieval

To appreciate why a dedicated search architecture is necessary, consider the difference between database storage and search indexing:

| Architecture Dimension | Timeline System (Designing Twitter) | Search System (Twitter Search) |
| :--- | :--- | :--- |
| **Primary Query Pattern** | "Fetch recent tweets from User X's followings" | "Find all tweets across the platform containing word Y" |
| **Data Organization** | Organized by Author / User ID (`User -> Tweets`) | Organized by Term / Keyword (`Word -> TweetIDs`) |
| **Storage Mechanism** | Key-Value Store / SQL Database | Distributed Inverted Index in RAM |
| **Target Read Latency** | $< 200\text{ ms}$ timeline rendering | $< 100\text{ ms}$ query matching |

Scanning raw tweet database rows using traditional SQL `LIKE %keyword%` queries across hundreds of billions of records would take seconds or minutes per query. To satisfy low latency requirements at massive scale, we must build a secondary data structure—an **Inverted Index**—which reorganizes data by tokenized words rather than tweet creation order.

> [!NOTE]
> This lesson builds upon the storage foundation designed in [Designing Twitter](./4.8-designing-twitter.md). That case study focuses on storing raw tweet payloads and serving follower feeds. This case study focuses exclusively on building, partitioning, caching, and querying the full-text search engine layer built on top of those tweets.

## Step 1: Clarify the Requirements

> [!TIP]
> Always clarify requirements with your interviewer at the start. Defining strict boundaries prevents over-engineering out-of-scope features and keeps your design focused on core bottlenecks.

### Functional Requirements

1. **Keyword Search**: Users can search all public tweets by entering words or phrases.
2. **Boolean Queries**: Search queries can combine multiple keywords using boolean operators (`AND`, `OR`).
3. **Result Sorting**: Search results can be ordered by:
   - `Latest` (Chronological descending order)
   - `Best Matched` (Textual relevance / TF-IDF scoring)
   - `Most Liked` (Popularity based on engagement metrics like likes and retweets)
4. **Pagination**: Results are returned in paginated chunks (e.g., 20 tweets per page).

### Non-Functional Requirements

1. **Low Latency**: Search queries must return matching tweets within **100 milliseconds** to maintain a snappy user experience.
2. **High Availability**: The search infrastructure must guarantee 99.99% availability; search is a primary discovery engine on the platform.
3. **High Scalability & Ingestion Volume**: The system must index **400 million new tweets daily** while serving **500 million search queries daily**.
4. **Fault Tolerance**: The system must withstand index node crashes without losing search coverage or suffering extended service degradation.

### Out of Scope
- Searching within private direct messages (DMs).
- Searching by user handle profile bio, media contents (image/video visual recognition), or spatial bounding boxes.

## Step 2: Estimate the Scale

System scale assumptions provided during the interview:
- **Total Registered Users**: 1.5 Billion
- **Daily Active Users (DAU)**: 800 Million
- **New Tweets Published per Day**: 400 Million
- **Average Payload Size per Tweet**: 300 Bytes (text + essential metadata)
- **Daily Search Queries**: 500 Million

```
                                  SCALE AT A GLANCE
┌──────────────────────────────┬──────────────────────────────┬──────────────────────────────┐
│       400M Tweets/Day        │       500M Searches/Day      │    21 TB Index Memory (RAM)  │
│    (1.38 MB/s Write Load)    │      (5,800 Avg Read QPS)    │   (Spread across 152 nodes)  │
└──────────────────────────────┴──────────────────────────────┴──────────────────────────────┘
```

### Storage Estimation (Raw Tweet Database)

#### 1. Daily Ingestion Volume
$$400\text{M tweets/day} \times 300\text{ bytes} = 120\text{ GB per day}$$

$$\text{Write Throughput} = \frac{120\text{ GB}}{86,400\text{ seconds}} \approx 1.38\text{ MB/second}$$

#### 2. Five-Year Raw Storage Requirement
$$120\text{ GB/day} \times 365\text{ days/year} \times 5\text{ years} = 219\text{ TB} \approx 200\text{ TB}$$

To prevent performance degradation on solid-state drives (SSDs), disk utilization should not exceed 80%:
$$\text{Usable Disk Capacity Required} = \frac{200\text{ TB}}{0.8} = 250\text{ TB}$$

To ensure fault tolerance and disaster recovery, we maintain **two complete copies (Replication Factor = 2)** of all tweet records:
$$\text{Total Raw Database Storage} = 250\text{ TB} \times 2 = 500\text{ TB}$$

#### 3. Storage Server Fleet Sizing
Assuming commodity database servers equipped with 4 TB usable SSD capacity:
$$\text{Database Storage Servers Needed} = \frac{500\text{ TB}}{4\text{ TB/server}} = 125\text{ servers}$$

---

### Throughput Estimation (Search Read Load)

$$\text{Average Search QPS} = \frac{500\text{M searches}}{86,400\text{ seconds}} \approx 5,787 \approx 5,800\text{ queries/second}$$

Assuming a peak-to-average traffic multiplier of $2\times$:
$$\text{Peak Search QPS} = 5,800 \times 2 = 11,600\text{ queries/second}$$

---

### Key Architectural Takeaways from Scale

1. **Data Cannot Fit on One Machine**: 120 GB of new text daily means raw tweets must be horizontally partitioned across 125 database servers.
2. **Full-Text Scanning is Impossible**: Serving 5,800 QPS over 500 TB of disk data requires maintaining a distributed, in-memory inverted index.
3. **Failures are Routine**: Operating over 270+ total servers (storage + index nodes) guarantees daily hardware failures. Automated replication and shard rebuild strategies are non-negotiable.

## Step 4: Define the Data Model

### 1. Tweet Primary Storage (Database)
The primary storage system holds complete tweet payloads. A relational database table (e.g., MySQL or a distributed SQL store) keeps the core records.

```
                          TWEET DATABASE TABLE
┌───────────────────────┬───────────────────────┬─────────────────────────┐
│ TweetID (5 bytes)     │ UserID (8 bytes)      │ TweetText (300 bytes)   │
├───────────────────────┼───────────────────────┼─────────────────────────┤
│ 9841203941            │ 4821039               │ "Building scalable..."  │
│ 9841198512            │ 1092834               │ "Understanding sys..." │
└───────────────────────┴───────────────────────┴─────────────────────────┘
```

#### Why a 5-Byte TweetID?
To calculate the size required for the `TweetID` integer field:
$$\text{Total Tweets in 5 Years} = 400\text{M/day} \times 365\text{ days} \times 5\text{ years} = 730\text{ Billion tweets}$$

- A standard **4-byte unsigned integer** maxes out at $2^{32} - 1 \approx 4.29\text{ Billion}$ IDs (insufficient for 730 billion tweets).
- A **5-byte unsigned integer** supports $2^{40} \approx 1.1\text{ Trillion}$ unique IDs, which comfortably covers 730 billion tweets while conserving memory.
- IDs are generated by a centralized Snowflake-style ID generator service to ensure system-wide uniqueness and coarse chronological sorting.

---

### 2. Dual Data Model Architecture

The search engine relies on three distinct data structures operating across different subsystems:

```
┌─────────────────────────────────────────────────────────────────────────┐
│                      1. PRIMARY TWEET DATABASE                          │
│  Stores complete tweet text and author metadata. Partitioned across 125 │
│  storage servers by Hash(TweetID).                                     │
└─────────────────────────────────────────────────────────────────────────┘
                                     │
                                     ▼
┌─────────────────────────────────────────────────────────────────────────┐
│                     2. IN-MEMORY INVERTED INDEX                         │
│  Maps Word -> [List of 5-byte TweetIDs + Pre-computed Popularity Score]. │
│  Stored entirely in RAM across 152 index nodes.                         │
└─────────────────────────────────────────────────────────────────────────┘
                                     │
                                     ▼
┌─────────────────────────────────────────────────────────────────────────┐
│                  3. REVERSE INDEX (INDEX-BUILDER)                       │
│  Maps IndexServerID -> HashSet<TweetID>. Used exclusively for rapid     │
│  shard rebuilds following server crashes.                               │
└─────────────────────────────────────────────────────────────────────────┘
```

1. **Tweet Row**: Stored in the Tweet Database across 125 servers, partitioned by `Hash(TweetID)`.
2. **Inverted Index Entry**: Resides in RAM on the Index Servers. Maps a single dictionary word key to a list of matching 5-byte `TweetID` values, alongside a pre-computed popularity score.
3. **Reverse Index Record**: Kept by a dedicated **Index-Builder** background service. Maps an `IndexServerID` to a `HashSet<TweetID>` representing every tweet assigned to that index shard.

## Step 5: Draw the High-Level Design

The system decouples **read-heavy search execution** from **durable tweet storage**. Searches read from the fast, memory-resident index cluster first, and only fetch full tweet payloads for the top matching IDs from the database or cache.

![High-Level Design for Twitter Search](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.12-twitter-search-high-level-design.svg)

### High-Level Request Execution Flow

1. **Query Submission**: The client sends a search request (`GET /v1/search?search_terms=system+design`) to the **Load Balancer**.
2. **App Server Routing**: The Load Balancer forwards the request to an available **Application Server**.
3. **Index Retrieval**: The Application Server passes query tokens to the **Index Cluster / Aggregator**. The inverted index searches RAM to instantly find matching `TweetID` lists.
4. **Payload Retrieval**: The Application Server collects top matching `TweetID`s, checks the **Memcached Cache Layer**, and fetches any missing complete tweet payloads from the **Tweet Database Cluster**.
5. **Response Delivery**: The Application Server formats the final payload into JSON and returns it to the user.

## Step 6: Go Deep

Now we explore the deep engineering details of tweet storage, inverted index sizing, sharding strategies, fault tolerance, caching, load balancing, and ranking algorithms.

---

### 1. Storing the Tweets

As established in Step 2, storing five years of tweet data requires 500 TB of total disk space across **125 storage servers**. 

To distribute tweets evenly, we use **Consistent Hashing / Hash Partitioning** on the unique `TweetID`:

$$\text{Storage Server ID} = \text{Hash}(\text{TweetID}) \pmod{125}$$

#### Why Hash Partitioning by TweetID?
- **Uniform Distribution**: Ensures data is evenly distributed across all 125 storage servers, eliminating disk hot spots.
- **Fast Lookups**: When an Application Server needs full text for a set of `TweetID`s returned by the search index, it computes $\text{Hash}(\text{TweetID}) \pmod{125}$ to route point lookups directly to the precise storage node.

---

### 2. Building the Index

#### What is an Inverted Index?
An inverted index functions like the index section at the back of a textbook. Instead of reading every page to find where "database" is mentioned, you look up the word "database" in the index to instantly find page numbers `[12, 45, 89, 102]`.

In Twitter Search:
- **Key**: Tokenized, normalized word (e.g., `"system"`).
- **Value**: Posting list of 5-byte `TweetID`s containing that word.

```
                         INVERTED INDEX STRUCTURE
  Term Key                                   Posting List
┌──────────┐         ┌─────────────────────────────────────────────────────────┐
│ "system" │ ──────> │ TweetID: 9841203941 | Popularity: 85                    │
└──────────┘         ├─────────────────────────────────────────────────────────┤
                     │ TweetID: 9841198512 | Popularity: 62                    │
                     └─────────────────────────────────────────────────────────┘
┌──────────┐         ┌─────────────────────────────────────────────────────────┐
│ "design" │ ──────> │ TweetID: 9841203941 | Popularity: 85                    │
└──────────┘         └─────────────────────────────────────────────────────────┘
```

#### Tokenization & Stop Word Filtering
When a new tweet arrives at the ingestion engine:
1. **Normalization**: Text is converted to lowercase, with punctuation and special characters removed.
2. **Stop Word Removal**: High-frequency non-informative words (e.g., `"the"`, `"an"`, `"is"`, `"at"`, `"and"`) are filtered out.
3. **Posting List Update**: For a 40-word tweet, removing stop words leaves roughly **15 indexable keywords**.

---

#### Index Memory Size Calculation

Holding five years of historical index data in memory is cost-prohibitive. Because 95%+ of user searches target recent events, we keep the past **2 years of tweets** in RAM. Older tweets remain accessible via disk-backed cold storage archives.

##### 1. Vocabulary Key Space Size
Assume indexing covers 300,000 standard English words plus 200,000 proper nouns (names, cities, trending handles) = **500,000 unique terms**.
Assuming an average word length of 5 bytes:
$$\text{Key Memory} = 500,000\text{ words} \times 5\text{ bytes} = 2.5\text{ MB}$$
*(Key memory is negligible).*

##### 2. Posting List Value Space Size
- Total tweets over 2 years ($400\text{M/day} \times 365 \times 2$): **292 Billion tweets**.
- Unique ID size per tweet: **5 bytes**.
- Base 2-year raw ID volume:
  $$292\text{B tweets} \times 5\text{ bytes} = 1,460\text{ GB}$$
- Because each tweet averages **15 indexable keywords** after stop-word filtering, every `TweetID` appears in roughly 15 posting lists:
  $$\text{Total Inverted Index RAM} = 1,460\text{ GB} \times 15 = 21,900\text{ GB} \approx 21.9\text{ TB}$$

##### 3. Index Server Fleet Sizing
Assuming high-memory server instances equipped with **144 GB RAM**:
$$\text{Index Servers Required} = \frac{21,900\text{ GB}}{144\text{ GB/server}} \approx 152\text{ servers}$$

---

### 3. Sharding the Index

Since 21.9 TB of index data cannot fit on a single server, the index must be sharded across the cluster. We evaluate two fundamental sharding architectures:

```
                               SHARDING STRATEGIES
┌──────────────────────────────────────────┬──────────────────────────────────────────┐
│        OPTION A: SHARD BY WORD           │        OPTION B: SHARD BY TWEET          │
│          (Term Partitioning)             │       (Document Partitioning)            │
├──────────────────────────────────────────┼──────────────────────────────────────────┤
│ • IndexNode = Hash(Word) % N             │ • IndexNode = Hash(TweetID) % N          │
│ • Single-word queries touch 1 node       │ • Ingestion writes to 1 local node       │
│ ❌ Hot words overload single nodes       │ ❌ Every query broadcasts to ALL nodes   │
│ ❌ Data distribution is wildly uneven    │ ✅ Perfect memory & write balance        │
└──────────────────────────────────────────┴──────────────────────────────────────────┘
```

#### Option A: Sharding by Word (Term Partitioning)
Each index server is assigned a specific subset of words based on a hash of the word key:
$$\text{Index Server ID} = \text{Hash}(\text{Word}) \pmod{152}$$

- **Pros**: A search query for a single term (e.g., `"design"`) touches exactly one index server.
- **Cons**:
  1. **Hot Word Bottlenecks**: If a major breaking news event occurs, queries for trending terms (e.g., `"election"`, `"earthquake"`) hit the single index server holding that word, causing catastrophic server overload.
  2. **Severe Data Imbalance**: Common words accumulate millions of posting list IDs, while obscure words hold very few. Balancing memory usage across nodes becomes nearly impossible.

#### Option B: Sharding by Tweet (Document Partitioning) — *Chosen Design*
When a tweet arrives, we pick an index server based on a hash of its `TweetID`:
$$\text{Index Server ID} = \text{Hash}(\text{TweetID}) \pmod{152}$$

That designated index server extracts and indexes **all words** contained within that specific tweet locally.

- **Pros**:
  1. **Uniform Workload Distribution**: Write traffic and index memory are perfectly balanced across all 152 servers.
  2. **Elimination of Word Hotspots**: The posting list for a popular keyword like `"breaking"` is evenly distributed across all 152 shards, preventing single-node query hotspots.
- **Cons**:
  1. **Query Scatter-Gather (Fan-out)**: Because any word can reside on any index node, a search query must be broadcast to **all 152 index nodes simultaneously**.

#### Solving Scatter-Gather Overhead: The Aggregator Layer
To manage query broadcasting efficiently, we introduce a dedicated **Aggregator Server** layer between Application Servers and Index Shards.

![Detailed Component Design of Twitter Search](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.12-twitter-search-detailed-component-design.svg)

1. The **Aggregator** receives the query from the Application Server.
2. It scatters the search query to all 152 Index Servers in parallel.
3. Each Index Server searches its local RAM partition and returns its top $K$ local matching `TweetID`s.
4. The Aggregator merges the pre-sorted candidate lists using a $K$-way merge algorithm, sorts the global top results, and returns the final paginated list.

### 4. Fault Tolerance

Operating a fleet of 152 index servers makes hardware failures a certainty. We design a multi-tiered resilience strategy to handle node outages seamlessly.

```
┌───────────────────────────────────────────────────────────────────────────┐
│                     TIER 1: PRIMARY-SECONDARY REPLICATION                 │
│  Each index shard runs an active Primary and Secondary replica. If the    │
│  Primary crashes, the Secondary takes over query handling instantly.      │
└───────────────────────────────────────────────────────────────────────────┘
                                     │
                                     ▼ (If BOTH replicas fail)
┌───────────────────────────────────────────────────────────────────────────┐
│                  TIER 2: REVERSE INDEX REBUILD ENGINE                     │
│  Replacement node asks Index-Builder: "Which TweetIDs belong to me?"     │
│  Index-Builder returns exact set from its Reverse Index HashSet.          │
│  New node fetches raw tweets from DB and rebuilds index in minutes.       │
└───────────────────────────────────────────────────────────────────────────┘
```

#### Tier 1: Primary-Secondary Replication
Each of the 152 index shards runs an active **Primary** and a hot **Secondary** replica. Both nodes receive identical write stream updates. If a Primary node goes offline, a health probe triggers automatic failover to the Secondary replica.

#### Tier 2: Disaster Recovery via the Index-Builder Reverse Index
What happens if **both** the Primary and Secondary replicas for a shard fail simultaneously?

##### The Flawed Brute-Force Approach
A replacement node could scan all 292 billion raw tweets in the primary database, re-computing $\text{Hash}(\text{TweetID}) \pmod{152}$ to locate tweets belonging to its partition. However, scanning hundreds of terabytes takes hours or days, causing missing search results during recovery.

##### The Optimized Solution: Reverse Indexing
To enable rapid shard recovery, we maintain a background **Index-Builder** service. The Index-Builder keeps a **Reverse Index** mapping each `IndexServerID` to the exact set of `TweetIDs` hosted on that shard:

$$\text{Reverse Index Record} = \text{Map}<\text{IndexServerID}, \text{HashSet}<\text{TweetID}>>$$

When a replacement index server boots up:
1. It queries the Index-Builder: *"Provide all TweetIDs assigned to Index Server #42."*
2. The Index-Builder returns the specific `HashSet<TweetID>` from memory.
3. The replacement node issues targeted batch read calls to the Tweet Database Cluster for only those specific `TweetID`s, re-indexing them in minutes.

> [!IMPORTANT]
> The Index-Builder itself is replicated across multiple nodes to ensure its reverse index mapping is never lost.

### 5. Cache

To protect the database cluster from read surges and minimize search response latencies, we deploy an in-memory caching layer (e.g., **Memcached**) in front of the Tweet Database Cluster.

```
                  CACHE ARCHITECTURE & LRU DECAY
  Search Request
        │
        ▼
  Index Search ──► Returns Top 20 TweetIDs
        │
        ▼
┌──────────────┐    Cache Hit (90%+)    ┌─────────────────────────┐
│ Memcached    │ ─────────────────────► │ Return Raw Tweet Payload│
└──────────────┘                        └─────────────────────────┘
        │
        ▼ Cache Miss
┌──────────────┐
│  Tweet DB    │ ──► Fetch from Disk SSD & Backfill Cache
└──────────────┘
```

#### Why Caching Tweet Text is Exceptionally Safe
- **Immutable Content**: Raw tweet text cannot be edited in place after creation.
- **Zero Invalidation Risk**: Cached tweet records never become stale, eliminating complicated cache invalidation logic.

#### Cache Eviction Strategy: Least Recently Used (LRU)
Tweet popularity follows a steep exponential decay curve (power-law distribution). High read traffic occurs immediately following publication, dropping off rapidly within hours. An **LRU (Least Recently Used)** eviction policy naturally retains hot, recently posted tweets in fast memory while evicting cold, dormant records.

### 6. Load Balancing

Load Balancers are deployed at two critical tier boundaries:

1. **Client-to-Application Tier**: Distributes incoming HTTP/REST search requests across Application Gateway nodes.
2. **Application-to-Backend Tier**: Manages traffic routing between Application Servers, Aggregators, Index Shards, and Database nodes.

```
┌──────────┐     ┌───────────────────────┐     ┌───────────────────────┐
│ Clients  │ ──► │  Round Robin Gateway  │ ──► │  Application Servers  │
└──────────┘     └───────────────────────┘     └───────────────────────┘
                                                           │
                                                           ▼
                                               ┌───────────────────────┐
                                               │ Load-Aware Balancer   │
                                               └───────────────────────┘
                                                           │
                                   ┌───────────────────────┴───────────────────────┐
                                   ▼                                               ▼
                       ┌───────────────────────┐                       ┌───────────────────────┐
                       │   Aggregator Nodes    │                       │   Index Shard Nodes   │
                       └───────────────────────┘                       └───────────────────────┘
```

#### Routing Algorithms
- **Round-Robin**: Used at the outer client gateway tier to distribute incoming user requests evenly across stateless application servers.
- **Least Response Time & Load-Aware Balancing**: Used between application servers and index shards. The load balancer monitors real-time CPU usage, memory pressures, and active connection counts across index nodes, dynamically shifting traffic away from slow or heavily loaded backend nodes.

### 7. Ranking

Search queries can request results sorted by **Latest** (chronological order), **Best Matched** (textual relevance), or **Most Liked** (engagement popularity score).

To support fast sorting on large result sets, we implement a **Two-Stage Distributed Ranking Pipeline**:

```
                       TWO-STAGE RANKING PIPELINE

   STAGE 1: LOCAL SHARD RANKING             STAGE 2: AGGREGATOR MERGE
┌─────────────────────────────────┐
│ Index Shard 1 (Top 100 Local)   │ ┐
└─────────────────────────────────┘ │
┌─────────────────────────────────┐ │     ┌──────────────────────────────────┐
│ Index Shard 2 (Top 100 Local)   │ ┼───► │ Aggregator K-Way Merge           │
└─────────────────────────────────┘ │     │ Selects Global Top 20 Matches    │
┌─────────────────────────────────┐ │     └──────────────────────────────────┘
│ Index Shard N (Top 100 Local)   │ ┘
└─────────────────────────────────┘
```

#### Stage 1: Local Shard Ranking
Every inverted index entry stores a pre-computed **Popularity Score** alongside the 5-byte `TweetID`. This score is calculated asynchronously based on engagement metrics:

$$\text{Popularity Score} = w_1 \cdot \text{Likes} + w_2 \cdot \text{Retweets} + w_3 \cdot \text{Replies}$$

When an index shard processes a search request, it sorts its local matching posting list by `Popularity Score` in RAM and returns only its **Top $K$ (e.g., $K = 100$)** candidate matches to the Aggregator.

#### Stage 2: Aggregator Merging
The Aggregator collects top $K$ pre-sorted candidate lists from all 152 index shards. It executes an efficient **$K$-way Merge Sort**, extracts the top global results requested by the client (e.g., 20 items), and fetches complete payload details from the cache/database layer.

## Step 7: Bottlenecks and Failure Points

Every large-scale distributed system has operational vulnerabilities. Identifying these points proactively is essential during system design evaluations:

```
┌───────────────────────────────────────────────────────────────────────────┐
│                     SYSTEMIC BOTTLENECKS & MITIGATIONS                    │
├───────────────────────────────┬───────────────────────────────────────────┤
│ Bottleneck / Failure Point    │ Architectural Mitigation Strategy         │
├───────────────────────────────┼───────────────────────────────────────────┤
│ 1. Word Hotspots              │ Shard index by TweetID (Document Sharding)│
│ 2. Query Scatter-Gather Tail  │ Speculative hedging & aggressive timeouts  │
│ 3. Aggregator Node Failure    │ Stateless aggregators behind load balancer│
│ 4. Index RAM Exhaustion       │ Dynamic retention windowing (e.g. 1.5 yrs)│
└───────────────────────────────┴───────────────────────────────────────────┘
```

### 1. Word Hotspots (Term Skew)
- **Vulnerability**: Under word sharding, a trending topic concentrates query traffic on a single node.
- **Mitigation**: Sharding by `TweetID` spreads every word's posting list evenly across all 152 nodes.

### 2. Query Fan-out & Tail Latency (The Straggler Problem)
- **Vulnerability**: Because tweet sharding broadcasts every query to all 152 index nodes, overall query response time is bounded by the slowest index node (the 99.9th percentile tail latency node).
- **Mitigation**: Implement **hedged requests** (re-issuing slow requests to secondary replicas after a tight 30ms timeout deadline) and aggressive deadline cancellation.

### 3. Aggregator Bottlenecks
- **Vulnerability**: Aggregators perform scatter-gather operations and $K$-way merges for all queries. An aggregator failure could stall active user searches.
- **Mitigation**: Keep aggregators entirely **stateless** and deploy them in redundant auto-scaling pools behind load balancers.

### 4. Index Memory Exhaustion
- **Vulnerability**: Unexpected spikes in daily tweet volume could exceed the 21.9 TB memory allocation across the 152 index nodes.
- **Mitigation**: Dynamically trim the in-memory window (e.g., reducing from 24 months to 18 months) or add new index nodes to the cluster using consistent hashing.

## Where AI Fits in This Design

Modern search engines augment traditional keyword matching with **AI-driven semantic search (Vector Retrieval)**.

```
                         HYBRID SEARCH RETRIEVAL
                              Search Query
                                   │
                 ┌─────────────────┴─────────────────┐
                 ▼                                   ▼
      Inverted Keyword Index               Vector Semantic Index
     (Exact Terms & Hashtags)            (Dense Embeddings / HNSW)
                 │                                   │
                 └─────────────────┬─────────────────┘
                                   ▼
                       Reciprocal Rank Fusion
                       (Hybrid Merged List)
```

### The Keyword Gap
Traditional inverted indexes match exact tokens. A search for `"earthquake"` finds tweets containing that word, but misses tweets like `"The ground was violently shaking in California"` because the literal token is absent.

### AI Integration Architecture

1. **Embedding Generation**: During ingestion, an AI model (e.g., BERT/SBERT fine-tuned encoder) computes a 768-dimensional floating-point **Dense Vector Embedding** capturing the contextual meaning of the tweet text.
2. **Vector Indexing**: Vector embeddings are stored in a distributed **Vector Database Index** (using algorithms like HNSW—Hierarchical Navigable Small World).
3. **Hybrid Retrieval**:
   - The inverted index retrieves **exact token matches** (names, hashtags, specific terms).
   - The vector index retrieves **conceptually similar matches** (semantic meaning).
   - The **Aggregator** uses **Reciprocal Rank Fusion (RRF)** to combine keyword matches and semantic matches into a unified, high-relevance ranking list.

> [!NOTE]
> AI semantic retrieval acts as a secondary complementary index alongside the inverted index, rather than replacing it entirely. Exact term matching remains essential for searching specific names, handles, and hashtags.
