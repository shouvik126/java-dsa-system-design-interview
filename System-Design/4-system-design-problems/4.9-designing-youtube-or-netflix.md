# Designing YouTube or Netflix

Every case study in this section follows the same seven-step methodology detailed in [System Design Interviews: A Step-by-Step Guide](./4.1-system-design-interviews-a-step-by-step-guide.md) and constructs its architecture using components from the [System Design Master Template](./4.2-system-design-master-template.md). Keep both open beside you, and attempt each problem independently before reviewing the solution.

---

## Why YouTube?

YouTube is one of the most popular video sharing platforms globally. Users can upload, stream, rate, and share video content, as well as post comments and report inappropriate videos. Video-on-demand services like Netflix share the majority of this core architecture.

---

#### Try It Yourself

Before reviewing the detailed solution, spend time attempting the design independently. Aim to outline four core aspects:
1. System requirements (functional and non-functional)
2. Capacity & scale estimations
3. API specifications
4. High-level architecture diagram

## Step 1: Clarify the Requirements

> [!TIP]
> Always clarify scope at the very beginning of the interview. Ask targeted questions to establish the precise boundaries and constraints expected by the interviewer.

We will focus on designing a core version of YouTube with the following specifications:

#### Functional Requirements
1. **Upload Video:** Users can upload videos to the platform.
2. **Stream Video:** Users can watch and stream videos smoothly on any device.
3. **Search Video:** Users can search for videos by title or keywords.
4. **Metadata & Comments:** Users can view video stats (views, likes) and post comments.

#### Non-Functional Requirements
1. **High Availability:** The system must remain accessible despite node failures.
2. **Low Latency Playback:** Video streaming startup delay must be minimal.
3. **High Reliability:** Uploaded videos must never be lost or corrupted.

#### Extended Requirements (Out of Core Scope)
* Video recommendations and personalized feeds.
* Most popular / trending videos.
* Channels, subscriptions, watch later lists, and favorites.

*Note: Non-functional requirement 2 trades immediate consistency for high availability. Step 6 demonstrates precisely where this temporary staleness appears.*

---

## Step 2: Estimate the Scale

Always request base metrics from the interviewer. Assume the following numbers for our baseline:
* **Total Users:** 1.5 Billion
* **Daily Active Users (DAU):** 500 Million
* **Average Video Views per User:** 5 videos / day
* **New Videos Uploaded Daily:** 20 Million

#### Read Volume (Video Views)
$$\text{Daily Views} = 500\text{M DAU} \times 5\text{ videos} = 2.5\text{ Billion views/day}$$
$$\text{Read QPS} = \frac{2.5\text{B}}{86,400\text{s}} \approx 29,000\text{ views/second}$$

#### Write Volume (Video Uploads)
$$\text{Write QPS} = \frac{20\text{M}}{86,400\text{s}} \approx 230\text{ uploads/second}$$

#### Storage Estimations
Assuming an average raw video file size of **50 MB**:
$$\text{Daily Raw Video Storage} = 20\text{M uploads} \times 50\text{ MB} = 1\text{ Petabyte / day}$$

#### Bandwidth Estimations
* **Ingress (Upload):** $\frac{1\text{ PB}}{86,400\text{s}} \approx 11.5\text{ GB/s}$
* **Egress (Streaming):** Assuming average stream bandwidth of 2 Mbps per view:
  $$\text{Egress Bandwidth} = 29,000 \times 2\text{ Mbps} = 58\text{ Gbps}$$

#### Key Architectural Takeaways from Estimates
1. **Read-Dominated:** The system is heavily read-dominated. Every performance optimization must prioritize the read path.
2. **Distributed Storage:** No single database or file server can store this. Video storage must be distributed from day one.
3. **CDN Requirement:** High egress bandwidth necessitates a Content Delivery Network (CDN) to handle traffic volume.

## Step 3: Define the API

We expose the service via standard RESTful APIs.

#### 1. Upload Video
```text
uploadVideo(api_dev_key, video_title, video_description, tags[], category_id, default_language, recording_details, video_contents)
```

#### 2. Search Video
```text
searchVideo(api_dev_key, search_query, user_location, maximum_videos_to_return, page_token)
```

#### 3. Stream Video
```text
streamVideo(api_dev_key, video_id, offset, codec, resolution)
```

#### 4. Additional APIs
* `addComment(api_dev_key, video_id, user_id, comment_text)`
* `updateVideoStats(api_dev_key, video_id, action_type)` (where action is like/dislike)

## Step 4: Define the Data Model

The system manages two fundamental categories of data:
1. **Large Binary Media Files:** Video files and thumbnails are large blobs stored in dedicated distributed object storage.
2. **Structured Metadata:** Small, highly structured records stored in a relational SQL database.

#### Database Schema

```text
+-------------------+       +--------------------+       +-------------------+
|       User        |       |       Video        |       |      Comment      |
+-------------------+       +--------------------+       +-------------------+
| UserID (PK)       |1    * | VideoID (PK)       |1    * | CommentID (PK)    |
| Name              |-------| Title              |-------| VideoID (FK)      |
| Email             |       | Description        |       | UserID (FK)       |
| Address           |       | Size               |       | Comment           |
| Age               |       | Thumbnail          |       | TimeOfCreation    |
| RegistrationDetails       | UploaderUserID(FK) |       +-------------------+
+-------------------+       | LikesCount         |
                            | DislikesCount      |
                            | ViewsCount         |
                            | FilePath           |
                            +--------------------+
```

![Database schema for YouTube](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.9-youtube-db-schema.png)
*Figure 01: Database schema showing User, Video, and Comment tables pointing to distributed object storage for media files.*

#### Table Definitions

##### 1. Video Table (MySQL)
* **`VideoID` (PK):** Unique identifier passed into `streamVideo`.
* **`Title`, `Description`, `Size`:** Metadata describing the upload.
* **`Thumbnail`:** Points to the video thumbnail image references.
* **`UploaderUserID` (FK):** References the `UserID` of the account that uploaded the video.
* **`FilePath`:** Stores the URI path to the raw video binary inside distributed object storage.

##### 2. Comment Table (MySQL)
* **`CommentID` (PK):** Unique comment identifier.
* **`VideoID` (FK):** Associated video ID.
* **`UserID` (FK):** Comment author user ID.
* **`Comment`:** Text content of the comment.

##### 3. User Table (MySQL)
* **`UserID` (PK):** Account identifier.
* **`Name`, `Email`, `Address`, `Age`, `RegistrationDetails`:** User profile credentials.

#### Storage Selection (SQL vs. NoSQL)
Relational SQL databases (like MySQL) fit these entities because the metadata features fixed field structures and explicit entity relationships. As metadata grows beyond a single database server, it is partitioned/sharded across multiple machines by `UserID` or `VideoID`.

## Step 5: Draw the High-Level Design

The high-level architecture comprises application servers behind load balancers, backed by partitioned database storage and media file storage.

1. **Processing Queue:** Asynchronous queue where newly uploaded videos wait to be processed for encoding, thumbnail generation, and storage. The queue decouples synchronous client uploads from heavy background execution.
2. **Encoder:** Decodes uploaded source files and re-encodes them into multiple container formats, codecs, and resolutions.
3. **Thumbnail Generator:** Extracts key frames to create video preview thumbnails.
4. **Video & Thumbnail Storage:** Distributed file/object storage holding encoded video chunks and thumbnail images.
5. **User Database:** Relational database storing user profile and authentication data.
6. **Video Metadata Storage:** Relational database cluster hosting video information, file paths, uploader links, stats (views, likes, dislikes), and user comments.

## Step 6: Go Deep

Because YouTube is heavily read-dominant (200:1 read-to-write ratio), architectural deep dives focus primarily on fast video retrieval and high-throughput delivery.

### Where are the videos stored?

Video files are write-once, read-many resources. Once encoded, they are never modified in place. Two storage options suit this pattern:

#### 1. Object Storage (Recommended)
Object stores like [Amazon S3](https://en.wikipedia.org/wiki/Amazon_S3) host files as named binary blobs served directly over HTTP. Object stores automatically replicate blobs across multiple physical storage servers, fulfilling the high-reliability non-functional requirement while seamlessly integrating with CDN networks.

#### 2. Distributed File System (HDFS / GlusterFS)
Distributed file systems like [HDFS](https://en.wikipedia.org/wiki/Apache_Hadoop#HDFS) or [GlusterFS](https://en.wikipedia.org/wiki/GlusterFS) optimize for heavy batch analytics jobs scanning huge sequential datasets. However, HDFS favors overall throughput over individual request latency and requires managing custom replication and name-node infrastructure. Object storage remains the simpler and more cost-effective choice for video streaming.

### How should we manage read traffic?

To isolate read queries from write workloads:
* **Primary-Secondary Database Replication:** Database writes hit primary nodes and replicate asynchronously to read-only secondaries. Secondaries handle the massive read volume.
* **Acceptable Staleness:** Asynchronous replication introduces slight read staleness (a few milliseconds). A user might not view a newly uploaded video for a split second after posting, matching our non-functional requirement trade-off.

### Where are thumbnails stored?

With an average of 5 thumbnails per video, thumbnail count rapidly explodes into billions of tiny files (~5 KB each). Reading billions of tiny files directly from standard disk file systems leads to excessive disk head seeks, degrading latency.

#### Storage in Bigtable
[Bigtable](https://en.wikipedia.org/wiki/Bigtable) is a wide-column key-value store that consolidates multiple small file records into unified sequential disk blocks. It provides fast read access for small data payloads. Furthermore, hot thumbnail images are cached in an in-memory cache to handle high visual view volumes.

### Video uploads

Because video payloads are large, network drops can interrupt uploads. The upload service supports **resumable chunked uploads**, allowing client devices to resume transfers from the last acknowledged byte offset rather than restarting from the beginning.

### Video encoding

When a user completes an upload, the source video is saved in temporary storage and a job is dispatched to the **Processing Queue**. Worker encoding nodes pull tasks from the queue to:
1. Encode video into multiple resolutions (e.g., 360p, 720p, 1080p, 4K).
2. Transcode into multiple streaming formats/codecs (e.g., H.264, VP9, AV1, HLS/DASH).
3. Generate multiple thumbnails.
4. Store formatted streams into distributed object storage.
5. Send an email/notification to the uploader once ready for playback.

### Metadata sharding

With millions of daily uploads, metadata outgrows a single database node. Data must be sharded across multiple machines:

#### Option A: Sharding by UserID
A hash function maps `UserID` to a specific database shard storing all videos uploaded by that user.
* **Pros:** Retrieving all videos for a specific user requires querying a single shard.
* **Cons (Hotspot & Imbalance):** Celebrities or popular creators cause severe read load bottlenecks on single shards. Additionally, heavy uploaders create storage imbalance across partitions.

#### Option B: Sharding by VideoID (Recommended)
`hash(VideoID)` maps each video's metadata randomly across shards.
* **Pros:** Evenly distributes write load and prevents popular accounts from overloading single partitions.
* **Cons:** Searching videos by user requires scatter-gather queries across all database shards. An aggregator server collects and ranks results.
* **Mitigation:** Placing an in-memory cache tier in front of database shards absorbs the vast majority of hot video lookup traffic.

### Video deduplication

Given huge upload volumes, users frequently upload duplicate content (differing slightly in resolution, aspect ratio, overlays, or trimmed length). Deduplication yields massive benefits:
* Reduces storage footprint.
* Maximizes cache efficiency.
* Saves outgoing network bandwidth and energy consumption.

#### Inline Deduplication
Deduplication runs **inline** during upload start rather than post-processing. Matching algorithms (e.g., [Block Matching](https://en.wikipedia.org/wiki/Block-matching_algorithm) or [Phase Correlation](https://en.wikipedia.org/wiki/Phase_correlation)) analyze stream signatures.
* If an exact duplicate exists, upload halts immediately and points to the existing stored copy.
* If a higher quality version is uploaded, the existing copy may be upgraded.
* If a video is a partial chunk/excerpt of an existing video, only the missing segments are uploaded and stored.

### Load balancing

Cache servers use [consistent hashing](../2-system-design-basics/2.13-consistent-hashing.md) to balance traffic and handle server churn smoothly. However, extremely popular viral videos can still overload individual physical cache nodes.

To mitigate hot spots, busy cache servers issue **Dynamic HTTP Redirections** (e.g., HTTP 302 Redirect), directing client devices to less loaded cache servers within the same cluster or edge location.

*Trade-off:* HTTP redirections add an extra HTTP round-trip delay before video playback begins.

### Cache

An in-memory cache cluster (e.g., Memcached / Redis) sits in front of database servers to store hot metadata rows:
* **Eviction Policy:** **Least Recently Used (LRU)** discards stale records first, matching video viewing patterns where popularity declines over time.
* **80-20 Rule:** 20% of popular videos generate 80% of daily traffic. Caching **20% of the daily read volume** of metadata and video chunks absorbs ~80% of overall traffic.

---

### Content Delivery Network (CDN)

A CDN is a geographically distributed network of edge caching servers that delivers content to users with low latency based on location proximity.

* **Popular Videos:** CDNs cache and serve popular video content directly from edge memory/SSD nodes close to end users.
* **Long-Tail Videos:** Obscure or infrequently viewed videos (1 to 20 views per day) are served directly from origin object storage servers in central data centers to minimize CDN storage costs.
* **Immutability Advantage:** Encoded video files are **immutable** (written once, never modified), making CDN caching safe from cache invalidation or staleness issues. Only dynamic metadata (like view counters) requires database coordination.

## Step 7: Bottlenecks and Failure Points

#### Identifying System Bottlenecks
1. **Database Node Failure:** Mitigated using consistent hashing across database shards and automated failover to read secondaries.
2. **Viral Video Surge:** Absorbed by CDN edge nodes, multi-tier LRU memory caches, and dynamic HTTP redirection.
3. **Processing Queue Backlog:** If encoding or thumbnail workers fall behind, new upload availability is delayed, but **existing video streaming remains completely unaffected**. Playback depends solely on object storage, caches, and CDNs.

## Where AI Fits in This Design

In a video platform architecture, AI components integrate into the **asynchronous upload processing pipeline**:

```text
[ Upload Stream ] ---> ( Processing Queue ) ---> [ Encoding Workers ]
                                          ---> [ Thumbnail Generator ]
                                          ---> [ Speech-to-Text AI (Captions) ]
                                          ---> [ Content Moderation AI (Safety) ]
```

1. **Automatic Captions (Speech-to-Text):** Automatic speech recognition (ASR) models transcribe audio tracks into subtitle text files stored alongside video metadata.
2. **Content Moderation (Visual & Audio Classifiers):** Computer vision and audio classification models scan video frames and audio for policy violations (e.g., copyright infringement, explicit content), routing flagged items to human moderation queues.

#### Architectural Principles for AI Tasks
* **Captions are non-blocking:** Caption generation failure must never block video publishing. If AI processing fails, the video goes live immediately, and captions append later.
* **Moderation policy control:** Moderation can be configured as blocking or non-blocking depending on product compliance rules.
* **Cost awareness:** AI model processing scales linearly with uploaded video minutes, representing an ongoing computational cost per upload.

---

#### Key Takeaways & Interview Guidance

> [!IMPORTANT]
> **Summary of Essential System Design Takeaways for Interviews:**
> * **Read-Heavy Ratio (200:1):** 46,000 views/sec vs 230 uploads/sec. Prioritize read-side caching and CDN distribution.
> * **Data Storage Separation:** Store large immutable video files in **Distributed Object Storage (Amazon S3)**, structured metadata in **Sharded MySQL**, and tiny hot thumbnails in **Bigtable** (to eliminate scattered disk seeks).
> * **Asynchronous Processing:** Return **HTTP 202 (Accepted)** on upload initiation and push video files to a processing queue for decoupled encoding, thumbnail generation, and AI captioning/moderation.
> * **80-20 Caching & CDN:** Cache the top 20% of daily read volume in RAM using LRU eviction policies, and serve hot content via CDNs while serving long-tail videos directly from origin servers.
> * **Sharding Strategy:** Shard metadata by `VideoID` to prevent single-creator hotspots, utilizing fronted cache clusters to absorb scatter-gather read latencies.
