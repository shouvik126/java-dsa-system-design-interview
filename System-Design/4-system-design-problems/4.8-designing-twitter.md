# Designing Twitter

Every case study in this chapter follows the same seven steps from [System Design Interviews: A step by step guide](./4.1-system-design-interviews-a-step-by-step-guide.md), and builds its design from the components in the [System Design Master Template](./4.2-system-design-master-template.md). Keep both open beside you, and try each problem yourself before reading the solution.

## What is Twitter?

Twitter is an online microblogging and social networking platform that allows users to publish, read, and interact with short messages known as "tweets." 

Users access the service through web browsers, mobile applications (iOS and Android), or legacy SMS interfaces. Unregistered public visitors can read public posts, whereas registered account holders can post new tweets, follow other users, favorite (like) posts, and view personalized timelines.

### The Engineering Challenge

The primary architectural challenge of Twitter centers on **timeline generation and rendering**. Fetching and aggregating real-time posts from hundreds of followed accounts for hundreds of millions of daily active users—billions of times per day—presents an immense data aggregation challenge. Because read requests outnumber write operations by orders of magnitude, nearly every engineering choice in this architecture is tailored to minimize read latency under a strict **200-millisecond response budget**.

## Step 1: Clarify the Requirements

> [!TIP]
> Always clarify requirements at the beginning of the interview. Ask questions until you know the exact scope of the system the interviewer has in mind.

We will design a simplified, production-grade version of Twitter focusing on the following requirements:

#### Functional Requirements
1. **Post Tweets**: Registered users can publish short text messages (up to 140 characters).
2. **Follow System**: Users can follow and unfollow other accounts.
3. **Favorites (Likes)**: Users can mark tweets as favorites.
4. **Timeline Generation**: The service generates and displays a user's home timeline, aggregating top recent tweets from all accounts the user follows.
5. **Rich Media Attachments**: Tweets can include embedded photos and videos.

#### Non-Functional Requirements
1. **High Availability**: The system must remain continuously operational despite server, rack, or network failures.
2. **Low Latency Timelines**: Generating and displaying a timeline must complete within **200 milliseconds**.
3. **Eventual Consistency**: The architecture favors availability over immediate consistency (CAP theorem trade-off). A slight delay before a newly posted tweet propagates across all follower timelines is completely acceptable.

#### Extended Requirements
1. **Search**: Full-text keyword and hashtag search.
2. **Replies & Threading**: Responding directly to specific tweets.
3. **Trending Topics**: Real-time tracking of popular keywords and hashtags.
4. **User Mentions & Tagging**: Alerting users when referenced in a post.
5. **Notifications**: Push notifications for likes, retweets, and mentions.
6. **Account Recommendations ("Who to follow")**: Suggesting relevant accounts based on social graph analysis.
7. **Curated Collections ("Moments")**: Categorized groupings of top daily news stories.

*Note: We design the core functional list first, then address extended requirements in Step 6.*

## Step 2: Estimate the Scale

System scale assumptions provided during the interview:
- **Total Registered Users**: 1 Billion
- **Daily Active Users (DAU)**: 200 Million
- **New Tweets Published per Day**: 100 Million
- **Average Follows per User**: 200 accounts

#### Favorites Volume
Assuming each DAU favorites an average of 5 tweets daily:

$$200\text{M active users} \times 5\text{ favorites/day} = 1\text{ Billion favorites per day}$$

#### Read Load & Tweet Views
Assuming an average DAU visits their home timeline 2 times a day and views 5 profile pages daily. If each page view loads 20 tweets:

$$\text{Page views per user/day} = (2\text{ timeline visits} + 5\text{ profile visits}) = 7\text{ page views/day}$$

$$\text{Total daily page views} = 200\text{M DAU} \times 7\text{ page views} = 1.4\text{ Billion page views/day}$$

$$\text{Total daily tweet views} = 1.4\text{B page views} \times 20\text{ tweets/page} = 28\text{ Billion tweet views per day}$$

#### Storage Estimates

##### Text & Metadata Storage
Each tweet contains up to 140 characters. To support internationalization (UTF-8 multi-byte encoding), we budget 2 bytes per character. Additional metadata (Tweet ID, User ID, timestamp, geo-location) requires 30 bytes.

$$\text{Size per tweet} = (140\text{ characters} \times 2\text{ bytes}) + 30\text{ bytes metadata} = 310\text{ bytes}$$

$$\text{Daily Text Storage} = 100\text{M new tweets} \times 310\text{ bytes} = 31\text{ GB per day}$$

$$\text{5-Year Text Storage} = 31\text{ GB/day} \times 365\text{ days} \times 5\text{ years} \approx 56.5\text{ TB}$$

##### Media Storage (Photos & Videos)
Assume 1 out of 5 tweets contains a photo (~200 KB) and 1 out of 10 tweets contains a video (~2 MB):

$$\text{Daily Photo Storage} = \frac{100\text{M tweets}}{5} \times 200\text{ KB} = 20\text{M photos} \times 200\text{ KB} = 4\text{ TB per day}$$

$$\text{Daily Video Storage} = \frac{100\text{M tweets}}{10} \times 2\text{ MB} = 10\text{M videos} \times 2\text{ MB} = 20\text{ TB per day}$$

$$\text{Total Daily Media Storage} = 4\text{ TB} + 20\text{ TB} = 24\text{ TB per day}$$

#### Bandwidth Estimates

##### Ingress (Incoming Write Data)
$$\text{Media Ingress} = \frac{24\text{ TB}}{86,400\text{ seconds}} \approx 290\text{ MB/s}$$

##### Egress (Outgoing Read Data)
Every tweet displayed on a client screen consumes egress bandwidth:
- **Text Egress**:

  $$\frac{28\text{B tweet views} \times 280\text{ text bytes}}{86,400\text{ s}} \approx 91\text{ MB/s}$$

- **Photo Egress** ($28\text{B views} / 5 = 5.6\text{B}$ photo views):

  $$\frac{5.6\text{B photos} \times 200\text{ KB}}{86,400\text{ s}} \approx 13\text{ GB/s}$$

- **Video Egress** (Assuming users watch 1 out of 3 videos in their timeline $\rightarrow 28\text{B} / 10 / 3 = 933.3\text{M}$ video views):

  $$\frac{933.3\text{M video views} \times 2\text{ MB}}{86,400\text{ s}} \approx 22\text{ GB/s}$$

- **Total Egress Bandwidth** $\approx 91\text{ MB/s} + 13\text{ GB/s} + 22\text{ GB/s} \approx 35\text{ GB/s}$

#### Throughput Rates & Read-to-Write Ratio
- **Write QPS**:

  $$\frac{100\text{M tweets}}{86,400\text{ s}} \approx 1,157\text{ writes per second (average)}$$

- **Read QPS**:

  $$\frac{28\text{B tweet views}}{86,400\text{ s}} \approx 324,074\text{ reads per second (average)}$$

- **Read-to-Write Ratio**: $\approx 280 : 1$

**Key Insight**: The system is overwhelmingly read-heavy. Because every single write generates nearly 280 read requests, all performance optimizations and caching strategies must target the read path.

## Step 3: Define the API

We expose RESTful HTTP APIs to manage client interactions.

#### 1. Post a Tweet
```http
tweet(api_dev_key, tweet_data, tweet_location?, user_location?, media_ids?)
```
- `api_dev_key` (*string*, required): Developer API key used for authentication and developer quota throttling.
- `tweet_data` (*string*, required): Text content of the tweet (up to 140 characters).
- `tweet_location` (*string*, optional): Geographic coordinates (`latitude, longitude`) referenced by the tweet.
- `user_location` (*string*, optional): Geographic coordinates of the posting user.
- `media_ids` (*array of numbers*, optional): Identifiers of attached media assets uploaded prior to this call.
- **Returns**: JSON object containing the URL of the created tweet, or an HTTP error status code.

> [!NOTE]
> **Media Decoupling Pattern**: Binary assets (images and videos) are uploaded to object storage *before* calling `tweet()`. Passing pre-assigned `media_ids` keeps the post API payload lightweight, prevents large files from holding open web connections, and enables atomic retries if text submission fails.

#### 2. Follow / Unfollow User
```http
follow(api_dev_key, target_user_id)
unfollow(api_dev_key, target_user_id)
```

#### 3. Favorite Tweet
```http
favorite(api_dev_key, tweet_id)
```

#### 4. Fetch Home Timeline
```http
getTimeline(api_dev_key, count, max_tweet_id?)
```
- Retrieves top recent tweets from accounts followed by the user.
- `count` (*number*): Number of tweets requested per page.
- `max_tweet_id` (*string*, optional): Cursor parameter used for pagination.

#### 5. Fetch User Profile Tweets
```http
getUserTweets(api_dev_key, user_id, count, max_tweet_id?)
```

#### Cursor-Based Pagination
Timeline endpoints use `max_tweet_id` cursor pagination rather than traditional offset-based pagination (`page=2&limit=20`). Offset pagination degrades in database performance at scale and suffers from skipped or duplicate posts when new tweets arrive while scrolling. Setting `max_tweet_id` to the smallest `TweetID` from the previous batch guarantees deterministic pagination.

## Step 4: Define the Data Model

The database schema manages four core entities: `User`, `Tweet`, `UserFollow`, and `Favorite`.

![Database Schema for Twitter](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.8-twitter-database-schema.png)

#### Entity Descriptions

1. **`Tweet` Table**:
   - `TweetID` (*64-bit integer*, Primary Key): Universal unique identifier containing an embedded timestamp (eliminating the need for a separate creation timestamp column).
   - `UserID` (*bigint*, Foreign Key): Author of the tweet.
   - `Content` (*varchar(140)*): Tweet text.
   - `MediaIDs` (*array / string*): Array referencing binary object storage.
   - `OriginalTweetID` (*bigint*, optional): Null for standard posts; holds parent `TweetID` for retweets without duplicating content.
   - `Latitude` / `Longitude` (*double*, optional): Geolocation coordinates.

2. **`User` Table**:
   - `UserID` (*bigint*, Primary Key): Unique user ID.
   - `Name`, `Email`, `CreationTimestamp`: Core profile attributes.

3. **`UserFollow` Table**:
   - `FollowerID` (*bigint*, Foreign Key)
   - `FolloweeID` (*bigint*, Foreign Key)
   - Composite Primary Key: `(FollowerID, FolloweeID)` (8 bytes total per row).

4. **`Favorite` Table**:
   - `UserID` (*bigint*, Foreign Key)
   - `TweetID` (*bigint*, Foreign Key)
   - Composite Primary Key: `(UserID, TweetID)`. With 1 billion favorites arriving daily, this small table experiences the highest write throughput.

#### SQL vs. NoSQL Considerations
- **Relational Databases (MySQL/PostgreSQL)**: Provide structured schemas and ACID guarantees. However, scaling to 30 GB/day of text and billions of follow/favorite records requires manual database sharding.
- **NoSQL Databases (Cassandra/DynamoDB)**: Offer native horizontal partitioning, high write throughput, and flexible key-value lookups ideal for `UserFollow` and `Favorite` tables.

## Step 5: Draw the High-Level Design

At a high level, incoming request traffic passes through Load Balancers to stateless Application Servers. Read queries interact with an In-Memory Cache tier, while persistent storage is split between a Sharded Database cluster (for text/metadata) and Object Storage/CDNs (for media assets).

![High-Level System Architecture for Twitter](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.8-twitter-high-level-design.png)

#### Traffic Dynamics & Capacity Planning
- **Average Load**: ~1,150 writes/sec and ~325,000 reads/sec.
- **Peak Load Factor**: Traffic spikes dramatically during major global events or breaking news. The architecture must be engineered for peak loads—scaling to thousands of writes/sec and over 1,000,000 reads/sec.

## Step 6: Go Deep

### Sharding the data

With 100 million new tweets arriving daily (~30 GB/day of metadata) and 325K read QPS, no single database server can store all data or handle the query throughput. We must shard (partition) the database across multiple physical nodes.

#### Evaluation of Partitioning Strategies

1. **Sharding by UserID**:
   Assign all data belonging to a specific user to a designated shard using `hash(UserID) % total_shards`.
   - *Advantage*: Profile pages (`getUserTweets`) and follow lists for a single user reside on a single server, making user-specific queries fast.
   - *Disadvantage*: **Hot User Problem**. High-profile celebrity accounts generate massive read/write traffic concentrated on a single shard, overwhelming that node. Furthermore, storage grows unevenly as some users post far more tweets than others.

2. **Sharding by TweetID**:
   Distribute tweets randomly across shards using `hash(TweetID) % total_shards`.
   - *Advantage*: Uniformly distributes write and read traffic across all database shards, resolving the hot user bottleneck.
   - *Disadvantage*: **Scatter-Gather Read Latency**. To generate a home timeline, an application server must fetch the follow list, query *every single database shard* for recent tweets from those followees, collect the results, and merge-sort them. A single slow database node will degrade the overall response time.

3. **Sharding by Tweet Creation Time**:
   Partition data into chronological database tables (e.g., one shard per day or per month).
   - *Advantage*: Fetching recent tweets requires querying only the current time-range shard.
   - *Disadvantage*: Severe write hotspotting. All current write operations and the majority of read queries target *only* the latest shard holding today's data, leaving older shards virtually idle.

#### Optimal Solution: Custom 64-Bit Epoch-Based TweetID

To combine the uniform write distribution of TweetID partitioning with fast chronological sorting, we embed an epoch timestamp directly inside the primary key `TweetID`.

![Structure of Epoch Time and Sequence Number in TweetID](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.8-twitter-tweet-id-structure.png)

##### 48-Bit / 64-Bit TweetID Construction
- **Timestamp Component**: Counts seconds (or milliseconds) elapsed since a fixed custom epoch.
- **Sequence Component**: An auto-incrementing local counter that resets every second.

For example, a 48-bit TweetID layout:
- 31 bits for Epoch Time (covers ~1.6 billion seconds $\approx 50$ years).
- 17 bits for Sequence Counter (allows $2^{17} = 131,072$ unique tweets per second).

To scale time resolution to milliseconds and span 100 years, we expand the key to **64 bits (8 bytes)**:
- 41 bits for Epoch Time in milliseconds ($2^{41} \approx 69$ years).
- 10 bits for Machine/Worker ID (supports up to 1,024 independent generator nodes).
- 12 bits for Local Sequence Counter ($2^{12} = 4,096$ tweets per millisecond per node).

> [!IMPORTANT]
> **Eliminating Secondary Indices**: Embedding the creation timestamp inside the primary key `TweetID` removes the need for a secondary B-tree index on `CreationTime`. Secondary indices significantly increase write latency because every insert requires updating index trees across disk blocks. With timestamp-bearing TweetIDs, primary key range scans inherently return chronologically ordered records.

##### Key Generation Architecture: Snowflake vs. Step-and-Offset
- **Dual Generator (Step & Offset)**: Running two key generation servers where Server 1 yields even IDs ($2, 4, 6\dots$) and Server 2 yields odd IDs ($1, 3, 5\dots$). While simple, changing the cluster size (e.g., moving from 2 to 3 generators) alters the step size globally and requires downtime.
- **Twitter Snowflake Architecture**: Each generator node embeds its assigned 10-bit Machine ID into every ID it produces. Nodes generate globally unique, time-ordered 64-bit IDs independently without locks, network coordination, or inter-node communication. Machine IDs are assigned at node startup via ZooKeeper or cloud metadata.

### Caching

To serve 325,000 read queries per second within a 200 ms latency SLA, we must minimize database access. An in-memory cache layer (e.g., Memcached or Redis) sits between application servers and database shards.

![Detailed Architecture with Caching and Partitioning for Twitter](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.8-twitter-detailed-design.png)

#### Cache Sizing & Pareto Principle
Applying the **80/20 Pareto Principle**, 20% of tweets account for 80% of read traffic. Furthermore, over 80% of users view tweets published within the last 3 days.

We cache all tweet metadata and text published over the **last 3 days**:

$$\text{Daily Text Storage} = 30\text{ GB/day}$$

$$\text{3-Day Cache Capacity} = 30\text{ GB/day} \times 3\text{ days} = 90\text{ GB}$$

A 90 GB dataset fits into memory on a modest cache cluster. We replicate this 90 GB cache across multiple cache nodes to distribute read traffic and ensure high availability.

#### In-Memory Data Structure & Eviction Policy
- **Cache Data Structure**: A Hash Table mapping `OwnerID` $\rightarrow$ Doubly Linked List of recent Tweet objects.
- **Insert/Eviction Mechanics**: New tweets from a user are pushed to the head of their doubly linked list ($O(1)$ time). When memory limits are reached, older tweets are evicted from the tail of the list.
- **Eviction Strategy**: **Least Recently Used (LRU)** ensures that active tweets remain in memory while stale content is evicted.

### Generating the timeline

Timeline assembly can follow a **Pull (Read-path Merge)** or **Push (Write-path Fan-Out)** architecture.

#### 1. Pull Model (Merge on Read)
When a user requests their home timeline:
1. The application server fetches the list of accounts the user follows (`UserFollow` table).
2. The server queries all database shards and caches for recent tweets authored by those followees.
3. The server collects the tweets, merge-sorts them by timestamp, and returns the top $N$ items.

- *Pros*: Simple write path; publishing a tweet requires writing only one database record.
- *Cons*: Heavy read latency ($O(K \times \text{shards})$ network calls) and high CPU load during timeline retrieval.

#### 2. Push Model (Fan-Out on Write)
Each user maintains a pre-computed timeline inbox cache.
1. When a user posts a tweet, background worker processes fetch the author's follower list.
2. The worker injects the new Tweet ID directly into the pre-computed timeline cache of **every follower**.
3. When a user opens Twitter, their timeline is retrieved in $O(1)$ time from their dedicated cache inbox.

- *Pros*: Extremely fast timeline reads ($O(1)$ lookup).
- *Cons*: **Write Amplification / Celebrity Bottleneck**. When a celebrity account with 50 million followers posts a tweet, the fan-out service must execute 50 million write operations into follower inbox caches.

#### 3. Hybrid Timeline Model
To balance read performance and write amplification:
- **Standard Accounts (< 10,000 followers)**: Use the **Push Model**. Tweets are fanned out into follower inbox caches at write time.
- **Celebrity Accounts (> 10,000 followers)**: Use the **Pull Model**. Tweets from celebrity accounts are *not* fanned out.
- **Timeline Assembly**: When a user opens their timeline, the system retrieves their pre-computed push inbox cache, fetches the latest tweets from any celebrity accounts they follow, and executes a lightweight in-memory merge-sort.

### Replication and fault tolerance

- **Primary-Replica Topology**: Each database shard uses a Primary-Replica (Master-Slave) setup.
- **Read Offloading**: Write operations target the Primary node, which asynchronously replicates data to multiple Replica nodes. All timeline read queries target Replica nodes, spreading read traffic evenly.
- **Automated Failover**: Consensus management services (e.g., ZooKeeper or Raft-based orchestrators) monitor node health. If a Primary node fails, a Replica is automatically promoted to Primary.

---

### Load balancing

Load balancers operate at three distinct architectural boundaries:
1. **Client $\rightarrow$ Application Server Tier**: Spreads incoming web/mobile HTTP traffic across stateless application instances.
2. **Application Server $\rightarrow$ Cache / Aggregation Tier**: Routes internal timeline assembly requests.
3. **Aggregation Server $\rightarrow$ Database Shards**: Distributes query loads across database replicas.

#### Routing Algorithms
- **Round Robin**: Distributes requests sequentially across servers. Simple to implement and automatically removes unhealthy nodes from rotation, but does not account for variations in backend server load.
- **Load-Aware / Least Connections Routing**: Dynamically monitors CPU utilization, memory consumption, and active request counts on backend nodes, steering traffic away from overloaded servers.

---

### Serving the extended requirements

1. **Retweets**: Represented as a `Tweet` record containing an `OriginalTweetID` reference pointing to the parent post, avoiding body text duplication.
2. **Trending Topics**: Real-time streaming analysis (e.g., Apache Flink or sliding-window counters) computes hashtag frequencies over time windows of $N$ seconds, updated every $M$ seconds.
3. **Who to Follow**: Graph algorithms traverse 2-hop and 3-hop follow connections (friends of friends). Candidate accounts are ranked using machine learning models based on mutual followers, location, and shared interests.
4. **Moments**: News aggregation pipelines cluster related tweets by topic using supervised learning and text clustering algorithms.
5. **Search**: Dedicated search cluster (e.g., Elasticsearch/Lucene) indexing tweet text, hashtags, and author attributes in inverted index tables.

## Step 7: Bottlenecks and Failure Points

1. **Scatter-Gather Read Overhead**: On TweetID-sharded databases, cache misses force timeline queries to hit every database shard. Protecting the cache layer is essential to prevent database overload.
2. **Hot Key & Cache Stampedes**: If a popular tweet or celebrity profile drops out of cache, a surge of simultaneous read requests can hit database shards at once. Using cache request coalescing (Singleflight pattern) mitigates this risk.
3. **Key Generator Failure**: If Snowflake key generation nodes lose network connectivity or system clock synchronization (NTP drift), write operations halt. Nodes must refuse to issue IDs if clock rollback is detected.
4. **Monitoring & Capacity Telemetry**:
   - Write throughput (tweets per second).
   - Read delivery volume and P99 timeline latency (target < 200 ms).
   - Cache hit ratio (target > 99%).

## Where AI Fits in This Design

Modern timelines often display algorithmically ranked content rather than purely reverse-chronological feeds. AI models fit into the timeline pipeline via a **Two-Stage Architecture**:

1. **Stage 1: Candidate Retrieval (Systems Tier)**
   The core system uses the deterministic caching and sharding infrastructure described in Step 6 to fetch a candidate pool of ~500 recent tweets from followed accounts.
2. **Stage 2: ML Ranking (AI Tier)**
   The candidate pool is passed to a machine learning ranking model (e.g., Deep Neural Networks or Gradient Boosted Decision Trees). The model scores each tweet based on predicted engagement probability (likes, retweets, replies, dwell time) using historical user interaction features.

```
+------------------+     Fetch ~500 Tweets     +----------------------+     Ranked Feed     +---------------+
| Timeline Service | ------------------------> | Candidate Retrieval  | ------------------> | User Viewport |
+------------------+                           +----------------------+                     +---------------+
                                                          |
                                                          v
                                               +----------------------+
                                               |  AI Ranking Model    |
                                               | (Scores & Reorders)  |
                                               +----------------------+
```

> [!NOTE]
> The AI model never queries the primary database or searches the global tweet archive. It operates strictly on a small candidate set pre-fetched by the retrieval layer. The underlying database sharding, Snowflake ID scheme, and 3-day caching architecture remain identical whether serving chronological or AI-ranked feeds.

### Summary & Key Takeaways

| Metric / Challenge | Architectural Solution |
| :--- | :--- |
| **Read-Heavy Asymmetry (280:1)** | In-memory 3-day tweet cache (90 GB RAM) with LRU eviction serving > 99% of read traffic. |
| **Timeline Latency Budget (< 200 ms)** | Hybrid Push/Pull model (Push for standard accounts, Pull for celebrity accounts). |
| **Partitioning & Hot Users** | Shard by 64-bit TweetID using Twitter Snowflake key generation. |
| **Eliminating Index Overhead** | Embed epoch creation timestamp inside `TweetID` to eliminate secondary indices on creation time. |
| **High Availability & Durability** | Primary-Replica database sharding with automated consensus failover. |
