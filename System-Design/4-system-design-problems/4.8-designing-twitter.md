# Designing Twitter

Every case study in this section follows the same seven-step methodology detailed in [System Design Interviews: A Step-by-Step Guide](./4.1-system-design-interviews-a-step-by-step-guide.md) and constructs its architecture using components from the [System Design Master Template](./4.2-system-design-master-template.md). Keep both open beside you, and attempt each problem independently before reviewing the solution.

---

## What is Twitter?

Twitter is an online social networking service where users publish and consume short messages known as "tweets." Registered users can post, like, and read tweets, while unregistered visitors can only read public tweets. Users access Twitter across web browsers, SMS, and mobile applications.

The central challenge in designing Twitter lies in the **timeline generation**. A single timeline request gathers fresh tweets from hundreds of followed accounts, executing billions of times per day. Virtually every architectural decision in this design prioritizes optimizing this critical read path.

## Step 1: Clarify the Requirements

> [!TIP]
> Always clarify scope at the very beginning of the interview. Ask targeted questions to establish the precise boundaries and constraints expected by the interviewer.

We will focus on designing a core version of Twitter with the following specifications:

#### Functional Requirements
1. **Posting Tweets:** Users can create and post new tweets.
2. **User Following:** A user can follow or unfollow other accounts.
3. **Favorites / Likes:** Users can mark tweets as favorites.
4. **Timeline Generation:** The service generates and displays a user's timeline, containing top tweets from accounts they follow.
5. **Media Support:** Tweets can contain attached photos and videos.

#### Non-Functional Requirements
1. **High Availability:** The system must remain available and operational despite server failures.
2. **Low Latency Timeline:** Fetching or generating a timeline must complete within **200 milliseconds**.
3. **Eventual Consistency:** High availability is prioritized over strict consistency. Brief delays in seeing newly posted tweets across all timelines are acceptable.

#### Extended Requirements (Out of Core Scope)
* Searching tweets.
* Replying to tweets or threaded conversations.
* Trending topics (popular hashtags and search queries in real time).
* Tagging other users.
* Push notifications for tweet activity.
* "Who to follow" account recommendations.
* "Moments" (curated collections of top stories and tweets).

We will establish the core design first, then revisit extended features in Step 6.

## Step 2: Estimate the Scale

Always request base metrics from the interviewer. Assume the following numbers for our baseline:
* **Total Users:** 1 Billion
* **Daily Active Users (DAU):** 200 Million
* **New Tweets Daily:** 100 Million
* **Average Follows per User:** 200 accounts

#### Daily Favorites / Likes Volume
Assuming each active user favorites 5 tweets per day on average:
$$\text{Favorites per day} = 200\text{M DAU} \times 5 = 1\text{ Billion favorites/day}$$

#### Tweet-Views (Read Volume)
Assuming a user views their timeline twice daily and visits 5 profile pages, with each page displaying 20 tweets:
$$\text{Daily Tweet Views} = 200\text{M DAU} \times ((2 + 5) \times 20\text{ tweets}) = 28\text{ Billion tweet-views/day}$$

#### Storage Estimations
Each tweet contains up to 140 characters. Allowing 2 bytes per character for multi-language UTF-8 support (uncompressed), plus 30 bytes for metadata (Tweet ID, Timestamp, User ID):
$$\text{Tweet Size} = (140 \times 2\text{ bytes}) + 30\text{ bytes metadata} = 310\text{ bytes per tweet}$$
$$\text{Daily Text Storage} = 100\text{M tweets} \times 310\text{ bytes} = 30\text{ GB / day}$$

#### Media Storage
Assuming 1 in 5 tweets contains a photo (~200 KB) and 1 in 10 contains a video (~2 MB):
* **Photos:** $\frac{100\text{M}}{5} \times 200\text{ KB} = 20\text{M} \times 200\text{ KB} \approx 4\text{ TB / day}$
* **Videos:** $\frac{100\text{M}}{10} \times 2\text{ MB} = 10\text{M} \times 2\text{ MB} \approx 20\text{ TB / day}$
* **Total Media Storage:** $\approx 24\text{ TB / day}$

#### Bandwidth Estimations
* **Ingress (Write Data):** 24 TB media / 86,400 seconds $\approx 290\text{ MB/s}$.
* **Egress (Read Data):** Assuming users watch 1 out of 3 videos displayed:
  * Text egress: $\frac{28\text{B} \times 280\text{ bytes}}{86,400\text{s}} \approx 93\text{ MB/s}$
  * Photo egress: $\frac{28\text{B} / 5 \times 200\text{ KB}}{86,400\text{s}} \approx 13\text{ GB/s}$
  * Video egress: $\frac{28\text{B} / 10 / 3 \times 2\text{ MB}}{86,400\text{s}} \approx 22\text{ GB/s}$
  * **Total Egress:** $\approx 35\text{ GB/s}$

#### Key Takeaways from Estimates
* **Writes (Posts):** $\frac{100\text{M}}{86,400\text{s}} \approx 1,150\text{ tweets/second}$
* **Reads (Views):** $\frac{28\text{B}}{86,400\text{s}} \approx 325,000\text{ tweet-views/second}$
* **Read-to-Write Ratio:** $\approx 280:1$

This is a heavily **read-dominated system**. Consequently, optimization resources must focus on the read path.

## Step 3: Define the API

We expose the service via standard RESTful APIs. The primary endpoint is for publishing new tweets:

```text
tweet(api_dev_key, tweet_data, tweet_location, user_location, media_ids)
```

**Parameters:**
* `api_dev_key` (*string*): Developer API key used for authentication and rate-limiting quota enforcement.
* `tweet_data` (*string*): Text payload of the tweet (up to 140 characters).
* `tweet_location` (*string*, optional): Longitude and latitude coordinates associated with the tweet content.
* `user_location` (*string*, optional): Current geographic coordinates of the author.
* `media_ids` (*number[]*, optional): Array of media identifiers previously uploaded.

**Returns:** (*string*) Returns the permalink URL of the published tweet upon success, or an appropriate HTTP error status on failure.

#### Additional Core APIs

```text
follow(api_dev_key, target_user_id)
unfollow(api_dev_key, target_user_id)
favorite(api_dev_key, tweet_id)
getTimeline(api_dev_key, count, max_tweet_id)
getUserTweets(api_dev_key, user_id, count, max_tweet_id)
```

* `follow` and `favorite` write records into their respective relational mapping tables.
* `getTimeline` retrieves top tweets from followed accounts, whereas `getUserTweets` fetches tweets written by a single user.
* Read endpoints utilize pagination via `max_tweet_id` (a cursor representing the smallest Tweet ID from the preceding page). Because Tweet IDs encode creation timestamps, this cursor doubles as a deterministic time marker.
* **Separation of Media:** Media files are uploaded independently via a dedicated media service prior to posting the tweet. This keeps the tweet creation request payload lightweight and enables upload retries without duplicating tweet posts.

## Step 4: Define the Data Model

The database schema manages four key entities: `User`, `Tweet`, `UserFollow`, and `Favorite`. All records remain compact; a tweet row is roughly 310 bytes. Large binary media objects are stored in distributed object store systems (e.g., S3/Blob storage), with database rows keeping only reference pointers (`MediaIDs`).

![Database schema for Twitter](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.8-twitter-db-schema.png)
*Figure 01: Relational Schema diagram representing User, Tweet, UserFollow, and Favorite entities.*

#### Primary Access Patterns
1. Retrieve recent tweets published by a given `UserID`.
2. Retrieve the set of accounts followed by a given `UserID`.

#### Entity Breakdown
* **Tweet:** Contains `TweetID`, `UserID`, `Content`, `MediaIDs`, `OriginalTweetID` (populated only for retweets to avoid content duplication), and location metadata. Notice that no separate creation timestamp column is required because timestamp information is embedded directly into the `TweetID`.
* **UserFollow:** Stores follow relationships. Primary key is the compound pair `(FollowerID, FolloweeID)`.
* **Favorite:** Connects a `UserID` to a `TweetID`. With ~1 Billion favorites daily, this table grows faster than any other entity.
* **User:** Holds account profile details, credentials, email, and registration timestamps.

#### Database Selection (SQL vs. NoSQL)
Both relational databases (with sharding) and NoSQL stores (Key-Value/Wide-Column) can host this schema. The architectural trade-offs mirror those discussed in [Designing Instagram](./4.5-designing-instagram.md).

The high-level architecture comprises application servers behind load balancers, backed by partitioned database storage and media file storage.

## Step 6: Go Deep

### Sharding the data

Because a single database node cannot sustain 30 GB of new text daily along with 325K reads/sec, data must be sharded across multiple nodes.

#### Strategy A: Sharding by UserID
A hash function maps `UserID` to a specific database node storing all tweets, follows, and favorites for that user.
* **Drawbacks:**
  * **Hot Accounts:** Celebrities or high-profile users generate massive read volume on a single partition, creating severe performance bottlenecks.
  * **Uneven Data Growth:** Some accounts post thousands of tweets while others post none, resulting in storage imbalance across shards.

#### Strategy B: Sharding by TweetID
Tweets are distributed randomly across database shards using `hash(TweetID)`.
* **Timeline Build Process:**
  1. App server retrieves the list of accounts the user follows.
  2. Query is broadcast to **all database partitions** (scatter-gather).
  3. Each partition returns matching recent tweets sorted by time.
  4. An aggregator server merges, sorts, and extracts the top tweets for the user.
* **Trade-off:** Eliminates hot-user partition bottlenecks, but increases read latency due to scatter-gather queries across all partitions. Placing an in-memory cache in front of database nodes mitigates this latency.

#### Strategy C: Sharding by Creation Time
Storing tweets partitioned by timestamp makes fetching recent tweets fast. However, it severely unbalances write traffic: all new writes hit the partition managing the current timeframe, leaving older partitions idle.

#### Strategy D: Combining TweetID and Creation Timestamp (Recommended)
By embedding the creation timestamp directly within the `TweetID`, we achieve the benefits of timestamp ordering without dedicated creation-time columns or index lookups.

![How epoch time and a sequence number form a TweetID](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.8-twitter-tweetid-structure.png)
*Figure 03: Encoding 48-bit TweetID using Epoch Time and Sequence Counter.*

#### 48-Bit TweetID Construction
* **Epoch Seconds (31 bits):** Covers ~50 years of timestamp data ($\approx 1.6\text{ Billion seconds}$).
* **Sequence Counter (17 bits):** Allows up to $2^{17} = 131,072$ unique tweets per second. The counter resets to zero at each second boundary.

#### Key Generation Mechanisms
1. **Dual Generator Nodes (Step & Offset):** Two auto-incrementing key generation servers generate keys (one even, one odd) to prevent collision and ensure fault tolerance.
2. **64-Bit Expansion:** Expanding `TweetID` to 64 bits allows millisecond timestamp resolution and extends system operation lifetime beyond 100 years.
3. **Twitter Snowflake:** Uses a 64-bit ID structure:
   * **Timestamp:** 41 bits (millisecond precision, ~69 years)
   * **Worker Machine ID:** 10 bits ($1,024$ unique machines)
   * **Sequence Number:** 12 bits ($4,096$ IDs per millisecond per machine)

Snowflake requires no inter-server locking or runtime coordination, allowing distributed nodes to generate unique, chronologically ordered IDs independently.

### Caching

To deliver timelines within the 200ms latency budget across 325K reads/sec, tweets must be served primarily from in-memory caches.

![Detailed component design for Twitter](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.8-twitter-detailed-component-design.png)
*Figure 04: Detailed Architecture showing Load Balancers, Application Layer, Aggregator Tier, In-Memory Caches, and Database Shards.*

#### Cache Eviction Policy
* **LRU (Least Recently Used):** Discards least recently accessed tweets to make space for active ones.

#### Caching Hot & Recent Content (80-20 Rule)
* 80% of read traffic targets 20% of content.
* **3-Day Cache Window:** Assuming 80% of users only read tweets from the past 3 days:
  $$\text{3 Days Text Storage} = 30\text{ GB/day} \times 3 = 90\text{ GB}$$
  A 90 GB cache payload easily fits within the memory of a single high-capacity cache server. This memory cache is replicated across multiple instances to distribute read throughput.

#### Cache Data Structure
Caches are organized as a Hash Map:
* **Key:** `OwnerID` (User ID of the tweet author)
* **Value:** A **Doubly Linked List** holding the author's tweets from the past 3 days. New tweets are inserted at the head, and expired/tail items are purged when capacity thresholds are reached.

### Generating the timeline

#### 1. Pull Model (Fan-Out on Read)
* Timeline is constructed dynamically when the user requests it.
* System fetches recent tweets from all followed accounts across cache/DB, merges, and sorts them.
* **Pros:** Simple write path; no overhead when posting tweets.
* **Cons:** High read latency for users following thousands of accounts.

#### 2. Push Model (Fan-Out on Write)
* When a tweet is posted, the system immediately injects a copy of the tweet into the pre-computed stored timeline cache of every follower.
* **Pros:** Timeline reads are instant ($O(1)$ cache lookup).
* **Cons:** Massive write amplification for accounts with millions of followers (e.g., a user with 20M followers triggers 20M cache writes for a single tweet).

#### 3. Hybrid Model (Optimized Strategy)
* Use the **Push model** for standard users (e.g., users with $< 5,000$ followers).
* Use the **Pull model** for high-follower celebrity accounts ("hot accounts"). During timeline generation, celebrity tweets are pulled dynamically and merged into the user's pre-computed push timeline.

For a deeper dive into fan-out trade-offs, consult [Push vs. Pull Architecture](../3-system-design-trade-offs/3.19-push-vs-pull-architecture.md).

---

### Replication and fault tolerance

* **Read Replicas:** Primary database partitions handle write traffic, while multiple read secondaries handle read queries asynchronously.
* **Failover:** If a primary database node fails, an automated leader election promotes an active secondary to primary.

---

### Load balancing

Load balancers are positioned at three distinct architectural tiers:
1. **Client to Application Server Tier**
2. **Application Server to Database Replication Tier**
3. **Aggregation Server to Cache Tier**

An initial Round-Robin strategy distributes requests evenly. To handle unequal node capabilities or localized traffic spikes, **load-aware dynamic routing** periodically polls backend server metrics (CPU, memory, active connections) to route requests intelligently.

---

### Serving the extended requirements

1. **Retweets:** Stored as a `Tweet` record containing the `OriginalTweetID`. Text payload remains empty to prevent data duplication.
2. **Trending Topics:** Maintain rolling frequency statistics of hashtags and keywords over time windows using sliding window counters.
3. **Who to Follow:** Traverses 2nd and 3rd degree connections in the social follow graph. Candidates are filtered and re-ranked using Machine Learning models based on mutual connections, profile similarity, and recent follower growth.
4. **Moments:** Uses text clustering algorithms and ML models to group news stories and associate related tweets into curated event collections.
5. **Search:** Utilizes dedicated inverted index clusters for tweet text indexing and retrieval.

## Step 7: Bottlenecks and Failure Points

#### System Bottlenecks
* **Scatter-Gather Latency:** Sharding by `TweetID` forces timeline queries to hit every database partition if cache misses occur. High cache hit ratios ($\ge 99\%$) are mandatory.
* **Key Generator Single Points of Failure:** Dual key generation nodes prevent single point failures; however, losing both key nodes halts all write operations.

#### Monitoring & Operations
Essential metrics to monitor continuously:
1. Write rate (tweets published per second, daily peak surges).
2. Timeline delivery throughput and request latency.
3. Cache hit/miss percentages across all tiers.

## Where AI Fits in This Design

In modern feed architectures, AI enhances timeline ranking beyond simple chronological ordering:

```text
[ All Tweets ] ---> ( Candidate Retrieval Step ) ---> [ ~500 Candidates ] ---> ( ML Ranking Model ) ---> [ Ranked Feed ]
```

1. **Candidate Retrieval (First Phase):** Fetches the latest ~500 tweets from accounts the user follows using existing pull/push cache lookups.
2. **ML Ranking Model (Second Phase):** A machine learning model ranks the retrieved candidate set using features such as author interaction history, tweet engagement (likes/retweets), media type preferences, and recency.
3. **Execution Efficiency:** The heavy ML model executes over a small candidate set ($\approx 500$ tweets) per feed refresh, rather than evaluating the global tweet store.

---

#### Key Takeaways & Interview Guidance

> [!IMPORTANT]
> **Summary of Essential Trade-Offs for Interviews:**
> * **Read-Heavy Nature:** 325,000 reads/sec vs. 1,150 writes/sec (~280:1 ratio). All design decisions prioritize read efficiency.
> * **Sharding Strategy:** Shard by `TweetID` to prevent celebrity hot-spot shards, accepting scatter-gather read queries across partitions.
> * **Timestamp-Encoded TweetID:** Embedding 41-bit epoch timestamp into the 64-bit `TweetID` (via Snowflake) eliminates secondary indexes on creation time and speeds up reads/writes.
> * **In-Memory Caching:** Cache the last 3 days of tweets (~90 GB metadata) in RAM using an LRU eviction policy to satisfy the 200ms latency requirement.
