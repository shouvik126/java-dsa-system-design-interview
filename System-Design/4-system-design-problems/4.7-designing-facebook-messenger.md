# Designing Facebook Messenger

Every case study in this chapter follows the same seven steps from [System Design Interviews: A step by step guide](https://www.designgurus.io/course-play/grokking-the-system-design-interview/doc/system-design-interviews-a-step-by-step-guide), and builds its design from the components in the [System Design Master Template](https://www.designgurus.io/course-play/grokking-the-system-design-interview/doc/system-design-master-template). Keep both open beside you, and try each problem yourself before reading the solution.

## What is Facebook Messenger?

Facebook Messenger is an instant messaging service. Users chat with their Facebook friends from their phones and from Facebook's website.

This chapter designs the core of such a service: delivering text messages between users in real time, at very large scale. The interesting problems are message delivery, message ordering, and online status.

---

## Try it yourself

Before reading the solution, try designing it. Aim to produce four things: the requirements, a rough load estimate, the API, and a first drawing of the components.

---

## Step 1: Clarify the Requirements

> [!TIP]
> Always clarify requirements at the beginning of the interview. Ask questions until you know the exact scope of the system the interviewer has in mind.

### Functional requirements
- Messenger should support one-on-one conversations between users.
- Messenger should keep track of the online and offline status of its users.
- Messenger should store chat history permanently.

### Non-functional requirements
- **Real-time chat with minimum latency:** A message should appear on the receiver's screen almost instantly.
- **High consistency:** A user should see the same chat history on every device they use.
- **High availability is desirable:** But if we must choose, we accept lower availability to keep consistency.

### Extended requirements
- **Group chats:** Several people can talk together in one conversation.
- **Push notifications:** The system can tell users about new messages while they are offline.

Both extended features get their own sections in Step 6.

---

## Step 2: Estimate the Scale

Ask the interviewer for two numbers: daily active users, and messages sent per user. Assume **500 million daily active users**. Assume each user sends **40 messages a day**.

$$500\text{M users} \times 40\text{ messages sent} = 20\text{ billion messages per day}$$

### Storage
Assume an average message is **100 bytes**.

$$20\text{B messages} \times 100\text{ bytes} = 2\text{ TB per day}$$

$$2\text{ TB} \times 365\text{ days} \times 5\text{ years} \approx 3.6\text{ PB}$$

Besides the messages, we store user information and message metadata, like the ID and the timestamp. The numbers above also ignore compression and replication. Treat them as a lower bound.

### Bandwidth

$$\frac{2\text{ TB}}{86,400\text{ seconds}} \approx 25\text{ MB/s incoming}$$

Every incoming message goes out to another user. So we need the same **25 MB/s** for outgoing traffic too.

Two of these numbers change the design:
- **3.6 PB of history:** Far too much for one machine, so the data must be partitioned.
- **20 billion small writes a day:** The database must absorb a very high rate of tiny inserts.

---

## Step 3: Define the API

Messenger is not a request-and-response product like a URL shortener. Each client keeps one connection open to the server. Messages and status updates travel over that connection. Three operations cover the core product:

```http
sendMessage(senderID, receiverID, messageText)
ack: { messageID, timestamp }

getMessages(userID, conversationID, beforeMessageID?, count)
200: one page of messages, newest first

getStatus(userIDs[])
200: online or offline, for each requested user
```

`getMessages` returns one page at a time. Step 6 explains why page size differs by device. `getStatus` exists for the moments when the client must ask, rather than be told. Step 6 lists those moments.

## Step 4: Define the Data Model

The data has a simple shape:
- Billions of tiny rows. A message row is about 100 bytes.
- One write pattern: append a new message.
- One read pattern that matters: fetch a range of recent messages from one conversation, in order.

The entities come directly from the requirements. Users send messages inside conversations. Some conversations are group chats. Push notifications need a record of each user's devices. That gives five tables:

![Database schema for Facebook Messenger](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.7-messenger-db-schema.png)

- **User** holds one row per account. `LastOnlineAt` is the only status field on disk. Live online status never touches the database. It lives in the memory of the chat servers, as Step 6 shows.
- **Conversation** gives each one-on-one chat an ID and names its two members. `getMessages` pages through a chat by this ID. The conversation list a user sees when the app opens comes from this table too.
- **Message** is the table that decides the design. `ConversationID` says which chat a message belongs to. `SequenceNumber` is the counter that keeps all of a user's devices showing the same order. Step 6 explains why the timestamp cannot do that job. `Text` is the 100 bytes from Step 2. The remaining columns are the metadata that Step 2 mentioned but did not count. They add about 40 more bytes to every row. That is one reason we treated the storage estimate as a lower bound.
- **Device** holds one row for each phone or browser that opted in to push notifications. The Notification server in Step 6 reads this table to reach users who are offline.

Only **Message** ever reaches billions of rows. It gains 20 billion rows every day. The other four tables grow only when a person signs up, starts a conversation, or adds a device. So the storage choice below, and the partitioning work in Step 6, are really about the Message table.

### Which storage system should we use?
We need a database that supports a very high rate of small writes. It must also fetch a range of records quickly, because users read messages sequentially.

A relational database like MySQL, or a document database like MongoDB, is a poor fit here. We cannot afford one row read or write per message, 20 billion times a day. Basic operations would run with high latency, and the load on the database would be huge.

A wide-column database like [HBase](https://en.wikipedia.org/wiki/Apache_HBase) meets both requirements. A wide-column database stores multiple values against one key, in multiple columns. HBase is modeled after Google's [BigTable](https://en.wikipedia.org/wiki/Bigtable) and runs on the Hadoop Distributed File System ([HDFS](https://en.wikipedia.org/wiki/Apache_Hadoop)).

HBase collects new data in a memory buffer. When the buffer is full, it writes the whole buffer to disk in one operation. That turns billions of tiny writes into a smaller number of large ones. HBase also fetches rows by key and scans ranges of rows quickly. It stores variable-sized data well, which chat messages are.

The **GroupChat** table shows how modeling changes in a wide-column store. Each group keeps its member list inside its own row. A relational design would move that list into a separate membership table, one row per member. A wide-column store shapes a row around the query that reads it. The query here is: find every member of this group, to deliver a message. Storing the list in the row is therefore normal here, not a mistake.

## Step 5: Draw the High-Level Design

At a high level, we need a chat server as the central piece. It coordinates all communication between users. A sender connects to the chat server and hands over the message. The server passes the message to the receiver and also stores it in the database.

![High Level Design](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.7-messenger-hld.png)

The workflow for one message looks like this:
1. User-A sends a message to User-B through the chat server.
2. The server receives the message and sends an acknowledgment to User-A.
3. The server stores the message in its database and sends it to User-B.
4. User-B receives the message and sends an acknowledgment to the server.
5. The server notifies User-A that the message was delivered successfully.

## Step 6: Go Deep

Start with a simple version where everything runs on one server. The system has three jobs:
1. Receive incoming messages and deliver outgoing messages.
2. Store and retrieve messages from the database.
3. Track which users are online or offline, and tell the relevant users when a status changes.

We take these one at a time.

### Delivering messages: pull or push?
A sender connects to the server and posts the message. The open question is how the receiver gets it. There are two options.

- **Pull model:** Each user asks the server for new messages from time to time. The server must keep track of messages that are still waiting for delivery. To keep latency low, users have to check very often. Most checks return nothing, so most of that work is wasted.
- **Push model:** Each active user keeps a connection open with the server. When a message arrives, the server passes it to the receiver immediately on that connection. The server no longer needs to track pending messages for online users. Latency is minimal, because delivery happens the moment the message arrives. This is the model we pick.

### Keeping the connection open
We can use HTTP long polling or WebSockets. In long polling, the client sends a request that the server does not answer right away. If the server has nothing new, it holds the request open and waits. When a message arrives, the server responds immediately on that open request. The client then sends a new request straight away.

A long-poll request can time out, or the connection can drop. In that case, the client simply opens a new request. [Long-Polling vs WebSockets vs Server-Sent Events](https://www.designgurus.io/course-play/grokking-the-system-design-interview/doc/longpolling-vs-websockets-vs-serversent-events) compares these options in detail.

### Finding a user's connection
The server keeps a hash table. The key is the `UserID`. The value is the connection object for that user. When a message arrives for a user, the server looks up the connection object and sends the message on it.

### When the receiver is offline
If the receiver has disconnected, the server can tell the sender that delivery failed. But some disconnects are temporary, like a long-poll request that just timed out. Then the server should expect a reconnect.

In that case there are two options, and the design allows both. The server can ask the sender's client to retry. That retry belongs in the client's logic, so the user never retypes the message. The server can also hold the message for a while and retry delivery when the receiver reconnects.

### How many chat servers do we need?
Plan for the worst case: all 500 million daily users connected at the same time. Assume a modern server can hold 50,000 concurrent connections.

$$\frac{500\text{M connections}}{50\text{K per server}} = 10,000\text{ chat servers}$$

The 50,000 figure is deliberately conservative. A well-tuned server can hold hundreds of thousands of mostly idle connections, and specialized systems have held over a million per machine. The per-server number is an assumption, so state yours and show the division. At one million connections per server, the same arithmetic needs 500 servers instead of 10,000. What to check when raising the number: memory per connection, the operating system limit on open connections, and the processing cost of heartbeats across them all.

### Which server holds which user?
Put a software load balancer in front of the chat servers. It maps each `UserID` to the server holding that user's connection, and it directs each request there.

### Processing a "deliver message" request
On a new message, the server must do three things: store the message in the database, send the message to the receiver, and send an acknowledgment to the sender.

The chat server first finds the server that holds the receiver's connection, and passes the message to it. It can then acknowledge the sender right away. It does not wait for the database write. Storing the message happens in the background.

### Keeping messages in order
Can a server timestamp order the messages? We can store the time the server received each message. That is not enough. Look at this sequence:
1. User-1 sends a message M1 to the server for User-2.
2. The server receives M1 at time T1.
3. Meanwhile, User-2 sends a message M2 to the server for User-1.
4. The server receives M2 at time T2, where $T2 > T1$.
5. The server sends M1 to User-2 and M2 to User-1.

User-1 sees M1 first and then M2. User-2 sees M2 first and then M1. Each user sees their own message first. No single global order can match both views.

The fix is a **sequence number**: a counter kept with every message, separately for each client. The sequence number fixes the exact order of messages for that user. The two participants still see different orders. But each user's view is the same on every device they use. That is exactly the consistency requirement from Step 1.

### Storing and retrieving messages
Every new message goes to HBase, and the chat server should not block on that write. There are two options. Start a separate thread that performs the database write, or send an asynchronous request, meaning a request the caller does not wait for.

Either way, plan for failure:
- Use the database connection pool efficiently.
- Retry writes that fail.
- Log writes that still fail after retries.
- Replay the logged writes once the underlying problem is fixed.

How should clients fetch history? In pages. Page size depends on the client. A phone screen shows fewer messages and conversations than a laptop, so it needs smaller pages.

### Managing user status
The server holds a connection object for every active user. So it always knows who is online. The expensive part is telling everyone else. Broadcasting every status change to 500 million active users would consume enormous resources. Five optimizations keep the cost down:
1. When the app starts, the client pulls the current status of everyone on the friends list.
2. When a user messages someone who went offline, the server returns a failure and the client updates that status.
3. When a user comes online, the server waits a few seconds before broadcasting. That avoids announcing users who disconnect again immediately.
4. Clients pull the status of the users visible in the viewport, meaning the part of the screen currently shown. This does not need to be frequent. The server broadcasts status changes anyway, and a briefly stale offline status is acceptable.
5. When a client opens a new chat, it pulls the other user's status at that moment.

Read the diagram as one path. Clients keep an open connection to a chat server, found through the load balancer. New messages are pushed to the receiver on that open connection. HBase stores the history. Status changes are broadcast, and clients pull status for the users on screen.

### Data partitioning
We will store 3.6 PB over five years, so the data must be spread over many database servers. What should the partition key be?

**Partition by UserID:** Hash the `UserID` and use the hash to pick a shard. A shard is one partition of the database, living on one server. All of a user's messages then sit on the same shard. Fetching any user's chat history touches one server, which makes it fast. If one shard holds 4 TB:

$$\frac{3.6\text{ PB}}{4\text{ TB}} \approx 900\text{ shards}$$

For simplicity, keep 1,000 shards. The shard number is then $\text{hash}(UserID) \bmod 1000$.

We do not need 1,000 physical servers on day one. A logical partition is a slice of data that can move as one unit. Many logical partitions can share one physical server, as long as the hash function knows the mapping. As storage grows, we add physical servers and move logical partitions onto them. Each user still maps to the same logical partition, so no data is ever re-hashed.

**Partition by MessageID?** No. The messages of one conversation would scatter across many shards. Fetching a range of messages would then touch many servers, and would be very slow.

### Caching
We can cache the last 15 messages in each of the last 5 conversations visible in a user's viewport. Those are the messages a user reads first after opening the app. Since all of a user's messages live on one shard, keep that user's cache on one machine too.

### Load balancing
We need two load balancers. One sits in front of the chat servers and maps each `UserID` to the server holding that user's connection. The other does the same for the cache servers.

### Fault tolerance and replication
What happens when a chat server fails? The server was holding open connections with its users. Moving an active TCP connection to another machine is extremely hard. The simpler answer is to make clients reconnect automatically whenever their connection is lost.

Should we store only one copy of the messages? No. If the server holding that copy dies permanently, the data is gone. Either replicate the data onto multiple servers, or use a technique like Reed-Solomon encoding. Reed-Solomon encoding splits data into coded pieces, so a subset of the pieces can rebuild the whole.

### Group chat
A group chat is a separate object in the system, stored on the chat servers. It is identified by a `GroupChatID` and holds the list of its members. The load balancer directs each group message by its `GroupChatID`. The server handling that group then iterates through the member list. For each member, it finds the server holding that member's connection and delivers the message.

In the database, group chats live in their own table, partitioned by `GroupChatID`.

### Push notifications
So far, only online users receive messages. If the receiver is offline, the sender gets a failure. Push notifications close that gap: they deliver an alert to a user whose app is not even open.

Each user opts in to notifications on their device or browser. Every device manufacturer, like Apple or Google, runs its own servers for pushing notifications to its devices. So we add a Notification server to our design. It takes messages addressed to offline users and hands them to the manufacturer's push servers. Those servers deliver the alert to the user's device.

## Step 7: Bottlenecks and Failure Points

The interviewer does not expect this design to be limitless. They expect you to know where it ends.
- **Chat servers are stateful:** Each one holds live connections. When one fails, 50,000 users reconnect at almost the same moment. The load balancer must spread that reconnect wave across healthy servers.
- **The load balancer's map is on every path:** Every message delivery asks which server holds the receiver. If that mapping is stale or unavailable, delivery stops.
- **Status traffic can exceed message traffic:** With 500 million users going online and offline, careless broadcasting would cost more than the chat itself. The five optimizations in Step 6 are what keep it affordable.
- **We chose consistency over availability:** During a database failover, some users may wait for their history instead of seeing a wrong version. Say this trade openly, because it came from the requirements.

## Where AI Fits in This Design

After the main design, interviewers often ask one more question: where would AI fit in this system?

For a messaging system, the question behind the question is privacy. Any server-side model that suggests replies or filters content must read the message text. Whether the server may read messages is a requirements decision, the kind Step 1 exists for, and it decides where AI can run.

Two fits show the two sides of that decision:
- **Smart replies:** Short suggested answers a user can tap, need the content of the conversation. If the product promises end-to-end encryption, where only the sender and the receiver can read a message, the servers never see the text. The model must then run on the device: the app computes suggestions locally, and nothing leaves the phone. The model is smaller and the suggestions are weaker, but the promise holds.
- **Spam detection:** Can stay on the servers, because it does not need the text. The signals are behavioral: sending rate, how many receivers block a sender, how many conversations a new account starts. The chat servers see all of this as delivery metadata. A classifier trained on those signals flags spammers without reading a single message.

Delivery itself stays AI-free. Connections, sequence numbers, and storage are ordering problems, and they need rules, not models.

> [!TIP]
> **In the interview:** Spend your time on delivery and ordering, and move quickly through everything else. Two moments give the interviewer most of the information. The first is choosing push over pull, because it removes pending-message tracking and gives instant delivery. The second is explaining why server timestamps cannot order messages, and why per-client sequence numbers can. If you have time left, the follow-up you are most likely to get is what happens when a chat server dies. The answer is client reconnection, because moving TCP connections is not practical.

**Key takeaway:** Messenger is a push system built on open connections. Plan for 500 million concurrent connections at 50,000 per server, which means about 10,000 stateful chat servers. A load balancer maps each UserID to its server. Store 20 billion daily messages in a wide-column store like HBase, which buffers small writes in memory and flushes them in bulk. Partition by UserID, so one shard holds a user's whole history, and never partition by MessageID. Order messages with per-client sequence numbers, not server timestamps, so every device shows the same history. Reach offline users through a Notification server and the manufacturer's push servers.
