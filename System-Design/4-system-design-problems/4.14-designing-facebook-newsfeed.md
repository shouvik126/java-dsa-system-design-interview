## What is Facebook's Newsfeed?

A **Newsfeed** is the continuously updating stream of content visible at the center of Facebook's home screen. It aggregates updates, photos, videos, links, app activities, likes, and comments generated by the people, pages, and groups that a user actively follows. Together, these updates assemble an individualized, scrollable record of a user's digital social network.

```
                  THE CORE NEWSFEED AGGREGATION PIPELINE
┌──────────────────────────────────────┐
│  Multi-Source Content Creators       │
│  - Friends (Posts, Likes, Comments)  │
│  - Pages   (Articles, Media)         │
│  - Groups  (Discussions, Updates)    │
└──────────────────┬───────────────────┘
                   │
                   ▼
┌──────────────────────────────────────┐
│  Newsfeed Aggregation & Ranking Engine│
│  - Fan-Out & Pre-Computation         │
│  - Relevance Scoring & Sorting       │
└──────────────────┬───────────────────┘
                   │
                   ▼
┌──────────────────────────────────────┐
│  User's Personalized Home Feed       │
│  - Ultra-Fast Timeline Rendering     │
│  - Chronological & Ranked Pagination │
└──────────────────────────────────────┘
```

Virtually every modern social network relies on a newsfeed variant. Platforms such as Twitter, Instagram, LinkedIn, and TikTok show updates from followed connections or recommendation engines. While [Designing Twitter](./4.8-designing-twitter.md) and [Designing Instagram](./4.5-designing-instagram.md) introduce high-level timeline concepts, this case study designs a production-grade, end-to-end newsfeed architecture capable of serving hundreds of millions of active users in real time.

### The Architectural Challenge: Pre-Computation vs. Request-Time Assembly

The central engineering trade-off in newsfeed design centers around **timing**:

* **Fan-Out-on-Read (Dynamic Pull)**: Assemble a user's feed on-demand *when* they open the application by querying every account they follow.
* **Fan-Out-on-Write (Pre-Computed Push)**: Pre-generate and cache each user's feed in memory *before* they open the application, updating their feed as soon as new content is posted.

As discussed in [Push vs Pull Architecture](../3-system-design-trade-offs/3.19-push-vs-pull-architecture.md), choosing between these strategies dictates whether the system experiences heavy database read bottlenecks or massive fan-out write bottlenecks under peak load.

> [!NOTE]
> Building a newsfeed requires balancing two competing latency metrics: serving the feed to a user in under 2 seconds when requested, and delivering newly created posts to followers' feeds within 5 seconds of publication.

## Step 1: Clarify the Requirements

> [!TIP]
> Always clarify requirements with your interviewer at the start of the interview. Defining strict boundaries prevents over-engineering out-of-scope features and keeps your design focused on core bottlenecks.

### Functional Requirements

1. **Multi-Source Feed Aggregation**: The system generates a personalized newsfeed from posts published by friends, followed pages, and joined groups.
2. **Rich Media Support**: Feed items contain text, photos, video references, or external links.
3. **Live Timeline Stream**: Newly published posts are appended to active users' feeds in real time without requiring complete application reloads.
4. **Asymmetrical Follow Dynamics**: Users can follow hundreds of accounts (friends, pages, groups) with varying post frequencies.

### Non-Functional Requirements

1. **Sub-2-Second Timeline Fetch Latency**: The system must assemble and serve a user's newsfeed in under **2 seconds** (target $< 500\text{ ms}$ for cached feeds).
2. **5-Second Post Delivery SLA**: A newly created post must reach an active follower's feed within **5 seconds** of publication.
3. **High Availability**: The read path must guarantee 99.99% uptime so users never face home timeline outages.
4. **Scalability**: The system must handle 300 million daily active users and process tens of thousands of concurrent requests smoothly.

```
                            LATENCY BOUNDARIES AT A GLANCE
                            
 ┌─────────────────────────────────────────────────────────────────────────┐
 │ Read Path Target: < 2 Seconds                                           │
 │ (User Opens App ───> API Request ───> Hydrated Feed Rendered)          │
 └─────────────────────────────────────────────────────────────────────────┘
 ┌─────────────────────────────────────────────────────────────────────────┐
 │ Write Path Delivery SLA: < 5 Seconds                                    │
 │ (Author Posts ───> Fan-Out Processing ───> Appended to Follower Caches) │
 └─────────────────────────────────────────────────────────────────────────┘
```

> [!IMPORTANT]
> The **2-second read target** starts when a user opens their app and requests their feed. The **5-second write SLA** starts earlier when an author publishes a post, governing the time required for background fan-out workers to update follower feeds.

## Step 2: Estimate the Scale

System scale dictates whether feeds can be computed dynamically or must be pre-generated in memory.

### Base Assumptions

* **Daily Active Users (DAU)**: $300\text{ million}$.
* **Average Daily Timeline Fetches**: $5\text{ fetches per user per day}$.
* **Average User Connections**: Each user has 300 friends and follows 200 pages/groups ($500\text{ total followed accounts}$).

### Traffic Estimations

* **Total Daily Feed Requests**: 
  $$300\text{M users} \times 5\text{ requests/day} = 1.5\text{ billion requests/day}$$
* **Average Read QPS (Queries Per Second)**:
  $$\frac{1.5 \times 10^9\text{ requests}}{86,400\text{ seconds}} \approx 17,361\text{ QPS}$$
* **Peak Read QPS**: Assuming a $2\times$ peak multiplier:
  $$\text{Peak QPS} \approx 35,000\text{ QPS}$$

### Storage & Memory Estimations

* **Post Payload Record Size**: Assume each cached feed post record is $1\text{ KB}$ (contains post metadata, text snippet, and author details; raw photos and videos live separately in Object Storage/CDN).
* **Feed Depth in Memory**: Store **500 post items** per user feed in cache for instant retrieval.
* **Per-User Memory Footprint**:
  $$500\text{ posts} \times 1\text{ KB} = 500\text{ KB per user}$$
* **Total In-Memory Feed Cache Requirement**:
  $$300\text{M users} \times 500\text{ KB} = 150\text{ Terabytes of RAM}$$
* **Cache Node Hardware Sizing**: Assuming each cache server node provides $100\text{ GB}$ of usable RAM:
  $$\frac{150\text{ TB}}{100\text{ GB per server}} = 1,500\text{ cache server nodes}$$

> [!TIP]
> If we optimize storage to retain **200 posts** per user in memory (which satisfies over 99% of browsing sessions), the required memory shrinks from $150\text{ TB}$ down to **$60\text{ TB}$**, reducing our cluster size to $\sim 600$ nodes.

### Architectural Drivers Derived from Scale

1. **Pre-Generation is Mandatory**: Serving $17,500\text{ QPS}$ where each request dynamically fetches and sorts posts across 500 followed accounts would instantly overwhelm database disk I/O. Feeds **must be pre-generated in memory**.
2. **Distributed Cache Sharding**: A $150\text{ TB}$ feed cache cannot fit on a single node. The feed cache **must be horizontally partitioned across a cluster of servers using consistent hashing**.

## Step 4: Define the Data Model

The data layer must manage user profiles, follow graphs, post payloads, media metadata, and pre-computed feed caches.

![Database Schema for Facebook Newsfeed](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.14-facebook-newsfeed-database-schema.svg)

### Entity Definitions & Database Tables

#### 1. `User` Table
Stores basic user profile information.

```sql
CREATE TABLE User (
    user_id       BIGINT PRIMARY KEY,
    name          VARCHAR(100) NOT NULL,
    email         VARCHAR(255) UNIQUE NOT NULL,
    created_at    TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

#### 2. `Entity` Table (Pages & Groups)
Stores metadata for non-person accounts (Pages and Groups).

```sql
CREATE TABLE Entity (
    entity_id     BIGINT PRIMARY KEY,
    name          VARCHAR(150) NOT NULL,
    type          TINYINT NOT NULL, -- 0 = Page, 1 = Group
    created_at    TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

#### 3. `UserFollow` Table
Stores graph connections mapping followers to users or entities. This represents the largest edge table in the relational database.

```sql
CREATE TABLE UserFollow (
    follower_id          BIGINT NOT NULL,
    entity_or_friend_id  BIGINT NOT NULL,
    type                 TINYINT NOT NULL, -- 0 = User, 1 = Entity
    created_at           TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (follower_id, entity_or_friend_id, type)
);
CREATE INDEX idx_follower_type ON UserFollow(follower_id, type);
```

#### 4. `FeedItem` Table
Stores post metadata, author references, text payload, and aggregate reaction metrics.

```sql
CREATE TABLE FeedItem (
    feed_item_id  BIGINT PRIMARY KEY,
    user_id       BIGINT NOT NULL, -- Author ID
    entity_id     BIGINT NULL,     -- Optional Page/Group ID
    content_text  TEXT,
    like_count    INT DEFAULT 0,
    comment_count INT DEFAULT 0,
    created_at    TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
CREATE INDEX idx_user_created ON FeedItem(user_id, created_at DESC);
```

#### 5. `Media` and `FeedMedia` Tables
Stores media file metadata and links photos/videos to post records. Media binary payloads (images, video streams) live in Blob Storage (e.g., AWS S3).

```sql
CREATE TABLE Media (
    media_id      BIGINT PRIMARY KEY,
    media_type    TINYINT NOT NULL, -- 0 = Photo, 1 = Video
    file_path     VARCHAR(512) NOT NULL, -- S3 / Blob Storage URL
    created_at    TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE FeedMedia (
    feed_item_id  BIGINT NOT NULL,
    media_id      BIGINT NOT NULL,
    PRIMARY KEY (feed_item_id, media_id)
);
```

### The In-Memory Pre-Generated Feed Cache Record

Unlike relational tables stored on disk, the **Feed Cache** lives entirely in RAM (e.g., Redis or Memcached). Each user possesses a single key-value entry holding an ordered array of feed item references:

```
Key: UserID (e.g., "user_feed:984512")
Value: LinkedHashMap / Array of [ FeedItemID, AuthorID, Timestamp, RankingScore ]
```

## Step 5: Draw the High-Level Design

At a high level, the system architecture splits into two distinct workflows: **Feed Publishing (Write Path)** and **Feed Retrieval (Read Path)**.

![High-Level Design of Facebook Newsfeed](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.14-facebook-newsfeed-high-level-design.svg)

### High-Level Architectural Workflows

#### 1. The Write Path (Post Creation & Fan-Out)
1. **User A** creates a post with text and photos.
2. The request hits the **API Gateway / Load Balancer** and routes to **Application Servers**.
3. **Application Servers** persist the post payload into the **Posts Database** and media binaries into **Blob Storage / CDN**.
4. The **Newsfeed Generation Service** intercepts the new post event, queries the **UserFollow Database** to locate User A's active followers (e.g., User B and User C), and updates their pre-generated feed caches in RAM.
5. The **Feed Notification Service** pushes a light notification signal to User B and User C via persistent connections (WebSockets / SSE) if they are currently online.

#### 2. The Read Path (Timeline Retrieval)
1. **User B** opens Facebook, sending a `getUserFeed` request.
2. The **Load Balancer** directs the request to an available **API Server**.
3. The **API Server** fetches User B's pre-sorted post IDs directly from the **In-Memory Feed Cache** ($O(1)$ memory read).
4. If necessary, post details are hydrated from the **Posts Cache** and returned as JSON to User B in $< 500\text{ ms}$.

## Step 6: Go Deep

Now we deep-dive into the core technical challenges: feed pre-computation, memory optimization, fan-out push/pull trade-offs, ranking algorithms, and distributed partitioning.

---

### Generating the feed

#### The Naïve Dynamic Query Approach (Fan-Out-on-Read)

In a traditional relational model, fetching a user's timeline executes a dynamic SQL join across their follow list at request time:

```sql
(
    SELECT feed_item_id, user_id, NULL AS entity_id, created_at 
    FROM FeedItem 
    WHERE user_id IN (
        SELECT entity_or_friend_id 
        FROM UserFollow 
        WHERE follower_id = :current_user_id AND type = 0
    )
)
UNION
(
    SELECT feed_item_id, user_id, entity_id, created_at 
    FROM FeedItem 
    WHERE entity_id IN (
        SELECT entity_or_friend_id 
        FROM UserFollow 
        WHERE follower_id = :current_user_id AND type = 1
    )
)
ORDER BY created_at DESC 
LIMIT 100;
```

#### Why Dynamic Assembly Fails at Scale

1. **Extreme Database I/O Overhead**: A user following 500 accounts forces the database to scan, merge, and sort 500 separate post lists every time they refresh their feed.
2. **Unacceptable Read Latency**: Executing complex multi-table joins over millions of rows breaches our 2-second SLA.
3. **Write Path Cascades**: Pushing live updates requires re-executing this expensive query repeatedly for every online user.

#### Offline Pre-Generation Architecture (Fan-Out-on-Write)

To deliver sub-second reads, dedicated background worker nodes continuously compile user newsfeeds in the background and store them in memory before the user requests them.

```
                      IN-MEMORY FEED CACHE STRUCTURE
┌────────────────────────────────────────────────────────────────────────┐
│ Key: "user_feed:984512"                                                │
│ Value: LinkedHashMap / TreeMap <FeedItemID, FeedItemMeta>              │
│                                                                        │
│   [FeedItemID: 10928375] ──> Author: User 44120  ──> Score: 98.4      │
│   [FeedItemID: 10928370] ──> Author: Entity 5012 ──> Score: 87.1      │
│   [FeedItemID: 10928362] ──> Author: User 12044  ──> Score: 76.5      │
└────────────────────────────────────────────────────────────────────────┘
```

When a feed generation worker runs, it checks `lastGeneratedTime`, fetches posts created since that timestamp, evaluates relevance scores, and appends the post IDs into an in-memory data structure such as Java's `LinkedHashMap` or Redis `ZSET` (Sorted Set).

```java
public class UserFeedCache {
    private String userId;
    // Map keeps items sorted by rank/chronology and supports O(1) random access by ID
    private LinkedHashMap<Long, FeedItemMeta> feedItems; 
    private LocalDateTime lastGeneratedTime;
}
```

> [!TIP]
> A `LinkedHashMap` or `ZSET` allows constant-time $O(1)$ lookups by `FeedItemID`, preserves ordering, and allows the server to jump directly to `max_id` or `since_id` parameters during user pagination.

---

### How much feed to keep in memory

#### Memory Sizing Trade-Offs

While keeping 500 items per user provides deep scrolling, analytics show that **99% of users rarely browse beyond 10 pages** ($20\text{ items/page} \times 10\text{ pages} = 200\text{ posts}$).

$$\text{Optimized Cache Memory} = 300\text{M users} \times 200\text{ posts} \times 1\text{ KB} = 60\text{ Terabytes}$$

If a user scrolls beyond 200 posts, the application server falls back to fetching historical posts directly from the database disk store.

#### Cache Eviction & Smart Pre-Generation

1. **LRU Cache Eviction**: Millions of registered users rarely open Facebook daily. Keeping pre-generated feeds for inactive users wastes precious RAM. An **LRU (Least Recently Used)** policy automatically evicts feeds for users who haven't logged in for $> 3\text{ days}$.
2. **Predictive Pre-Generation**: Instead of pre-generating feeds for all 300 million users continuously, an ML scheduler analyzes historical login patterns (e.g., user opens app at 8:00 AM daily) and generates their feed 5 minutes prior to their expected activity window.

---

### Publishing the feed

Publishing a post to all follower feeds is called **fan-out**. The fundamental design choices are:

#### 1. Push Model (Fan-Out-on-Write)
* **Mechanic**: When User A creates a post, the system immediately writes that post ID into the feed cache of every follower.
* **Pros**: Extremely fast feed reads ($O(1)$ RAM fetch).
* **Cons**: **The Celebrity Hotspot Problem**. If a celebrity with 50 million followers posts, the fan-out service must execute 50 million cache writes simultaneously, causing massive worker queues and system degradation.

#### 2. Pull Model (Fan-Out-on-Load)
* **Mechanic**: Clients fetch posts from followed accounts on-demand when loading their feed.
* **Pros**: Zero fan-out overhead during post creation.
* **Cons**: Heavy read latencies; frequent empty polling wastes bandwidth.

#### 3. The Hybrid Fan-Out Architecture (Production Solution)

To balance write fan-out costs with ultra-fast read latencies, modern social networks implement a **Hybrid Fan-Out Pipeline**:

```
                         HYBRID FAN-OUT DECISION MATRIX
                         
                        ┌──────────────────────────────┐
                        │   User Publishes a Post      │
                        └──────────────┬───────────────┘
                                       │
                         Follower Count > 10,000?
                        ┌──────────────┴───────────────┐
                        │                              │
                    YES │                              │ NO
                        ▼                              ▼
          ┌──────────────────────────┐    ┌──────────────────────────┐
          │  CELEBRITY ACCOUNT       │    │  STANDARD USER           │
          │  (Pull / Fan-Out-on-Load)│    │  (Push / Fan-Out-on-Write│
          ├──────────────────────────┤    ├──────────────────────────┤
          │ Bypass fan-out queue.    │    │ Fan-out post to all      │
          │ Followers fetch post     │    │ follower cache arrays    │
          │ on-demand during read.   │    │ immediately in RAM.      │
          └──────────────────────────┘    └──────────────────────────┘
```

* **Standard Users ($< 10,000\text{ followers}$)**: Use **Fan-out-on-write (Push)**. Posts are pushed directly to all follower feed caches in RAM.
* **Celebrity Accounts ($> 10,000\text{ followers}$)**: Use **Fan-out-on-load (Pull)**. Disable write fan-out. When a user opens their timeline, the system fetches their pre-generated standard feed and **merges in recent posts from the few celebrity accounts they follow**.

| Feature / Dimension | Fan-Out-on-Write (Push) | Fan-Out-on-Load (Pull) | Hybrid Architecture |
| :--- | :--- | :--- | :--- |
| **Write Latency** | High for popular users | Ultra-low ($O(1)$ post write) | Low and predictable |
| **Read Latency** | Ultra-low ($< 100\text{ ms}$) | High ($> 2\text{ seconds}$) | Low ($< 300\text{ ms}$) |
| **Celebrity Handling** | Crashes worker queues | Natural fit | Eliminates celebrity bottlenecks |
| **Best Used For** | Accounts with $< 10\text{k}$ followers | Inactive accounts / Celebrities | Production at scale |

### Ranking the feed

While pure reverse-chronological sorting orders posts by `created_at DESC`, modern feeds rely on multi-factor relevance ranking to maximize user engagement.

#### Scoring Formula Concepts

The ranking engine computes a composite relevance score for candidate posts:

$$\text{FeedScore} = (w_1 \cdot \text{Affinity}) + (w_2 \cdot \text{Weight}) + (w_3 \cdot \text{Decay})$$

1. **Affinity Score ($w_1$)**: Measures historical interaction strength between the reader and author (frequency of likes, direct messages, photo tags, profile views).
2. **Weight Score ($w_2$)**: Assigns static weights based on content format (Videos $>$ Photos $>$ Text-only links) and engagement velocity (rapid accumulation of likes/comments).
3. **Time Decay ($w_3$)**: Applies exponential decay based on post age so older posts naturally decline in score over time.

---

### Partitioning the data

#### Sharding Database & Media Storage
* **Posts & Metadata DB**: Sharded by `PostID` or `AuthorID` using **Consistent Hashing** to distribute storage evenly across database nodes.
* **Media Payloads**: Images and videos live in Object Storage (e.g., S3) fronted by a global CDN.

#### Sharding In-Memory Feed Caches
Feed caches are sharded by `UserID`:

$$\text{CacheServerID} = \text{Hash}(\text{UserID}) \pmod{\text{TotalCacheServers}}$$

```
                       CONSISTENT HASH RING FOR FEED CACHE
                       
                              [Server Node 1]
                                 /       \
                                /         \
                  [Server Node 4]         [Server Node 2]
                                \         /
                                 \       /
                              [Server Node 3]
```

Using **Consistent Hashing with Virtual Nodes** ensures that:
1. Every feed request for User X targets exactly **one deterministic cache server**, keeping read queries ultra-fast.
2. Adding or removing cache servers re-allocates only a fraction of cached user feeds, preventing ring-wide cache eviction cascades.

## Where AI Fits in This Design

In modern interview discussions, interviewers frequently ask: *"How would Machine Learning or AI enhance this system?"*

```
                       AI FEATURE STORE & RANKING PIPELINE
                       
 ┌──────────────────────┐    Real-Time Events   ┌──────────────────────┐
 │ User Interaction Logs│ ───────────────────> │ Streaming Pipeline   │
 │ (Likes, Clicks, Views)│                      │ (Kafka + Flink)      │
 └──────────────────────┘                       └──────────┬───────────┘
                                                           │ Feature Extraction
                                                           ▼
 ┌──────────────────────┐                       ┌──────────────────────┐
 │ Feed Generation      │ <──────────────────── │ AI Feature Store     │
 │ Ranking Service      │  Low-Latency Vectors  │ (Redis / Feast)      │
 └──────────────────────┘                       └──────────────────────┘
```

### 1. Deep Learning Recommendation Models (DLRM)
Rather than using static weight formulas, machine learning models (e.g., Two-Tower Neural Networks, DLRM, Transformers) predict the probability of user interactions ($P(\text{click}), P(\text{like}), P(\text{comment}), P(\text{share})$).

### 2. The Infrastructure Requirement: Feature Store
Machine learning models require real-time feature vectors (user engagement history, post click-through rates, time of day) during feed generation ($< 10\text{ ms}$).

* **The Problem**: Querying the relational database to calculate user engagement features at runtime introduces catastrophic latency.
* **The Solution**: Implement a dedicated **Feature Store** (e.g., Redis or Feast). A streaming pipeline (Kafka + Flink) ingests real-time user activity logs, computes rolling aggregations, and writes feature vectors into the low-latency Feature Store for instant retrieval by ML ranking models.

### 3. Predictive Feed Pre-Generation
ML models analyze historical usage patterns to predict *when* a user is likely to log in. Pre-generating feeds only for users predicted to open the app within the next 15 minutes reduces background server workloads by up to 60%.
