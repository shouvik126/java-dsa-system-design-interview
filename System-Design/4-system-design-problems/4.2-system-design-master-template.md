# System Design Master Template

A system design interview question presents you with a blank canvas and around forty minutes. For almost everyone, two primary issues arise:
1. You do not know where to begin.
2. You finish without knowing whether you left something important out.

A template fixes both. Not by giving you a design to memorize, but by giving you a fixed sequence to think in. You always start at the same place, move in the same direction, and at the end, you can look at the parts you did not use and explain out loud why you did not need them.

![System Design Master Template Overview](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.2-system-design-master-template-overview.png)
*The System Design Master Template: every component a large system might contain, arranged in the six layers a request travels through.*

*(Video Walkthrough: System Design Master Template)*

## How to Actually Use This

Three rules guide this process, and the third rule is what separates a strong, tailored response from a memorized recitation:

1. **It is a menu, not a checklist.** Almost no real design uses every box, and most use well under half of them. Drawing all twenty-two components does not demonstrate breadth; it indicates you are working from memory instead of engineering from the requirements.
2. **Walk it from the outside in.** Start where the request enters the system and follow it to where the data is stored, then trace the response back. This gives your explanation a clear direction, allowing an interviewer to follow without asking "where are we now?"
3. **Every box needs a reason from the requirements.** If you cannot state which exact requirement forced a component into the diagram, it does not belong there yet. "I am adding a cache because we agreed this is a hundred reads per write" is a design decision. "I am adding a cache" explains nothing.

The template splits into six layers. Each layer answers one central question.

![Master Template 6-Layer Overview](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.2-master-template-6-layer-overview.png)
*The master template arranged as six layers. Walk them in order, from how the request reaches you down to where the data goes afterwards.*

## Layer 1: How the Request Reaches You

Everything in this layer happens before your application code runs. Its job is to get the request to a healthy machine, quickly, and to keep as much unnecessary traffic away from your servers as possible.

### 1. Domain Name System (DNS)
DNS translates a human-friendly name into an address a machine can route to. When someone types `www.example.com`, DNS turns that string into an IP address so the browser knows where to send the request.

The lookup walks a resolution chain: a resolver queries a root server, which points at the Top-Level Domain (TLD) server (such as `.io` or `.com`), which points at the authoritative name server holding the record for your domain. The answer is then cached at several points along the path, making subsequent visits significantly faster.

* **The question it answers:** Where is this service located?
* **When it matters in an interview:** When you serve users in more than one region. DNS is where geographic routing occurs, directing a user in Singapore to Singapore servers rather than to Virginia. Mention it there and move on. If your system is single-region, a single sentence is enough.

![DNS Lookup Flow](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.2-dns-lookup-flow.png)
*A DNS lookup. The resolver walks the root, top-level domain, and authoritative servers, caching the answer at every step.*

---

### 2. Content Delivery Network (CDN)
A CDN is a network of servers distributed globally that hold copies of your static content: images, video files, stylesheets, and scripts. A user's request routes to whichever CDN location is geographically nearest to them.

If that location already holds the file (a cache hit), it serves it directly and the request never touches your origin servers. If it does not (a cache miss), it fetches the file from your origin once, keeps a copy, and serves subsequent regional users from that copy.

* **The question it answers:** How do we serve large, unchanging files without the latency that distance adds and without touching our own servers?
* **When you need it:** Any system delivering images, videos, downloadable files, or serving users located far from your primary data centers.
* **When you do not:** Internal tools, or systems whose responses are entirely personalized. A CDN caches content that is identical for everybody.

![CDN Edge Caching Flow](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.2-cdn-edge-caching-flow.png)
*On a cache hit, the nearest edge server answers and the request never reaches your origin. The miss path occurs once per region.*

---

### 3. Load Balancer
A load balancer sits in front of a pool of identical servers and distributes requests across them. Crucially, it monitors node health and stops routing traffic to any server that fails its health checks.

That second responsibility is often overlooked: a load balancer not only splits work evenly, but also allows a server instance to fail without end users noticing.

Common algorithms for choosing where to send each request include:
* **Round Robin:** Takes each server in turn sequentially.
* **Least Connections:** Directs requests to whichever server is handling the fewest active connections.
* **IP Hash:** Hashes the client IP address so the same client consistently lands on the same server node.

* **The question it answers:** How do we run more than one server?
* **When you need it:** Every time you have more than one instance of any component—in front of web servers, application servers, or database replicas.
* **Common oversight:** A single load balancer is itself a single point of failure (SPOF). Production deployments run at least two in a failover setup.

![Load Balancer and Health Check](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.2-load-balancer-health-check.png)
*A load balancer performs two jobs: spreading requests and removing failing servers from rotation.*

---

### 4. API Gateway
An API gateway serves as a single entry point in front of multiple backend microservices. A client issues a single call to the gateway, and the gateway decides which microservice should process it.

It also centralizes cross-cutting concerns that every service would otherwise have to implement separately:
* **Routing:** Direct `/orders` to the Order Service and `/users` to the User Service.
* **Authentication and Authorization:** Validate tokens once at the edge so downstream services can trust the caller.
* **Rate Limiting:** Reject excessive or abusive traffic before it reaches expensive backend infrastructure.
* **Response Caching:** Return common responses directly without invoking downstream services.
* **Request & Response Shaping:** Combine multiple service calls into one client response, or translate between protocols.

* **The question it answers:** How does a client talk to twenty backend services without keeping track of twenty separate addresses?
* **When you need it:** Crucial for microservices architectures.
* **When you do not:** A single monolithic service. A gateway in front of one backend adds operational complexity without immediate benefit.

**Load Balancer vs. API Gateway:** Typically, both are used together. A load balancer selects a physical machine; an API gateway selects a target service and enforces policy. A standard setup places a load balancer in front of multiple gateway instances, with further load balancing behind the gateway.

![API Gateway Architecture](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.2-api-gateway-architecture.png)
*A single entry point handling cross-cutting concerns that every service would otherwise repeat.*

---

### 5. Rate Limiting
A rate limiter counts how many requests a caller has made within a designated time window and throttles anything exceeding the agreed threshold (typically returning `HTTP 429 Too Many Requests`).

It operates at the edge, usually inside the API gateway. This placement is key: requests destined for rejection should be blocked before reaching application services, databases, or downstream infrastructure that incurs costs.

* **The question it answers:** What stops a single caller from consuming the entire system's capacity?
* **Key decisions to articulate:**
  * **Tracking Key:** Decide what you count per—per user ID, per API key, or per IP address. A single global limit is rarely appropriate because one abusive caller could degrade performance for everyone.
  * **State Storage:** The counter state must be shared across gateway instances (typically using a fast store like Redis); otherwise, a caller can bypass limits by spreading traffic across nodes.
  * **Algorithms:**
    * *Token Bucket:* Allows brief bursts of traffic while enforcing a steady long-term rate.
    * *Leaky Bucket:* Smooths incoming traffic to a constant output rate with no burst tolerance. Selection depends on whether bursts represent legitimate traffic or abuse.

![Rate Limiter at Edge](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.2-rate-limiter-at-edge.png)
*A rate limiter rejects requests exceeding configured limits at the edge before they consume backend resources.*

---

### 6. A Note on Proxies
* **Forward Proxy:** Sits in front of clients and makes requests on their behalf (e.g., a corporate proxy filtering outbound employee browsing).
* **Reverse Proxy:** Sits in front of backend servers and receives requests on their behalf. The client believes it is communicating directly with the origin server, while the reverse proxy determines which backend server actually responds.

Both load balancers and API gateways operate as specialized reverse proxies. Forward proxies rarely feature in backend system design because client environments lie outside backend control.

![Forward Proxy vs Reverse Proxy](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.2-forward-proxy-vs-reverse-proxy.png)
*A forward proxy acts on behalf of clients; a reverse proxy acts on behalf of backend servers.*

## Layer 2: Where the Work Happens

The request has crossed the edge. Something must now execute the business logic requested by the user.

### 7. Services
Services encompass your application logic (e.g., "URL Shortener Service", "Upload Service", "Feed Service"). The primary architectural decision here is determining service granularity and count.

* **Monolith:** A single deployable unit containing all application functionality. It is simpler to build, test, and reason about, making it the appropriate choice far more often than candidates acknowledge.
* **Microservices:** Splits the application into small services that each own a specific domain and communicate over the network. Key properties include:
  * Independent deployment and scaling per service—heavy load on one service requires scaling only that component.
  * Domain data ownership: each service manages its own data store.
  * Fault isolation: a failure in one service does not necessarily crash the entire application.
  * *Trade-offs:* Network calls introduce latency and failure points, distributed data consistency is harder to maintain, and debugging requires distributed tracing.

**Interview Strategy:** Partition along boundaries where scaling requirements differ. If photo uploads are resource-intensive while profile reads are light, separate them. Splitting a three-feature system into fifteen services is over-engineering.

![Monolith vs Microservices Architecture](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.2-monolith-vs-microservices.png)
*A monolith is a single unit with one database; microservices each own their data for independent scaling.*

---

### 8. Asynchronous Processing & Message Queues
Operations that do not need to finish before responding to the user (e.g., encoding an uploaded video, sending confirmation emails, updating follower feeds) should be executed asynchronously.

A message queue allows your service to publish a task message and return an immediate response. A separate worker pool reads messages from the queue (e.g., Apache Kafka, RabbitMQ) and executes the long-running tasks asynchronously.

**Key Benefits:**
1. **Fast Responses:** Removes slow background tasks from the synchronous request path.
2. **Spike Absorption (Load Leveling):** If traffic spikes tenfold, the queue buffers incoming messages while workers process them at a manageable pace, preventing system failure.
3. **Decoupling:** Message producers do not require message consumers to be online simultaneously.

*Trade-off:* Work completes eventually rather than immediately. The user receives "Your video is processing" instead of "Your video is ready."

![Message Queue Buffering](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.2-message-queue-buffering.png)
*A queue removes slow operations from the response path, allowing bursts to wait in line safely.*

---

### 9. Real-Time Delivery
When something happens on the server and the client must be notified immediately (e.g., chat messages, driver location updates, payment completions), traditional request-response is insufficient.

Four primary patterns trade off update freshness against connection overhead:

1. **Short Polling:** The client requests updates periodically every few seconds. Simple to implement, but largely wasteful as most responses are empty and updates can lag by one polling interval.
2. **Long Polling:** The client issues a request, and the server holds it open until new data is available. Provides near-instant updates over HTTP, but requires maintaining open connections.
3. **Server-Sent Events (SSE):** A persistent HTTP connection where the server streams updates down to the client. Clean solution for feeds, live notifications, and dashboards where data flows in one direction.
4. **WebSockets:** A persistent, full-duplex connection allowing real-time bidirectional communication. Required for chat and multiplayer applications. *Trade-off:* Servers maintain persistent connection state, complicating scaling and restarts.
5. **Webhooks:** Server-to-server push communication. One system registers a URL callback with another, which POSTs an event payload when actions occur, avoiding polling between backends.

![Real-Time Delivery Mechanisms](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.2-real-time-delivery-mechanisms.png)
*Four ways a server pushes events to clients, trading update freshness against connection state overhead.*

---

### 10. Specialized Services
Two specialized components appear frequently enough to warrant distinct consideration:

* **Notification Service:** Handles dispatches for email, push notifications, and SMS messages. Typically driven by a queue because delivery can be slow or unreliable and must not block user flows.
* **Full-Text Search Service:** Answers complex queries like "find all documents matching these terms." Traditional database indexes evaluate exact column values rather than ranked text matches. Search engines (e.g., Elasticsearch) build an **inverted index**—mapping words to document lists—to perform fast search queries. This runs as a dedicated component kept in sync with the primary database.

![Inverted Index Structure](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.2-inverted-index-structure.png)
*An inverted index maps terms to documents containing them, intersecting term lists during search.*

## Layer 3: Where the Data Lives

This layer often dictates system scalability. Most real-world systems are bounded by storage limits rather than application server CPU.

### 11. Choosing the Database
* **Relational Databases (RDBMS):** Store rows in structured tables with schemas, enforcing relationships, foreign key constraints, and ACID transactions (e.g., PostgreSQL, MySQL). Choose an RDBMS when your data has clear relationships or requires multi-record atomic consistency (e.g., moving money between accounts).
* **NoSQL Databases:** Relax strict schemas and cross-record transactions to simplify horizontal scaling. Categorized into four main types:
  * **Key-Value Stores:** (e.g., Redis, DynamoDB) Simple lookups by a single key; fast and easy to partition.
  * **Document Stores:** (e.g., MongoDB) Store records as self-contained documents (JSON/BSON) with dynamic schemas.
  * **Wide-Column Stores:** (e.g., Cassandra, HBase) Built for high write volume and range reads on composite keys.
  * **Graph Databases:** (e.g., Neo4j) Optimized for densely connected network data (e.g., social connections, recommendation graphs).

**Interview Strategy:** Start from data access patterns rather than technology names. Define your key queries and data volume first; the database selection will naturally follow.

![NoSQL Database Categories](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.2-nosql-database-categories.png)
*The four NoSQL data store models and their strengths. Choose based on access patterns.*

---

### 12. Indexes
An index is a secondary data structure (often a B-Tree) that allows the database engine to find matching rows by column value without scanning the entire table.

* **Trade-off:** Indexes accelerate read queries but slow down write operations (inserts, updates, deletes) and consume additional disk space.
* **Interview Application:** Explicitly name the column to index and the query it optimizes (e.g., "Indexing `short_key` turns URL lookup into an O(log N) operation").

![Database Index B-Tree](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.2-database-index-btree.png)
*An index transforms table scans into sorted lookups, costing extra space and write latency.*

---

### 13. Data Partitioning (Sharding)
When dataset size or request volume outgrows a single machine, data must be partitioned.

* **Horizontal Partitioning (Sharding):** Splits table rows across nodes (e.g., Users A–M on Node 1, N–Z on Node 2). Each node holds the same table schema with a subset of rows. Essential for scaling storage.
* **Vertical Partitioning:** Splits table columns, moving rarely used or large columns into separate tables so routine queries scan less data.

**Selecting a Shard Key:** The primary challenge of sharding is selecting an effective partition key. A good key distributes storage and traffic evenly. A poor key creates hot shards that process most traffic while others remain underutilized.

![Horizontal vs Vertical Partitioning](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.2-horizontal-vs-vertical-partitioning.png)
*Sharding divides rows for horizontal scale; vertical partitioning divides columns to minimize read overhead.*

---

### 14. Replication
Replication maintains copies of identical data across multiple physical machines to ensure availability and performance.

The standard layout uses one primary node accepting writes, with multiple read replicas copying state from it. This provides read scalability, failover promotion if the primary dies, and data redundancy.

* **Replication Modes:**
  * *Synchronous Replication:* The primary waits for replica confirmation before acknowledging writes. Guarantees consistency but adds write latency.
  * *Asynchronous Replication:* The primary acknowledges writes immediately and propagates updates asynchronously. Faster performance, but risks serving slightly stale reads and potential data loss if an un-replicated primary fails.

![Primary Replica Replication Flow](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.2-primary-replica-replication-flow.png)
*Writes target the primary node and replicate to read nodes. Synchronous copying adds latency; asynchronous copying introduces stale reads.*

---

### 15. Consistency Model
With data distributed across multiple nodes, you must define read behavior following a write:

* **Strong Consistency:** Every read operation returns the result of the most recent write, guaranteed. Achieving this requires waiting for node agreement, increasing write latency.
* **Eventual Consistency:** Reads return immediately, but may briefly return stale data until replicas converge (typically within milliseconds).

**Interview Strategy:** Avoid applying a single consistency model across an entire application. In the same system, account balances demand strong consistency, while view counters or follower counts tolerate eventual consistency.

![Strong vs Eventual Consistency](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.2-strong-vs-eventual-consistency.png)
*A strongly consistent read waits to ensure correctness; an eventually consistent read responds immediately and converges shortly.*

---

### 16. Blob & File Storage
Databases are poorly suited for storing large binary assets (e.g., photos, videos, media files). Large assets should be stored in Object Storage (such as Amazon S3 or Google Cloud Storage) or distributed file systems, while the database records only metadata (ownership, timestamps, file URIs).

![Object Storage Architecture](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.2-object-storage-architecture.png)
*Large binary files go to object storage, while database records retain only pointers and metadata.*

---

## Layer 4: How You Make It Fast

### 17. Caching
A cache is high-speed storage holding temporary copies of data that are expensive to fetch or compute.

Caching occurs at multiple tiers along the request path:
1. **Browser Cache:** Prevents requests from leaving the client device.
2. **CDN Cache:** Serves static content from edge locations near the user.
3. **API Gateway Cache:** Delivers responses without hitting backend microservices.
4. **Application Cache:** (e.g., Redis, Memcached) Caches hot data entities in memory to bypass database reads.
5. **Database Buffer Pool:** Keeps active data pages in memory automatically.

**Cache Invalidation:** The primary difficulty of caching is keeping cached entries consistent with underlying database changes (e.g., Cache-Aside, Read-Through, Write-Through, Write-Back).

![Multi-Tier Caching Layers](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.2-multi-tier-caching-layers.png)
*Caching is not a single box; it can intercept requests at five distinct stages along the path.*

## Layer 5: How You Keep It Alive

This layer distinguishes an experienced system design from a basic one by addressing failure modes directly.

### 18. Health Checks & Heartbeats
In distributed environments, system components must detect node failures. Under a heartbeat mechanism, servers send periodic status signals to a monitoring component. If heartbeats cease beyond a configured timeout, the system marks the server dead, stops routing traffic to it, and provisions a replacement.

Load balancers perform active health checks by invoking status endpoints on registered instances.

* **Timeout Consideration:** Short timeouts risk taking healthy servers out of service during brief network blinks; long timeouts leave traffic routing to dead nodes.

![Heartbeat and Node Failover](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.2-heartbeat-node-failover.png)
*When server heartbeats stop beyond timeout limits, the instance is isolated and replaced.*

---

### 19. Checksums
Data can suffer silent corruption in transit or on disk. A checksum system computes a cryptographic hash (e.g., SHA-256) of data upon writing and stores it alongside the payload. When data is read, the hash is recomputed and compared. Discrepancies flag corruption, prompting recovery from an uncorrupted replica.

![Checksum Verification](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.2-checksum-verification.png)
*Checksums verify data integrity on read, triggering replica recovery upon hash mismatch.*

---

### 20. Coordination Services
Certain distributed choices require global consensus: electing a leader node, acquiring a distributed lock, or updating shared configuration. Doing this reliably across unreliable networks is complex, leading architectures to rely on dedicated consensus services (e.g., ZooKeeper, etcd, Consul).

![Distributed Coordination Service](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.2-distributed-coordination-service.png)
*When nodes must agree on a single state choice, a coordination service manages consensus.*

---

### 21. Observability
Observability encompasses three core telemetry signals:

1. **Metrics:** Numeric time-series values (RPS, CPU load, error rates, p99 latency) used for real-time monitoring and alerting (*something is wrong*).
2. **Logs:** Detailed, discrete event records useful for diagnosing root causes (*what happened*).
3. **Traces:** Tracks a single request's execution path across distributed microservices to isolate latency bottlenecks (*where time was spent*).

*Diagnostic Workflow:* Metrics detect the problem $\rightarrow$ Traces pinpoint the service $\rightarrow$ Logs reveal the cause.

![Three Pillars of Observability](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.2-three-pillars-of-observability.png)
*Metrics spot the issue, traces locate the service, and logs reveal the cause.*

---

## Layer 6: Where the Data Goes Afterwards

Analytics, business reporting, and recommendation engines operate off the critical user request path to avoid impacting online service performance.

### 22. Analytics & Data Pipelines
**Golden Rule:** Analytics queries must never execute directly against primary operational databases.

**Pipeline Structure:**
1. **Event Emission:** Services publish asynchronous event records for user actions (e.g., clicks, views, purchases).
2. **Event Streaming:** An event bus (e.g., Apache Kafka) absorbs event volume for concurrent downstream consumption.
3. **Processing Tiers:**
   * *Stream Processing:* Computes real-time metrics for live dashboards.
   * *Batch Processing:* Executes over larger time windows for comprehensive reports.
4. **Data Warehouse:** Stores historical aggregated data optimized for analytical scanning (OLAP).

![Asynchronous Analytics Pipeline](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.2-asynchronous-analytics-pipeline.png)
*Analytics flows asynchronously off an event stream, isolating production databases from heavy scans.*

## Putting It Together: Photo Sharing Service Example

Here is how the master template applies to designing a photo-sharing service:

1. **DNS:** Resolves domain requests to regional edge endpoints.
2. **CDN:** Serves media files (photos, thumbnails), handling the majority of read traffic at the edge.
3. **Load Balancer:** Spreads incoming requests across application servers.
4. **API Gateway:** Handles authentication and rate-limits upload requests.
5. **Services:** Split into an *Upload Service* (write-heavy) and a *Feed Service* (read-heavy).
6. **Object Storage:** Stores raw photo files; database retains metadata pointers.
7. **Message Queue:** Offloads asynchronous thumbnail generation and feed updates.
8. **Metadata Database:** Key-Value or Wide-Column store sharded by `photo_id` for fast key lookups without joins.
9. **Replication & Consistency:** Asynchronous replication with eventual consistency for feed reads.
10. **Caching:** Redis cache in front of metadata database for hot items.
11. **Observability:** Tracks upload success rate, p99 feed latency, and CDN hit ratios.
12. **Analytics:** Events flow to a Kafka stream and land in a data warehouse.

*Omitted Components:* Full-Text Search (no text search specified), Coordination Service (no leader election needed), Real-Time Delivery (instant push not required), and Checksums (handled natively by object storage).

![System Design Applied to Photo Sharing](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.2-system-design-photo-sharing.png)
*Applying the menu against a photo sharing architecture, highlighting active parts and deliberate omissions.*

### Key Takeaways & Practice Advice

> [!TIP]
> Download the **System Design Master Template (PDF)** to reference during practice sessions.

**In the Interview:** Draw the template outward from the client and narrate each layer as you proceed. For example: *"The request comes in through DNS and the load balancer, hits the gateway for auth, and reaches the feed service."* Before completing your explanation, spend 30 seconds detailing the components you deliberately left out. Explicitly naming omitted components demonstrates intentional engineering choices rather than passive diagram recitation.

**Key Takeaway:** The template is a menu of about 22 components arranged in 6 logical layers:
1. How the request reaches you
2. Where the work happens
3. Where the data lives
4. How you make it fast
5. How you keep it alive
6. Where the data goes afterwards

Its primary value is providing a structured sequence of thought. Walk it from the outside in so your explanation flows logically, connect every component to an agreed requirement, and clearly articulate which parts of the menu this system does not need.
