# Designing Instagram

Every case study in this section follows the same seven-step methodology detailed in [System Design Interviews: A Step-by-Step Guide](./4.1-system-design-interviews-a-step-by-step-guide.md) and constructs its architecture using components from the [System Design Master Template](./4.2-system-design-master-template.md).

---

## 1. What is Instagram?

Instagram is a photo and video sharing social network that enables users to upload media, apply filters, share content publicly or privately, and interact with followers. Public content is visible to all users, whereas private content is restricted to approved followers.

For this system design problem, we will focus on designing a simplified core version of Instagram where users can upload photos, follow other users, and view a personalized **News Feed** consisting of top photos uploaded by people they follow.

---

## 2. Requirements and Goals of the System

> [!TIP]
> Always define scope and trade-offs early. Specify latency bounds, feed consistency trade-offs, and out-of-scope features before starting the design.

### Functional Requirements
1. **Photo Operations:** Users can upload, view, and download photos.
2. **Title Search:** Users can perform searches for photos based on photo titles.
3. **User Following:** Users can follow other users.
4. **News Feed:** The system generates and displays a personalized News Feed showing top photos from accounts the user follows.

### Non-Functional Requirements
1. **High Availability:** The service must be highly available to allow seamless viewing.
2. **Low Latency:** News Feed generation latency must be under **200ms**.
3. **Eventual Consistency:** In the interest of availability, consistency can be eventual. If a user sees a newly uploaded photo a few seconds late, it is acceptable.
4. **High Reliability:** Uploaded media must be 100% durable; photos/videos must never be lost.

### Out of Scope
* Commenting on photos, photo tagging, location check-ins, stories, reels, and user follow recommendations.

---

## 3. Design Considerations

* **Read-Heavy System:** The system is heavily read-oriented (news feed views outnumber photo uploads significantly). Retrieving photos and rendering feeds quickly is the main priority.
* **Storage Efficiency:** Users can upload unlimited photos over time. Efficient multi-terabyte storage management is critical.
* **Durability Guarantee:** Photo data must be 100% reliable with redundant replicas across object stores.

---

## 4. Capacity Estimation and Constraints

### Scale Assumptions
* **Total Registered Users:** 500 million
* **Daily Active Users (DAU):** 1 million
* **Daily Photo Uploads:** 2 million new photos per day

#### Write QPS (Uploads):
$$\text{Write QPS} = \frac{2,000,000\text{ photos}}{86,400\text{ seconds}} \approx 23\text{ photos/sec}$$

### Storage Estimates
* **Average Photo File Size:** 200 KB per photo

#### Daily Storage Requirements:
$$\text{Daily Photo Storage} = 2\text{M photos/day} \times 200\text{ KB} = 400\text{ GB/day}$$

#### 10-Year Photo Storage Requirements:
$$\text{10-Year Media Storage} = 400\text{ GB/day} \times 365\text{ days} \times 10\text{ years} \approx 1,425\text{ TB}$$

---

## 5. High-Level System Design

At a high level, the system must handle two primary execution paths:
1. **Photo Upload Path (Write):** Uploads raw image files to Object Storage and stores metadata in database servers.
2. **Photo View / Feed Path (Read):** Queries metadata database and renders personalized news feeds.

* **Object Storage (Amazon S3 / Distributed File Store):** Stores raw image files.
* **Metadata Database:** Stores metadata related to users, photos, and follow relationships.

## 7. Data Size Estimation

Let's estimate total database metadata storage for 10 years across all tables:

### 1. `User` Table Storage:
$$\text{Row Size} = 4 + 20 + 32 + 4 + 4 + 4 = 68\text{ bytes/row}$$
$$\text{500M Users} \times 68\text{ bytes} \approx 32\text{ GB}$$

### 2. `Photo` Table Storage:
$$\text{Row Size} = 4 + 4 + 256 + 4 + 4 + 4 + 4 + 4 = 284\text{ bytes/row}$$
$$\text{Daily Growth} = 2\text{M photos/day} \times 284\text{ bytes} \approx 0.5\text{ GB/day}$$
$$\text{10-Year Photo Metadata} = 0.5\text{ GB/day} \times 365 \times 10 \approx 1.88\text{ TB}$$

### 3. `UserFollow` Table Storage:
$$\text{Row Size} = 4 + 4 = 8\text{ bytes/row}$$
Assuming 500 million users following an average of 500 accounts each:
$$\text{Total Edges} = 500\text{M users} \times 500\text{ follows} = 250\text{ billion rows}$$
$$\text{Storage Required} = 250\text{B rows} \times 8\text{ bytes} \approx 1.82\text{ TB}$$

### Total 10-Year Database Storage:
$$\text{Total Metadata Storage} = 32\text{ GB} + 1.88\text{ TB} + 1.82\text{ TB} \approx 3.7\text{ TB}$$

## 8. Component Design

Photo uploads (writes) are slow disk-bound operations, whereas reads are fast in-memory operations.

If write uploads hog web server HTTP connections (e.g. max 500 connections per server), incoming read requests will starve and fail. To prevent write bottlenecks from impacting read availability, **read and write services must be decoupled onto separate server pools**.

![Instagram Component Design](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.5-instagram-component-design.png)
*Component architecture isolating photo upload write servers from read/feed servers.*

* **Dedicated Upload (Write) Service:** Processes image uploads and writes to S3 and Metadata DB.
* **Dedicated Read / Feed Service:** Serves photo downloads and constructs news feeds.

---

## 9. Reliability and Redundancy

To guarantee zero data loss, all uploaded files are stored redundantly across multiple storage nodes and geographical zones.

![Redundancy and Failover Architecture](https://raw.githubusercontent.com/shouvik126/HLD_images/main/4.5-instagram-redundancy.png)
*Redundancy and automatic failover configuration for high availability.*

* **Service Redundancy:** Multiple stateless app server instances behind Load Balancers eliminate single points of failure (SPOF).
* **Database Failover:** Primary-Replica database setup with automatic failover ensures read/write availability even if a primary node fails.

---

## 10. Data Sharding

To partition 3.7 TB of metadata across multiple database nodes, we evaluate two partitioning strategies:

### Scheme A: Partitioning based on `UserID`
* Shard number determined by `UserID % NumberOfShards`.
* **Drawbacks:**
  1. **Hotspot Users:** Celebrity accounts generate disproportionately high read QPS on a single shard.
  2. **Non-Uniform Storage:** High-volume uploaders fill their shard faster than inactive users.
  3. **Multi-Shard Queries:** Fetching a news feed requires querying shards of all followed users, increasing feed generation latency.

### Scheme B: Partitioning based on `PhotoID` (Recommended)
* Generate unique `PhotoID`s first, then shard by `PhotoID % NumberOfShards`.

#### Unique `PhotoID` Generation (Key Generation Service - KGS):
To avoid single-point-of-failure bottlenecks on auto-incrementing databases, we use dedicated KGS instances with even/odd sequence offsets:

* **KGS Server 1 (Odd IDs):** `auto-increment-increment = 2`, `auto-increment-offset = 1`
* **KGS Server 2 (Even IDs):** `auto-increment-increment = 2`, `auto-increment-offset = 2`

A Load Balancer distributes key allocation requests between KGS instances.

## 11. Ranking and News Feed Generation

Generating a News Feed requires fetching top 100 recent photos from all people a user follows.

### Naive Real-Time Query Approach:
1. Query `UserFollow` table to get followed user IDs.
2. Query `Photo` table for the latest 100 photos for each followed user.
3. Submit photo list to ranking algorithm and return top 100 photos.
*Drawback:* High latency (>200ms) due to multi-table joins and real-time sorting across shards.

### Optimized Approach: Pre-Generated News Feed
Dedicated **News Feed Generation Servers** continuously pre-compute feeds and store pre-rendered photo ID lists in a `UserNewsFeed` memory table. When a user requests their feed, the system simply fetches the pre-calculated list instantly.

### Feed Update Delivery Mechanisms
1. **Pull Model:** Client polls server periodically. *Drawback:* Empty responses when no new photos exist.
2. **Push Model:** Server pushes updates immediately to connected clients via Long Polling / WebSockets. *Drawback:* Fan-out bottleneck for accounts with millions of followers.
3. **Hybrid Model (Recommended):**
   * **Push** updates to standard users with < 1,000 followers.
   * **Pull** updates on-demand for celebrity accounts with > 100,000 followers.

---

## 12. News Feed Creation with Sharded Data

To perform fast time-based sorting across database shards, time creation metadata is embedded directly into the 64-bit `PhotoID`:

### 64-Bit `PhotoID` Layout:
* **Epoch Time (31 bits):** Represents seconds elapsed from a custom epoch start date (covers ~50 years).
* **Auto-Increment Sequence (9 bits):** Supports up to $2^9 = 512$ photos per second, reset every second.
* **Shard Identifier / Padding (24 bits):** Logical shard allocation identifier.

Sorting by `PhotoID` automatically sorts by creation timestamp without secondary table indexing.

---

## 13. Cache and Load Balancing

* **CDN (Content Delivery Network):** Caches popular images close to users geographically for sub-50ms rendering.
* **Redis Metadata Cache:** Caches top 20% hot metadata rows in RAM under an **LRU (Least Recently Used)** eviction policy (80/20 Pareto rule).

## Summary & Key Takeaways

| Metric / Layer | Architecture Choice | Rationale |
| :--- | :--- | :--- |
| **Traffic Profile** | 23 Write QPS / Read-Heavy | Isolated read and write server pools |
| **10-Year Media Storage** | 1,425 TB Object Storage (S3) | Cheap, highly durable blob storage |
| **10-Year Metadata Storage** | 3.7 TB Metadata Store | $O(1)$ lookups partitioned by `PhotoID` |
| **Feed Latency Target** | < 200ms | Pre-generated feeds + Hybrid Push/Pull delivery |
| **Caching Layer** | CDN for photos + Redis LRU for metadata | Serves 80% read traffic from RAM / Edge CDNs |
