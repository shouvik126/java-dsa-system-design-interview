# Strong vs. Eventual Consistency

## Introduction

In distributed systems and databases, **data consistency** refers to the property that all data replicas across different nodes reflect the exact same state at any given point in time. When multiple users or microservices query datasets distributed across nodes, the system must determine whether everyone receives identical, up-to-date values.

Failing to synchronize state across nodes causes data anomalies. For example, consider an e-commerce platform with inventory data replicated across global data centers: if one server marks an item as in stock while another marks it as sold out, the system risks selling unavailable inventory. 

However, enforcing strict data synchronization across distributed environments becomes increasingly difficult as systems scale out. This challenge gives rise to different consistency models, with **Strong Consistency** and **Eventual Consistency** marking the two ends of the spectrum.

---

## What is Strong Consistency?

**Strong consistency** (often referred to as strict consistency or linearizability) guarantees that any read operation immediately returns the value of the most recent committed write.

Once a write operation completes, every subsequent read from any client or node across the cluster is guaranteed to observe that update. Under strong consistency, stale reads are impossible.

To provide this guarantee, systems rely on **synchronous replication**: when a write request arrives, the update is synchronously propagated to multiple replica nodes before confirming success back to the client.

![Simplified Illustration of Strong Consistency](https://raw.githubusercontent.com/shouvik126/HLD_images/main/3.2-strong-consistency.png)

### Execution & Trade-offs

In a strongly consistent setup, a write operation is not committed until all required replicas confirm state updates:
1. A client issues a write request to a primary or coordinator database node.
2. The coordinator initiates a transaction to replicate the update across peer nodes.
3. The client receives an `OK` confirmation only after the data is committed across all designated replicas.
4. Reads to that record are blocked until the commit completes to prevent clients from reading partial updates.

### Real-World Analogy: Banking & ATM Withdrawals

Consider an ATM cash withdrawal. If an account has a balance of $500 and a client withdraws $100, every bank teller, mobile app, and ATM worldwide must immediately reflect the updated $400 balance. If replica updates were delayed, a client could make duplicate withdrawals across multiple locations simultaneously, overdrawing the account.

### Technologies & Use Cases

Modern distributed databases such as **Google Spanner** and **CockroachDB**, alongside traditional RDBMS systems, enforce strong consistency. Writes route through a primary node and synchronously replicate to secondary nodes before transaction commit.

### Trade-offs of Strong Consistency

- **Increased Latency**: Because writes wait for cross-node network round-trips before acknowledging completion, response times are higher.
- **Reduced Availability**: If network partitions occur or replica nodes become unreachable, a strongly consistent system intentionally blocks writes (and sometimes reads) to prevent data divergence, prioritizing **Consistency over Availability** (CP in the CAP theorem).

---

## What is Eventual Consistency?

**Eventual consistency** is a relaxed model guaranteeing that if no new updates are made to a data record, all replicas will eventually converge to identical states.

The key distinction is timing: eventual consistency does not promise immediate synchronization. During a propagation window, different nodes may temporarily serve stale data until updates replicate across the cluster.

Eventual consistency uses **asynchronous replication**: when a write reaches a node, the node updates its local state and immediately returns a success response to the client. It then propagates the change to other replicas in the background.

![Simplified Illustration of Eventual Consistency](https://raw.githubusercontent.com/shouvik126/HLD_images/main/3.2-eventual-consistency.png)

### Real-World Analogies

- **Social Media Feeds**: When a user posts a photo, friends on different continents might not see it at the exact same second. The post propagates asynchronously to edge caches. Over a short window (milliseconds to seconds), all friend feeds catch up and display identical timeline states.
- **DNS (Domain Name System)**: Updating a website's IP address takes time to propagate across global DNS servers. During propagation, some users resolve the old IP while others receive the new record. Eventually, all DNS caches reflect the updated address.

### Technologies & Use Cases

NoSQL databases such as **Apache Cassandra**, **Amazon DynamoDB**, and **Apache CouchDB** default to eventual consistency under the **BASE** framework (Basically Available, Soft-state, Eventually consistent). They handle concurrent updates using conflict resolution strategies such as **Last-Write-Wins (LWW)** or **Vector Clocks**.

### Trade-offs of Eventual Consistency

- **High Availability & Low Latency**: Writes and reads execute locally without waiting for global consensus, yielding fast response times and fault tolerance even during node outages.
- **Temporary Inconsistency**: Clients querying lagging replicas may receive stale data during the propagation window.

---

## Comparison: Strong vs. Eventual Consistency

| Aspect | Strong Consistency | Eventual Consistency |
| :--- | :--- | :--- |
| **Data Guarantee** | Reads always return the latest written value; no stale reads. | Reads may return stale values temporarily until replicas converge. |
| **Latency** | Higher latency due to synchronous replication coordination. | Low latency; writes and reads return quickly without global locks. |
| **Availability** | Reduced availability during node failures or network splits. | High availability; nodes accept operations independently. |
| **Consistency Model** | Strict / Linearizable. | Weak / Optimistic (Eventual Convergence). |
| **Ideal Use Cases** | Financial transactions, inventory counts, booking systems, authentication. | Social media feeds, messaging apps, product view counts, CDN caching. |

> [!NOTE]
> **Intermediate Consistency Models**: Strong and eventual consistency form the boundaries of a spectrum. Modern databases often support intermediate levels such as **Causal Consistency**, **Read-Your-Writes Consistency**, and **Bounded Staleness** (e.g., Azure Cosmos DB and MongoDB).

---

## When to Use Which?

### Choose Strong Consistency When:
- **Accuracy Is Critical**: Financial ledgers, payment processing, inventory tracking (preventing double-selling), reservation systems (preventing double-booking).
- **Stale Data Causes System Errors**: Operations depend strictly on previous state transitions where reading old data corrupts business logic.

### Choose Eventual Consistency When:
- **Low Latency & High Throughput Are Primary Goals**: High-volume applications such as social media timelines, metrics ingestion, product recommendations, and analytics.
- **Temporary Divergence Is Harmless**: Applications where reading data that is a few seconds out of date does not negatively impact business rules.

### Hybrid & Tunable Consistency

In production architectures, systems often combine both models:
- An e-commerce platform uses **Strong Consistency** for payment checkout and inventory updates, but uses **Eventual Consistency** for product reviews, recommendations, and view counters.
- Tunable databases like **Apache Cassandra** allow per-query configuration (e.g., executing strong reads for critical data and eventual reads for non-critical feeds).

---

## Conclusion

Strong consistency guarantees absolute accuracy at the expense of latency and availability. Eventual consistency maximizes availability and speed by permitting temporary data divergence. Selecting the right consistency model involves evaluating business requirements, latency SLAs, and the acceptable tolerance for stale data across system operations.
