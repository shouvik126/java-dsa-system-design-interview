# REST vs. RPC

**REST (Representational State Transfer)** and **RPC (Remote Procedure Call)** are two widely adopted architectural styles for building networked applications, APIs, and microservice communications. Each style embodies a distinct philosophy for managing client-server interactions.

---

## REST (Representational State Transfer)

### Concept
REST is a resource-oriented architectural style that leverages standard HTTP mechanisms to access and manipulate data. It models server-side data as **resources**, identified by unique URIs, and manipulated using standard HTTP verbs (**GET**, **POST**, **PUT**, **DELETE**, **PATCH**).

### Core Principles
- **Stateless Communication**: Every request from client to server must contain all necessary authentication and context details. The server stores no client session context between requests.
- **Resource-Centric**: Focuses on nouns (resources) identified by URL paths (e.g., `/articles`, `/users/123`), with data state transferred over HTTP in human-readable formats like JSON or XML.
- **Cacheability**: Leverages native HTTP caching headers (`Cache-Control`, `ETag`) for optimized content delivery.

### Real-World Example: Blog API
A RESTful API for a publishing platform exposes URI endpoints:
- `GET /articles`: Retrieves a list of published articles.
- `POST /articles`: Creates a new article.
- `GET /articles/42`: Retrieves article with ID `42`.
- `DELETE /articles/42`: Deletes article `42`.

### Advantages & Disadvantages
- **Advantages**:
  - **Scalability**: Stateless interactions enable easy horizontal scaling and load balancing.
  - **HTTP Caching**: Directly utilizes browser and CDN caching infrastructure.
  - **Standardized Uniform Interface**: Uses native HTTP verbs and status codes (`200 OK`, `404 Not Found`).
- **Disadvantages**:
  - **Over-fetching & Under-fetching**: Standard endpoints may return unnecessary fields or require multiple round-trips for related data.
  - **Implementation Drift**: Lacks strict, enforced schema validation across different vendor implementations.

---

## RPC (Remote Procedure Call)

### Concept
RPC is an action/procedure-oriented protocol where a client program executes a function or subroutine on a remote server as if it were a local function call. 

### Core Principles
- **Procedure-Oriented**: Focuses on verbs/actions (procedures) rather than resources (e.g., `getArticle()`, `calculateTax()`).
- **Explicit Method Invocation**: The client invokes a named procedure with arguments, and the server executes the function and returns the result.
- **Data Serialization**: Transmits data using formats like JSON (JSON-RPC), XML (XML-RPC), or high-performance binary formats like Protocol Buffers (gRPC).

### Real-World Example: Microservices Function Call
A client service invokes a remote procedure `getArticle(articleId)` over gRPC/HTTP2. The remote server executes the procedure logic and returns a binary Protocol Buffer response containing article details.

### Advantages & Disadvantages
- **Advantages**:
  - **High Efficiency & Speed**: Binary protocols like gRPC (over HTTP/2 with Protobuf) offer low serialization overhead, low latency, and multiplexing.
  - **Strong Schema Contracts**: Strictly defined interface definition languages (IDL) generate typed client/server stubs automatically.
  - **Action-Oriented Simplicity**: Directly maps to complex procedural workflows that do not naturally map to CRUD resources.
- **Disadvantages**:
  - **Tight Coupling**: Clients depend heavily on server-defined method signatures and contracts.
  - **Limited Web Caching**: Does not naturally fit standard HTTP caching mechanisms since requests often use POST endpoints for procedure execution.

---

## Key Differences

| Feature / Aspect | REST | RPC |
| :--- | :--- | :--- |
| **Architectural Model** | Resource-Oriented (Nouns / URIs). | Action-Oriented (Verbs / Procedures). |
| **Primary Abstraction** | Resources (`/articles/42`). | Procedures (`getArticle(42)`). |
| **Data Payload Formats** | Typically JSON, XML, or HTML. | JSON-RPC, XML-RPC, or Binary (Protobuf). |
| **Protocol / Transport** | Strictly HTTP/HTTPS. | Transport agnostic (HTTP/2, TCP, custom protocols). |
| **Caching Support** | Excellent (Native HTTP headers & CDN integration). | Complex / Custom (HTTP POST procedure calls skip default caching). |
| **Coupling Level** | Loose coupling (uniform interface). | Tight coupling (shared interface definitions). |
| **Ideal Use Case** | Public APIs, web applications, third-party integrations. | Internal microservices, low-latency inter-service calls. |

---

## Conclusion

- **REST** is best suited for public APIs, web services, and mobile backends where uniform interfaces, HTTP caching, and loose client-server coupling are primary requirements.
- **RPC** (especially modern **gRPC**) is the preferred choice for internal microservice communication, real-time streaming, and high-performance distributed systems where speed, low latency, and strict schema contracts are critical.
